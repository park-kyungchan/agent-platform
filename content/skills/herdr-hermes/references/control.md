# Native Hermes control

Use current Herdr help, selected machine and live foreground inventory. For new starts, resolve `hermes` in the executor that will launch it, inspect its parser, choose the concrete profile and working directory, and select fresh or explicit stored-session resume. Reuse trusted known facts rather than probing every host repeatedly.

Profile creation/cloning can seed files, register services and notify gateways. Startup can maintain SessionDB/cache and refresh or adopt shared OAuth. Inspect those effects before a disposable test; do not copy credentials or assume a new HERMES_HOME isolates authentication. Native hooks, approval semantics, retries and learning remain native owners.

For an already recognized native Herdr agent, use its live server-scoped identity. For an authorized SSH/Docker foreground process that is not recognized, use the raw owned-pane surface. Do not use manual report-agent, takeover or a new wrapper to fake support. Resolve command syntax from installed help; preserve SSH host-key checking and Tailscale boundaries.

For an authorized handoff, include current Strategy link, KPI/guardrail moved, exact source revision/write set and shared-build owner where applicable, alongside the goal, effects, output and TASK/STATE paths. [Context Governance](../../../runtime-references/CONTEXT-GOVERNANCE.md) owns isolation/continuity; [lead](../../lead/SKILL.md) owns reporting. Follow the assigned [Herdr](../../herdr/SKILL.md) topology; an existing Hermes service is not automatically a worker or a new role.

Version promotion uses only the installed target helper's one-shot path, under current task authority. Never edit updater state, receipts, jobs or transactions directly. Keep SSH host-key checking, Tailscale and native runtime/service identities intact.

After dispatch, correlate the actual response with the submitted request and native stored session. A timeout, idle state or interrupt does not establish absence of tool/model effects. Read existing state before resubmission and preserve owned result evidence before cleanup.

For native Desktop/Screen work, backend readiness and a backend screenshot do not prove that the user's client displayed the same selected profile. Inspect the actual native viewer and permitted action result. Preserve the human/agent lease; do not clear it or fall back to another display as a shortcut.

At closure, use [worker closure](../../lessons-loop/references/worker-closure.md) and record the actual executor, profile, session identity (or unknown), output/effect readback, checks and owned processes. A response, idle state or success marker alone cannot establish completion. Keep future dated executor/version facts in current task STATE rather than this generic reference. Do not import session content or student data into memory; zero durable lesson candidates is valid.
