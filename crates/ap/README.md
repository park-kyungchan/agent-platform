# ap

`ap --version` (and `ap version`) prints one line `ap <Cargo package version> <40-hex commit>[-dirty]`, or `unknown` for the commit when Git was unavailable at build time.
The install of `ap` is `ap deliver` ("Delivery" below; the timer `ap-deliver.timer`). `scripts/install-ap.sh` is the step it calls, run by hand only for the repairs `deploy/README.md` names: `check` compares the installed binary (`AP_INSTALL_DIR`, default `/usr/local/bin`) with `origin/main`, `install <expected commit>` builds from a temporary detached worktree of that exact commit and installs it after verifying the staged and installed `--version` report exactly that commit, and `rollback <before-file>` restores a backup.
For `install`, `origin/main` means the local ref, so run `git fetch` first; the previous binary is backed up as `ap.before-<first 7 hex of its sha256>` in `AP_BACKUP_DIR` (default `/var/lib/agent-platform/install`), and `rollback` accepts only that name in that directory and prints the restored version (or `no_version_output`). The script lock is `AP_INSTALL_LOCK` (default `/run/lock/ap-install.lock`).
Limitation: a source tarball nested inside another Git repository reports the outer repository's revision, because the build derives the revision from the enclosing repository.

## The older verbs

`ap --help` (or `-h`) prints one line per verb the command dispatches: the verb, its request form and the heading of the section of this file that documents it; `ap <verb> --help` prints that verb's own usage. `ap version` is `--version`, above. The earlier installer's verbs `install`, `doctor` and `render` were removed: the command refuses them like any unknown verb. Every other verb has its own section below.

## One stage

`ap run < request.json` runs ONE headless session of Claude Code, of the Codex CLI with `runtime: "codex"` ("A stage on the Codex CLI" below) of the Muse Code CLI with `runtime: "muse"` ("A stage on Muse Code" below) or, for a reviewer, of the Antigravity CLI with `runtime: "agy"` ("A stage on the Antigravity CLI" below) (a stage: implementer, reviewer or fixer) in a transient systemd scope `ap-run-<uuid>.scope` under `agents.slice` and returns when nothing of it is alive. It prints the run record on stdout. Exit 0 `ok`, 75 `cut`, 3 any other end, 5 a file of the run could not be written after the record was claimed, which includes the case in which nothing ran (stdout holds the final record; the file holds it when a write in place succeeded). Exit 2 is a refusal before any effect, and nothing else: `{"error":{"code","field","detail"}}` on stderr. It reads no role table, calls no store, Herdr or GitHub.

The request: `role` (`implementer`, `reviewer`, `fixer`), `account` (the Claude configuration directory, required), optional `next_accounts`, `model`, `effort`, `permission_mode` (one of Claude Code's: `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan`), `cwd`, `prompt` (a regular file, at most 1 MiB, given to the CLI on stdin), `out` (the answer's path), and optional `timeout_seconds` (1 to 86400; default implementer 5400, fixer 3600, reviewer 3300), `expect` (`file`: a path that this run must write nonempty; `first_line`: a pattern the answer's first line must match, where `*` matches any run of characters), `resume` (`{"record": "<absolute path of the earlier run's record>"}`), `continue_dirty`, `integration` (a reviewer's only: another role refuses `invalid_input`; it does not choose the account), `mcp_config` (files; the only MCP servers loaded), `env` (extra variables; a name beginning `HERDR_`, `CLAUDE_` or `ANTHROPIC_`, and `HOME`, refuse `env_forbidden`: the account named in the record is the account that answers), `runtime` (`claude`, the default, `codex`, `muse` or `agy`), `bind` (the name of a systemd unit that is active now: when it ends for any reason, stopped, killed or failed, the stage's unit stops), `skills` and `memory` (booleans: the account's skills and slash commands, and its auto-memory, load only when true), `answer_schema` (a typed answer: "A typed answer" below), and `compact_window` (a Claude stage's only: an integer from 100000 to 1000000, read as `timeout_seconds` is read, so a fraction, an exponent, a string or null refuses `invalid_input` with that field; the CLI starts with `CLAUDE_CODE_AUTO_COMPACT_WINDOW` set to it in the `env` of its `--settings` value, so the stage's compaction window is this one; without it the account's settings decide, and a Codex stage refuses the member with `invalid_input`, field `compact_window`). `bind` is for a transient unit (the caller's own, as a chain's): one that ended between the request and the launch makes the launch fail (the record says `failed`); a unit that systemd can start again by name is started again by the launch, because `BindsTo` requires it. Every path is absolute; another member refuses `invalid_input`, and so does an `out` whose file name ends with a suffix `ap run` derives (`.run.json`, `.stream.jsonl`, `.err`, `.ap-tmp`): no run's answer path is another run's file. A resume is a run of its own with its own `out`; it continues the session of the earlier run on that run's account, and when a usage limit cuts it, goes on as a new session on another account ("The move of a resumed call" below). `ap run` guards a run's files against another run; it does not guard a session against its caller: two resumes of one record at the same time are not refused, because the caller is the one owner of a session and runs its stages in sequence. On a resume the prompt file is the next message to the session: give a continuation or the findings, not the first prompt again.

Refusals (exit 2, before any effect, no file written): `invalid_input`; `account_missing` (`account` or an entry of `next_accounts` is not an existing directory; `/root/.claude` is an account like any other, for every role, as `account` and in `next_accounts`); `cwd_missing`; `prompt_unreadable`; `out_unwritable`; `out_named_in_prompt` (the prompt contains the out file's name); `out_exists` (`out`, `<out>.run.json`, `<out>.stream.jsonl` or `<out>.err` exists: nothing of an earlier run is replaced, removed or truncated by a later one); `worktree_dirty` (a fresh implementer run in a Git worktree with changes, unless `continue_dirty`); `worktree_unreadable` (Git cannot read `cwd` for a reason other than "not a git repository"; `git` runs with the fixed short list of variables only, not the request's `env`); `resume_record_missing`, `resume_runtime_differs` (field `runtime`: the earlier record's `runtime` is not the request's; a record without the member is a Claude stage's), `resume_account_differs`, `resume_cwd_differs`, `resume_role_differs` (a resume keeps the earlier record's runtime, `cwd` and role, or is a `fixer` over an implementer's or a fixer's record); `bind_inactive` (`systemctl is-active` for `bind` did not answer `active`); `run_still_active` (whatever the earlier record's state, `systemctl is-active` for its unit did not answer a state in which nothing of its unit lives: `active`, `activating`, `deactivating`, `reloading`, `refreshing`, a failed call and no answer all refuse); `env_forbidden`; `systemd_absent`. The host's policy file (`/etc/agent-platform/policy.json`, or the file `AP_POLICY_FILE` names) refuses `policy_invalid`, `model_not_allowed` and `account_not_allowed` after the refusals of the request's own members, files and resume record and before `run_still_active`, `worktree_dirty`, `worktree_unreadable`, `bind_inactive`, `systemd_absent` and any effect, and the record's `policy` names the file that was read (`{path, sha256}`, null without one): the specification is `specs/ap/policy.md`.

The run: every run, fresh or resumed, creates its own record. `<out>.run.json` is created exclusively, and that creation is the claim: of two requests on one `out` started at the same instant, one passes and the other is refused `out_exists`. Then `<out>.stream.jsonl` and `<out>.err` are created exclusively; every write of the answer or the record goes through a temporary name unique to that write and created exclusively, so it is never another run's file. A session id is chosen (or taken from the earlier record on a resume), and the record is written with state `running` BEFORE the launch; a resume's record names the earlier record in `resumes`. The launch is `systemd-run --scope --quiet --collect --unit=… --slice=agents.slice -p RuntimeMaxSec=<timeout + 10>s -p TimeoutStopSec=10s [-p BindsTo=<bind> -p After=<bind>] -- claude --print --output-format stream-json --verbose --model … --effort … --permission-mode … --permission-prompts none --setting-sources user --settings <settings> --disallowedTools Monitor --strict-mcp-config [--mcp-config …] [--disable-slash-commands] (--session-id | --resume) <session>`. The settings, for every role and with nothing in the request: `disableAllHooks: true`; `env` with `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS` at 2700000 (a 40-minute check runs in the foreground of one Bash call) and `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` (a command that reaches its limit stops instead of moving to the background); `autoMemoryEnabled: false` unless `memory`; with `compact_window`, `env` holds one more name, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, whose value is the window as a decimal string (the other names are as they are). `--disable-slash-commands` is left out only with `skills`. So the stage has no `Monitor` and no background shell, and its first event lists no skill and no memory directory, while the account's `CLAUDE.md` still loads (shown on Claude Code 2.1.325). Its environment is only `PATH HOME USER LOGNAME SHELL LANG LC_ALL TERM TMPDIR TZ` of the caller (when set), the request's `env`, and `CLAUDE_CONFIG_DIR=<account>`: no hook (of the account, the host, a project or a plugin), no MCP server the request does not name, and only the account's settings (a worktree's `.claude/settings.json` and `settings.local.json` do not load; with them the project's `CLAUDE.md` and `.claude/agents` do not load either, while the account's `CLAUDE.md` does). stdout goes to `<out>.stream.jsonl`, which `ap run` reads only through the handle it opened before the launch; stderr to `<out>.err`, removed at the end when empty. The stream holds the session's transcript (answers and tool output): keep `out` where it is private. `RuntimeMaxSec` is the unit's own bound: it ends the stage when `ap run` is gone.

The end, by role. A print session that left a background shell emits a `result`, waits for the shell, then may run a second turn and emit another `result` (each `result` carries the `usage` and `num_turns` of its own part; the sum is the session's). So a `result` ends the stage only for a `reviewer`: at its first `result`. An `implementer` or a `fixer` runs to the CLI's exit; for every role `timeout_seconds` ends the stage. Then `systemctl stop` ends every process in the unit, the stream is read to its end (a last line without a newline included), and `systemctl is-active` must answer a state that is not `active`, `activating`, `deactivating`, `reloading` or `refreshing`; anything else, a failed call included, makes the state `failed` with `unmet: stop`.

States, from the result the stage is judged by: the LAST `result` whose answer is nonempty, not an error or a cut, and meets `expect.first_line` when one met it (a later result does not unmake it), else the last `result` seen (a reviewer has only its first): `ok` (a non-error result whose text is nonempty and meets `expect`); `no_result` (a non-error result that is empty or does not meet `expect`; `unmet` names which: `answer`, `file`, `first_line`, `schema`; a nonempty answer is still saved); `cut` (an error result with a rejected rate-limit event, API status 429 or the usage-limit text, or a non-error result with the usage-limit text and a rejected rate-limit event; no answer is written); `timeout` (the bound ended the stage, for every role, even when a result is read during the shutdown; the last answer, if any, is saved and `expect_met` says whether it met `expect`); `failed` (the CLI ended without a result event, an error result that is not a cut, the launch failed, the stop was not confirmed, or a write failed: `unmet` `result_event`, `launch`, `stop` or `write`). A refusal has no record. The answer is the result text, byte for byte. `expect.file` is met only by a nonempty file whose digest or modification time differs from `expect_file_before`: the file as it was before THIS run's launch. Only a resume that continues the same unfinished stage (the earlier record has the same role and a state other than `ok`) takes the earlier record's `expect_file_before` instead; a fixer over an implementer always takes its own. A fresh run cut before it did any work (the stream holds no `tool_use` block, so no tool ran), and a fresh run of a `reviewer` cut at any point (it changes no file: what it did is lost, not wrong), is run again, within the same run and its record, on the next of `next_accounts` with a new session. So is an `implementer` or a `fixer` cut after a tool ran, when a next account is left, with the continuation (below); with none left it stays cut. A resumed call is moved in the same way, as the paragraph "The move of a resumed call" says. A move to a next account is read from `attempts` of the record.

The continuation. For the roles `implementer` and `fixer`, once a launch of a fresh call has worked (a tool ran) and was cut, every later launch of the call (a new session, as above) reads on stdin the continuation text, then the bytes of the prompt file; no file is written for it (the input is a pipe), so the names a call writes are the same. The text is these four sentences in one line, followed by one empty line: "A session of this stage on another account was cut by a usage limit after it had begun to work. This directory may hold its work, committed or not. First read the state it left: in a Git worktree `git status`, `git log --oneline origin/main..HEAD` and `git diff HEAD`. Keep what serves the task, do not start over, and go on until the task below is done." A reviewer's next launch starts over without it, a launch that is not preceded by a launch that worked gets none, and a resumed call gets the text of a move instead (below).

The move of a resumed call. The launches of a call with `resume` take the accounts in this order: the account of the record it names; then the request's `account` and the entries of `next_accounts` in their order, without any that equals the record's account and without a repetition (the record's account must be one of the request's accounts, else `resume_account_differs`). The first launch resumes the record's session exactly as above, with the prompt file as its input. When it ends `cut`, before or after a tool ran, for every role, an account is left, and the resumed record holds `prompt.path` and `answer.path` as strings that hold no control character and do not contain the file name of the call's `out` (the reason of `out_named_in_prompt`), the call goes on within the same run and record: the next launch is a NEW session on the next account (a new session id, no resume argument) whose input is one line, an empty line, and the bytes of the prompt file; no file is written for it. A later launch that ends `cut` moves on in the same way while an account is left. With no account left, or with a record that lacks the two paths in that form, the call stays cut; a launch that ends in any other state ends the call. The line, with `<P>` the resumed record's `prompt.path` and `<A>` its `answer.path` byte for byte, is for every role: "This stage was to resume an earlier session, and a usage limit cut that session on its account. You are a new session and hold nothing of what it read or wrote: before anything else read completely the prompt it was given, the file <P>, and the answer it gave, the file <A>. The task below was written for that session: where it speaks of what you did, wrote or were told, it means that session, its answer and its prompt." and, for the roles `implementer` and `fixer`, on the same line after one space: "This directory holds its work, committed or not. Read the state it left: in a Git worktree `git status`, `git log --oneline origin/main..HEAD` and `git diff HEAD`. Keep what serves the task, do not start over, and go on until the task below is done." The text goes only to a launch that follows a cut launch of the same call; the resumed launch reads the prompt file alone, and no launch of a resumed call gets the continuation text. After a move the record's `session` and `account` are the new session's, so a later `resume` of that record resumes the new session on its account. Codex stages have one account and never move. A move of a resumed call is read from its record: `resumes` is not null and `attempts` holds more than one entry (the first is the resumed launch, with the resumed record's session; every later one is a new session). The record's `prompt` stays the path and the digest of the prompt file.

The record `<out>.run.json`: `role, runtime` (`claude`, `codex`, `muse` or `agy`), `model, effort, account, session, cwd, unit, prompt{path,sha256}, answer{path,sha256}|null, start, end|null` (UTC, RFC 3339), `state, turns, tokens{input,output,cache_read,cache_creation}` (sums over the `result` events; null where the CLI did not report), `permission_denials` (`tool_name` and `tool_use_id` as reported, over all results), `results` (the number of `result` events read), `expect_met` (null without a result), `expect_file_before` (`{path, sha256, modified}` or null), `unmet`, `resumes` (the earlier record's path, or null), `compact_window` (the request's window, or null without the member; for either runtime, from the first write of the record, a launch that could not be started included), and with `answer_schema` the member `answer_schema{path,sha256}`. A stage on the Claude runtime also holds `limit` and `attempts`, both described next; a stage on Muse Code holds both too (its `limit` is read as "A stage on Muse Code" says). A stage on `agy` also holds `home`, the directory it ran in ("A stage on the Antigravity CLI" says). No prompt or answer text.

`limit` is what the last launch's stream held of rate limits: null when it held no line of type `rate_limit_event` (and always for a Codex stage, and while a launch runs); else an object made from ONE such line, the last whose `rate_limit_info.status` is `rejected` when the launch saw one, else the last line. Its members: `status` (`rate_limit_info.status` when it is a string, else null), `kind` (`rateLimitType` when it is a string, else null), `resets_at` (`resetsAt` when it is a non-negative integer, copied as that number, else null: a number in float form, `1794772800.0` included, is null) and `windows` (an object: for at most eight members of `unifiedWindows` whose value is an object, taken in the order of their names, the same name with `status`, `utilization` (a number, else null) and `resets_at`, by the same rules; `{}` when there is none). No other member of the event is read: `overageStatus` is never a status, and no line of the stream alone makes a stage `cut` (what makes it so is above). `status` `allowed`, `allowed_warning` and `rejected` are what the SDK documents; `rateLimitType` and `unifiedWindows` are shown by the CLI and not documented, and the members of a `rejected` event have not been seen: a member of another shape is null.

`attempts` is an array with one entry per launch the call began, in order, a launch that could not be started included: `account`, `session`, `start`, `end`, `state` (as the record holds them for that launch), `worked` (a tool ran in it), `continued` (it got the continuation text; false for a launch that could not be started and in every entry of a resumed call) and `limit` (as above, of that launch). While a launch runs its entry is the last one, with `state` `running`, `end` null and `limit` null. Every other member of the record is the last launch's, and the last entry agrees with them; a Codex stage has one entry (`continued` false, `limit` null). A call whose files could not be opened writes the record without `limit`, `attempts` and `compact_window`. `ci/host-run-scope.sh` exercises the real unit on a host with systemd.

### A typed answer

`answer_schema` makes the answer of a stage on the Claude runtime one JSON object that the CLI validated against a schema of the request, in place of free text. Its value is the absolute path of a regular file of at most 65,536 bytes whose text parses as one JSON object (the JSON Schema; the CLI refuses a schema it cannot use, and the stage then ends without an answer). A value that is no such path or file, the member together with `expect.first_line` (there is no first line to match), and the member with `runtime: "codex"` (that runtime gets its typed answer in a later unit) refuse `invalid_input` with the field `answer_schema`, before any effect. Without the member every argument list, record, file, output and exit code is what it is without this section.

With the member the CLI's arguments gain `--json-schema` followed by the file's text exactly as read, for a first run and for a `resume` alike; nothing else of them changes. The record holds `answer_schema{path,sha256}` (the file as it was read) from the launch on. A `result` event counts as an answer only when its member `structured_output` is a JSON object; the choice among several `result` events is the one of "States" with that condition in place of the first-line pattern. The answer file `out` then holds that object as JSON text, pretty-printed with one trailing newline, written through a temporary name, and the record's `answer` names its path and digest; the text of the `result` member is not the answer. A chosen `result` whose `structured_output` is absent, null or not an object ends the stage `no_result` with `unmet: schema` (exit code 3 as for any `no_result`); its result text, when it is not empty, is saved to `out` as a miss of `expect.first_line` saves it. An error, a cut and a time bound end as without the member.

`ap run` does not validate the object against the schema: the CLI did, and a stage that ends `ok` holds the object the CLI accepted. A reader of the answer types the members it reads: it checks each member's type when it reads it, and does not take a type from `ap run`.

### A stage on the Codex CLI

`runtime: "codex"` starts the stage on the Codex CLI instead, through the same request, scope, record files and order of judgment. The request differs here: `role` is `implementer` or `fixer` (a `reviewer` refuses `invalid_input` with `role`: reviewers run on Claude Code); `account` is a Codex home (an existing directory, given to the CLI as `CODEX_HOME`); `next_accounts` must be absent or empty, and `mcp_config` absent or empty; `skills`, `memory`, `integration` and `compact_window` must be absent (each refuses `invalid_input` with its name: not built for this runtime; a Codex stage has no compaction window of the request); `model` is the CLI's model name and `effort` its reasoning effort; `permission_mode` must be stated and be `bypassPermissions`: the CLI then runs with no approval and no sandbox of its own, for both roles, so a Codex stage is held to its worktree or its copy by its prompt alone (a Claude stage in `ap unit` runs in the mode `auto` by default); `env` refuses `env_forbidden` also for a name beginning `CODEX_` or `OPENAI_`, so the home named in the record is the home that answers. Every other member means what it means above.

The launch, after the same `systemd-run … --`: `codex --no-daemon exec --json --ignore-user-config --ignore-rules --disable hooks --disable apps --disable plugins --disable plugin_discovery_prefetch --disable skill_mcp_dependency_install --disable memories --disable multi_agent -c features.multi_agent_v2.max_concurrent_threads_per_session=1 --skip-git-repo-check --dangerously-bypass-approvals-and-sandbox -m <model> -c model_reasoning_effort="<effort>" -C <cwd> -`, the prompt on stdin (`-`), the environment of a Claude stage with `CODEX_HOME=<account>` in place of `CLAUDE_CONFIG_DIR`. A resume is `codex --no-daemon exec resume <the same flags> -m <model> -c model_reasoning_effort="<effort>" <session> -` in the record's `cwd`. What each flag carries, for a fresh and a resumed stage alike: no shared background server (`--no-daemon`); the home's `config.toml` does not load, so no MCP server, hook trust, profile, project trust, app, plugin or skill switch registered there applies, while the login of the home still answers (`--ignore-user-config`); the flag `--ignore-user-config` itself also leaves out the project `.codex/` layer of the working root, even when that root is marked trusted; no hook runs, of the home or of the working root, and hook trust is never bypassed (`--disable hooks`, and no `--dangerously-bypass-hook-trust`); no app connector of the login (`--disable apps`); no plugin loaded or fetched (`--disable plugins`, `--disable plugin_discovery_prefetch`); no MCP server installed for a skill (`--disable skill_mcp_dependency_install`); no memory read or written (`--disable memories`); no further agent: the model catalog of CLI 0.167.2 turns the agent tools on whatever the feature says, so the session's thread limit is 1 and a spawn fails with `agent thread limit reached` (`--disable multi_agent`, `features.multi_agent_v2.max_concurrent_threads_per_session=1`); no command rules of the home (`--ignore-rules`); a working root outside a Git repository is accepted (`--skip-git-repo-check`); the session's files are kept (no `--ephemeral`). What such a stage still reads: the home's instruction pointer (`AGENTS.md` of the home), an `AGENTS.md` of the working root, and the skill list the CLI finds by itself. Measured on CLI 0.167.2 with a scratch home and a working root whose `config.toml` and `hooks.json` each register a canary: the bare CLI starts all four, a stage of `ap run` none, fresh or resumed; `ap` writes no file of the home.

The stream (the CLI's `--json` events) is read into the shape the judgment above reads, so one order of judgment serves both runtimes. `thread.started` names the session: its `thread_id` is written into the record at once (state `running`), and stays there in every state (null only when the CLI named no thread); a failed write of the record at that point is a failed write of the record after the launch (exit 5), as above. A turn end is a result: `turn.completed` gives the answer, the text of the LAST `agent_message` item completed in that turn (empty when there is none: `no_result` with `unmet: answer`), and the usage; `turn.failed` is an error result whose message is the error's, never written to `out` or to the record (the stream holds it). A message of a turn that did not complete is never an answer. An `error` event alone decides nothing: the CLI prints one for each reconnection attempt before a turn that may still complete. So a completed turn is judged like a result above; a failed turn is `failed`, or `cut` (exit 75) when its message is the usage-limit text (every sentence CLI 0.167.2 holds for a usage limit meets that rule; no real limit has been seen, and where such a text arrives is not shown); no turn end is `timeout` when the bound stopped the stage and `failed` (`unmet: result_event`) when the CLI ended by itself. The record: `tokens` maps the turn's usage as `evals/readout.py` maps a Codex session: `input` is `input_tokens` without `cached_input_tokens` and `cache_write_input_tokens`, `cache_read` is `cached_input_tokens`, `cache_creation` is `cache_write_input_tokens` (0 when the CLI gives none), `output` is `output_tokens`. The CLI reports the usage of the whole thread at each turn end, so a resume's record holds its own part, as a Claude resume does: the reported usage less the `tokens` of the earlier record and of every record that one resumes (a record without tokens counts 0); when that chain cannot be followed to its end (more than 256 records, a record that cannot be read, or a record met twice), the record's `tokens` are null, as where the CLI did not report. `turns` is the number of completed items (messages, reasoning, commands, file changes, …), not comparable with a Claude stage's turns; `results` the number of turn ends read; `permission_denials` is empty. A tool ran when an item that is neither an agent message, nor reasoning, nor an error started or completed.

### A stage on Muse Code

`runtime: "muse"` starts the stage on the Muse Code CLI, through the same request, scope, record files and order of judgment. The request differs here: `role` is any of the three roles; `account` is the Muse Code configuration directory (an existing directory, else `account_missing`) whose last path component is `muse` (else `invalid_input`, field `account`), and the CLI is given its parent as `XDG_CONFIG_HOME`; `next_accounts` must be absent or empty, and `mcp_config` absent or empty; `skills`, `memory`, `integration`, `answer_schema` and `compact_window` must be absent (each refuses `invalid_input` with its name: not built for this runtime); `model` is the CLI's model name and `effort` its reasoning effort, both passed as they are, each as an argument of its own, so a value that begins with `-` refuses `invalid_input` with its field; `permission_mode` must be stated and be `bypassPermissions` (`ap unit` gives no default mode to a Muse block): the CLI then runs with no approval and no sandbox of its own, so a Muse stage is held to its worktree or its copy by its prompt alone; `env` refuses `env_forbidden` also for a name beginning `MUSE_` and for `XDG_CONFIG_HOME`, so the directory named in the record is the one that answers. Every other member means what it means above. A resume refuses `resume_runtime_differs` across runtimes in both directions.

The launch, after the same `systemd-run … --`: `muse exec --json --model <model> --reasoning-effort <effort> --contributor-mode off --disable-reminders --session-id <session> --workspace <cwd> --prompt-file <prompt> --yolo`, these arguments in this order and no other, for a fresh and a resumed stage alike (a resume is the same launch with the session of the record, in its `cwd`). The environment is that of a Claude stage with `XDG_CONFIG_HOME=<the parent directory of account>` in place of `CLAUDE_CONFIG_DIR`, and `MUSE_NO_AUTO_UPDATE=1`; the standard input is the null device, the prompt reaches the CLI as the path. The session id is chosen by `ap run`, as for a Claude stage, and stands in the record before the launch. What each flag carries: headless JSON lines on standard output (`exec --json`); the stage's model and reasoning effort; the CLI's per-run contributor mode off (`--contributor-mode off`: with the user's setting the CLI served the stage by a `-contributor` variant of the model named, and one run with the flag was served by the model named); no reminders (`--disable-reminders`); the session, the working directory and the prompt (`--session-id`, `--workspace`, `--prompt-file`); and no approval, no sandbox and a trusted workspace for this run (`--yolo`, by the CLI's help: "Disable approval and sandbox, trust this workspace (this run)"). A Muse stage has one account: a launch that ends `cut` ends the call, with no continuation and no move. `ap run` reads and writes no file under the account directory.

What such a stage still loads (observed: the shortest run read 33,091 input tokens, twelve runs of two model calls each between 66,038 and 68,400): the instruction file of the configuration directory, the catalog of skills and a memory snapshot, and, with `--yolo`, the MCP servers registered in the configuration directory; by the CLI's help a trusted workspace also loads its own rules and skills (not tried). No switch of one run keeps out a hook the configuration directory registers (its `settings.json` holds no member `hooks` today), nor the skills, the memory snapshot or the registered servers, and no flag bounds the time of a run: the stage's `timeout_seconds` does.

The lines of standard output (each one JSON object whose member `payload.kind` names it) are read into the shape the judgment above reads. A line of kind `task_lifecycle` whose `payload.event.task_kind` begins with `tool.` shows that the session did work. The serving model is checked: a `task_lifecycle` line with an entry of `payload.event.details.facets` whose `detail.model` is a string other than the request's `model` stops the stage at once, as the bound stops one, and the launch is `failed` with `unmet: model`, whatever else was read before or after it; no answer is written to `out`, and the record's member `served_by` names that model (the only record member a stage of another runtime does not hold). Each line of kind `run_terminal` is a result: `terminal` `completed` gives the answer, `text` (empty: `no_result`, `unmet: answer`); any other `terminal` is an error result whose message is `reason`, never written to `out`: `failed`, or `cut` (exit 75) when `reason` meets the usage-limit rule above. A `text` or a `reason` that is no string counts as empty. A reviewer's stage ends at the first `run_terminal`; for the other roles it ends when the CLI ends or at the bound, and a CLI that outlives its `run_terminal` to the bound is `timeout` with that answer kept (one process was seen to stay alive after the line, with a command left running). No `run_terminal` ends `timeout` when the bound stopped the stage and `failed` with `unmet: result_event` when the CLI ended by itself. A line that is no JSON object, or of another kind, decides nothing.

The record: `tokens` and `turns` come from the last line `run_usage`, which a failed run may not print: `cache_read` is `cached_tokens`, `input` is, per entry of `models`, `input_tokens` less `cached_tokens` (never below 0), summed, `output` is `output_tokens`, `cache_creation` is 0, `turns` is `calls`; a member that is no number counts 0 (`turns` null for a `calls` that is none), and without the line all five are null. The CLI counts the one run, also on a resume, so a resume's record holds its own run's numbers and nothing is subtracted. `limit` is null without a `run_usage` line or when its `allowance` is no object; else an object of the Claude shape with `status`, `resets_at` and `kind` null and `windows` holding an entry for each of `weekly` and `window` that is an object: `status` null, `resets_at` the integer `resets_at_ms` divided by 1000 without its remainder (null when it is no integer of 0 or more), `utilization` the hundredth of `used_percent` (null when that is no number). `permission_denials` is empty; `results` is the number of `run_terminal` lines read.

Observed on Muse Code CLI 1.4.20 by the program's own runs: the flags above, `payload.kind` of every line, one `run_usage` before the `run_terminal` of a completed run, exit 0 on a completed run and 1 on a failed one, a second run with the same `--session-id` and `--workspace` continuing the session (also after the first was ended by a signal, when it printed no `run_terminal` and no `run_usage`), and the serving model in the `provider` facet. Assumed, not observed: that `input_tokens` of an entry includes its `cached_tokens` (in every line kept `cached_tokens` is the smaller), what the CLI prints when the allowance is used up (the binary holds "usage limit reached" and "This turn stopped because your usage limit was reached."; such a failure is read by the rule above), and whether the CLI prints further result lines in one process when a command a stage left running ends.

### A stage on the Antigravity CLI

`runtime: "agy"` starts a reviewer stage on the Antigravity CLI (`agy`), through the same request, scope, record files and order of judgment. The request differs here: `role` is `reviewer` alone (an `implementer` or a `fixer` refuses `invalid_input` with `role`: the CLI's home is a directory given as `HOME`, so the stage's `git`, `gh` and `cargo` lose their own files, and `ap` does not yet give a writing stage those files); `account` is the template of the stage's homes and is never given to the CLI as `HOME`: an existing directory (else `account_missing`) that holds `.gemini/antigravity-cli/antigravity-oauth-token` (a symbolic link to the real token counts, as the template is made with one; a missing file or a link to nothing refuses `invalid_input`, field `account`) and holds no `.gemini/config` (the same refusal: a `config` there is where the CLI reads the MCP servers, hooks, skills and plugins registered for it, and the home made from the template would link into it); the CLI is given the stage's own home as `HOME` (below), which replaces the caller's `HOME` (the child's environment holds one `HOME`); `model` is the CLI's slug (`agy models`; for Hydrogen `gemini-4-hydrogen-low`, `-medium`, `-high`, `-xhigh`), passed as one argument of its own, so a value that begins with `-` refuses `invalid_input` with `model`; `effort` is required, as for every runtime, and must be the level the slug ends with (`low`, `medium`, `high` or `xhigh`), else `invalid_input` with `effort`: the slug carries the level, so `effort` is not passed to the CLI (`--effort` was never run); `permission_mode` must be stated and be `bypassPermissions`; `next_accounts` and `mcp_config` must be absent or empty; `skills`, `memory`, `integration`, `answer_schema` and `compact_window` must be absent (each refuses `invalid_input` with its name: not built for this runtime); `env` refuses `env_forbidden` also for a name beginning `AGY_` or `GEMINI_`, so the home and the update setting named below are the ones that answer. A resume refuses `resume_runtime_differs` across runtimes in both directions. In `ap unit` a verifier block may name `runtime: "agy"`; an `implementer` block (and so its fixer) that names it is refused before any effect with the error `ap run` gives, under the block's field (`implementer.role`); the second look of an agy verifier resumes its record as for the other runtimes. `git`, `gh`, `cargo` and `rustup` of the stage read the directory given as `HOME`, which is the stage's home and not the caller's home: a request whose stage needs them names their directories in `env` (`GH_CONFIG_DIR`, `CARGO_HOME`, `RUSTUP_HOME`).

The launch, after the same `systemd-run … --`: `agy --print <prompt> --output-format stream-json --model <model> --dangerously-skip-permissions --print-timeout <seconds>s`, these arguments in this order and no other for a fresh stage, in the request's `cwd`; a resume adds `--conversation <session>` at the end and runs in the record's `cwd`. The environment is that of a Claude stage with `HOME=<the stage's home>` in place of `CLAUDE_CONFIG_DIR`, and `AGY_CLI_DISABLE_AUTO_UPDATE=1`; the standard input is the null device. What each flag carries: the prompt text, run once without a terminal (`--print`: the next argument is its value, also when it begins with dashes, observed); one JSON object per line on standard output (`--output-format stream-json`); the stage's model, whose slug carries the level (`--model`); no approval prompt (`--dangerously-skip-permissions`; the line `init` then shows `permission_mode` `always-proceed`); and the stage's own bound, `timeout_seconds`, as the CLI's time limit (`--print-timeout`; `ap run` ends the stage at the same bound and judges by what it read). The CLI has no working-directory flag: it works in the process's `cwd`, which also keys its conversations. The session cannot be chosen: the CLI names it, in the line `{"event":"init"}` as `conversation_id`, and `ap run` writes that id into the record at once (state `running`, as it writes a Codex thread); before the line the record's `session` is null, and after it the id stays in the record in every state. 

The stage's home. For a fresh stage `ap run` makes `<account>/homes/<new uuid>` (mode 0700; `homes` is made, mode 0700, when it is absent). The new home holds three symbolic links, with the directories that hold them, and nothing else: `.gemini/antigravity-cli/antigravity-oauth-token` to the account's token, and `.gemini/AGENTS.md` and `.gemini/GEMINI.md` to the account's files of those names (a link is made also when its target is absent). ## The gate

`ap gate < request.json` waits on ONE pull request's head until its required checks are done, and the automatic review too when the request names its reviewer, and prints one JSON answer on stdout. It reads GitHub through `gh api graphql` (the caller's `gh` login) and decides nothing a person decides: it resolves no thread, posts no status, merges nothing and calls no store. Its only writes are `gh pr ready` on a draft (once) and the one toggle below.

The request: `repository` (`owner/name`), `pull_request` (number), optional `head` (40 hex: the head the caller expects), `autoreview` (the login of an automatic reviewer whose comment carries the marker, for example `chatgpt-codex-connector[bot]`; absent or `false`, the default since 2026-11-17: no automatic reviewer is waited for, because the review of a unit is its `verifier` stage), `check_minutes` (default 90) and `autoreview_minutes` (default 40), each 1 to 1440. Another member, or a malformed one, refuses `invalid_input` with exit 2 before any read: `{"error":{"code","field","detail"}}` on stderr.

It reads every 30 seconds. The head it waits on is the one GitHub reports at the first reading. In order:
1. Merged or closed (at any reading) ends `merged` or `closed`. A caller's `head` that differs from GitHub's ends `head_differs` (`expected` names the caller's). A head that moves later ends `head_moved` (`head_now`). A draft is marked ready once; a failed mark ends `ready_failed`.
2. The required checks, judged at every reading, also while the gate waits for the review: every entry on the head's commit whose `isRequired` is true, except the status `lead-review` (a `StatusContext` of that context: the output of the Lead's accept, not a check that precedes the review, so a revoked or pending acceptance never blocks the gate; a check run of that name is judged like any other), over every page (a reading that could not be completed is no reading). One that completed with any conclusion but `SUCCESS`, or a status that is not `SUCCESS` or pending, ends `check_failed` with `failed_check: {name, state, run}`. None yet, or one pending, waits; at the bound of the phase (`check_minutes`, or `autoreview_minutes` once the review wait began) it ends `check_timeout`. A repository without a required check ends `check_timeout`.
3. The automatic review (only when `autoreview` names a login; skipped when it is absent or `false`): the marker `codex-review-state:v1 {…}` counts only in a comment of that login (a bot's GraphQL login gets `[bot]`, so a user of the same name does not count); the last such comment's `code_review` is read, from the last occurrence in that comment that parses. The marker is looked for in the last 100 comments. When the checks have passed and it names another commit (or none), the gate marks the pull request draft and ready ONCE, because a push to a ready pull request is not reviewed; not when the gate itself just marked a draft ready. It ends `passed` when `commit_sha` is the head and `status` is `completed`, and also at `autoreview_minutes`: the time limit passing is not a failure, `autoreview.state` says `timeout`.

The answer: `end`, `repository`, `pull_request`, `head`, `marked_ready`, `checks` (`[{name, state, run}]`: the judged entries, then the status `lead-review` with its state and `judged: false` when the head has one, required or not), `autoreview` (`login`, `state`: `completed`, `timeout`, `waiting` when the gate ended before it, or `off`; `commit`, `has_unresolved_findings` as the marker says, `toggled`, `threads_on_head`: the number of review threads, resolved or not, whose first comment is the automatic reviewer's and was made on the head commit (the comment's `originalCommit`); `null` when the threads could not be read or no reviewer is named), `threads` (every unresolved review thread: `id`, `path`, `line`, `author`, `answered`: its last comment is not the automatic reviewer's, `comments`: its number of comments; `null` when it could not be read), and `failed_check`, `expected`, `head_now`, `left_draft` (a toggle whose ready mark failed three times) or `unreadable` with their ends. `answered` is true for every thread when no reviewer is named. `passed` with exit 0 also covers a review that reached its time limit and a review with unresolved findings: the caller reads `autoreview.state`, `has_unresolved_findings`, `threads_on_head` and `threads`: the marker's flag does not change when a person answers and resolves a thread, the threads do. `ap gate` decides nothing of this and writes nothing more. Exit by end: 0 `passed`; 10 `merged`, `closed`, `head_differs`, `head_moved`; 11 `check_failed`, `check_timeout`; 12 `ready_failed`, `github_unreadable` (`unreadable` names the cause: `not_found`, `no_login` or `gh_not_started` end at the first reading; `no_answer` when a reading still failed at the bound of the phase).

## One review

`ap review start|close|revoke` reads one JSON object on stdin and writes
one JSON answer; a refusal is `{"error":{"code","field","detail"}}` on stderr with exit 3.
Every path is absolute. Optional `store` forwards `--store` to every `ont` call.
The review object owns the verdict; `lead-review` is a derived commit status.
The rulesets of the three platform repositories require it beside `rust`.

`start` reads and hashes a regular prompt file below `/home/palantirkc/work/`.
With a pull request, it checks that the request is open at exactly `head`.
Each optional run must exist, belong to the task and occur once. It applies
`start_review` with a stable request id based on task key, kind, head and prompt
hash, returning `status: started`, `outcome: applied`, the complete `review` id
and `prompt_sha256`. Optional integer `attempt` (2 to 99) appends a newline and
that number to the digest input; omit it for the first attempt. A repeated request
reads the review and returns `outcome: already_applied` only while it is running.
A closed review is refused with `review_already_closed`; retry with a new `attempt`.
It does not launch a reviewer. Example stdin for `ap review start`:

```json
{"task_dir":"/home/palantirkc/work/example","kind":"packet","head":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","base":"bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb","repository":"owner/repo","pull_request":12,"runs":[{"object_type":"worker_run","namespace":{"instance":"vps://palantirkc","account":"root"},"native_key":"run-key"}],"model":"reviewer-model","effort":"high","prompt":"/home/palantirkc/work/example/prompt.md"}
```

`close` reads a regular report file below the work root, at most 1 MiB. Its
first line must be exactly `Verdict: accept` or `Verdict: repair`. It hashes the
bytes and applies `close_review`; optional `account` and `session` are recorded.
Alternatively, supply `verdict: abandoned` with no report. The answer contains
`status: closed`, `verdict` and `report_sha256` (null for abandoned). The stable
close request id hashes the review key and report hash (`abandoned` without a
report). Example stdin for `ap review close`:

```json
{"review":{"object_type":"review","namespace":{"instance":"vps://palantirkc","account":"root"},"native_key":"review-key"},"report":"/home/palantirkc/work/example/report.md","account":"b","session":"reviewer-session"}
```

`revoke` reads a review with a repository and head. When its `status` is
`closed` it applies `revoke_review` with the reason, under the request id
`rv-revoke-` and the first 40 hex of the SHA-256 of the review's key, the same
for every revoke of that review; a refusal or a failure of the store ends the
command with `store_refused` or `store_answer_unreadable` and nothing is posted.
When the `status` already is `revoked` it applies nothing. Only then does it post
`lead-review=failure` with `revoked: <reason>`. The object changes before the
status, because the store is what a later reader asks: a come-back of `ap unit`
and `start_install` read `status: closed`, so a revoked review is not found
again, while a status alone would be overwritten by the next `success`. A crash
between the two leaves a revoked object and no posted failure; the repeated
command finds `revoked` and posts it. A running review is not changed. The
reason must contain text and fit within 100 UTF-8 bytes. It returns
`status: revoked` and `head`. Example stdin for `ap review revoke`:

```json
{"review":{"object_type":"review","namespace":{"instance":"vps://palantirkc","account":"root"},"native_key":"review-key"},"reason":"Report missed a changed path"}
```

Refusals (local checks precede writes and status posts):

- `invalid_input`: malformed object, id, path, run list, reason or explicit verdict; field identifies the member.
- `review_prompt_unreadable`: prompt is not a readable regular file below the work root.
- `review_head_differs`: pull request is closed or has another head.
- `review_run_unknown`: a start run cannot be read as the exact current object.
- `review_run_of_other_task`: a run supplied to `start` belongs to another task.
- `review_already_closed`: `start` repeated after its review closed; repeat with a new `attempt`.
- `store_refused`: the store refused an attempted action; detail carries its codes; no retry occurs.
- `review_report_unreadable`: close report is unreadable, outside the work root or larger than 1 MiB.
- `review_report_lacks_verdict`: the report's first line is not one of the two exact verdict lines.
- `review_not_accepting`: required review state or evidence is absent; detail names the first failing member.
- `store_review_unreadable`: the exact review's current observation cannot be read.
- `store_answer_unreadable`: an action reply is malformed or does not confirm the expected create.
- `process_failed`: an external command failed or returned unreadable Git output; no automatic retry occurs.
- `io_error`: stdin or the caller's working directory cannot be read.
- `input_too_large`: stdin exceeds 1 MiB.
- `usage`: exactly one supported verb is required.

## The page's block

A page may hold a typed block: the write set and the checks of the unit, as data that code tested in this repository evaluates, instead of a line `Write set:` and an acceptance executable written for the unit. The block is the text between a line that is exactly three backticks followed by `unit` and the next line that is exactly three backticks (a line with anything else on it, or a carriage return, is no such line); it must parse as ONE JSON object. A page has no block when it holds no opening line.

Members: `unit` (required; 1 to 40 characters of `A-Z`, `a-z`, `0-9`, `-`), `write_set` (required; 1 to 40 patterns, each a nonempty string without a comma and without a space at its start or end, matched as a pattern of the line `Write set:` is: exactly the path, or a trailing `/**` for the descendants, not the directory itself), `checks` (optional, below) `repository` (`owner/name`), `branch` (a branch name as the request's `branch`), `item` (as the request's `item`), `merge` (a boolean), `implementer` and `verifier` (each an object: `model` and `effort`, nonempty strings, and optional `runtime`, `permission_mode` (nonempty strings) and `timeout_seconds` (an integer above 0); no other member), all read by `ap unit <page>` and required there ("A unit from its page"; `ap accept` and a request on stdin do not need them), and `tier` (1 to 40 characters), read and not used by any verb. `checks` holds any of four lists of at most 40 entries each; "the diff" is everywhere the change from the merge base of `origin/main` and `HEAD` to `HEAD`, and a path pattern is a pattern of the write set:

| List | An entry | It holds when |
| --- | --- | --- |
| `unchanged` | a path pattern | no changed path matches it |
| `adds` | `{"path": <pattern>, "words": [<text>, ...]}` (at least one word) | for each word, at least one ADDED line of the diff of the paths the pattern matches contains the word literally (a word that is only in a removed line, or only in an added line of another path, does not count; a pattern that matches no changed path fails every word) |
| `holds` | `{"path": <exact path>, "text": <text>}` or `{"path": <exact path>, "exact": <text>}`, exactly one of the two | the file, read from the commit `HEAD` through Git as bytes (never from the working tree), contains the text, or is exactly the text's UTF-8 bytes; a path that is not a regular file of that commit (missing, a directory, a symbolic link) fails. The path has no empty component, no `.` and no `..` |
| `lines` | `{"path": <pattern>, "max": <n>, "min": <n>}`, `min` optional (default 0), both integers not negative, `min` not above `max` | the added plus removed lines of the diff of the matched paths are at most `max` and at least `min` |

A word or a text is 1 to 2,000 bytes without a line feed; `exact` may hold line feeds and is at most 65,536 bytes. The diff's changed paths are read with `git diff --no-renames --ignore-submodules=none --no-relative --name-only -z <merge base> HEAD` (`git --no-replace-objects`); added and removed lines, for `adds` and `lines` alike, per matched path with `-U0 --no-ext-diff --no-textconv` and the same three options (the lines of the hunks: a header, also the second of a typechange, is none). A binary file is a changed path, has no added line and counts as no line. No check runs a command of the page or of the repository: a check reads Git and files only.

Refusals of a block, in `ap unit` and `ap accept` alike, before any effect, with the field `page`: `page_block_invalid` with `detail` `{"reason": ..., "member": ...}`: `two_blocks` (two opening lines), `unclosed`, `not_an_object` (the text is not one JSON object, or an object holds a member twice), `unknown_member` (`member` names it; one inside `checks` is `checks.<name>`), `shape` (`member` names the member, a member inside `checks` as `checks.<list>`; also a required member that is missing; `implementer` and `verifier` are named whole, not by the member inside them) and `no_block` (`ap accept` only: the page has none); and `write_set_twice` (a block and a line `Write set:` in one page). With a block the page holds no line `Write set:`: the write set is the block's, for the step `write_set` and for the record, in the same form. A page without a block is read as before in `ap unit` (`write_set_missing` and the rest). A case call takes no part in this.

`ap accept <page>` evaluates a page's block in the current directory, which must be a Git worktree that knows `origin/main`. It refuses with exit 2, in the error form of the other verbs (`{"error":{"code","field","detail"}}` on stderr) and writes nothing: another number of arguments, or a relative path (`usage`); a page that cannot be read (`page_unreadable`); a page without a block, or a bad block or both a block and a line `Write set:` (above); a current directory that is no worktree (`not_a_worktree`, field `cwd`); `origin/main` unknown there (`origin_main_unknown`); a Git call that failed (`git_failed`). Otherwise it checks, in this order: `clean` (`git status --porcelain` prints nothing), `write_set` (every changed path is inside the write set), then the block's lists in the order `unchanged`, `adds`, `holds`, `lines`, each entry in its order. It prints one line `accept: FAILED: <kind>: <what>` per failed check (one per missing word of `adds`) and exits 1, or prints `accept: ok` and exits 0. It calls no network and no store. A unit call without `acceptance` evaluates the same lists by the same code ("One unit").

What a check reads, stated as the code does it: a `holds` path is given to Git as a pathspec (`git ls-tree -- <path>`), so a path that begins with `:` is read as pathspec magic and fails the check as "is not a regular file of HEAD"; the changed paths of the diff are read as UTF-8 by the step `write_set` of `ap unit` (a path that is not UTF-8 fails the Git call: `git_failed`) and lossily by `ap accept` and the step `acceptance` (each invalid byte read as U+FFFD, the path matched as that text); a Git answer above 1 MiB, the bound of every call's output, is a failed call and no check passes by it: `process_failed` (field `git`) from `ap accept` and from the step `acceptance` of `ap unit`, `git_failed` from the step `write_set`; the reason is not `shape` or any other reason of the block.

## One unit

`ap unit < request.json` takes ONE unit of work once from its page to the merge: worktree, one implementer stage, the pull request, the gate, the page's acceptance executable (or the checks of its block), the write set, one verifier stage, the `review` object, the status `lead-review`, the guarded merge, the removal of the worktree. It returns when the unit merged or when the first step that did not pass ended it, and prints the unit record on stdout. A request with the member `case` is a case call instead ("One case" below); a request without it is a unit call, as this section says. Exit 0 `merged`, or `accepted` when the request says not to merge; 3 `stopped` (the record names the step and the cause); 5 the record could not be written after it was claimed (stdout holds the last record). Exit 2 is a refusal before any effect, in the form of `ap run`: `{"error":{"code","field","detail"}}` on stderr, no record. Without `repair` it is one pass: at most one implementer and one verifier stage, no fixer, no round, no step repeated, no wait but the stage's own and the gate's; it never continues an earlier call's record. With `repair` a `Verdict: repair` gets ONE round: a fixer stage and one come-back ("The round" below). No path accepts without the verdict of a model: every call has a verifier stage or the answer of an earlier one, and the command never writes a verdict itself.

The request: `repository` (`owner/name`), `clone` (the local clone whose `origin` is the repository), `worktree` (the path of the unit's worktree), `branch` (a new branch), `task_key` (the store's task the `review` hangs on, `^[a-z0-9][a-z0-9-]{0,63}$`; not derived from a directory), `page` (the packet: a regular file with exactly one line beginning `Write set:` at the first column, comma-separated patterns matched as exact paths or as a directory with a trailing `/**` (the descendants, not the directory itself), or a typed block and no such line: "The page's block"), `out` (the prefix of every file of the call), `acceptance` (optional: the page's acceptance executable; without it the page must hold a block, whose `checks` the step `acceptance` evaluates), `implementer` and `verifier` (each `account`, `model`, `effort`, `prompt`, optional `runtime` (`claude` by default; `codex` for the implementer only, `agy` for the verifier only and `muse` for either block; a Codex, Muse or agy block must state `permission_mode`: a verifier with `runtime: "codex"`, an implementer with `runtime: "agy"` and a Codex, Muse or agy stage without a stated mode are refused here, before any effect), `permission_mode` (default `auto` for a stage on Claude Code only: a block on Codex, Muse Code or agy states its own, which `ap run` admits as `bypassPermissions` alone), `timeout_seconds`, `next_accounts`, `env`, `resume` and `compact_window` (the window of its Claude stage: "One stage"; a value `ap run` would refuse is refused by the call before any effect, as `implementer.compact_window` or `verifier.compact_window`), given to `ap run` as they are: a stage cut before it did any work, and a verifier cut at any point, runs again on the next account inside the same stage and its one record; with `resume` (`{"record": "<path>"}`) a repaired head returns to the session that reviewed it, the Lead's prompt file is the next message to that session and the block of facts is appended as before), optional `acceptance_seconds` (1 to 86400, default 2700), `gate` (`autoreview`, `check_minutes`, `autoreview_minutes` as `ap gate` takes them), `store` (forwarded to every `ont` call), `merge` (false: the call ends `accepted` after the review is closed, with no status), `pull_request` (a come-back after a repair by hand: steps 2 to 4 are skipped and the existing `worktree` on `branch` is used) and `verdict` (with `pull_request` only, instead of `verifier`: the answer of an earlier reviewer stage; step 8 is skipped and the file is checked against the head), `repair` (a unit call without `pull_request` and `verdict` only: `prompt` and `verifier_prompt`, absolute paths of regular files outside `worktree`, and `timeout_seconds`, all three required; "The round" below), `judge_threads` (a boolean, `false` the same as absent: the verifier judges the automatic reviewer's threads, "The threads" below, which needs `gate.autoreview` to name that reviewer's login; without `true` every record, file, output and exit code is what it is without the member), and `item` (a string of at most 60 bytes: the key of an item of the task's board, "The item" below; a case call refuses the member and never needs it). `verdict` is taken only when `<verdict>.run.json` lies beside it: an `ap run` record with role `reviewer`, state `ok`, `answer.path` and `answer.sha256` equal to the file and its digest, and a prompt file (below the work root) that still has the recorded digest. Every path is absolute; `page`, `out` and `verdict` lie below the work root (`/home/palantirkc/work/`), because the `review` object records them. `acceptance`, when given, and the verifier's prompt lie outside `worktree`.

The use of `merge: false`: a unit with a real effect, where the Lead reads the diff after the verifier accepted and before the merge. The come-back with `pull_request` and `verdict` (the verifier's answer `<out>.verifier.md`) then posts the status and merges; it uses the review the first call closed (step `review` below). The same come-back finishes a call that stopped at `status` or `merge`.

Refusals (exit 2, before any effect: no file, worktree, branch, process or network call): `invalid_input` (an unknown or malformed member, a relative path, neither or both of `verifier` and `verdict`; `field` names the member, `implementer.prompt` for a nested one); `outside_work_root`; `inside_worktree` (`acceptance` or the verifier's prompt); `page_unreadable`; `page_block_invalid` and `write_set_twice` (the page's block, "The page's block"); `write_set_missing` (a page without a block: no line `Write set:`, or more than one, or one without a pattern); `invalid_input` with the field `acceptance` (no `acceptance` and a page without a block; it comes after the page's own refusals above); `prompt_unreadable` (also a verifier prompt that leaves no room for the block of facts within `ap run`'s 1 MiB); `acceptance_unreadable` (not a regular executable file); `verdict_unreadable` (no file, or no record beside it as above); `out_exists` (`<out>.unit.json` or another file of the call exists); `out_unwritable` (the record cannot be created); `worktree_exists` (a fresh call whose `worktree` exists); `worktree_missing` (a come-back whose `worktree` is not a directory). `invalid_input` also for a `judge_threads` that is not a boolean and for an `item` that is not a string of 1 to 60 bytes (a case call refuses both members). After these checks the item is resolved ("The item" below); its refusals have the same form (exit 2, field `item`, no record). With `repair`: `invalid_input` (`repair` malformed or beside `pull_request` or `verdict`, `field` `repair` or `repair.<member>`; a case call refuses the member); `inside_worktree` (`repair.prompt`, `repair.verifier_prompt`); `prompt_unreadable` (either file, also one that leaves no room for its block of facts); `out_exists` also for `<out>.fixer.md`, `<out>.fixer.prompt.md` and every file of the call `<out>-2`, `<out>-2.unit.json` included; the fixer's request is judged by `ap run`'s code as a fresh fixer (field `repair.timeout_seconds`, `repair.prompt`), its prompt as the fixer will get it: `repair.prompt` followed by its block of facts (e.g. `out_named_in_prompt` with the field `repair.prompt` for a `page` whose path holds `<out>.fixer.md`), and the come-back's verifier stage as a fresh reviewer with `repair.verifier_prompt` and the answer `<out>-2.verifier.md` (its code with the field `repair.verifier_prompt`, e.g. `out_named_in_prompt` for a prompt that names that answer). Every member of `implementer` and `verifier` that `ap run` can judge before the stage's worktree exists (its shape, `permission_mode`, `timeout_seconds`, `model`, `effort`, `next_accounts`, `resume`, the account rules, the prompt, the stage's files) is judged here by `ap run`'s own code, with its code and the field prefixed (`verifier.timeout_seconds`); what only the stage's start shows ends the call at that stage with the cause `stage_refused`.

The item (`item`). A task of the store can have a board: the order of its items (`board`, `item` and `objective` of version 9 of the work schema, `ontology/README.md`). At the start of EVERY unit call (a first call, a come-back with `pull_request`, a call with `verdict`, the come-back of a round), after the checks above and before any other effect (no worktree, no call to GitHub, no stage, no other store write), the command reads the board of `task_key` and resolves the item:

- The task has no board: a request without `item` runs exactly as without the member (every record, file, output and exit code); a request with `item` is refused `item_not_ordered`.
- The task has a board and the request no `item`: `item_required`.
- No item of the task has the key: `item_unknown`. The item is `done`: `item_done`; `dropped`: `item_dropped`.
- The item's objective is retired: `objective_not_current`. The objective's source row is not `current`: `objective_source_superseded`.
- The item is `in_work` and its `repository` and `branch` are the request's: the call goes on (a come-back, a round, a call repeated after a death); else `item_of_another_unit`.
- The item is `queued`: the command applies `start_item` with the request's `repository` and `branch`. The store's refusal `item_not_ordered` (the board does not name the item) refuses the call with that code; any other refusal or failure refuses it with `item_unwritten` (`detail` `{"code"}`: the store's first code, or the failure's). The request id holds the item's and the board's revisions, so after a `release_item` a new call for the same item, repository and branch is a new request and starts the item again.

A failed read of the store refuses the call with its code (`store_answer_unreadable`, `process_failed`), with or without `item`. The record gets `item` (`key`, the item's `id`, `objective` with its `name` and `id`), and the verifier's block of facts gets the item's key, title, statement and first use and the objective's name and statement; without `item` the block is byte for byte the one above. Immediately before `gh pr merge` the item is read again: `dropped` or `done` stops the call at `merge` with `item_dropped` or `item_done`, and nothing is merged. After the merge the command applies `close_item` with the accepting review of the step `review`: applied, the record's `item` gets `closed: true`; a refusal or a failure gives `closed: false` and `code` (the store's first code, or the failure's), the state stays `merged` and the exit code 0, and `close_item` applied later by hand succeeds, because the item is still `in_work`. A call that does not merge (`merge: false`, a stop) closes and releases nothing: the item stays `in_work` for its come-back.

The sequence. Each step is recorded before it begins and after it ends; the first that does not pass ends the call with `state: stopped`, `stopped_at` (the step) and `cause` (`io_error` when a file of the call cannot be created):

| --- | --- | --- |
| `worktree` | `git fetch origin main` in `clone`; the worktree and `branch` from the fetched `origin/main` (recorded as `base` until step `write_set`) | `fetch_failed`, `worktree_failed` |
| `implementer` | ONE `ap run` stage, role `implementer`, cwd `worktree`, the Lead's prompt file unchanged, no `expect`; answer `<out>.implementer.md`, which is the unit's report: the Lead's prompt asks for the report as the final message | `stage_refused`, or the stage's state when it is not `ok` (`cut`, `timeout`, `no_result`, `failed`); `stage_record_unwritten` (the state is `ok` and `ap run` exited with another status than 0: the stage's final record could not be written; the same for the verifier and the fixer) |
| `pull_request` | the one open pull request of `branch` against `main` | `no_pull_request`, `pull_request_ambiguous`, `github_unreadable` |

The step's `detail` is `{"lead_review": <state>}`: the state of the status `lead-review` the gate lists and does not judge, or null, so that a revoked acceptance is seen | the gate's end when it is not `passed`; `unresolved_findings` (the marker says `has_unresolved_findings: true` for the head and `threads_on_head` is 0 or `null`: the findings are not visible as threads, so nothing shows that anyone answered them; with `judge_threads` and `threads_on_head` 0 it does not stop when at least one thread is given to the verifier, an earlier thread of the reviewer that the marker still names: "The threads"); `unresolved_threads` (one or more, or not readable: where the marker says true and the reviewer has threads on the head, the threads decide, so a finding the Lead answered and resolved without a push passes; with `judge_threads` a thread given to the verifier does not stop the step and the detail lists only the others) |
| `acceptance` | `acceptance` in `worktree`, no arguments, stdin `/dev/null`, under `timeout -k 10 <acceptance_seconds>`; stdout and stderr to `<out>.accept.log`. Without `acceptance`: after the same conditions (the clean worktree, `HEAD` the gate's head) and a `git fetch origin main` in `clone` as the step `write_set` makes it, the `checks` of the page's block (the bytes of the page read at admission, whose digest the record holds; the page is not read again) are evaluated in process by the code of `ap accept`, except the kinds `clean` and `write_set`, which the step's own conditions and the step `write_set` hold; the lines of `ap accept` (`accept: ok`, or `accept: FAILED: <kind>: <what>` per failed check) go to `<out>.accept.log`. | `write_set` | `git fetch origin main` in `clone`, in a fresh call too; the fetched `origin/main` must be an ancestor of the head (the rulesets require an up-to-date branch, so the merge would fail after the verifier was paid) and becomes `base`; the changed paths of `git diff <base> <head>` (`git --no-replace-objects` with `diff --no-renames --ignore-submodules=none --no-relative --name-only -z`, paths read NUL-separated) against the page's write set | `fetch_failed`, `git_failed`, `behind_main` (`detail`: the commit of `origin/main`), `path_outside_write_set` (at most ten paths and the count in `detail`) |
| `verifier` | ONE `ap run` stage, role `reviewer`, cwd `worktree`, `expect.first_line` `Verdict: *`, prompt `<out>.verifier.prompt.md`: the Lead's prompt file unchanged followed by a block of facts (repository, pull request, head, the diff command, the paths of the gate's answer and of the acceptance output, and with `judge_threads` each thread given to it: id, path and line; with none the block is the same as without the member); answer `<out>.verifier.md`. Come-back with `verdict`: skipped, that file is the report and `stages.verifier` names the record beside it. For either path, the first line is exactly `Verdict: accept` or `Verdict: repair`; the second line must contain exactly one run of 40 hexadecimal characters, outside any longer run of letters or digits, equal to the head. Labels and punctuation around it are ignored. A report with anything before its verdict line ends the stage `no_result` (`unmet: first_line`); the caller resumes the session with the required form | `digest_differs`, `worktree_dirty`, `head_differs`, `git_failed`, `stage_refused`, a state not `ok`, `stage_record_unwritten`, `verdict_repair`, `verdict_unreadable`, `verdict_head_differs` (the second line has no such run, has two or more, or its one run differs from the head); with `judge_threads`, after the head rule of an accept, `threads_unjudged` and `thread_blocking` ("The threads") |
| `review` | when the store holds a closed (not revoked: `status` is `closed`) review of kind `packet` with verdict `accept` for this task, repository and head whose report digest is the report's, that review is used: its id goes into the record, `detail` `{"reused": true}`, and no second one starts. Otherwise `ap review start` (kind `packet`, the head, `base`, the pull request; `model`, `effort` and `prompt` of the verifier's `ap run` record) and `ap review close` with the report and that record's `account` and `session` (`detail` `{"reused": false}`) | `verdict_unreadable` (the record of the verifier cannot be read), the codes of `ap review` (`review_head_differs`, `store_refused`, …) |
| `status` | the pull request is read open against `main` at the head; with `judge_threads` the threads of the record are resolved ("The threads"); then `lead-review=success` on the head through the code of `ap review` | `github_unreadable`, `head_differs`, `thread_changed`, `thread_not_resolved`, `status_failed` |
| `merge` | with `item`, first the item is read again; then `gh pr merge --merge --match-head-commit <head>`, then a read of the pull request, also after a call that failed: `merged` only when it says merged at the head and names the merge commit | `item_dropped`, `item_done` (the item was dropped or closed since the call began: nothing is merged; a failed read stops with its code, e.g. `store_answer_unreadable`), `merge_failed` (the call failed), `merge_unconfirmed` (the call succeeded) |
| `cleanup` | in `clone`: `git fetch origin main`, `git worktree remove` without force, then, only after the removal, `git branch -d` (the branch tracks `origin/main`, which now holds the merge). The remote branch is not touched: the repositories delete the branch of a merged pull request themselves | none: a failure is recorded in the step (`result: failed`, `detail` `{fetch, worktree: removed|failed, branch: deleted|failed|kept}`) and the state stays `merged` |

The round (`repair`). When the step `verifier` ends with `verdict_repair` and the report's second line names the head by the rule of the `verifier` row (and only then: a `Verdict: repair` without that line ends with `verdict_repair` and no round, and every other end, `verdict_unreadable` and `verdict_head_differs` included, ends the call as above), the record is completed as above (`state: stopped`, `stopped_at: verifier`, `cause: verdict_repair`) with `repair.fixer` (`<out>.fixer.md.run.json`) and `repair.next` (`<out>-2.unit.json`) in the same save, before anything else starts; when that save fails the call ends with exit 5 as any call whose record cannot be written, and no fixer starts. Then ONE `ap run` stage, role `fixer`, resumes the session of this call's implementer record with that record's runtime, model and effort, on the accounts of the `implementer` block (its `account` and `next_accounts`, so a fixer cut by a usage limit goes on as a new session on the next, as "One stage" says); of the `implementer` block it keeps every other member except `resume` (so a stage on the Codex CLI states its own `permission_mode` or is refused); cwd `worktree`, `timeout_seconds` of `repair`; its prompt `<out>.fixer.prompt.md` is `repair.prompt` unchanged followed by a block of facts (repository, pull request, the head the verifier judged, the path of the verifier's report, the path of the page); its answer `<out>.fixer.md`. `repair.state` is the stage's state. Not `ok`: the call prints the first record and exits 3. `ok`: when the worktree's `HEAD` is not the judged head (the fixer committed), the call reads the pull request every 5 seconds through the code of `ap review` until GitHub reports that `HEAD` as its head, for at most 120 seconds (a come-back that begins right after a push would read the old head first and end `head_moved`); then it goes on as the come-back a Lead would start, through the code of a come-back call as it is: the same request with `pull_request` (this unit's), `out` `<out>-2`, `verifier.prompt` `repair.verifier_prompt`, `verifier.resume` naming this call's verifier record, the same `merge` and `judge_threads` and no `repair`; it writes `<out>-2.unit.json` and its files, and the process prints THAT record and exits with ITS code. So a second `Verdict: repair` stops the come-back (no second round), and a verdict that names the old head after the fixer pushed ends it `verdict_head_differs`. Where the round ends before the come-back for another reason, the first record says why in `repair.cause` and `repair.detail` and the call exits 3: `digest_differs` (`{"path"}`: a file of `repair` changed), `head_not_seen` (`{"head"}`: the bound passed before GitHub reported the worktree's head), `git_failed`, `stage_refused` (`{"code","field"}` of `ap run`), `stage_record_unwritten`, `io_error`, `come_back_refused` (`{"code","field"}`: the come-back's request was refused, e.g. `worktree_missing`).

The threads (`judge_threads: true`). At the step `gate` a thread is *given to the verifier* when it is unresolved, has exactly one comment (`comments` of the gate's answer), and that comment's author is the login the gate's answer names in `autoreview.login` (compared as the gate compares it, so with `autoreview` absent or `false` none is); with `verdict`, only when the report also holds exactly one line for its id whose word is not `blocking`. A given thread does not stop the step; every other unresolved thread stops it with `unresolved_threads` as without the member, and `unresolved_findings` stops as before, except in one case: the marker says `has_unresolved_findings: true`, `threads_on_head` is 0 and at least one thread is given (in a call with `verifier` and in a call with `verdict` alike). The marker stays true while an earlier thread of the reviewer is open, so there the given threads are the finding it names and the step does not stop with `unresolved_findings`; they go on as below (named in the record and in the verifier's facts, judged, resolved inside the step `status`). `unresolved_findings` still stops when no thread is given, when `threads_on_head` is `null`, and in a call without the member or with `false`; an unresolved thread that is not given stops with `unresolved_threads` also beside given threads and a true marker (the marker's stop is judged first, so with a true marker, `threads_on_head` 0 and no thread given, the cause is `unresolved_findings`). What the runner then does not see: a finding of the reviewer that is neither a thread on the head nor an open earlier thread. The record gets `threads`: one entry per given thread, `id`, `path`, `line` (an empty list when none is given). After the head rule of a `Verdict: accept` (of the stage, or of `verdict`), the report holds for each given id exactly one line that is exactly `Thread <id>: <word>`, the word `fixed`, `wrong`, `note` or `blocking`: an id with no such line, with more than one or with another word stops the call at `verifier` with `threads_unjudged`; else a `blocking` word stops it with `thread_blocking` (the detail of each: `{"threads": [<ids>]}`); else each entry gets `word`. A `Verdict: repair` is read as without the member, its thread lines not inspected; no cause of the threads starts a round. The come-back of a round keeps the member: its gate reads the threads anew on the new head, and the old threads and new ones are judged by its verifier. Inside the step `status`, after the pull request was read open at the head and before the status is posted, each id of `threads` is read again (`gh api graphql`, the thread's `isResolved` and its number of comments): one that is resolved already or no longer has exactly one comment stops the call with `thread_changed`, and nothing is resolved; else each is resolved (`resolveReviewThread`) and read back: one that does not read resolved stops it with `thread_not_resolved`, and no status is posted; the others get `resolved: true`. A call that does not reach the step `status` (also one with `merge: false`) resolves nothing. The command writes no comment and no reply, resolves no thread it did not record and never unresolves one.

The status is posted only after all of: the gate ended `passed` with no unresolved finding (a marker that says true for the head counts as one unless the reviewer's threads on the head are visible, and then only an unresolved thread stops; with `judge_threads`, nor when `threads_on_head` is 0 and a thread is given to the verifier) and no unresolved thread; the acceptance executable exited 0, or, without `acceptance`, the block's checks hold; every changed path is inside the write set and the branch contains the fetched `main`; with `judge_threads` every given thread judged by the report and none `blocking`, and each resolved; one `review` object is closed with `Verdict: accept` for the head, by a report of a model (the answer of the verifier stage of this call, or a `verdict` admitted as above) whose first line is exactly `Verdict: accept` and whose second line meets the head rule in the `verifier` row. One accepted head has one review object. Acceptance and verifier start only while `worktree` is clean and its `HEAD` is the head the gate passed; the review, the status and the merge name exactly that head. No `--admin`, no auto-merge, no force anywhere. Condition of use: the repository's `main` has no merge queue and auto-merge is off (true of the three platform repositories), so `gh pr merge` merges at once or fails; the command does not detect a merge queue. The `review` object owns the verdict; the status is derived from it, as in "One review". The page's write set is checked here: stages of `ap run` leave no `worker_run`.

What judges a stage cannot be changed by it: the SHA-256 of `acceptance` (without it the block's checks, which the call holds as read from the page at admission), of the verifier's prompt, of `verdict`, of `page` and of both files of `repair` are in the record before the implementer starts; a file whose digest differs when it is used ends the call (`digest_differs`). The verifier's prompt holds neither the implementer's answer nor its path.

The record `<out>.unit.json` is created exclusively before any effect (the claim, as in `ap run`) and replaced after every step through a temporary name: `repository, clone, worktree, branch, task_key, base, page{path,sha256} (the digest of the bytes read at admission, the ones a block is read from), write_set (the page's block's, or its line's), acceptance{path,sha256}|null (null when the request has none), verifier_prompt{path,sha256}|null, verdict_file{path,sha256}|null, merge, pull_request, head, review` (the complete id), `merge_commit, stages{implementer, verifier}` (the paths of their `ap run` records, written before the stage starts, or null), `files{gate, acceptance_output, report}, mode` (`"unit"`), only with `judge_threads: true` and from the step `gate`: `threads` (above), only with `item`: `item{key, id, objective{name, id}}` and after the merge `closed` (and `code`), "The item" below, only with `repair`: `repair{prompt{path,sha256}, verifier_prompt{path,sha256}}`, and after a `Verdict: repair` also `fixer`, `next`, `state`, and `cause`, `detail` (above), `state` (`running`, `merged`, `accepted`, `stopped`; `passed` and `failed` exist only in a case call, and so does exit 4), `step` (the step begun, null at the end), `stopped_at, cause, detail, steps` (each step done, in order: `name`, `result` (`passed`, `skipped`, `stopped`, `failed`), `start`, `end`, `detail`), `start, end`. No prompt or answer text and no credential. A unit record without `mode` is a unit call: it was written before the member existed. A killed call leaves this file naming the step begun; the Lead goes on by hand from it, or calls again with `pull_request` (and `verdict`, or `verifier` with `resume`) and a new `out`. Inside the call that starts the review the file shows step `review` with `review` null; the id is on disk from the save after that call returns.

### A unit from its page

`ap unit <page>` composes the request and the unit's two prompts from the page and one file of its task directory, then runs the unit exactly as a request on stdin does. `<page>` is the one argument, an absolute path; standard input is not read. `ap unit --compose-only <page>` does the composition of points 2 to 5 below with the refusals of points 1 to 4, writes no file, prints ONE JSON object `{"request", "prompt", "verify_prompt"}` (the request as an object, the two prompts as strings) on stdout and exits 0, with no other effect: no worktree, store, network call or record, and the request's admission is not run. `ap unit` with no argument reads a request on stdin as before; any other form of arguments is `usage` (exit 2, field `args`). A call from a page takes no `pull_request`, `verdict` or `resume`: those stay a request on stdin.

1. The refusals of the composition come before any effect and write nothing, in the form of the other refusals (exit 2): `page_unreadable` (field `page`); `units_unreadable` (field `page`: `units.json` is missing, not a regular file or unreadable); `invalid_input` with the field `units` (the file is not ONE JSON object); `page_block_invalid` (a page without a block: reason `no_block`; a member `repository`, `branch`, `item`, `merge`, `implementer` or `verifier` absent from the block: reason `shape` with the member); `page_section_missing` and `page_section_twice` (the page does not hold exactly one line that is exactly `## Unit notes`, and exactly one that is exactly `## Verifier questions`; `detail` is the heading); `invalid_input` with the field `units.<member>` for each unknown, missing or malformed member of `units.json`, and `units.clones` for a repository the file's `clones` does not name. The order: page, its block and sections, `units.json`, its members in the order of point 2, the clone, the accounts, then the composed request goes to the admission of a request on stdin. The admission refuses by its own rules and fields (`page`, `out_exists`, `outside_work_root`, a stage's refusal as `implementer.<member>` and the rest); a page's directory outside the work root is `outside_work_root`.
2. `units.json`, in the directory of the page (the task directory), is ONE JSON object with exactly these members: `task_key` (as the request's); `clones` (an object: a repository `owner/name` to the absolute path of its local clone); `accounts` (an object: a key to an array of one or more absolute account paths, the first the stage's `account`, the rest its `next_accounts`, so one account gives no `next_accounts`; a key is a runtime name, `claude`, `codex`, `muse` or `agy`, or a runtime, `/` and a role (`implementer`, `verifier`) or a model as the block names it (up to 40 bytes of letters, digits and `._-[]`, as `ap run` takes a model), such as `claude/verifier`, `claude/opus` or `claude/opus[1m]`; `<runtime>/fixer` is refused, the fixer having the implementer's accounts, and `<runtime>/reviewer` too, the verifier's key being `<runtime>/verifier`; a key that names neither a stage's role nor its model is not read, so a misspelled role falls to the model or runtime key; `codex` and `muse` keys exactly one account, as `ap run` takes them; to keep a model off an account, give the runtime key the safe list and name the models that may use the others, as in `{"claude": ["/root/.claude"], "claude/sonnet": ["/root/.claude-b", "/root/.claude"], "claude/verifier": ["/root/.claude"]}`, so a model no key names, `claude-opus-5-5` or `opus[1m]` as much as `opus`, takes the runtime's list); `timeouts` (an object `implementer`, `verifier`, `fixer`, each seconds from 1 to 86400); `compact_window` (an object: a model name to its window, an integer, read for a Claude stage only); `prompts` (an object `implementer`, `verifier`, `fix`, `second_look`, each the absolute path of a standing text); `judge_threads` (a boolean). A stage for which none of the three keys of point 4 is present is `units.accounts`.
3. The page's block, beside its members ("The page's block"): `implementer` and `verifier`, each `{"model", "effort"}` with optional `runtime` (default `claude`), `permission_mode` (passed to the request as it is; the composition adds none, so a Codex or Muse block without it is refused by the admission, which keeps "only when the request says so") and `timeout_seconds` (replaces the `timeouts` value of that stage). The page holds exactly one section `## Unit notes` and exactly one section `## Verifier questions`: a section is every line after its heading line, with its line ends as the page has them, up to the next line that begins `## ` or the opening line of the block, or the end of the page.
4. The composed request: `repository`, `branch`, `item` and `merge` from the block; `clone` from `clones` by the repository; `task_key` and `judge_threads` from `units.json` (a page sets no `gate`, so a composed unit waits for no automatic reviewer and gives no thread to its verifier); `page` the argument; `out` `<task directory>/runs/U-<unit>`; `worktree` `<task directory>/wt/<repository name>-<unit in lower case>`; `implementer` and `verifier` each with `model`, `effort` and `runtime` of the block, `permission_mode` of the block when it states one and absent otherwise, `account` and `next_accounts` from `accounts` by the first key present of `<runtime>/<role>`, `<runtime>/<model>` and `<runtime>` (so the role decides before the model, and both before the runtime; the fixer of a repair runs on the implementer's; `next_accounts` absent for one account), `timeout_seconds` of the block or else of `timeouts`, `compact_window` of `units.json` by the model for a Claude block (absent for another runtime and for a model it does not name) and `prompt` the composed file of point 5; `repair` with `prompt` the `fix` text, `verifier_prompt` the `second_look` text and `timeout_seconds` the `fixer` timeout. `runs/` and `wt/` are not made: the claim `<out>.unit.json` fails with `out_unwritable` when `runs/` does not exist. There is no `gate`, `store`, `acceptance` or `acceptance_seconds`: the page's block judges, as for a request without them.
5. The composed prompts. `<out>.prompt.md` is the standing `implementer` text (its last line ended by a line feed when it lacks one), one empty line, then the section `## Unit notes` without its heading, byte for byte; `<out>.verify.prompt.md` the same with the `verifier` text and `## Verifier questions`. In a standing text, and only there, `{page}`, `{unit}` and `{repository}` are replaced, in one pass, by the page's path, the block's `unit` and the block's `repository`; any other text in braces stays, and so does a placeholder inside a section. A standing text that cannot be read or is not UTF-8 is `prompt_unreadable` (field `units.prompts.<name>`). The composed request is written, as the JSON of the printed request, to `<out>.request.json`. The order of reads and writes: the page is read once, and the digest of those bytes is the record's `page`; the admission and the record's `verifier_prompt` take the composed prompts from memory, not from disk; the three paths join the `out_exists` scan, so an existing one refuses before any store write; after the claim `<out>.unit.json` the three files are the first thing created, each exclusively, and a failure ends the call at once `stopped` (`stopped_at` and the step `composed`, cause `io_error`, exit 3, as a file of a step). The record gets `composed`: `{request, prompt, verify_prompt}`, each `{path, sha256}`, the digests equal to the files' bytes; the record of the round's come-back `<out>-2.unit.json` gets `composed` with `request` alone, the first call's. A call from stdin writes no `composed`, and the record of a call from a page equals that of the same request on stdin in every other member.

## One case

`ap unit < request.json` with the member `case` is a case call: it runs a past unit again, in a copy that holds only that unit's base, and judges it by the tests the unit was accepted with. One record says whether a stage of the named model made those tests pass; with no stage the call shows whether the case is valid. It is one pass, like a unit call: at most one stage, no fixer, no step repeated. It starts no `gh` and no `ont`, makes no network call and writes nothing outside `worktree` and the files of `out`; what the stage and the commands of the case do is theirs.

The case file (`evals/engineering/cases/<id>.json`, see `evals/README.md`), JSON with exactly these members: `id` (`^[a-z0-9][a-z0-9-]{0,63}$`; the file is `<id>.json`), `repository` (`owner/name`), `pull_request` (the merged pull request the case was taken from), `base` and `head` (40 hex digits: the first parent of the merge commit, and the accepted head), `tests` (a nonempty array of relative repository paths without `..`: every file that judges; the candidate gets them with their bytes at `head` and the evaluator restores them), `commands` (a nonempty array of argument arrays: what the evaluator runs in the copy, in order), `page_sha256` (64 hex digits: the page given to the candidate; its text is a host file and never enters this repository).

The request, exactly: `case` (the absolute path of the case file), `clone` (a local clone that holds `base` and `head`), `worktree` (the path of the case's copy; it must not exist), `page`, `out`, `acceptance` (the evaluator, `evals/engineering/evaluate`), optional `implementer` (the members of a stage of a unit call without `resume`, `runtime` included), optional `at` (`"base"`, the default, or `"head"`), optional `acceptance_seconds` (1 to 86400, default 2700). `at: "head"` together with `implementer` is refused (`invalid_input`, `at`): no stage ever works in a copy that holds the head. Every other member of a unit call (`repository`, `branch`, `task_key`, `verifier`, `verdict`, `gate`, `store`, `merge`, `pull_request`) is refused with `invalid_input` and its name.

Refusals (exit 2, before any effect, in the form of a unit call): those of a unit call that apply (`invalid_input`, `outside_work_root` for `page` and `out`, `inside_worktree` for `acceptance`, `page_unreadable`, `prompt_unreadable` (also a prompt that leaves no room for the block of facts), `acceptance_unreadable`, `out_exists`, `out_unwritable`, `worktree_exists`, and the stage's own, judged by `ap run`'s code with the prefix `implementer.`), and `case_unreadable` (`case` is not a regular file, not JSON, or a member is missing, unknown or malformed); `case_page_differs` (the SHA-256 of `page` is not `page_sha256`); `case_commit_missing` (`base` or `head` is not a commit of `clone`, or a path of `tests` is not a regular file at `head`: Git mode `100644` or `100755`, so a symbolic link, whose target would be the candidate's to change, is no judging file; `field` is `case.base`, `case.head` or `case.tests`). A case call's page needs no line `Write set:`.

The steps, each recorded before it begins and after it ends; no other step is in a case record:

| Step | What it does | How it ends |
| --- | --- | --- |
| `worktree` | creates `worktree` as a new Git repository with ONE commit and no remote: at `base` the tree of `base` with every path of `tests` holding its bytes (and mode) at `head`; at `head` the tree of `head`. Only the objects of that tree are copied out of `clone` (`pack-objects` into `unpack-objects`): the copy shares no object store with `clone` and names it nowhere, so no commit of `clone` can be reached from inside the copy. The commit is made with an identity given on the command line (`-c user.name=… -c user.email=…`), so it needs none from the host. Every `git` of this step runs with `GIT_NO_REPLACE_OBJECTS=1`: a `refs/replace/` entry of `clone` changes neither the tree nor a judging file of the copy | stops with `copy_failed` |
| `implementer` | only with `implementer`: ONE `ap run` stage, role `implementer`, cwd the copy; its prompt is `<out>.implementer.prompt.md`: the request's prompt file unchanged, followed by a block of facts (the page's path, the copy's path, the paths of `tests`, each array of `commands` as JSON on a line of its own, and that the copy has no remote); answer `<out>.implementer.md` | the stage's state `ok`: the step passed. `timeout`: the call ends `failed` (`detail` `{"stage": "timeout"}`), `acceptance` does not run, `cleanup` does. Any other state (`cut`, `no_result`, `failed`), `stage_refused`, or `stage_record_unwritten` (as in a unit call): the call stops with it as the cause |
| `acceptance` | first `worktree` must still be a directory and not a link (a process of the candidate may have put a link there, which would send the evaluator to another place); else the call stops with `copy_replaced`, starts no evaluator, removes nothing and leaves the path for a reader. Then the digest of `acceptance` is compared as in a unit call, and so is the digest of the case file with `case.sha256` (it names the judging files and the commands, so the stage cannot change it); then `acceptance <case> <clone>` runs in the copy, stdin `/dev/null`, under `timeout -k 10 <acceptance_seconds>`, with the environment of the `ap unit` call (so the caller's `CARGO_TARGET_DIR` and `HOST_CARGO_LOCK` reach it); output to `<out>.accept.log`. No condition on the copy's state: the candidate may have committed or not | exit 0: the call ends `passed`. Exit 1, or the bound reached (exit 124): the call ends `failed` (`detail` `{"exit": 1}` or `{"exit": 124}`). Any other exit: the call stops with `acceptance_failed` (the evaluator could not judge). The suite's evaluator ends on the first signal, so the bound reached is exit 124; an evaluator that had to be killed (exit 137: it ignored the signal, or the host killed it) is another exit and a no-result row, because a kill is no statement about the candidate. `digest_differs` (of `acceptance` or of the case file) stops the call before the run |
| `cleanup` | after the result is `passed` or `failed`: first the same check of `worktree` (a link ends the call `stopped` at this step with `copy_replaced`, with no diff written and nothing removed); then writes `<out>.candidate.diff`, the difference between the copy's one commit and its final files (new files included, ignored files not, binary as Git's binary patch), then removes the copy. After a stop the copy stays for the Lead to read | a failure is recorded in the step (`result: failed`, `detail` `{diff, copy: removed\|failed}`) and changes no result |

The ends: exit 0 with `state: passed`; exit 4 with `state: failed`; exit 3 with `state: stopped` (`stopped_at`, `cause`, `detail`); 2 a refusal and 5 a record that could not be written, as in a unit call. A unit call never exits 4.

The record `<out>.unit.json` is claimed and replaced as in a unit call, with the same members; those that have no meaning in a case call are null: `branch`, `task_key`, `write_set`, `verifier_prompt`, `verdict_file`, `merge`, `pull_request`, `head`, `review`, `merge_commit`, `stages.verifier`, `files.gate`. `repository` and `base` are the case's, `files.report` is the stage's answer (null without a stage), and `detail` is the failed step's detail at `failed` too. It adds `mode` (`"case"`), `case` (`{path, sha256, id}`), `at`, `prompt` (`{path, sha256}` of the request's prompt file, null without a stage: the digest of the stage's own prompt is of a file that holds the copy's path and differs in every call), `stage_seconds` (the stage's bound in effect, its `timeout_seconds` or `ap run`'s default; null without a stage: it defines what `failed` by timeout means) and `files.candidate_diff`. A killed case call leaves the record naming the step begun.

What a case record means, for the read-out (`evals/readout.py`) and any other reader. One record is one row of the suite: the case (`case.id`, its digest `case.sha256`), the target (the model and effort in the record of `stages.implementer`, whose usage is the row's cost), the prompt's digest (`prompt.sha256`), the result. The reader reads `mode` first and then `state` alone, never a step's result: `passed` is a pass, `failed` is a fail, `stopped` is no result. A no-result row is run again once; a second stop stays in the reading as no result; the usage of a no-result row counts in the reading's cost. A record without a stage is a validity row: a case is valid when its row at `base` ends `failed` and its row at `head` ends `passed`; a case with another pair counts in no reading. A suite value measures implementing to given tests, the easier half of the same work (the other half is writing the tests from the page): the read-out prints that beside it. A reading runs alone on the host: a build that waits on the build lock spends the stage's bound.

## The board

`ap backlog <task key> [--text] [--store <path>]` prints the board of a task of the store and writes nothing: no store write, no file. It reads the task's board, items, objectives and decisions (searches by `task`), and an element of the order that is no item of the task with `ont get`. `--store` is forwarded to every `ont` call. A malformed argument is refused with `{"error":{"code":"usage","field":"args","detail":null}}` on stderr and exit 2; a failed read with its code (`store_answer_unreadable`, `process_failed`) in the same form.

The answer is one JSON object on stdout:

- `board`: `set_at` and `reason` of the board, or null when the task has none.
- `objectives`: the task's objectives by `rank`, each `name`, `rank`, `status`, `statement` and `last_check` (`exit`, `line`, `at`, or null when none was recorded).
- `order`: the items of the task the order names, in its sequence, each `key`, `title`, `state`, `objective` (its name), `repository` and `branch` when `in_work`, and `refusal`: the code a unit call for the item would be refused with before any effect, computed by the function of `ap unit` ("The item" in "One unit") without the write of `start_item`, or null. A queued item of the order has null (its start is the store's to refuse); an item in work has `item_of_another_unit`, because no new unit may start it (its own unit goes on).
- `bad`: the elements of the order that are of another task, `done`, `dropped` or missing (`id`, `key` for an item of the task, `problem`: `another_task`, `done`, `dropped`, `missing`). A done or dropped item is also in `order`.
- `unplaced`: the queued items the order does not name (`key`, `title`, `added_at`), oldest first.
- `in_work_unlisted`: the items in work the order does not name (`key`, `title`, `repository`, `branch`).
- `untriaged`: `count` and `topics` (at most 10, oldest first) of the task's `current` rows decided by the user that have no `triage`.

A task without a board prints `board: null` with `objectives`, `unplaced` (every queued item) and `untriaged`. `--text` prints the same as plain lines for a reader: the board, one line per objective, one per item of the order (with its refusal), one per bad element, unplaced item and item in work that is not ordered, and one for the untriaged rows; at most 80 lines (the 80th says how many more the JSON form holds); a line break inside a value is printed as a space.

## One row

`ap row [--store <path>] < row.json` records one row of the user or of the Lead as a `decision` of a task and, for a row of the user, triages it, in one call. `--store` is forwarded to every `ont` call; any other argument is refused with `{"error":{"code":"usage","field":"args","detail":null,"after":null}}` on stderr and exit 2. It uses the store's actions `record_decision` and `triage_decision` with the client `lead`, and no other action; it writes no file.

The request is one JSON object (at most 1 MiB); a member that is not named here, a missing one and one of the wrong kind is refused with `invalid_input` and its field:

- `task`: the task key, made into the store's task as `ap backlog` makes it; `request_id`: a string (the two actions use `<request_id>-record` and `<request_id>-triage`, so at most 57 bytes of ASCII letters, digits, `.`, `_` and `-`); `agent` and `session`, passed to both actions; `topic`; `text`, the reading (at most 1000 bytes); `by`: `user` or `lead`. Each is a non-empty string. The store's own rules for `task`, `topic`, `request_id`, `agent`, `session` and `form` are not repeated: `ont action validate` of the record refuses a breach, with the store's code, before anything is applied.
- `by: "user"`: exactly one of `words` (the user's words), `words_file` (an absolute path of a regular UTF-8 file whose whole text is the words) and `words_from` (`record`: the absolute path of a Claude Code session record; `at`: a UTC time to the second, `YYYY-MM-DDTHH:MM:SS`); `form`, `decision` (the default) or `question`; `triage`: `word` (`item`, `intent`, `not_adopted` or `none`), `item` (an item key of the task: with the word `item` and with no other), `objective` (an objective name of the task: with `intent` and with no other), `reason` (at most 600 bytes; required for `not_adopted` and `none`). A `triage` member that breaks this is `invalid_input` with the field `triage` (`triage.word`, `triage.reason` or `triage.<member>` for a member of its own).
- `by: "lead"`: `reason` (at most 600 bytes) and `undo` (at most 300 bytes); no words and no triage.

The words from a session record are the string of exactly one line whose `timestamp` begins with `at` and that is a line of `type` `user` with a `message.content` that is a string, or of `type` `queue-operation` with `operation` `enqueue` and a string `content` (a message sent while a turn ran); no such line is `words_not_found`, more than one `words_ambiguous`, both with the count as `detail`. The words are that string byte for byte. They are never cut, trimmed or changed: words above 1000 bytes are refused `words_too_long` with `{"bytes","limit"}` as `detail`, and the Lead then gives `words` itself; `text`, `reason`, `undo` and `triage.reason` likewise against their limits (`text_too_long`, `reason_too_long`, `undo_too_long`; `detail` as above). An item key or objective name the task does not have is `item_unknown` or `objective_unknown`. Every one of these refusals is made before any call that changes the store.

The order: `ont action validate` of the record; its `apply`; then the current row of the task with that `topic` is read back (a search of the task's decisions) and its words (`user_words`; for a row of the Lead `text`) compared byte for byte with the request's (`readback_differs` when they differ); then, for a row of the user, the triage validated and applied on that row. `validate` does not see the store's record of applied requests, so a repeated call meets `decision_already_current` (record) or `already_triaged` (triage) there: these two alone do not stop the call, and `apply` answers a repeated `request_id` with `already_applied`. A call cut after the record and run again triages the row and records nothing twice; a call repeated whole answers `already_applied` twice and writes nothing.

The answer is one JSON line on stdout, exit 0: `topic`, `decision` (the row's id), `record` (`applied` or `already_applied`), `triage` (the word, or null for a row of the Lead) and `words_bytes` (the byte count of the compared words). A refusal is `{"error":{"code","field","detail","after"}}` on stderr with exit 2: `after` is null before any change, and `record` when the record was applied and the triage was not (also for a failed read-back); a refusal of the store keeps the store's first code (`user_question_is_not_a_decision`, `decision_already_current`, `not_a_user_row`, ...) in `code` and the action (`record` or `triage`) in `field`; a failed `ont` call is `process_failed` or `store_answer_unreadable`.

## The task's state

`ap state <task directory> [--text]` prints what the records of a task's directory and Git say of its unit calls and stages, so that a Lead types none of it into `STATE.md`. It reads the directory's `runs/` (the files directly in it: `*.unit.json`, `*.run.json`, `*.stream.jsonl`) with the file system, Git with `--no-optional-locks -c core.fsmonitor=false` (`rev-parse HEAD`, `status --porcelain`: no index lock, no refresh of the index, no hook named by the repository's configuration), `systemctl is-active` and `ps` through the host's `System`; it writes nothing (no file, no store call, no network, no `gh`). A malformed argument (no directory, another word or option, `--text` twice) or a directory without `runs/` is refused with `{"error":{"code":"usage","field":"args","detail":null}}` on stderr and exit 2. A record that does not parse as one JSON object is listed in `unreadable` and the rest is printed, exit 0. It reads no session record and no prompt or answer text, and changes no record's member.

The answer is one JSON object on stdout:

- `at`: the time of the read (UTC, RFC 3339).
- `task`: `dir` (the resolved directory), `head` (`git rev-parse HEAD` there, null when Git says nothing) and `uncommitted` (the number of lines `git status --porcelain` prints; null when that call fails, as without Git).
- `units`: the calls of `ap unit`, the records `runs/*.unit.json`, in chains: the records with the same `repository` and the same non-null `pull_request` are one chain, a call whose `pull_request` is null is a chain of its own. A chain has `item` (the `item.key` of its first call that has one, else null), `repository`, `pull_request` and `calls` in order of `start`, each `record` (the path relative to the directory), `state`, `stopped_at`, `cause`, `head`, `merge_commit`, `start`, `end` (null where the record lacks the member) and `stale`. Chains are newest first by their last call's `start`.
- `stages`: every record `runs/*.run.json` whose `end` is null, and the newest 20 by `start` of those that belong to no unit call, newest first. A stage record belongs to a call when its path begins with the call's record path less `.unit.json`, followed by `.` (`runs/U-1.unit.json` owns `runs/U-1.implementer.md.run.json`, not `runs/U-1-2.fixer.md.run.json`). Each has `record`, `role`, `runtime`, `model`, `account`, `state`, `start`, `end`, `stale` and, where the record has it, `served_by`.
- `stale`: for a stage record whose `end` is null, read from `systemctl is-active` of its systemd unit (the record's `unit`): the answer is the word on stdout and the exit is not read. `active`, `activating`, `deactivating`, `reloading` or `refreshing` gives false; any other word, including `inactive` of a unit that does not exist (exit 4), gives true; no word (the call failed, timed out or printed nothing) gives null. A record whose `start` is less than 10 seconds before `at` prints null where true would be printed, because `ap run` writes the record before it starts the unit. For a unit call whose `state` is `running`: false when one of its stage records (the ownership above) is live (its `stale` is false), else true when no process of `ap unit` lives on the host (`ps`: a process whose program is named `ap` and whose first argument is `unit`), else null (some `ap unit` lives and nothing ties it to this record); a failed `ps` call, a non-zero exit or empty output gives null for a call that no live stage decides. Null for every record that does not say it runs. `stale: true` speaks only for this host's service manager and process table: a stage or call that runs under another host's manager is stale here.
- `streams_without_record`: the files `runs/*.stream.jsonl` that have no `.run.json` of the same stem (stages started by hand), each `path` and `modified` (the modification time, UTC).
- `limits`: per account named by a stage record (every readable `*.run.json`), the newest record by `end`, else `start`, whose `limit` is present and not null: `account`, `record` and that `limit`; a missing `limit` counts as null; an account with none is not listed.
- `unreadable`: the paths of the `*.unit.json` and `*.run.json` files that do not parse as one JSON object.

`--text` prints the same as plain lines, at most 60: first every stage record that runs (`end` null) and every unit call that is `running`, each with the word `stale` when it is, then the newest ten chains (item, pull request, last state, the merge commit or the head in its first 12 characters, end), then one line per account with a limit; when lines were cut, the last line says how many more the JSON form holds. A line break inside a value is printed as a space.

What it does not print: the installed revisions (`deploy/README.md`, "Read the state"), the store's holds, items and rows ("The board"), the host's disk and CPU.

## Delivery

`ap deliver < request.json`, called by a Lead or by the timer `ap-deliver.timer` (`deploy/README.md`), brings the pair `ap` and content of this repository to the fetched tip of `origin/main` when every merge on the way is accepted, records the attempt as an `install` object of the store, rolls the pair back by itself when the installers leave it at no single commit, and prints one JSON record on stdout. A Lead's rollback request undoes the newest install by the same command. It replaces the install by hand of `BUILD-AND-DELIVERY.md` section 5. Its only network call is the fetch; it calls no API of the hosting provider and needs no token.

The request, one JSON object on stdin, with these members: `repository` (`owner/name`, the name the reviews carry), `url` (where `git` fetches it from), `state` (an absolute directory, made when absent: the command's clone `<state>/<name>`, its build directory `<state>/target`, its last record `<state>/last.json`), `build_lock` (the absolute path of the host's build lock, the file `scripts/install-ap.sh` locks around its build), optional `build_wait_seconds` (an integer from 0 to 900, absent means 0), and one of three forms, told apart by the other members:
- a Lead's install: `by` (who calls: a session id, 1 to 200 bytes), `reason` (1 to 400 bytes) and optional `past` (an array of at most 50 commits of 40 hex);
- a Lead's rollback: `by`, `reason` and `rollback: true`, no `past`;
- the timer's: none of `by`, `reason`, `past`, `rollback`. Its `by` in the record and in the attempt is `timer:` followed by the value of the environment variable `INVOCATION_ID` (systemd sets it for each run of a unit), or `timer` when that is unset or empty.

An unknown, missing or malformed member, or any other combination of the four, refuses `invalid_input` before anything is made (`detail.field`: a malformed or false `rollback` names `rollback`; else the first missing member of `by`, `reason`; `past` beside `rollback` names `past`). The name of the clone may not be `.`, `..`, `target` or `last.json`.

The target is the `installed_artifact` whose key is `/usr/local/bin/ap`, always. The pair is the file `ap` in the directory `AP_INSTALL_DIR` names and the content tree `AP_CONTENT_DST` names; the command reads these two, `AP_BACKUP_DIR` and `AP_CONTENT_BACKUP_DIR` from its environment with the installers' own defaults and passes its environment on to the installers. The pair is at commit C when `ap --version` of that file names C and every line of `content/SHA256SUMS` of C (read from the clone) matches the file of the tree (what `sha256sum -c` checks). A tree can pass the manifests of several commits at once (most merges change no file of `content/`): every read asks whether the pair is at one named commit, first T, then I, and never gives the tree a commit of its own; "the tree is not at I" means that it does not pass I's manifest. The lock is the file `AP_DELIVER_LOCK` names (default `/run/lock/ap-deliver.lock`), one per host whatever `state` a request names; its descriptor is inherited by every installer, so the lock stays held while an installer lives after the command alone was killed, and a free lock means that nothing of a call runs. The installers take no deliver lock: a Lead stops the timer before calling one by hand.

The handles of an attempt, the copies a rollback of it restores. The file handle is the kept copy `<AP_BACKUP_DIR>/ap.before-<first 7 hex of the attempt's from_sha256>`; it counts only when the file's whole digest equals `from_sha256`. The content handle is a tarball `agents-before-<UTC stamp>-<pid>.tar` of the directory `AP_CONTENT_BACKUP_DIR` names that HOLDS THE TREE OF `from` and that the content installer takes back. Holding the tree: every line of `content/SHA256SUMS` at `from` names a regular file of the archive with that digest, the check the tree is read with; the archive is read in memory and never extracted, and one that cannot be read to its end does not pass. Taking back: `scripts/install-content.sh rollback-check <tarball>`, of the clone's script that a rollback would call, exits 0. That verb runs every check of `rollback` that does not read the target (the files `<tarball>.sha256` and `<tarball>.paths`, the checksum, the member names, the entries of `.paths`), writes nothing, and exits 2 with the refusal line `rollback` prints; `rollback` runs the same lines, so the rule has one home, the script. A script that does not know the verb answers exit 2: the tarball is no handle. Only a tarball whose members pass is asked. Where the content installer printed a tarball in this call (on stdout after `backup=` at success, on stderr after `kept copy` at its exit 1), that one is the handle when it passes. Where none was printed (a dead call, a repair, a close after an `unrecorded` end, a second install of one attempt), it is the OLDEST tarball stamped not older than the attempt's `started_at` (to the second) that passes. Which call made a tarball, and in which second, decides nothing: a tarball that holds the tree of `from` restores the tree of `from` whoever made it, and a tarball of another tree, or of a half-swapped tree that a repair or a killed install kept, does not pass. A tarball that does not pass either check is never recorded as a handle and never given to `install-content.sh rollback`: one function answers the content handle of an attempt, and every close, the repair and the rollback request that reads a recorded handle use it. Every close of an attempt whose installers ran records both handles (`rollback_binary`, `rollback_content`), each when there is one. The command reads `content/SHA256SUMS` of a commit from the clone once per call.

The store: both install actions are applied with the client `ap-deliver` and the agent `ap-deliver`, whoever calls. The request id of an attempt is `ap.<commit>.<attempt>`, of a rollback attempt `ap.<commit>.rb<attempt>`; its close is that id followed by `.close`. Every search names only properties every object of its type has: a review by `kind`, `head`, `status` (`ap unit` adds its task), an attempt by `target`, `status`, `commit`, `kind`; `verdict`, `repository`, an attempt's `outcome` and a report's digest are compared on the objects of the answer, which must be qualified. On the engine of `ontology/ENGINE-PIN` a filter on an optional property answers `qualified: false` as soon as one scanned object lacks it, while `unresolved_excluded` stays 0 (`ontology/README.md`, "Version 8").

The order of a call, each step once:

1. The lock, taken without waiting and held to the end, including while this call waits for the build lock in step 7. Held by another (or not openable): `busy`; another call waiting for the build lock is busy too.
2. The running attempt of the target (`target` and `status: running`). Because the lock is free it belongs to a dead call. The pair is read against it, from the clone as it stands: at its `from` it is closed `not_started` with the code `dead_call`; at its `commit` it is closed `installed` with its handles. A running attempt of kind `forward` at neither is repaired: when the clone's `origin/main` as it stands is the attempt's commit, the installers are called again, each only for the part that is not at the commit (the file by `install-ap.sh install <commit>`, then, when that was not needed or exited 0, the tree by `install-content.sh install <commit>`); the pair is read; at the commit the attempt is closed `installed`. When the pair is still not at the commit, or `origin/main` is not the attempt's commit (no installer is called then), the command's rollback of step 10 runs with the attempt's handles; the pair is read; at `from` the attempt is closed `failed_restored`, else `failed`. After a close with `failed` the call ends there: `end: failed`, exit 4, the record names the attempt (`install`, `attempt`, `from`, `outcome`, `to`, `code`, the handles) and `closed`. After any other close the call goes on, and the record's `closed` names the attempt and its outcome; a repair's programs are rows of `installers`, and the index run of step 12 follows its close. `attempt_running` with the attempt's id remains for: a clone that cannot answer (another `state`, a lost clone: no `content/SHA256SUMS` of the attempt's commit or `from` to read and no scripts to call); a running attempt of kind `rollback` at neither of its commits (a dead rollback is not repaired: below, "What a Lead does"); a close by a read that the store did not apply. A repair whose close the store did not apply ends `unrecorded` (exit 5, or 4 when its outcome is `failed`); the next call reads the attempt again.
3. A rollback request goes to "A Lead's rollback" below. The clone `<state>/<name>` is made (`git init`) or reused, `main` of `url` is fetched into `refs/remotes/origin/main` (nothing else), and the clone is checked out detached at that tip T. A failure: `fetch_failed`.
4. The pair is read. At T: the end `current`. At a commit I that is not T, file and tree both: I is the `from` of the attempt. Anything else (file and tree at different commits, a tree at none): `pair_differs`.
5. `engine_differs`: `ontology/ENGINE-PIN` at T is not the commit `ont --version` names. `schema_differs`: the `version` of `ontology/work.schema.json` at T is not the version of the installed work schema (the store's answers name it).
6. Accepted. I must be on the first-parent chain of T. Every commit after I up to T, oldest first, unless `past` names it: it has two parents (`not_a_merge`); its tree is its second parent's tree (`tree_differs`); the store holds a review of kind `packet`, `status: closed`, `verdict: accept`, this `repository` and the second parent as `head` (`no_accepting_review`; a revoked review is not closed). For T alone, also: the report file of that review exists (`report_missing`) and has the digest the object names (`report_differs`). When a head has more than one accepting review the one closed last is used. The first that fails ends the call `not_accepted` (`detail`: `commit`, `why`: `not_on_chain`, `not_a_merge`, `tree_differs`, `no_accepting_review`, `report_missing`, `report_differs`). T is never exempt, also when `past` names it. A commit of `past` that is not one of the commits after I up to T: `past_not_on_chain`.
   The timer's limits, for the timer's request only, read from every attempt of the target (one search by `target`), newest first by `started_at` as the view `installs` orders them. Each refuses with `detail` `{"install"}`, the attempt it names; a Lead's request has none of them.
   - `suppressed` (exit 3): the newest attempt whose outcome is not `not_started` (a running one has none) ended `failed_restored` or `failed`. The unit stays failed until a Lead's install call ended `installed`; a later `not_started` attempt of anyone does not lift it.
   - `held_by_rollback` (exit 2): that attempt is of kind `rollback`. A Lead undid an install; the timer installs nothing until a Lead's install call ended `installed`.
   - `attempt_exists` (exit 2): an attempt of kind `forward` on T ended `installed`, `failed_restored` or `failed`. The timer installs a commit at most once.
   - `attempts_exhausted` (exit 3): three attempts of kind `forward` on T ended `not_started`.
   - After `failed` the pair is at no one commit, so the timer's next call ends at step 4 with `pair_differs` and never reaches these limits. For the timer's request only, `pair_differs` therefore exits 3 (the unit stays failed until a Lead repaired the pair: a pair at no one commit is never repaired by waiting), and its `detail` is `{"install"}` with the newest attempt of the target whose outcome is not `not_started`, or null when there is none. A Lead's request keeps exit 2 and `detail` null.
7. `disk_low`: under 10,240 MiB free where `<state>` lies (`df`). The build lock is probed with `flock -n`. When held, `build_wait_seconds: 0` refuses `build_busy` at once; a positive bound N waits up to N seconds with `flock -w`, then proceeds when the lock is free, or refuses `build_busy` if it remains held. The command releases the build lock at the end of this step, before the installers take it themselves. Only when starting to wait, it writes one JSON line on stderr: `{"at":"<UTC RFC 3339, to the second>","waiting":"build_lock","seconds":N}`. Stdout remains the call's one answer line. No new attempt exists yet, and the wait changes neither the pair nor the store; a call killed while waiting needs no repair by the next call.
8. `ont index --source installed_binaries`. The attempt is one more than the attempts of this target and T the store holds. `start_install` is applied with `kind: forward`, the target, `repository`, `commit` T, `attempt`, `from` I, `from_sha256` (the digest of the installed `ap` file, read now), `by`, `reason` (absent for the timer), `head` (the second parent of T), `review` (its accepting review), `reviews` (the accepting reviews of step 6, oldest first) and `past` (the request's commits joined by one space, absent when empty). Only the answer `applied` that names the created attempt goes on; `already_applied` or a refusal ends `store_refused`, a failure `store_unreadable`, and no installer is called. An answer `applied` that names no created object also ends `store_unreadable`: the store may hold a running attempt then, which the next call closes by the read of step 2 (at `from`: `not_started`).
9. The installers, from the clone, with the command's environment and its lock: `scripts/install-ap.sh install <T>` with `CARGO_TARGET_DIR=<state>/target`; when it exits 0, `scripts/install-content.sh install <T>`.
10. The pair is read again and decides the outcome, not an exit code. At T: `installed`. At I: `not_started` when the first installer ended with its code `install_busy`, else `failed_restored`. Anything else: the command rolls back with the installers' own verbs, `install-ap.sh rollback <the file handle>` when the file is not at I and the handle counts, and `install-content.sh rollback <the content handle>` when the tree is not at I and that installer printed a tarball that holds the tree of I (no printed path, no content rollback in this step), reads again, and the outcome is `failed_restored` at I, else `failed`.
11. `close_install` with the outcome, `to` (the commit the pair is at, or `neither`), `rollback_binary` and `rollback_content` (the file handle when it counts, the content handle when there is one) and `code` (the failing installer's). The read decides: an attempt closed `installed` can carry the code of an installer that failed (an installer that exited non-zero after the pair was at T). When the store cannot be written here the end is `unrecorded`: the attempt stays `running` and the record still says the outcome the read decided.
12. After every close of an attempt whose installers ran, also one the store did not apply (`unrecorded`): the index run of step 8 again; its failure is in the record's `index` and changes no outcome.

A Lead's rollback, after steps 1 and 2. The pair is read from the clone as it stands, with no fetch; it must be at one commit C (`pair_differs`). A is the newest attempt of the target of kind `forward` with outcome `installed` and `commit` C. `nothing_to_roll_back` (exit 2, `detail` null) when: there is no A; A's file handle does not count; A has no content handle (its recorded `rollback_content` is gone, or does not hold the tree of A's `from`: it is checked as above before it is used, and then counts as absent) while `content/SHA256SUMS` differs between A's `from` and C. Then the index run, and `start_install` with `kind: rollback`, `commit` A's `from`, `from` C, `from_sha256`, `rolls_back` A, `by`, `reason`, the attempt number counted over the rollback attempts of this target and commit, under the request id `ap.<commit>.rb<attempt>`; only `applied` goes on, as in step 8. Then, in this order: `install-content.sh rollback <A's content handle>` when A has one; only when that exited 0 or was not needed, `install-ap.sh rollback <A's file handle>`. A content rollback that does not exit 0 ends the attempt by the read: at C `not_started` (its refusal, exit 2) or `failed_restored` (any other exit), else `failed`; the file is not touched. After both: at A's `from`, `installed`; at C, `failed_restored`; else `failed`. Then `close_install` (with `to` and `code` as in step 11), the index run, the record (`tip` null, `from` C, `to` A's `from` when `installed`). A rollback that ends `installed` holds the timer (`held_by_rollback`) until a Lead's install call ended `installed`.

An installer's code: for `install-ap.sh` the word before `@` of its line `code@install-ap.sh:LINE` on stderr; for `install-content.sh`, which prints no code, `content_refused` at exit 2, `content_failed_restored` at exit 1, `content_exit_<n>` otherwise. Null at exit 0. A program ended by a signal has the exit 128 plus the signal. The `code` of a closed attempt is the first code of its installers; for a repair and a rollback, of its rollbacks as well.

The record, on stdout and, for every end but `invalid_input`, replaced through a temporary name in `<state>/last.json` (the record is still printed when that write fails). Exactly these members, null where one does not apply: `at` (UTC), `by` (the request's, or the timer's), `repository`, `target` (`/usr/local/bin/ap`), `tip`, `from`, `end`, `outcome`, `code`, `detail`, `install` (the attempt's id), `attempt`, `installers` (one row per program of steps 2, 9 and 10 and of a rollback, in order: `name` one of `ap`, `content`, `ap-rollback`, `content-rollback`; `exit`; `code`; an empty array when none ran), `to`, `rollback_binary`, `rollback_content`, `index` (`{"before", "after"}`, each `ok`, `failed` or null; null when no index ran), `closed` (`{"install", "outcome"}` of the dead call's attempt that step 2 closed). `end` is one of `current`, `refused`, `installed`, `not_started`, `failed_restored`, `failed`, `unrecorded`; `outcome` is null or one of `installed`, `not_started`, `failed_restored`, `failed`, and under `unrecorded` it is what the read decided. `code` is the refusal's code or the failing installer's. `detail`: `{"field"}` for `invalid_input`; `{"install"}` for `attempt_running`, `suppressed`, `held_by_rollback`, `attempt_exists` and `attempts_exhausted`, and for the timer's `pair_differs` (or null); `{"commit", "why"}` for `not_accepted`; `{"commit"}` for `past_not_on_chain`; `{"tip", "installed"}` for `engine_differs` and `schema_differs`; `{"store"}` for `store_refused` and `store_unreadable` (the store's code: its failed criteria joined by a space, its `code`, `already_applied`, or null when its answer could not be read); else null. No credential, no text of a report and nothing of an installer's output but its code and the printed tarball path; of the two backup directories only names are read.

Exit codes: 0 `installed` and `current`; 2 `refused` (no installer ran in this call), except 3 for `suppressed`, `attempts_exhausted` and, for the timer's request only, `pair_differs` and `attempt_running` (a Lead's request keeps exit 2 for both); 3 `not_started` and `failed_restored` (an attempt is recorded, the pair is where it was); 4 whenever `outcome` is `failed` (the pair is at no single commit: a person acts), recorded or not; 5 `unrecorded` with any other outcome. The service `deploy/ap-deliver.service` states that exit 2 is no failure of the unit (`SuccessExitStatus=2`); 3, 4 and 5 fail it.

Refusal codes, the complete list: `invalid_input`, `busy`, `attempt_running`, `fetch_failed`, `pair_differs`, `engine_differs`, `schema_differs`, `not_accepted`, `past_not_on_chain`, `suppressed`, `held_by_rollback`, `attempt_exists`, `attempts_exhausted`, `nothing_to_roll_back`, `disk_low`, `build_busy`, `store_refused`, `store_unreadable`.

Where a Lead sees it, with the request of the host in `/etc/agent-platform/deliver.json` (`deploy/deliver.json`, `state` `/var/lib/agent-platform/deliver`):
- whether the timer runs: `systemctl is-enabled ap-deliver.timer` answers `enabled`; `systemctl is-failed ap-deliver.service` answers `failed` after a run that exited 3, 4 or 5, until the next run;
- the last call, its end, code and time: `python3 -m json.tool /var/lib/agent-platform/deliver/last.json` (`end`, `code`, `detail`, `at`, `by`);
- the newest attempt: the first row of the view `installs`, `printf '{"view":"installs","args":{}}' | ont render`.

What a Lead does after each end:

- `installed`, `current`: nothing; the view `installs` shows the attempt.
- `not_started`: another install held the installers' lock; call again later (the timer tries a commit three times). `failed_restored`: the pair is back at `from`; read `code` and `installers`, repair, call again (the next attempt has the next number); the timer stays `suppressed` until then.
- `failed`: the pair is at no single commit, and every later request refuses `pair_differs`; the timer's runs then exit 3, name the failed attempt, and keep `ap-deliver.service` failed until the pair is repaired. Stop the timer, read the pair (`ap --version`, `sha256sum -c content/SHA256SUMS` in the content tree at the commit it should be at), put it back by hand with the installers' `rollback` verbs and the handles of the record (`deploy/README.md` names the commands), then, if the attempt is still running, close it by hand as below, and call `ap deliver` with `by` and `reason`.
- `refused`: `code` and `detail` say why; nothing was installed in this call. `not_accepted`: review the commit named, or name it in `past` with a reason when it is a commit a Lead steps over. `busy`, `build_busy`, `disk_low`: call again later. `engine_differs`, `schema_differs`: install the engine or the schema first. `pair_differs`: read and repair the pair by hand. `suppressed`, `held_by_rollback`: the timer waits for a Lead's install call that ends `installed`. `attempt_exists`, `attempts_exhausted`: the timer is done with T; a Lead's call installs it. `nothing_to_roll_back`: no verified handle; restore by hand or install forward.
- `attempt_running` and `unrecorded`: an attempt is `running` that no call will close (the timer's `attempt_running` exits 3 and keeps `ap-deliver.service` failed until a call settled the attempt; a Lead's exits 2). For a dead rollback (kind `rollback`) at neither commit, stop the timer and run again the two commands of the rollback, from the clone, with the handles of the attempt it rolls back (`rolls_back`): `bash <state>/<name>/scripts/install-content.sh rollback <its rollback_content>`, and when that exited 0, `bash <state>/<name>/scripts/install-ap.sh rollback <its rollback_binary>`. Read the pair as above, then close the attempt by hand with the outcome the read shows (`installed` at its `commit`, `not_started` or `failed_restored` at its `from`, `failed` otherwise) through `ont action apply --client ap-deliver` with the agent `ap-deliver`, for example `{"action_type":"close_install","request_id":"ap.<commit>.<attempt>.close","agent":"ap-deliver","parameters":{"install":<id>,"outcome":"installed","to":"<commit>"}}` (`ap.<commit>.rb<attempt>.close` for a rollback); an `unrecorded` record holds the id, the outcome, `to` and the handles to give.
