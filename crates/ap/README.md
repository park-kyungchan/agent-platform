# ap

`ap --version` (and `ap version`) prints one line `ap <Cargo package version> <40-hex commit>[-dirty]`, or `unknown` for the commit when Git was unavailable at build time.
`scripts/install-ap.sh` is the install script for `ap`: `check` compares the installed binary (`AP_INSTALL_DIR`, default `/usr/local/bin`) with `origin/main`, `install <expected commit>` builds from a temporary detached worktree of that exact commit and installs it after verifying the staged and installed `--version` report exactly that commit, and `rollback <before-file>` restores a backup.
For `install`, `origin/main` means the local ref, so run `git fetch` first; the previous binary is backed up as `ap.before-<first 7 hex of its sha256>` in `AP_BACKUP_DIR` (default `/var/lib/agent-platform/install`), and `rollback` accepts only that name in that directory and prints the restored version (or `no_version_output`). The script lock is `AP_INSTALL_LOCK` (default `/run/lock/ap-install.lock`).
Limitation: a source tarball nested inside another Git repository reports the outer repository's revision, because the build derives the revision from the enclosing repository.

## One worker run

`ap work --help` lists the commands. `ap work start`, `ap work wait` and `ap work close` each read one JSON object from stdin (at most 1 MiB) and emit one JSON object. Refusals emit `{"error":{"code","field","detail"}}` on stderr with a nonzero exit. These commands execute the installed `ont` and `herdr`; they do not install either program.

`start` takes `task_dir`, `name`, `packet`, `report`, `thread`, `layer`, `tier`, `cwd`, `model`, `effort`, `workspace`, and optional `worktree`, `store`, `continue_dirty`. Paths are absolute; packet/report references are relative to `/home/palantirkc/work/`. Names match `^[a-z][a-z0-9-]{0,31}$`. A worktree requires a clean Git status unless `continue_dirty` is true, plus exactly one packet line beginning `Write set:` (`ontology/README.md`). The packet's other lines are not checked: its form is `content/skills/lead/references/task-packet.md`.

The store validates admission before any Herdr call, with `session` omitted. After admission, `start` creates one Codex agent and polls for its exact name, created pane and tab, kind `codex`, and `interactive_ready: true` for at most 60 seconds (`agent_not_ready` on timeout). A session id is optional at this point. It records the full run Id using a stable packet-hash request id; only an ok apply with exactly one initial `worker_run` edit permits the one pane-targeted prompt. Its output includes `run`, `binding`, nullable `session`, `pane`, `tab` and `prompt` (`sent` or `uncertain`); `prompt_target` identifies the created pane, and `worktree_head` records the Git head when supplied. Keep the full `run` for closing. There is no polling after the prompt.

The existing store field `worker_run.session` holds the pane/tab binding, not the runtime session id: `ap-work/1:` followed by the compact JSON array `["<pane>","<tab>"]`, for example `ap-work/1:["w1:p2","w1:t2"]`. Both ids must be nonempty and the entire value at most 200 UTF-8 bytes. The reader requires exactly the writer's canonical encoding, including two parts and no extra whitespace. Old session ids, `unknown`, absent fields and other encodings refuse `run_binding_missing`; the Lead reconciles those rows manually.

An uncertain create/start/apply leaves the tab open for the Lead to reconcile; a confirmed store refusal closes the unprompted tab by its just-created id without label or state checks, because this process created it and has sent no prompt. A failed refusal cleanup reports `tab_closed: false`.

`wait` takes `name`, `report`, `timeout_seconds` (unsigned integer), and optional `pane` (used instead of the name when supplied). It waits once and checks the report even if waiting fails. A present report returns its `sha256` and `bytes` with exit 0; an absent or empty report returns `report_missing` with exit 3. `agent_status` is null when unavailable. It sends no prompt and reads no pane.

`close` takes the full `run`, `result`, `name`, `tab`, and optional `session`, `report`, `store`, `agent_gone`. It reads that exact run's current observation, requires `running` and a valid binding, and checks the supplied name/tab against it. It checks the stored tab's label and single-pane count, then reads the stored pane to confirm its tab membership. The live agent with the run's name must occupy both bound ids, be `idle`, `done` or `blocked`, and report a nonempty session id. A caller-known non-null `session` must match (`session_mismatch`); `start`'s null session may be omitted. The stored result appends `; session=<live id>`; the entire result must fit within 600 UTF-8 bytes before any write.

A missing agent requires `agent_gone: true`, supplied after the Lead observed it ended, the same bound sole-pane membership, and no listed agent with that name, pane or tab. Its result appends `; session=unavailable (agent_gone)`, explicitly recording the absence of a live session. Only an ok apply with the two updates of that exact `worker_run` (the modification and the cleared `running_in`), followed by readback of its closed status, result and unchanged binding/name, permits tab closure. A failed tab close returns `tab_closed: false` with exit 3. An uncertain store close or readback leaves the tab open.

`store` forwards `--store <absolute path>` to every Ontology call, permitting disposable-store use. Uncertainty requires readback by the Lead; no command automatically retries a prompt or sends keys.

## One stage

`ap run < request.json` runs ONE headless Claude Code session (a stage: implementer, reviewer or fixer) in a transient systemd scope `ap-run-<uuid>.scope` under `agents.slice` and returns when nothing of it is alive. It prints the run record on stdout. Exit 0 `ok`, 75 `cut`, 3 any other end, 5 a file of the run could not be written after the record was claimed, which includes the case in which nothing ran (stdout holds the final record; the file holds it when a write in place succeeded). Exit 2 is a refusal before any effect, and nothing else: `{"error":{"code","field","detail"}}` on stderr. It reads no role table, calls no store, Herdr or GitHub.

The request: `role` (`implementer`, `reviewer`, `fixer`), `account` (the Claude configuration directory, required), optional `next_accounts`, `model`, `effort`, `permission_mode` (one of Claude Code's: `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan`), `cwd`, `prompt` (a regular file, at most 1 MiB, given to the CLI on stdin), `out` (the answer's path), and optional `timeout_seconds` (1 to 86400; default implementer 5400, fixer 3600, reviewer 3300), `expect` (`file`: a path that this run must write nonempty; `first_line`: a pattern the answer's first line must match, where `*` matches any run of characters), `resume` (`{"record": "<absolute path of the earlier run's record>"}`), `continue_dirty`, `integration` (a reviewer's only: another role refuses `invalid_input`; it does not choose the account), `mcp_config` (files; the only MCP servers loaded), `env` (extra variables; a name beginning `HERDR_`, `CLAUDE_` or `ANTHROPIC_`, and `HOME`, refuse `env_forbidden`: the account named in the record is the account that answers), `runtime` (`claude`; `codex` refuses `runtime_not_built`), `bind` (the name of a systemd unit that is active now: when it ends for any reason, stopped, killed or failed, the stage's unit stops), `skills` and `memory` (booleans: the account's skills and slash commands, and its auto-memory, load only when true). `bind` is for a transient unit (the caller's own, as a chain's): one that ended between the request and the launch makes the launch fail (the record says `failed`); a unit that systemd can start again by name is started again by the launch, because `BindsTo` requires it. Every path is absolute; another member refuses `invalid_input`, and so does an `out` whose file name ends with a suffix `ap run` derives (`.run.json`, `.stream.jsonl`, `.err`, `.ap-tmp`): no run's answer path is another run's file. A resume is a run of its own with its own `out`; it continues the session of the earlier run on that run's account. `ap run` guards a run's files against another run; it does not guard a session against its caller: two resumes of one record at the same time are not refused, because the caller is the one owner of a session and runs its stages in sequence. On a resume the prompt file is the next message to the session: give a continuation or the findings, not the first prompt again.

Refusals (exit 2, before any effect, no file written): `invalid_input`; `runtime_not_built`; `account_missing` (`account` or an entry of `next_accounts` is not an existing directory; `/root/.claude` is an account like any other, for every role, as `account` and in `next_accounts`); `cwd_missing`; `prompt_unreadable`; `out_unwritable`; `out_named_in_prompt` (the prompt contains the out file's name); `out_exists` (`out`, `<out>.run.json`, `<out>.stream.jsonl` or `<out>.err` exists: nothing of an earlier run is replaced, removed or truncated by a later one); `worktree_dirty` (a fresh implementer run in a Git worktree with changes, unless `continue_dirty`); `worktree_unreadable` (Git cannot read `cwd` for a reason other than "not a git repository"; `git` runs with the fixed short list of variables only, not the request's `env`); `resume_record_missing`, `resume_account_differs`, `resume_cwd_differs`, `resume_role_differs` (a resume keeps the earlier record's `cwd` and its role, or is a `fixer` over an implementer's or a fixer's record); `bind_inactive` (`systemctl is-active` for `bind` did not answer `active`); `run_still_active` (whatever the earlier record's state, `systemctl is-active` for its unit did not answer a state in which nothing of its unit lives: `active`, `activating`, `deactivating`, `reloading`, `refreshing`, a failed call and no answer all refuse); `env_forbidden`; `systemd_absent`.

The run: every run, fresh or resumed, creates its own record. `<out>.run.json` is created exclusively, and that creation is the claim: of two requests on one `out` started at the same instant, one passes and the other is refused `out_exists`. Then `<out>.stream.jsonl` and `<out>.err` are created exclusively; every write of the answer or the record goes through a temporary name unique to that write and created exclusively, so it is never another run's file. A session id is chosen (or taken from the earlier record on a resume), and the record is written with state `running` BEFORE the launch; a resume's record names the earlier record in `resumes`. The launch is `systemd-run --scope --quiet --collect --unit=… --slice=agents.slice -p RuntimeMaxSec=<timeout + 10>s -p TimeoutStopSec=10s [-p BindsTo=<bind> -p After=<bind>] -- claude --print --output-format stream-json --verbose --model … --effort … --permission-mode … --permission-prompts none --setting-sources user --settings <settings> --disallowedTools Monitor --strict-mcp-config [--mcp-config …] [--disable-slash-commands] (--session-id | --resume) <session>`. The settings, for every role and with nothing in the request: `disableAllHooks: true`; `env` with `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS` at 2700000 (a 40-minute check runs in the foreground of one Bash call) and `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` (a command that reaches its limit stops instead of moving to the background); `autoMemoryEnabled: false` unless `memory`. `--disable-slash-commands` is left out only with `skills`. So the stage has no `Monitor` and no background shell, and its first event lists no skill and no memory directory, while the account's `CLAUDE.md` still loads (shown on Claude Code 2.1.325). Its environment is only `PATH HOME USER LOGNAME SHELL LANG LC_ALL TERM TMPDIR TZ` of the caller (when set), the request's `env`, and `CLAUDE_CONFIG_DIR=<account>`: no hook (of the account, the host, a project or a plugin), no MCP server the request does not name, and only the account's settings (a worktree's `.claude/settings.json` and `settings.local.json` do not load; with them the project's `CLAUDE.md` and `.claude/agents` do not load either, while the account's `CLAUDE.md` does). stdout goes to `<out>.stream.jsonl`, which `ap run` reads only through the handle it opened before the launch; stderr to `<out>.err`, removed at the end when empty. The stream holds the session's transcript (answers and tool output): keep `out` where it is private. `RuntimeMaxSec` is the unit's own bound: it ends the stage when `ap run` is gone.

The end, by role. A print session that left a background shell emits a `result`, waits for the shell, then may run a second turn and emit another `result` (each `result` carries the `usage` and `num_turns` of its own part; the sum is the session's). So a `result` ends the stage only for a `reviewer`: at its first `result`. An `implementer` or a `fixer` runs to the CLI's exit; for every role `timeout_seconds` ends the stage. Then `systemctl stop` ends every process in the unit, the stream is read to its end (a last line without a newline included), and `systemctl is-active` must answer a state that is not `active`, `activating`, `deactivating`, `reloading` or `refreshing`; anything else, a failed call included, makes the state `failed` with `unmet: stop`.

States, from the result the stage is judged by: the LAST `result` whose answer is nonempty, not an error or a cut, and meets `expect.first_line` when one met it (a later result does not unmake it), else the last `result` seen (a reviewer has only its first): `ok` (a non-error result whose text is nonempty and meets `expect`); `no_result` (a non-error result that is empty or does not meet `expect`; `unmet` names which: `answer`, `file`, `first_line`; a nonempty answer is still saved); `cut` (an error result with a rejected rate-limit event, API status 429 or the usage-limit text, or a non-error result with the usage-limit text and a rejected rate-limit event; no answer is written); `timeout` (the bound ended the stage, for every role, even when a result is read during the shutdown; the last answer, if any, is saved and `expect_met` says whether it met `expect`); `failed` (the CLI ended without a result event, an error result that is not a cut, the launch failed, the stop was not confirmed, or a write failed: `unmet` `result_event`, `launch`, `stop` or `write`). A refusal has no record. The answer is the result text, byte for byte. `expect.file` is met only by a nonempty file whose digest or modification time differs from `expect_file_before`: the file as it was before THIS run's launch. Only a resume that continues the same unfinished stage (the earlier record has the same role and a state other than `ok`) takes the earlier record's `expect_file_before` instead; a fixer over an implementer always takes its own. A fresh run cut before it did any work (the stream holds no `tool_use` block, so no tool ran), and a fresh run of a `reviewer` cut at any point (it changes no file: what it did is lost, not wrong), is run again, within the same run and its record, on the next of `next_accounts` with a new session; an implementer or a fixer cut after a tool ran stays cut, and a resume never changes account.

The record `<out>.run.json`: `role, runtime, model, effort, account, session, cwd, unit, prompt{path,sha256}, answer{path,sha256}|null, start, end|null` (UTC, RFC 3339), `state, turns, tokens{input,output,cache_read,cache_creation}` (sums over the `result` events; null where the CLI did not report), `permission_denials` (`tool_name` and `tool_use_id` as reported, over all results), `results` (the number of `result` events read), `expect_met` (null without a result), `expect_file_before` (`{path, sha256, modified}` or null), `unmet`, `resumes` (the earlier record's path, or null). No prompt or answer text. `ci/host-run-scope.sh` exercises the real unit on a host with systemd.

## The gate

`ap gate < request.json` waits on ONE pull request's head until its required checks and the automatic review are done, and prints one JSON answer on stdout. It reads GitHub through `gh api graphql` (the caller's `gh` login) and decides nothing a person decides: it resolves no thread, posts no status, merges nothing and calls no store. Its only writes are `gh pr ready` on a draft (once) and the one toggle below.

The request: `repository` (`owner/name`), `pull_request` (number), optional `head` (40 hex: the head the caller expects), `autoreview` (the login whose comment carries the marker, default `chatgpt-codex-connector[bot]`; `false` for a repository without an automatic reviewer), `check_minutes` (default 90) and `autoreview_minutes` (default 40), each 1 to 1440. Another member, or a malformed one, refuses `invalid_input` with exit 2 before any read: `{"error":{"code","field","detail"}}` on stderr.

It reads every 30 seconds. The head it waits on is the one GitHub reports at the first reading. In order:
1. Merged or closed (at any reading) ends `merged` or `closed`. A caller's `head` that differs from GitHub's ends `head_differs` (`expected` names the caller's). A head that moves later ends `head_moved` (`head_now`). A draft is marked ready once; a failed mark ends `ready_failed`.
2. The required checks, judged at every reading, also while the gate waits for the review: every entry on the head's commit whose `isRequired` is true, except the status `lead-review` (a `StatusContext` of that context: the output of the Lead's accept, not a check that precedes the review, so a revoked or pending acceptance never blocks the gate; a check run of that name is judged like any other), over every page (a reading that could not be completed is no reading). One that completed with any conclusion but `SUCCESS`, or a status that is not `SUCCESS` or pending, ends `check_failed` with `failed_check: {name, state, run}`. None yet, or one pending, waits; at the bound of the phase (`check_minutes`, or `autoreview_minutes` once the review wait began) it ends `check_timeout`. A repository without a required check ends `check_timeout`.
3. The automatic review (skipped with `autoreview: false`): the marker `codex-review-state:v1 {…}` counts only in a comment of that login (a bot's GraphQL login gets `[bot]`, so a user of the same name does not count); the last such comment's `code_review` is read, from the last occurrence in that comment that parses. The marker is looked for in the last 100 comments. When the checks have passed and it names another commit (or none), the gate marks the pull request draft and ready ONCE, because a push to a ready pull request is not reviewed; not when the gate itself just marked a draft ready. It ends `passed` when `commit_sha` is the head and `status` is `completed`, and also at `autoreview_minutes`: the time limit passing is not a failure, `autoreview.state` says `timeout`.

The answer: `end`, `repository`, `pull_request`, `head`, `marked_ready`, `checks` (`[{name, state, run}]`: the judged entries, then the status `lead-review` with its state and `judged: false` when the head has one, required or not), `autoreview` (`login`, `state`: `completed`, `timeout`, `waiting` when the gate ended before it, or `off`; `commit`, `has_unresolved_findings` as the marker says, `toggled`), `threads` (every unresolved review thread: `id`, `path`, `line`, `author`, `answered`: its last comment is not the automatic reviewer's; `null` when it could not be read), and `failed_check`, `expected`, `head_now`, `left_draft` (a toggle whose ready mark failed three times) or `unreadable` with their ends. `answered` is true for every thread when `autoreview` is `false`. `passed` with exit 0 also covers a review that reached its time limit and a review with unresolved findings: the caller reads `autoreview.state`, `has_unresolved_findings` and `threads`. Exit by end: 0 `passed`; 10 `merged`, `closed`, `head_differs`, `head_moved`; 11 `check_failed`, `check_timeout`; 12 `ready_failed`, `github_unreadable` (`unreadable` names the cause: `not_found`, `no_login` or `gh_not_started` end at the first reading; `no_answer` when a reading still failed at the bound of the phase).

## One review

`ap review start|close|accept|revoke` reads one JSON object on stdin and writes
one JSON answer; errors use the same stderr envelope and exit codes as `ap work`.
Every path is absolute. Optional `store` forwards `--store` to every `ont` call.
The review object owns the verdict; `lead-review` is a derived commit status.
The rulesets of the three platform repositories require it beside `rust`.

`start` reads and hashes a regular prompt file below `/home/palantirkc/work/`.
With a pull request, it checks that the request is open at exactly `head`.
Each optional run must exist, belong to the task and occur once. It applies
`start_review` with a stable request id based on task key, kind, head and prompt
hash, returning `status: started`, `outcome: applied`, the complete `review` id
and `prompt_sha256`. Optional integer `attempt` (2 to 99) appends a newline and
that number to the digest input; omit it for the first attempt. A repeated request
reads the review and returns `outcome: already_applied` only while it is running.
A closed review is refused with `review_already_closed`; retry with a new `attempt`.
It does not launch a reviewer. Example stdin for `ap review start`:

```json
{"task_dir":"/home/palantirkc/work/example","kind":"packet","head":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","base":"bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb","repository":"owner/repo","pull_request":12,"runs":[{"object_type":"worker_run","namespace":{"instance":"vps://palantirkc","account":"root"},"native_key":"run-key"}],"model":"reviewer-model","effort":"high","prompt":"/home/palantirkc/work/example/prompt.md"}
```

`close` reads a regular report file below the work root, at most 1 MiB. Its
first line must be exactly `Verdict: accept` or `Verdict: repair`. It hashes the
bytes and applies `close_review`; optional `account` and `session` are recorded.
Alternatively, supply `verdict: abandoned` with no report. The answer contains
`status: closed`, `verdict` and `report_sha256` (null for abandoned). The stable
close request id hashes the review key and report hash (`abandoned` without a
report). Example stdin for `ap review close`:

```json
{"review":{"object_type":"review","namespace":{"instance":"vps://palantirkc","account":"root"},"native_key":"review-key"},"report":"/home/palantirkc/work/example/report.md","account":"b","session":"reviewer-session"}
```

`accept` requires a closed `packet` or `integrated` review with verdict `accept`,
repository, pull request, head, base and an unchanged report. Every named run
must belong to the review task and have a nonempty write set. It verifies the open pull request targets `main`
at the review head, fetches `origin main`, checks the merge base and compares
changed paths to the union of those write sets, using `git --no-replace-objects`
and `diff --no-renames --ignore-submodules=none --no-relative --name-only -z`. Paths are read NUL-separated,
so non-ASCII names are compared unquoted, including names containing newlines or
quotes. A path that is not valid UTF-8 ends with `process_failed` (field `git`).
A moved file must have both its
old and new paths in that union. A pattern matches its exact
path; a trailing `/**` matches descendants, not the directory itself or another
name with the same prefix. The caller must be outside the task's `wt/`.
Only then does it post `lead-review=success` for that head and return
`status: accepted`, `head` and the number of `paths`. Repeating it posts again.
Example stdin for `ap review accept`:

```json
{"review":{"object_type":"review","namespace":{"instance":"vps://palantirkc","account":"root"},"native_key":"review-key"},"worktree":"/home/palantirkc/work/example/wt/repo"}
```

`revoke` reads a review with a repository and head. When its `status` is
`closed` it applies `revoke_review` with the reason, under the request id
`rv-revoke-` and the first 40 hex of the SHA-256 of the review's key, the same
for every revoke of that review; a refusal or a failure of the store ends the
command with `store_refused` or `store_answer_unreadable` and nothing is posted.
When the `status` already is `revoked` it applies nothing. Only then does it post
`lead-review=failure` with `revoked: <reason>`. The object changes before the
status, because the store is what a later reader asks: a come-back of `ap unit`
and `start_install` read `status: closed`, so a revoked review is not found
again, while a status alone would be overwritten by the next `success`. A crash
between the two leaves a revoked object and no posted failure; the repeated
command finds `revoked` and posts it. A running review is not changed. The
reason must contain text and fit within 100 UTF-8 bytes. It returns
`status: revoked` and `head`. Example stdin for `ap review revoke`:

```json
{"review":{"object_type":"review","namespace":{"instance":"vps://palantirkc","account":"root"},"native_key":"review-key"},"reason":"Report missed a changed path"}
```

Refusals (local checks precede writes and status posts):

- `invalid_input`: malformed object, id, path, run list, reason or explicit verdict; field identifies the member.
- `review_prompt_unreadable`: prompt is not a readable regular file below the work root.
- `review_head_differs`: pull request is closed, has another head, or (at accept) targets another branch.
- `review_run_unknown`: a start run cannot be read as the exact current object.
- `review_run_of_other_task`: a run supplied to `start` or `accept` belongs to another task.
- `review_already_closed`: `start` repeated after its review closed; repeat with a new `attempt`.
- `store_refused`: the store refused an attempted action; detail carries its codes; no retry occurs.
- `review_report_unreadable`: close report is unreadable, outside the work root or larger than 1 MiB.
- `review_report_lacks_verdict`: the report's first line is not one of the two exact verdict lines.
- `review_not_accepting`: required review state or evidence is absent; detail names the first failing member.
- `review_report_changed`: report is unreadable or its current bytes have another digest.
- `review_runs_required`: an accepting review needs a nonempty array of runs.
- `review_run_lacks_write_set`: a run is unreadable or lacks a nonempty write set; detail gives its key.
- `review_base_differs`: fetched merge base differs from the review base; detail gives the merge base.
- `review_path_outside_write_set`: changed paths escape the union; detail contains at most ten paths and the total count.
- `review_accept_from_worktree`: caller's working directory is under the reviewed task's `wt/`.
- `store_review_unreadable`: the exact review's current observation cannot be read.
- `store_answer_unreadable`: an action reply is malformed or does not confirm the expected create.
- `process_failed`: an external command failed or returned unreadable Git output; no automatic retry occurs.
- `io_error`: stdin or the caller's working directory cannot be read.
- `input_too_large`: stdin exceeds 1 MiB.
- `usage`: exactly one supported verb is required.

## One unit

`ap unit < request.json` takes ONE unit of work once from its page to the merge: worktree, one implementer stage, the pull request, the gate, the page's acceptance executable, the write set, one verifier stage, the `review` object, the status `lead-review`, the guarded merge, the removal of the worktree. It returns when the unit merged or when the first step that did not pass ended it, and prints the unit record on stdout. A request with the member `case` is a case call instead ("One case" below); a request without it is a unit call, as this section says. Exit 0 `merged`, or `accepted` when the request says not to merge; 3 `stopped` (the record names the step and the cause); 5 the record could not be written after it was claimed (stdout holds the last record). Exit 2 is a refusal before any effect, in the form of `ap run`: `{"error":{"code","field","detail"}}` on stderr, no record. It is one pass: at most one implementer and one verifier stage, no fixer, no round, no step repeated, no wait but the stage's own and the gate's; it never continues an earlier call's record. No path accepts without the verdict of a model: every call has a verifier stage or the answer of an earlier one, and the command never writes a verdict itself.

The request: `repository` (`owner/name`), `clone` (the local clone whose `origin` is the repository), `worktree` (the path of the unit's worktree), `branch` (a new branch), `task_key` (the store's task the `review` hangs on, `^[a-z0-9][a-z0-9-]{0,63}$`; not derived from a directory), `page` (the packet: a regular file with exactly one line beginning `Write set:` at the first column, comma-separated patterns matched as `ap review accept` matches them), `out` (the prefix of every file of the call), `acceptance` (the page's acceptance executable), `implementer` and `verifier` (each `account`, `model`, `effort`, `prompt`, optional `permission_mode` (default `auto`), `timeout_seconds`, `next_accounts`, `env` and `resume`, given to `ap run` as they are: a stage cut before it did any work, and a verifier cut at any point, runs again on the next account inside the same stage and its one record; with `resume` (`{"record": "<path>"}`) a repaired head returns to the session that reviewed it, the Lead's prompt file is the next message to that session and the block of facts is appended as before), optional `acceptance_seconds` (1 to 86400, default 2700), `gate` (`autoreview`, `check_minutes`, `autoreview_minutes` as `ap gate` takes them), `store` (forwarded to every `ont` call), `merge` (false: the call ends `accepted` after the review is closed, with no status), `pull_request` (a come-back after a repair by hand: steps 2 to 4 are skipped and the existing `worktree` on `branch` is used) and `verdict` (with `pull_request` only, instead of `verifier`: the answer of an earlier reviewer stage; step 8 is skipped and the file is checked against the head). `verdict` is taken only when `<verdict>.run.json` lies beside it: an `ap run` record with role `reviewer`, state `ok`, `answer.path` and `answer.sha256` equal to the file and its digest, and a prompt file (below the work root) that still has the recorded digest. Every path is absolute; `page`, `out` and `verdict` lie below the work root (`/home/palantirkc/work/`), because the `review` object records them. `acceptance` and the verifier's prompt lie outside `worktree`.

The use of `merge: false`: a unit with a real effect, where the Lead reads the diff after the verifier accepted and before the merge. The come-back with `pull_request` and `verdict` (the verifier's answer `<out>.verifier.md`) then posts the status and merges; it uses the review the first call closed (step `review` below). The same come-back finishes a call that stopped at `status` or `merge`.

Refusals (exit 2, before any effect: no file, worktree, branch, process or network call): `invalid_input` (an unknown or malformed member, a relative path, neither or both of `verifier` and `verdict`; `field` names the member, `implementer.prompt` for a nested one); `outside_work_root`; `inside_worktree` (`acceptance` or the verifier's prompt); `page_unreadable`; `write_set_missing` (no line `Write set:`, or more than one, or one without a pattern); `prompt_unreadable` (also a verifier prompt that leaves no room for the block of facts within `ap run`'s 1 MiB); `acceptance_unreadable` (not a regular executable file); `verdict_unreadable` (no file, or no record beside it as above); `out_exists` (`<out>.unit.json` or another file of the call exists); `out_unwritable` (the record cannot be created); `worktree_exists` (a fresh call whose `worktree` exists); `worktree_missing` (a come-back whose `worktree` is not a directory). Every member of `implementer` and `verifier` that `ap run` can judge before the stage's worktree exists (its shape, `permission_mode`, `timeout_seconds`, `model`, `effort`, `next_accounts`, `resume`, the account rules, the prompt, the stage's files) is judged here by `ap run`'s own code, with its code and the field prefixed (`verifier.timeout_seconds`); what only the stage's start shows ends the call at that stage with the cause `stage_refused`.

The sequence. Each step is recorded before it begins and after it ends; the first that does not pass ends the call with `state: stopped`, `stopped_at` (the step) and `cause` (`io_error` when a file of the call cannot be created):

| Step | What it does | Causes that stop it |
| --- | --- | --- |
| `worktree` | `git fetch origin main` in `clone`; the worktree and `branch` from the fetched `origin/main` (recorded as `base` until step `write_set`) | `fetch_failed`, `worktree_failed` |
| `implementer` | ONE `ap run` stage, role `implementer`, cwd `worktree`, the Lead's prompt file unchanged, no `expect`; answer `<out>.implementer.md`, which is the unit's report: the Lead's prompt asks for the report as the final message | `stage_refused`, or the stage's state when it is not `ok` (`cut`, `timeout`, `no_result`, `failed`) |
| `pull_request` | the one open pull request of `branch` against `main` | `no_pull_request`, `pull_request_ambiguous`, `github_unreadable` |
| `gate` | `ap gate`'s code on that pull request, with `head` the pull request's head read at `pull_request` (none in a come-back); its answer `<out>.gate.json`; its `head` becomes the unit's head. The step's `detail` is `{"lead_review": <state>}`: the state of the status `lead-review` the gate lists and does not judge, or null, so that a revoked acceptance is seen | the gate's end when it is not `passed`; `unresolved_findings`; `unresolved_threads` (one or more, or not readable) |
| `acceptance` | `acceptance` in `worktree`, no arguments, stdin `/dev/null`, under `timeout -k 10 <acceptance_seconds>`; stdout and stderr to `<out>.accept.log` | `digest_differs`, `worktree_dirty`, `head_differs`, `git_failed`, `acceptance_failed` (`detail`: `{"exit": <code>}`, null when no exit was read; an executable that ignores SIGTERM is killed 10 s after the bound and ends here with exit 137), `acceptance_timeout` (exit 124, also when the executable itself exits 124) |
| `write_set` | `git fetch origin main` in `clone`, in a fresh call too; the fetched `origin/main` must be an ancestor of the head (the rulesets require an up-to-date branch, so the merge would fail after the verifier was paid) and becomes `base`; the changed paths of `git diff <base> <head>` (the options of `ap review accept`) against the page's write set | `fetch_failed`, `git_failed`, `behind_main` (`detail`: the commit of `origin/main`), `path_outside_write_set` (at most ten paths and the count in `detail`) |
| `verifier` | ONE `ap run` stage, role `reviewer`, cwd `worktree`, `expect.first_line` `Verdict: *`, prompt `<out>.verifier.prompt.md`: the Lead's prompt file unchanged followed by a block of facts (repository, pull request, head, the diff command, the paths of the gate's answer and of the acceptance output); answer `<out>.verifier.md`. Come-back with `verdict`: skipped, that file is the report and `stages.verifier` names the record beside it | `digest_differs`, `worktree_dirty`, `head_differs`, `git_failed`, `stage_refused`, a state not `ok`, `verdict_repair`, `verdict_unreadable`, `verdict_head_differs` (the second line is not the head) |
| `review` | when the store holds a closed (not revoked: `status` is `closed`) review of kind `packet` with verdict `accept` for this task, repository and head whose report digest is the report's, that review is used: its id goes into the record, `detail` `{"reused": true}`, and no second one starts. Otherwise `ap review start` (kind `packet`, the head, `base`, the pull request; `model`, `effort` and `prompt` of the verifier's `ap run` record) and `ap review close` with the report and that record's `account` and `session` (`detail` `{"reused": false}`) | `verdict_unreadable` (the record of the verifier cannot be read), the codes of `ap review` (`review_head_differs`, `store_refused`, …) |
| `status` | the pull request is read open against `main` at the head, then `lead-review=success` on the head through the code of `ap review` | `github_unreadable`, `head_differs`, `status_failed` |
| `merge` | `gh pr merge --merge --match-head-commit <head>`, then a read of the pull request, also after a call that failed: `merged` only when it says merged at the head and names the merge commit | `merge_failed` (the call failed), `merge_unconfirmed` (the call succeeded) |
| `cleanup` | in `clone`: `git fetch origin main`, `git worktree remove` without force, then, only after the removal, `git branch -d` (the branch tracks `origin/main`, which now holds the merge). The remote branch is not touched: the repositories delete the branch of a merged pull request themselves | none: a failure is recorded in the step (`result: failed`, `detail` `{fetch, worktree: removed|failed, branch: deleted|failed|kept}`) and the state stays `merged` |

The status is posted only after all of: the gate ended `passed` with no unresolved finding and no unresolved thread; the acceptance executable exited 0; every changed path is inside the write set and the branch contains the fetched `main`; one `review` object is closed with `Verdict: accept` for the head, by a report of a model (the answer of the verifier stage of this call, or a `verdict` admitted as above) whose first line is `Verdict: accept` and whose second line is the head. One accepted head has one review object. Acceptance and verifier start only while `worktree` is clean and its `HEAD` is the head the gate passed; the review, the status and the merge name exactly that head. No `--admin`, no auto-merge, no force anywhere. Condition of use: the repository's `main` has no merge queue and auto-merge is off (true of the three platform repositories), so `gh pr merge` merges at once or fails; the command does not detect a merge queue. The `review` object owns the verdict; the status is derived from it, as in "One review". `ap review accept` is not used: stages of `ap run` leave no `worker_run`, and the page's write set is checked here instead.

What judges a stage cannot be changed by it: the SHA-256 of `acceptance`, of the verifier's prompt, of `verdict` and of `page` are in the record before the implementer starts; a file whose digest differs when it is used ends the call (`digest_differs`). The verifier's prompt holds neither the implementer's answer nor its path.

The record `<out>.unit.json` is created exclusively before any effect (the claim, as in `ap run`) and replaced after every step through a temporary name: `repository, clone, worktree, branch, task_key, base, page{path,sha256}, write_set, acceptance{path,sha256}, verifier_prompt{path,sha256}|null, verdict_file{path,sha256}|null, merge, pull_request, head, review` (the complete id), `merge_commit, stages{implementer, verifier}` (the paths of their `ap run` records, written before the stage starts, or null), `files{gate, acceptance_output, report}, mode` (`"unit"`), `state` (`running`, `merged`, `accepted`, `stopped`; `passed` and `failed` exist only in a case call, and so does exit 4), `step` (the step begun, null at the end), `stopped_at, cause, detail, steps` (each step done, in order: `name`, `result` (`passed`, `skipped`, `stopped`, `failed`), `start`, `end`, `detail`), `start, end`. No prompt or answer text and no credential. A unit record without `mode` is a unit call: it was written before the member existed. A killed call leaves this file naming the step begun; the Lead goes on by hand from it, or calls again with `pull_request` (and `verdict`, or `verifier` with `resume`) and a new `out`. Inside the call that starts the review the file shows step `review` with `review` null; the id is on disk from the save after that call returns.

## One case

`ap unit < request.json` with the member `case` is a case call: it runs a past unit again, in a copy that holds only that unit's base, and judges it by the tests the unit was accepted with. One record says whether a stage of the named model made those tests pass; with no stage the call shows whether the case is valid. It is one pass, like a unit call: at most one stage, no fixer, no step repeated. It starts no `gh` and no `ont`, makes no network call and writes nothing outside `worktree` and the files of `out`; what the stage and the commands of the case do is theirs.

The case file (`evals/engineering/cases/<id>.json`, see `evals/README.md`), JSON with exactly these members: `id` (`^[a-z0-9][a-z0-9-]{0,63}$`; the file is `<id>.json`), `repository` (`owner/name`), `pull_request` (the merged pull request the case was taken from), `base` and `head` (40 hex digits: the first parent of the merge commit, and the accepted head), `tests` (a nonempty array of relative repository paths without `..`: every file that judges; the candidate gets them with their bytes at `head` and the evaluator restores them), `commands` (a nonempty array of argument arrays: what the evaluator runs in the copy, in order), `page_sha256` (64 hex digits: the page given to the candidate; its text is a host file and never enters this repository).

The request, exactly: `case` (the absolute path of the case file), `clone` (a local clone that holds `base` and `head`), `worktree` (the path of the case's copy; it must not exist), `page`, `out`, `acceptance` (the evaluator, `evals/engineering/evaluate`), optional `implementer` (the members of a stage of a unit call without `resume`), optional `at` (`"base"`, the default, or `"head"`), optional `acceptance_seconds` (1 to 86400, default 2700). `at: "head"` together with `implementer` is refused (`invalid_input`, `at`): no stage ever works in a copy that holds the head. Every other member of a unit call (`repository`, `branch`, `task_key`, `verifier`, `verdict`, `gate`, `store`, `merge`, `pull_request`) is refused with `invalid_input` and its name.

Refusals (exit 2, before any effect, in the form of a unit call): those of a unit call that apply (`invalid_input`, `outside_work_root` for `page` and `out`, `inside_worktree` for `acceptance`, `page_unreadable`, `prompt_unreadable` (also a prompt that leaves no room for the block of facts), `acceptance_unreadable`, `out_exists`, `out_unwritable`, `worktree_exists`, and the stage's own, judged by `ap run`'s code with the prefix `implementer.`), and `case_unreadable` (`case` is not a regular file, not JSON, or a member is missing, unknown or malformed); `case_page_differs` (the SHA-256 of `page` is not `page_sha256`); `case_commit_missing` (`base` or `head` is not a commit of `clone`, or a path of `tests` is not a file at `head`; `field` is `case.base`, `case.head` or `case.tests`). A case call's page needs no line `Write set:`.

The steps, each recorded before it begins and after it ends; no other step is in a case record:

| Step | What it does | How it ends |
| --- | --- | --- |
| `worktree` | creates `worktree` as a new Git repository with ONE commit and no remote: at `base` the tree of `base` with every path of `tests` holding its bytes (and mode) at `head`; at `head` the tree of `head`. Only the objects of that tree are copied out of `clone` (`pack-objects` into `unpack-objects`): the copy shares no object store with `clone` and names it nowhere, so no commit of `clone` can be reached from inside the copy. The commit is made with an identity given on the command line (`-c user.name=… -c user.email=…`), so it needs none from the host | stops with `copy_failed` |
| `implementer` | only with `implementer`: ONE `ap run` stage, role `implementer`, cwd the copy; its prompt is `<out>.implementer.prompt.md`: the request's prompt file unchanged, followed by a block of facts (the page's path, the copy's path, the paths of `tests`, each array of `commands` as JSON on a line of its own, and that the copy has no remote); answer `<out>.implementer.md` | the stage's state `ok`: the step passed. `timeout`: the call ends `failed` (`detail` `{"stage": "timeout"}`), `acceptance` does not run, `cleanup` does. Any other state (`cut`, `no_result`, `failed`), or `stage_refused`: the call stops with it as the cause |
| `acceptance` | the digest of `acceptance` is compared as in a unit call; then `acceptance <case> <clone>` runs in the copy, stdin `/dev/null`, under `timeout -k 10 <acceptance_seconds>`, with the environment of the `ap unit` call (so the caller's `CARGO_TARGET_DIR` and `HOST_CARGO_LOCK` reach it); output to `<out>.accept.log`. No condition on the copy's state: the candidate may have committed or not | exit 0: the call ends `passed`. Exit 1, or the bound reached (exit 124): the call ends `failed` (`detail` `{"exit": 1}` or `{"exit": 124}`). Any other exit: the call stops with `acceptance_failed` (the evaluator could not judge); `digest_differs` stops it before the run |
| `cleanup` | after the result is `passed` or `failed`: writes `<out>.candidate.diff`, the difference between the copy's one commit and its final files (new files included, ignored files not, binary as Git's binary patch), then removes the copy. After a stop the copy stays for the Lead to read | a failure is recorded in the step (`result: failed`, `detail` `{diff, copy: removed\|failed}`) and changes no result |

The ends: exit 0 with `state: passed`; exit 4 with `state: failed`; exit 3 with `state: stopped` (`stopped_at`, `cause`, `detail`); 2 a refusal and 5 a record that could not be written, as in a unit call. A unit call never exits 4.

The record `<out>.unit.json` is claimed and replaced as in a unit call, with the same members; those that have no meaning in a case call are null: `branch`, `task_key`, `write_set`, `verifier_prompt`, `verdict_file`, `merge`, `pull_request`, `head`, `review`, `merge_commit`, `stages.verifier`, `files.gate`. `repository` and `base` are the case's, `files.report` is the stage's answer (null without a stage), and `detail` is the failed step's detail at `failed` too. It adds `mode` (`"case"`), `case` (`{path, sha256, id}`), `at`, `prompt` (`{path, sha256}` of the request's prompt file, null without a stage: the digest of the stage's own prompt is of a file that holds the copy's path and differs in every call), `stage_seconds` (the stage's bound in effect, its `timeout_seconds` or `ap run`'s default; null without a stage: it defines what `failed` by timeout means) and `files.candidate_diff`. A killed case call leaves the record naming the step begun.

What a case record means, for the read-out (`evals/readout.py`) and any other reader. One record is one row of the suite: the case (`case.id`, its digest `case.sha256`), the target (the model and effort in the record of `stages.implementer`, whose usage is the row's cost), the prompt's digest (`prompt.sha256`), the result. The reader reads `mode` first and then `state` alone, never a step's result: `passed` is a pass, `failed` is a fail, `stopped` is no result. A no-result row is run again once; a second stop stays in the reading as no result; the usage of a no-result row counts in the reading's cost. A record without a stage is a validity row: a case is valid when its row at `base` ends `failed` and its row at `head` ends `passed`; a case with another pair counts in no reading. A suite value measures implementing to given tests, the easier half of the same work (the other half is writing the tests from the page): the read-out prints that beside it. A reading runs alone on the host: a build that waits on the build lock spends the stage's bound.
