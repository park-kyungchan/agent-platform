`ap --version` (and `ap version`) prints one line `ap <Cargo package version> <40-hex commit>[-dirty]`, or `unknown` for the commit when Git was unavailable at build time (`specs/ap/verbs.md` R3).
The install of `ap` is `ap deliver` (`specs/ap/deliver.md`; the timer `ap-deliver.timer`). `scripts/install-ap.sh` is the step it calls, run by hand only for the repairs `deploy/README.md` names: `check` compares the installed binary (`AP_INSTALL_DIR`, default `/usr/local/bin`) with `origin/main`, `install <expected commit>` builds from a detached worktree of that exact commit, a new directory of mode 0700 under the build base `AP_INSTALL_BUILD_DIR` (default `/var/lib/agent-platform/build`, never under `/tmp` or `$TMPDIR`, so no other local account can give Cargo a `.cargo/config.toml`), and installs it after verifying the staged and installed `--version` report exactly that commit, and `rollback <before-file>` restores a backup.
For `install`, `origin/main` means the local ref, so run `git fetch` first; the previous binary is backed up as `ap.before-<first 7 hex of its sha256>` in `AP_BACKUP_DIR` (default `/var/lib/agent-platform/install`), and `rollback` accepts only that name in that directory and prints the restored version (or `no_version_output`). The script lock is `AP_INSTALL_LOCK` (default `/run/lock/ap-install.lock`). `install` creates an absent build base and its missing parents with mode 0700; it refuses `build_dir_unsafe@install-ap.sh:<line>: <component>` when the base is not absolute or a component from `/` to the base (read as it stands, never through a link) is a symbolic link, not a directory, owned by neither root nor the running user, or writable by group or other (a sticky directory such as `/tmp` counts), naming the deepest such component, and `build_dir_unusable` when the base cannot be created or cleared. Under `AP_INSTALL_LOCK` it removes every entry of the base (the worktree of an install killed before its cleanup), so a run by hand with the default base uses the default lock or stops the timer first (`deploy/README.md`).

## The gate

`ap gate < request.json` waits on ONE pull request's head until its required checks are done, and the automatic review too when the request names its reviewer, and prints one JSON answer on stdout. It reads GitHub through `gh api graphql` (the caller's `gh` login) and decides nothing a person decides: it resolves no thread, posts no status, merges nothing and calls no store. Its only writes are `gh pr ready` on a draft (once) and the one toggle below.

The request: `repository` (`owner/name`), `pull_request` (number), optional `head` (40 hex: the head the caller expects), `autoreview` (the login of an automatic reviewer whose comment carries the marker, for example `chatgpt-codex-connector[bot]`; absent or `false`, the default since 2026-11-17: no automatic reviewer is waited for, because the review of a unit is its `verifier` stage), `check_minutes` (default 90) and `autoreview_minutes` (default 40), each 1 to 1440. Another member, or a malformed one, refuses `invalid_input` with exit 2 before any read: `{"error":{"code","field","detail"}}` on stderr.

It reads every 30 seconds. The head it waits on is the one GitHub reports at the first reading. In order:
1. Merged or closed (at any reading) ends `merged` or `closed`. A caller's `head` that differs from GitHub's ends `head_differs` (`expected` names the caller's). A head that moves later ends `head_moved` (`head_now`). A draft is marked ready once; a failed mark ends `ready_failed`.
2. The required checks, judged at every reading, also while the gate waits for the review: every entry on the head's commit whose `isRequired` is true, except the status `lead-review` (a `StatusContext` of that context: the output of the Lead's accept, not a check that precedes the review, so a revoked or pending acceptance never blocks the gate; a check run of that name is judged like any other), over every page (a reading that could not be completed is no reading). One that completed with any conclusion but `SUCCESS`, or a status that is not `SUCCESS` or pending, ends `check_failed` with `failed_check: {name, state, run}`. None yet, or one pending, waits; at the bound of the phase (`check_minutes`, or `autoreview_minutes` once the review wait began) it ends `check_timeout`. A repository without a required check ends `check_timeout`.
3. The automatic review (only when `autoreview` names a login; skipped when it is absent or `false`): the marker `codex-review-state:v1 {…}` counts only in a comment of that login (a bot's GraphQL login gets `[bot]`, so a user of the same name does not count); the last such comment's `code_review` is read, from the last occurrence in that comment that parses. The marker is looked for in the last 100 comments. When the checks have passed and it names another commit (or none), the gate marks the pull request draft and ready ONCE, because a push to a ready pull request is not reviewed; not when the gate itself just marked a draft ready. It ends `passed` when `commit_sha` is the head and `status` is `completed`, and also at `autoreview_minutes`: the time limit passing is not a failure, `autoreview.state` says `timeout`.

The answer: `end`, `repository`, `pull_request`, `head`, `marked_ready`, `checks` (`[{name, state, run}]`: the judged entries, then the status `lead-review` with its state and `judged: false` when the head has one, required or not), `autoreview` (`login`, `state`: `completed`, `timeout`, `waiting` when the gate ended before it, or `off`; `commit`, `has_unresolved_findings` as the marker says, `toggled`, `threads_on_head`: the number of review threads, resolved or not, whose first comment is the automatic reviewer's and was made on the head commit (the comment's `originalCommit`); `null` when the threads could not be read or no reviewer is named), `threads` (every unresolved review thread: `id`, `path`, `line`, `author`, `answered`: its last comment is not the automatic reviewer's, `comments`: its number of comments; `null` when it could not be read), and `failed_check`, `expected`, `head_now`, `left_draft` (a toggle whose ready mark failed three times) or `unreadable` with their ends. `answered` is true for every thread when no reviewer is named. `passed` with exit 0 also covers a review that reached its time limit and a review with unresolved findings: the caller reads `autoreview.state`, `has_unresolved_findings`, `threads_on_head` and `threads`: the marker's flag does not change when a person answers and resolves a thread, the threads do. `ap gate` decides nothing of this and writes nothing more. Exit by end: 0 `passed`; 10 `merged`, `closed`, `head_differs`, `head_moved`; 11 `check_failed`, `check_timeout`; 12 `ready_failed`, `github_unreadable` (`unreadable` names the cause: `not_found`, `no_login` or `gh_not_started` end at the first reading; `no_answer` when a reading still failed at the bound of the phase).

## One review

`ap review start|close|revoke` reads one JSON object on stdin and writes
one JSON answer; a refusal is `{"error":{"code","field","detail"}}` on stderr with exit 3.
Every path is absolute. Optional `store` forwards `--store` to every `ont` call.
The review object owns the verdict; `lead-review` is a derived commit status.
The rulesets of the three platform repositories require it beside `rust`.

`start` reads and hashes a regular prompt file below `/home/palantirkc/work/`.
With a pull request, it checks that the request is open at exactly `head`.
Each optional run must exist, belong to the task and occur once. It applies
`start_review` with a stable request id based on task key, kind, head and prompt
hash, returning `status: started`, `outcome: applied`, the complete `review` id
and `prompt_sha256`. Optional integer `attempt` (2 to 99) appends a newline and
that number to the digest input; omit it for the first attempt. A repeated request
reads the review and returns `outcome: already_applied` only while it is running.
A closed review is refused with `review_already_closed`; retry with a new `attempt`.
It does not launch a reviewer. Example stdin for `ap review start`:

```json
{"task_dir":"/home/palantirkc/work/example","kind":"packet","head":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","base":"bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb","repository":"owner/repo","pull_request":12,"runs":[{"object_type":"worker_run","namespace":{"instance":"vps://palantirkc","account":"root"},"native_key":"run-key"}],"model":"reviewer-model","effort":"high","prompt":"/home/palantirkc/work/example/prompt.md"}
```

`close` reads a regular report file below the work root, at most 1 MiB. Its
first line must be exactly `Verdict: accept` or `Verdict: repair`. It hashes the
bytes and applies `close_review`; optional `account` and `session` are recorded.
Alternatively, supply `verdict: abandoned` with no report. The answer contains
`status: closed`, `verdict` and `report_sha256` (null for abandoned). The stable
close request id hashes the review key and report hash (`abandoned` without a
report). Example stdin for `ap review close`:

```json
{"review":{"object_type":"review","namespace":{"instance":"vps://palantirkc","account":"root"},"native_key":"review-key"},"report":"/home/palantirkc/work/example/report.md","account":"b","session":"reviewer-session"}
```

`revoke` reads a review with a repository and head. When its `status` is
`closed` it applies `revoke_review` with the reason, under the request id
`rv-revoke-` and the first 40 hex of the SHA-256 of the review's key, the same
for every revoke of that review; a refusal or a failure of the store ends the
command with `store_refused` or `store_answer_unreadable` and nothing is posted.
When the `status` already is `revoked` it applies nothing. Only then does it post
`lead-review=failure` with `revoked: <reason>`. The object changes before the
status, because the store is what a later reader asks: a come-back of `ap unit`
and `start_install` read `status: closed`, so a revoked review is not found
again, while a status alone would be overwritten by the next `success`. A crash
between the two leaves a revoked object and no posted failure; the repeated
command finds `revoked` and posts it. A running review is not changed. The
reason must contain text and fit within 100 UTF-8 bytes. It returns
`status: revoked` and `head`. Example stdin for `ap review revoke`:

```json
{"review":{"object_type":"review","namespace":{"instance":"vps://palantirkc","account":"root"},"native_key":"review-key"},"reason":"Report missed a changed path"}
```

Refusals (local checks precede writes and status posts):

- `invalid_input`: malformed object, id, path, run list, reason or explicit verdict; field identifies the member.
- `review_prompt_unreadable`: prompt is not a readable regular file below the work root.
- `review_head_differs`: pull request is closed or has another head.
- `review_run_unknown`: a start run cannot be read as the exact current object.
- `review_run_of_other_task`: a run supplied to `start` belongs to another task.
- `review_already_closed`: `start` repeated after its review closed; repeat with a new `attempt`.
- `store_refused`: the store refused an attempted action; detail carries its codes; no retry occurs.
- `review_report_unreadable`: close report is unreadable, outside the work root or larger than 1 MiB.
- `review_report_lacks_verdict`: the report's first line is not one of the two exact verdict lines.
- `review_not_accepting`: required review state or evidence is absent; detail names the first failing member.
- `store_review_unreadable`: the exact review's current observation cannot be read.
- `store_answer_unreadable`: an action reply is malformed or does not confirm the expected create.
- `process_failed`: an external command failed or returned unreadable Git output; no automatic retry occurs.
- `io_error`: stdin or the caller's working directory cannot be read.
- `input_too_large`: stdin exceeds 1 MiB.
- `usage`: exactly one supported verb is required.

## The page's block

A page may hold a typed block: the write set and the checks of the unit, as data that code tested in this repository evaluates, instead of a line `Write set:` and an acceptance executable written for the unit. The block is the text between a line that is exactly three backticks followed by `unit` and the next line that is exactly three backticks (a line with anything else on it, or a carriage return, is no such line); it must parse as ONE JSON object. A page has no block when it holds no opening line.

Members: `unit` (required; 1 to 40 characters of `A-Z`, `a-z`, `0-9`, `-`), `write_set` (required; 1 to 40 patterns, each a nonempty string without a comma and without a space at its start or end, matched as a pattern of the line `Write set:` is: exactly the path, or a trailing `/**` for the descendants, not the directory itself), `checks` (optional, below) `repository` (`owner/name`), `branch` (a branch name as the request's `branch`), `item` (as the request's `item`), `merge` (a boolean), `implementer` and `verifier` (each an object: `model` and `effort`, nonempty strings, and optional `runtime`, `permission_mode` (nonempty strings) and `timeout_seconds` (an integer above 0); no other member), all read by `ap unit <page>` and required there ("A unit from its page"; `ap accept` and a request on stdin do not need them), and `tier` (1 to 40 characters), read and not used by any verb. `checks` holds any of four lists of at most 40 entries each; "the diff" is everywhere the change from the merge base of `origin/main` and `HEAD` to `HEAD`, and a path pattern is a pattern of the write set:

| List | An entry | It holds when |
| --- | --- | --- |
| `unchanged` | a path pattern | no changed path matches it |
| `adds` | `{"path": <pattern>, "words": [<text>, ...]}` (at least one word) | for each word, at least one ADDED line of the diff of the paths the pattern matches contains the word literally (a word that is only in a removed line, or only in an added line of another path, does not count; a pattern that matches no changed path fails every word) |
| `holds` | `{"path": <exact path>, "text": <text>}` or `{"path": <exact path>, "exact": <text>}`, exactly one of the two | the file, read from the commit `HEAD` through Git as bytes (never from the working tree), contains the text, or is exactly the text's UTF-8 bytes; a path that is not a regular file of that commit (missing, a directory, a symbolic link) fails. The path has no empty component, no `.` and no `..` |
| `lines` | `{"path": <pattern>, "max": <n>, "min": <n>}`, `min` optional (default 0), both integers not negative, `min` not above `max` | the added plus removed lines of the diff of the matched paths are at most `max` and at least `min` |

A word or a text is 1 to 2,000 bytes without a line feed; `exact` may hold line feeds and is at most 65,536 bytes. The diff's changed paths are read with `git diff --no-renames --ignore-submodules=none --no-relative --name-only -z <merge base> HEAD` (`git --no-replace-objects`); added and removed lines, for `adds` and `lines` alike, per matched path with `-U0 --no-ext-diff --no-textconv` and the same three options (the lines of the hunks: a header, also the second of a typechange, is none). A binary file is a changed path, has no added line and counts as no line. No check runs a command of the page or of the repository: a check reads Git and files only.

Refusals of a block, in `ap unit` and `ap accept` alike, before any effect, with the field `page`: `page_block_invalid` with `detail` `{"reason": ..., "member": ...}`: `two_blocks` (two opening lines), `unclosed`, `not_an_object` (the text is not one JSON object, or an object holds a member twice), `unknown_member` (`member` names it; one inside `checks` is `checks.<name>`), `shape` (`member` names the member, a member inside `checks` as `checks.<list>`; also a required member that is missing; `implementer` and `verifier` are named whole, not by the member inside them) and `no_block` (`ap accept` only: the page has none); and `write_set_twice` (a block and a line `Write set:` in one page). With a block the page holds no line `Write set:`: the write set is the block's, for the step `write_set` and for the record, in the same form. A page without a block is read as before in `ap unit` (`write_set_missing` and the rest). A case call takes no part in this.

`ap accept <page>` evaluates a page's block in the current directory, which must be a Git worktree that knows `origin/main`. It refuses with exit 2, in the error form of the other verbs (`{"error":{"code","field","detail"}}` on stderr) and writes nothing: another number of arguments, or a relative path (`usage`); a page that cannot be read (`page_unreadable`); a page without a block, or a bad block or both a block and a line `Write set:` (above); a current directory that is no worktree (`not_a_worktree`, field `cwd`); `origin/main` unknown there (`origin_main_unknown`); a Git call that failed (`git_failed`). Otherwise it checks, in this order: `clean` (`git status --porcelain` prints nothing), `write_set` (every changed path is inside the write set), then the block's lists in the order `unchanged`, `adds`, `holds`, `lines`, each entry in its order. It prints one line `accept: FAILED: <kind>: <what>` per failed check (one per missing word of `adds`) and exits 1, or prints `accept: ok` and exits 0. It calls no network and no store. A unit call without `acceptance` evaluates the same lists by the same code ("One unit").

What a check reads, stated as the code does it: a `holds` path is given to Git as a pathspec (`git ls-tree -- <path>`), so a path that begins with `:` is read as pathspec magic and fails the check as "is not a regular file of HEAD"; the changed paths of the diff are read as UTF-8 by the step `write_set` of `ap unit` (a path that is not UTF-8 fails the Git call: `git_failed`) and lossily by `ap accept` and the step `acceptance` (each invalid byte read as U+FFFD, the path matched as that text); a Git answer above 1 MiB, the bound of every call's output, is a failed call and no check passes by it: `process_failed` (field `git`) from `ap accept` and from the step `acceptance` of `ap unit`, `git_failed` from the step `write_set`; the reason is not `shape` or any other reason of the block.

## One unit

`ap unit < request.json` takes ONE unit of work once from its page to the merge: worktree, one implementer stage, the pull request, the gate, the page's acceptance executable (or the checks of its block), the write set, one verifier stage, the `review` object, the status `lead-review`, the guarded merge, the removal of the worktree. It returns when the unit merged or when the first step that did not pass ended it, and prints the unit record on stdout. A request with the member `case` is a case call instead ("One case" below); a request without it is a unit call, as this section says. Exit 0 `merged`, or `accepted` when the request says not to merge; 3 `stopped` (the record names the step and the cause); 5 the record could not be written after it was claimed (stdout holds the last record). Exit 2 is a refusal before any effect, in the form of `ap run`: `{"error":{"code","field","detail"}}` on stderr, no record. Without `repair` it is one pass: at most one implementer and one verifier stage, no fixer, no round, no step repeated, no wait but the stage's own and the gate's; it never continues an earlier call's record. With `repair` a `Verdict: repair` gets ONE round: a fixer stage and one come-back ("The round" below). No path accepts without the verdict of a model: every call has a verifier stage or the answer of an earlier one, and the command never writes a verdict itself.

The request: `repository` (`owner/name`), `clone` (the local clone whose `origin` is the repository), `worktree` (the path of the unit's worktree), `branch` (a new branch), `task_key` (the store's task the `review` hangs on, `^[a-z0-9][a-z0-9-]{0,63}$`; not derived from a directory), `page` (the packet: a regular file with exactly one line beginning `Write set:` at the first column, comma-separated patterns matched as exact paths or as a directory with a trailing `/**` (the descendants, not the directory itself), or a typed block and no such line: "The page's block"), `out` (the prefix of every file of the call), `acceptance` (optional: the page's acceptance executable; without it the page must hold a block, whose `checks` the step `acceptance` evaluates), `implementer` and `verifier` (each `account`, `model`, `effort`, `prompt`, optional `runtime` (`claude` by default; `codex` for the implementer only, `agy` for the verifier only and `muse` for either block; a Codex, Muse or agy block must state `permission_mode`: a verifier with `runtime: "codex"`, an implementer with `runtime: "agy"` and a Codex, Muse or agy stage without a stated mode are refused here, before any effect), `permission_mode` (default `auto` for a stage on Claude Code only: a block on Codex, Muse Code or agy states its own, which `ap run` admits as `bypassPermissions` alone), `timeout_seconds`, `next_accounts`, `env`, `resume` and `compact_window` (the window of its Claude stage: "One stage"; a value `ap run` would refuse is refused by the call before any effect, as `implementer.compact_window` or `verifier.compact_window`), given to `ap run` as they are: a stage cut before it did any work, and a verifier cut at any point, runs again on the next account inside the same stage and its one record; with `resume` (`{"record": "<path>"}`) a repaired head returns to the session that reviewed it, the Lead's prompt file is the next message to that session and the block of facts is appended as before), optional `acceptance_seconds` (1 to 86400, default 2700), `gate` (`autoreview`, `check_minutes`, `autoreview_minutes` as `ap gate` takes them), `store` (forwarded to every `ont` call), `merge` (false: the call ends `accepted` after the review is closed, with no status), `pull_request` (a come-back after a repair by hand: steps 2 to 4 are skipped and the existing `worktree` on `branch` is used) and `verdict` (with `pull_request` only, instead of `verifier`: the answer of an earlier reviewer stage; step 8 is skipped and the file is checked against the head), `repair` (a unit call without `pull_request` and `verdict` only: `prompt` and `verifier_prompt`, absolute paths of regular files outside `worktree`, and `timeout_seconds`, all three required; "The round" below), `judge_threads` (a boolean, `false` the same as absent: the verifier judges the automatic reviewer's threads, "The threads" below, which needs `gate.autoreview` to name that reviewer's login; without `true` every record, file, output and exit code is what it is without the member), and `item` (a string of at most 60 bytes: the key of an item of the task's board, "The item" below; a case call refuses the member and never needs it). `verdict` is taken only when `<verdict>.run.json` lies beside it: an `ap run` record with role `reviewer`, state `ok`, `answer.path` and `answer.sha256` equal to the file and its digest, and a prompt file (below the work root) that still has the recorded digest. Every path is absolute; `page`, `out` and `verdict` lie below the work root (`/home/palantirkc/work/`), because the `review` object records them. `acceptance`, when given, and the verifier's prompt lie outside `worktree`.

The use of `merge: false`: a unit with a real effect, where the Lead reads the diff after the verifier accepted and before the merge. The come-back with `pull_request` and `verdict` (the verifier's answer `<out>.verifier.md`) then posts the status and merges; it uses the review the first call closed (step `review` below). The same come-back finishes a call that stopped at `status` or `merge`.

Refusals (exit 2, before any effect: no file, worktree, branch, process or network call): `usage` with the field `op` (a request with a member `op`, before any other check, a case call's too: the op of `ap unit add|amend|ready|drop` is the first argument, `specs/ap/unit.md` R1); `invalid_input` (an unknown or malformed member, a relative path, neither or both of `verifier` and `verdict`; `field` names the member, `implementer.prompt` for a nested one); `outside_work_root`; `inside_worktree` (`acceptance` or the verifier's prompt); `page_unreadable`; `page_block_invalid` and `write_set_twice` (the page's block, "The page's block"); `write_set_missing` (a page without a block: no line `Write set:`, or more than one, or one without a pattern); `invalid_input` with the field `acceptance` (no `acceptance` and a page without a block; it comes after the page's own refusals above); `prompt_unreadable` (also a verifier prompt that leaves no room for the block of facts within `ap run`'s 1 MiB); `acceptance_unreadable` (not a regular executable file); `verdict_unreadable` (no file, or no record beside it as above); `out_exists` (`<out>.unit.json` or another file of the call exists); `out_unwritable` (the record cannot be created); `worktree_exists` (a fresh call whose `worktree` exists); `worktree_missing` (a come-back whose `worktree` is not a directory). `invalid_input` also for a `judge_threads` that is not a boolean and for an `item` that is not a string of 1 to 60 bytes (a case call refuses both members). After these checks the item is resolved ("The item" below); its refusals have the same form (exit 2, field `item`, no record). With `repair`: `invalid_input` (`repair` malformed or beside `pull_request` or `verdict`, `field` `repair` or `repair.<member>`; a case call refuses the member); `inside_worktree` (`repair.prompt`, `repair.verifier_prompt`); `prompt_unreadable` (either file, also one that leaves no room for its block of facts); `out_exists` also for `<out>.fixer.md`, `<out>.fixer.prompt.md` and every file of the call `<out>-2`, `<out>-2.unit.json` included; the fixer's request is judged by `ap run`'s code as a fresh fixer (field `repair.timeout_seconds`, `repair.prompt`), its prompt as the fixer will get it: `repair.prompt` followed by its block of facts (e.g. `out_named_in_prompt` with the field `repair.prompt` for a `page` whose path holds `<out>.fixer.md`), and the come-back's verifier stage as a fresh reviewer with `repair.verifier_prompt` and the answer `<out>-2.verifier.md` (its code with the field `repair.verifier_prompt`, e.g. `out_named_in_prompt` for a prompt that names that answer). Every member of `implementer` and `verifier` that `ap run` can judge before the stage's worktree exists (its shape, `permission_mode`, `timeout_seconds`, `model`, `effort`, `next_accounts`, `resume`, the account rules, the prompt, the stage's files) is judged here by `ap run`'s own code, with its code and the field prefixed (`verifier.timeout_seconds`); what only the stage's start shows ends the call at that stage with the cause `stage_refused`.

The item (`item`). A task of the store can have a board: the order of its items (`board`, `item` and `objective` of version 9 of the work schema, `ontology/README.md`). At the start of EVERY unit call (a first call, a come-back with `pull_request`, a call with `verdict`, the come-back of a round), after the checks above and before any other effect (no worktree, no call to GitHub, no stage, no other store write), the command reads the board of `task_key` and resolves the item:

- The task has no board: a request without `item` runs exactly as without the member (every record, file, output and exit code); a request with `item` is refused `item_not_ordered`.
- The task has a board and the request no `item`: `item_required`.
- No item of the task has the key: `item_unknown`. The item is `done`: `item_done`; `dropped`: `item_dropped`.
- The item's objective is retired: `objective_not_current`. The objective's source row is not `current`: `objective_source_superseded`.
- The item is `in_work` and its `repository` and `branch` are the request's: the call goes on (a come-back, a round, a call repeated after a death); else `item_of_another_unit`.
- The item is `queued`: the command applies `start_item` with the request's `repository` and `branch`. The store's refusal `item_not_ordered` (the board does not name the item) refuses the call with that code; any other refusal or failure refuses it with `item_unwritten` (`detail` `{"code"}`: the store's first code, or the failure's). The request id holds the item's and the board's revisions, so after a `release_item` a new call for the same item, repository and branch is a new request and starts the item again.

A failed read of the store refuses the call with its code (`store_answer_unreadable`, `process_failed`), with or without `item`. The record gets `item` (`key`, the item's `id`, `objective` with its `name` and `id`), and the verifier's block of facts gets the item's key, title, statement and first use and the objective's name and statement; without `item` the block is byte for byte the one above. Immediately before `gh pr merge` the item is read again: `dropped` or `done` stops the call at `merge` with `item_dropped` or `item_done`, and nothing is merged. After the merge the command applies `close_item` with the accepting review of the step `review`: applied, the record's `item` gets `closed: true`; a refusal or a failure gives `closed: false` and `code` (the store's first code, or the failure's), the state stays `merged` and the exit code 0, and `close_item` applied later by hand succeeds, because the item is still `in_work`. A call that does not merge (`merge: false`, a stop) closes and releases nothing: the item stays `in_work` for its come-back.

The sequence. Each step is recorded before it begins and after it ends; the first that does not pass ends the call with `state: stopped`, `stopped_at` (the step) and `cause` (`io_error` when a file of the call cannot be created):

| Step | What it does | Causes that stop it |
| --- | --- | --- |
| `worktree` | `git fetch origin main` in `clone`; the worktree and `branch` from the fetched `origin/main` (recorded as `base` until step `write_set`) | `fetch_failed`, `worktree_failed` |
| `implementer` | ONE `ap run` stage, role `implementer`, cwd `worktree`, the Lead's prompt file unchanged, no `expect`; answer `<out>.implementer.md`, which is the unit's report: the Lead's prompt asks for the report as the final message | `stage_refused`, or the stage's state when it is not `ok` (`cut`, `timeout`, `no_result`, `failed`); `stage_record_unwritten` (the state is `ok` and `ap run` exited with another status than 0: the stage's final record could not be written; the same for the verifier and the fixer) |
| `pull_request` | the one open pull request of `branch` against `main` | `no_pull_request`, `pull_request_ambiguous`, `github_unreadable` |
| `gate` | `ap gate`'s code on that pull request, with `head` the pull request's head read at `pull_request` (none in a come-back); its answer `<out>.gate.json`; its `head` becomes the unit's head. The step's `detail` is `{"lead_review": <state>}`: the state of the status `lead-review` the gate lists and does not judge, or null, so that a revoked acceptance is seen | the gate's end when it is not `passed`; `unresolved_findings` (the marker says `has_unresolved_findings: true` for the head and `threads_on_head` is 0 or `null`: the findings are not visible as threads, so nothing shows that anyone answered them; with `judge_threads` and `threads_on_head` 0 it does not stop when at least one thread is given to the verifier, an earlier thread of the reviewer that the marker still names: "The threads"); `unresolved_threads` (one or more, or not readable: where the marker says true and the reviewer has threads on the head, the threads decide, so a finding the Lead answered and resolved without a push passes; with `judge_threads` a thread given to the verifier does not stop the step and the detail lists only the others) |
| `acceptance` | `acceptance` in `worktree`, no arguments, stdin `/dev/null`, under `timeout -k 10 <acceptance_seconds>`; stdout and stderr to `<out>.accept.log`. Without `acceptance`: after the same conditions (the clean worktree, `HEAD` the gate's head) and a `git fetch origin main` in `clone` as the step `write_set` makes it, the `checks` of the page's block (the bytes of the page read at admission, whose digest the record holds; the page is not read again) are evaluated in process by the code of `ap accept`, except the kinds `clean` and `write_set`, which the step's own conditions and the step `write_set` hold; the lines of `ap accept` (`accept: ok`, or `accept: FAILED: <kind>: <what>` per failed check) go to `<out>.accept.log`. A request with `acceptance` runs the executable only: the block's checks are not evaluated, and the block's write set is still the page's | `fetch_failed` and `git_failed` (without `acceptance`), `acceptance_failed` (without `acceptance`: `detail` `{"checks": [<the failed lines without `accept: FAILED: `, at most ten>], "count": <number>}`), `digest_differs`, `worktree_dirty`, `head_differs`, `git_failed`, `acceptance_failed` (`detail`: `{"exit": <code>}`, null when no exit was read; an executable that ignores SIGTERM is killed 10 s after the bound and ends here with exit 137), `acceptance_timeout` (exit 124, also when the executable itself exits 124) |
| `write_set` | `git fetch origin main` in `clone`, in a fresh call too; the fetched `origin/main` must be an ancestor of the head (the rulesets require an up-to-date branch, so the merge would fail after the verifier was paid) and becomes `base`; the changed paths of `git diff <base> <head>` (`git --no-replace-objects` with `diff --no-renames --ignore-submodules=none --no-relative --name-only -z`, paths read NUL-separated) against the page's write set | `fetch_failed`, `git_failed`, `behind_main` (`detail`: the commit of `origin/main`), `path_outside_write_set` (at most ten paths and the count in `detail`) |
| `verifier` | ONE `ap run` stage, role `reviewer`, cwd `worktree`, `expect.first_line` `Verdict: *`, prompt `<out>.verifier.prompt.md`: the Lead's prompt file unchanged followed by a block of facts (repository, pull request, head, the diff command, the paths of the gate's answer and of the acceptance output, and with `judge_threads` each thread given to it: id, path and line; with none the block is the same as without the member); answer `<out>.verifier.md`. Come-back with `verdict`: skipped, that file is the report and `stages.verifier` names the record beside it. For either path, the first line is exactly `Verdict: accept` or `Verdict: repair`; the second line must contain exactly one run of 40 hexadecimal characters, outside any longer run of letters or digits, equal to the head. Labels and punctuation around it are ignored. A report with anything before its verdict line ends the stage `no_result` (`unmet: first_line`); the caller resumes the session with the required form | `digest_differs`, `worktree_dirty`, `head_differs`, `git_failed`, `stage_refused`, a state not `ok`, `stage_record_unwritten`, `verdict_repair`, `verdict_unreadable`, `verdict_head_differs` (the second line has no such run, has two or more, or its one run differs from the head); with `judge_threads`, after the head rule of an accept, `threads_unjudged` and `thread_blocking` ("The threads") |
| `review` | when the store holds a closed (not revoked: `status` is `closed`) review of kind `packet` with verdict `accept` for this task, repository and head whose report digest is the report's, that review is used: its id goes into the record, `detail` `{"reused": true}`, and no second one starts. Otherwise `ap review start` (kind `packet`, the head, `base`, the pull request; `model`, `effort` and `prompt` of the verifier's `ap run` record) and `ap review close` with the report and that record's `account` and `session` (`detail` `{"reused": false}`) | `verdict_unreadable` (the record of the verifier cannot be read), the codes of `ap review` (`review_head_differs`, `store_refused`, …) |
| `status` | the pull request is read open against `main` at the head; with `judge_threads` the threads of the record are resolved ("The threads"); then `lead-review=success` on the head through the code of `ap review` | `github_unreadable`, `head_differs`, `thread_changed`, `thread_not_resolved`, `status_failed` |
| `merge` | with `item`, first the item is read again; then `gh pr merge --merge --match-head-commit <head>`, then a read of the pull request, also after a call that failed: `merged` only when it says merged at the head and names the merge commit. A failed call whose read shows the pull request open is tried once more, 5 seconds later and read again, only when the head's statuses (`gh api repos/<repository>/commits/<head>/status`) read `lead-review` `success`: GitHub may refuse a merge for a status it has not yet taken | `item_dropped`, `item_done` (the item was dropped or closed since the call began: nothing is merged; a failed read stops with its code, e.g. `store_answer_unreadable`), `merge_failed` (the last call failed; `detail` `{state, reply}`, the reply redacted as below), `merge_unconfirmed` (the last call succeeded) |
| `cleanup` | in `clone`: `git fetch origin main`, `git worktree remove` without force, then, only after the removal, `git branch -d` (the branch tracks `origin/main`, which now holds the merge). The remote branch is not touched: the repositories delete the branch of a merged pull request themselves | none: a failure is recorded in the step (`result: failed`, `detail` `{fetch, worktree: removed|failed, branch: deleted|failed|kept}`) and the state stays `merged` |

Three rules of every step. The implementer's and the fixer's `ap run` requests carry `git_author: true`, as in `ap unit run`, so their commits name the stage as author and committer. A `gh` call that fails keeps its reply (its standard output, else its standard error) in the stop's `detail` as `reply` (`github_unreadable`, `status_failed`, `merge_failed`): every token (`gh[opsur]_…`, `github_pat_…`), the user and password of a URL, a `…TOKEN=` value and the value after `token` or `Bearer` is replaced by `<redacted>`, then the text is cut to its last 200 bytes at a character boundary. A `git fetch origin main` that fails with Git's `cannot lock ref` (another fetch into the same clone at that moment) is tried once more after one second; any other failure, or a second one, is `fetch_failed`.

The round (`repair`). When the step `verifier` ends with `verdict_repair` and the report's second line names the head by the rule of the `verifier` row (and only then: a `Verdict: repair` without that line ends with `verdict_repair` and no round, and every other end, `verdict_unreadable` and `verdict_head_differs` included, ends the call as above), the record is completed as above (`state: stopped`, `stopped_at: verifier`, `cause: verdict_repair`) with `repair.fixer` (`<out>.fixer.md.run.json`) and `repair.next` (`<out>-2.unit.json`) in the same save, before anything else starts; when that save fails the call ends with exit 5 as any call whose record cannot be written, and no fixer starts. Then ONE `ap run` stage, role `fixer`, resumes the session of this call's implementer record with that record's runtime, model and effort, on the accounts of the `implementer` block (its `account` and `next_accounts`, so a fixer cut by a usage limit goes on as a new session on the next, as "One stage" says); of the `implementer` block it keeps every other member except `resume` (so a stage on the Codex CLI states its own `permission_mode` or is refused); cwd `worktree`, `timeout_seconds` of `repair`; its prompt `<out>.fixer.prompt.md` is `repair.prompt` unchanged followed by a block of facts (repository, pull request, the head the verifier judged, the path of the verifier's report, the path of the page); its answer `<out>.fixer.md`. `repair.state` is the stage's state. Not `ok`: the call prints the first record and exits 3. `ok`: when the worktree's `HEAD` is not the judged head (the fixer committed), the call reads the pull request every 5 seconds through the code of `ap review` until GitHub reports that `HEAD` as its head, for at most 120 seconds (a come-back that begins right after a push would read the old head first and end `head_moved`); then it goes on as the come-back a Lead would start, through the code of a come-back call as it is: the same request with `pull_request` (this unit's), `out` `<out>-2`, `verifier.prompt` `repair.verifier_prompt`, `verifier.resume` naming this call's verifier record, the same `merge` and `judge_threads` and no `repair`; it writes `<out>-2.unit.json` and its files, and the process prints THAT record and exits with ITS code. So a second `Verdict: repair` stops the come-back (no second round), and a verdict that names the old head after the fixer pushed ends it `verdict_head_differs`. Where the round ends before the come-back for another reason, the first record says why in `repair.cause` and `repair.detail` and the call exits 3: `digest_differs` (`{"path"}`: a file of `repair` changed), `head_not_seen` (`{"head"}`: the bound passed before GitHub reported the worktree's head), `git_failed`, `stage_refused` (`{"code","field"}` of `ap run`), `stage_record_unwritten`, `io_error`, `come_back_refused` (`{"code","field"}`: the come-back's request was refused, e.g. `worktree_missing`).

The threads (`judge_threads: true`). At the step `gate` a thread is *given to the verifier* when it is unresolved, has exactly one comment (`comments` of the gate's answer), and that comment's author is the login the gate's answer names in `autoreview.login` (compared as the gate compares it, so with `autoreview` absent or `false` none is); with `verdict`, only when the report also holds exactly one line for its id whose word is not `blocking`. A given thread does not stop the step; every other unresolved thread stops it with `unresolved_threads` as without the member, and `unresolved_findings` stops as before, except in one case: the marker says `has_unresolved_findings: true`, `threads_on_head` is 0 and at least one thread is given (in a call with `verifier` and in a call with `verdict` alike). The marker stays true while an earlier thread of the reviewer is open, so there the given threads are the finding it names and the step does not stop with `unresolved_findings`; they go on as below (named in the record and in the verifier's facts, judged, resolved inside the step `status`). `unresolved_findings` still stops when no thread is given, when `threads_on_head` is `null`, and in a call without the member or with `false`; an unresolved thread that is not given stops with `unresolved_threads` also beside given threads and a true marker (the marker's stop is judged first, so with a true marker, `threads_on_head` 0 and no thread given, the cause is `unresolved_findings`). What the runner then does not see: a finding of the reviewer that is neither a thread on the head nor an open earlier thread. The record gets `threads`: one entry per given thread, `id`, `path`, `line` (an empty list when none is given). After the head rule of a `Verdict: accept` (of the stage, or of `verdict`), the report holds for each given id exactly one line that is exactly `Thread <id>: <word>`, the word `fixed`, `wrong`, `note` or `blocking`: an id with no such line, with more than one or with another word stops the call at `verifier` with `threads_unjudged`; else a `blocking` word stops it with `thread_blocking` (the detail of each: `{"threads": [<ids>]}`); else each entry gets `word`. A `Verdict: repair` is read as without the member, its thread lines not inspected; no cause of the threads starts a round. The come-back of a round keeps the member: its gate reads the threads anew on the new head, and the old threads and new ones are judged by its verifier. Inside the step `status`, after the pull request was read open at the head and before the status is posted, each id of `threads` is read again (`gh api graphql`, the thread's `isResolved` and its number of comments): one that is resolved already or no longer has exactly one comment stops the call with `thread_changed`, and nothing is resolved; else each is resolved (`resolveReviewThread`) and read back: one that does not read resolved stops it with `thread_not_resolved`, and no status is posted; the others get `resolved: true`. A call that does not reach the step `status` (also one with `merge: false`) resolves nothing. The command writes no comment and no reply, resolves no thread it did not record and never unresolves one.

The status is posted only after all of: the gate ended `passed` with no unresolved finding (a marker that says true for the head counts as one unless the reviewer's threads on the head are visible, and then only an unresolved thread stops; with `judge_threads`, nor when `threads_on_head` is 0 and a thread is given to the verifier) and no unresolved thread; the acceptance executable exited 0, or, without `acceptance`, the block's checks hold; every changed path is inside the write set and the branch contains the fetched `main`; with `judge_threads` every given thread judged by the report and none `blocking`, and each resolved; one `review` object is closed with `Verdict: accept` for the head, by a report of a model (the answer of the verifier stage of this call, or a `verdict` admitted as above) whose first line is exactly `Verdict: accept` and whose second line meets the head rule in the `verifier` row. One accepted head has one review object. Acceptance and verifier start only while `worktree` is clean and its `HEAD` is the head the gate passed; the review, the status and the merge name exactly that head. No `--admin`, no auto-merge, no force anywhere. Condition of use: the repository's `main` has no merge queue and auto-merge is off (true of the three platform repositories), so `gh pr merge` merges at once or fails; the command does not detect a merge queue. The `review` object owns the verdict; the status is derived from it, as in "One review". The page's write set is checked here: stages of `ap run` leave no `worker_run`.

What judges a stage cannot be changed by it: the SHA-256 of `acceptance` (without it the block's checks, which the call holds as read from the page at admission), of the verifier's prompt, of `verdict`, of `page` and of both files of `repair` are in the record before the implementer starts; a file whose digest differs when it is used ends the call (`digest_differs`). The verifier's prompt holds neither the implementer's answer nor its path.

The record `<out>.unit.json` is created exclusively before any effect (the claim, as in `ap run`) and replaced after every step through a temporary name: `repository, clone, worktree, branch, task_key, base, page{path,sha256} (the digest of the bytes read at admission, the ones a block is read from), write_set (the page's block's, or its line's), acceptance{path,sha256}|null (null when the request has none), verifier_prompt{path,sha256}|null, verdict_file{path,sha256}|null, merge, pull_request, head, review` (the complete id), `merge_commit, stages{implementer, verifier}` (the paths of their `ap run` records, written before the stage starts, or null), `files{gate, acceptance_output, report}, mode` (`"unit"`), only with `judge_threads: true` and from the step `gate`: `threads` (above), only with `item`: `item{key, id, objective{name, id}}` and after the merge `closed` (and `code`), "The item" below, only with `repair`: `repair{prompt{path,sha256}, verifier_prompt{path,sha256}}`, and after a `Verdict: repair` also `fixer`, `next`, `state`, and `cause`, `detail` (above), `state` (`running`, `merged`, `accepted`, `stopped`; `passed` and `failed` exist only in a case call, and so does exit 4), `step` (the step begun, null at the end), `stopped_at, cause, detail, steps` (each step done, in order: `name`, `result` (`passed`, `skipped`, `stopped`, `failed`), `start`, `end`, `detail`), `start, end`. No prompt or answer text and no credential. A unit record without `mode` is a unit call: it was written before the member existed. A killed call leaves this file naming the step begun; the Lead goes on by hand from it, or calls again with `pull_request` (and `verdict`, or `verifier` with `resume`) and a new `out`. Inside the call that starts the review the file shows step `review` with `review` null; the id is on disk from the save after that call returns.

### A unit from its page

`ap unit <page>` composes the request and the unit's two prompts from the page and one file of its task directory, then runs the unit exactly as a request on stdin does. `<page>` is the one argument, an absolute path; standard input is not read. `ap unit --compose-only <page>` does the composition of points 2 to 5 below with the refusals of points 1 to 4, writes no file, prints ONE JSON object `{"request", "prompt", "verify_prompt"}` (the request as an object, the two prompts as strings) on stdout and exits 0, with no other effect: no worktree, store, network call or record, and the request's admission is not run. `ap unit` with no argument reads a request on stdin as before; any other form of arguments is `usage` (exit 2, field `args`). A call from a page takes no `pull_request`, `verdict` or `resume`: those stay a request on stdin.

1. The refusals of the composition come before any effect and write nothing, in the form of the other refusals (exit 2): `page_unreadable` (field `page`); `units_unreadable` (field `page`: `units.json` is missing, not a regular file or unreadable); `invalid_input` with the field `units` (the file is not ONE JSON object); `page_block_invalid` (a page without a block: reason `no_block`; a member `repository`, `branch`, `item`, `merge`, `implementer` or `verifier` absent from the block: reason `shape` with the member); `page_section_missing` and `page_section_twice` (the page does not hold exactly one line that is exactly `## Unit notes`, and exactly one that is exactly `## Verifier questions`; `detail` is the heading); `invalid_input` with the field `units.<member>` for each unknown, missing or malformed member of `units.json`, and `units.clones` for a repository the file's `clones` does not name. The order: page, its block and sections, `units.json`, its members in the order of point 2, the clone, the accounts, then the composed request goes to the admission of a request on stdin. The admission refuses by its own rules and fields (`page`, `out_exists`, `outside_work_root`, a stage's refusal as `implementer.<member>` and the rest); a page's directory outside the work root is `outside_work_root`.
2. `units.json`, in the directory of the page (the task directory), is ONE JSON object with exactly these members: `task_key` (as the request's); `clones` (an object: a repository `owner/name` to the absolute path of its local clone); `accounts` (an object: a key to an array of one or more absolute account paths, the first the stage's `account`, the rest its `next_accounts`, so one account gives no `next_accounts`; a key is a runtime name, `claude`, `codex`, `muse` or `agy`, or a runtime, `/` and a role (`implementer`, `verifier`) or a model as the block names it (up to 40 bytes of letters, digits and `._-[]`, as `ap run` takes a model), such as `claude/verifier`, `claude/opus` or `claude/opus[1m]`; `<runtime>/fixer` is refused, the fixer having the implementer's accounts, and `<runtime>/reviewer` too, the verifier's key being `<runtime>/verifier`; a key that names neither a stage's role nor its model is not read, so a misspelled role falls to the model or runtime key; `codex` and `muse` keys exactly one account, as `ap run` takes them; to keep a model off an account, give the runtime key the safe list and name the models that may use the others, as in `{"claude": ["/root/.claude"], "claude/sonnet": ["<another account>", "/root/.claude"], "claude/verifier": ["/root/.claude"]}`, so a model no key names, `claude-opus-5-5` or `opus[1m]` as much as `opus`, takes the runtime's list); `timeouts` (an object `implementer`, `verifier`, `fixer`, each seconds from 1 to 86400); `compact_window` (an object: a model name to its window, an integer, read for a Claude stage only); `prompts` (an object `implementer`, `verifier`, `fix`, `second_look`, each the absolute path of a standing text); `judge_threads` (a boolean). A stage for which none of the three keys of point 4 is present is `units.accounts`.
3. The page's block, beside its members ("The page's block"): `implementer` and `verifier`, each `{"model", "effort"}` with optional `runtime` (default `claude`), `permission_mode` (passed to the request as it is; a block on `muse`, `codex` or `agy` that names none is composed with `bypassPermissions`, the one mode `ap run` admits for them: the Lead's decision, which reverses the earlier "the composition adds none", since a block on such a runtime that names a mode can name only that one; a stated mode stays as it is, so `ap run` still refuses another, and a Claude block that names none gets none) and `timeout_seconds` (replaces the `timeouts` value of that stage). The page holds exactly one section `## Unit notes` and exactly one section `## Verifier questions`: a section is every line after its heading line, with its line ends as the page has them, up to the next line that begins `## ` or the opening line of the block, or the end of the page.
4. The composed request: `repository`, `branch`, `item` and `merge` from the block; `clone` from `clones` by the repository; `task_key` and `judge_threads` from `units.json` (a page sets no `gate`, so a composed unit waits for no automatic reviewer and gives no thread to its verifier); `page` the argument; `out` `<task directory>/runs/U-<unit>`; `worktree` `<task directory>/wt/<repository name>-<unit in lower case>`; `implementer` and `verifier` each with `model`, `effort` and `runtime` of the block, `permission_mode` of the block when it states one, `bypassPermissions` for a `muse`, `codex` or `agy` block that states none, and absent otherwise, `account` and `next_accounts` from `accounts` by the first key present of `<runtime>/<role>`, `<runtime>/<model>` and `<runtime>` (so the role decides before the model, and both before the runtime; the fixer of a repair runs on the implementer's; `next_accounts` absent for one account), `timeout_seconds` of the block or else of `timeouts`, `compact_window` of `units.json` by the model for a Claude block (absent for another runtime and for a model it does not name) and `prompt` the composed file of point 5; `repair` with `prompt` the `fix` text, `verifier_prompt` the `second_look` text and `timeout_seconds` the `fixer` timeout. `runs/` and `wt/` are not made: the claim `<out>.unit.json` fails with `out_unwritable` when `runs/` does not exist. There is no `gate`, `store`, `acceptance` or `acceptance_seconds`: the page's block judges, as for a request without them.
5. The composed prompts. `<out>.prompt.md` is the standing `implementer` text (its last line ended by a line feed when it lacks one), one empty line, then the section `## Unit notes` without its heading, byte for byte; `<out>.verify.prompt.md` the same with the `verifier` text and `## Verifier questions`. In a standing text, and only there, `{page}`, `{unit}` and `{repository}` are replaced, in one pass, by the page's path, the block's `unit` and the block's `repository`; any other text in braces stays, and so does a placeholder inside a section. A standing text that cannot be read or is not UTF-8 is `prompt_unreadable` (field `units.prompts.<name>`). The composed request is written, as the JSON of the printed request, to `<out>.request.json`. The order of reads and writes: the page is read once, and the digest of those bytes is the record's `page`; the admission and the record's `verifier_prompt` take the composed prompts from memory, not from disk; the three paths join the `out_exists` scan, so an existing one refuses before any store write; after the claim `<out>.unit.json` the three files are the first thing created, each exclusively, and a failure ends the call at once `stopped` (`stopped_at` and the step `composed`, cause `io_error`, exit 3, as a file of a step). The record gets `composed`: `{request, prompt, verify_prompt}`, each `{path, sha256}`, the digests equal to the files' bytes; the record of the round's come-back `<out>-2.unit.json` gets `composed` with `request` alone, the first call's. A call from stdin writes no `composed`, and the record of a call from a page equals that of the same request on stdin in every other member.

A carried review is a verdict but not a round: neither the unit's `rounds` nor `ap status --indicators` counts it.

## One case

`ap unit < request.json` with the member `case` is a case call: it runs a past unit again, in a copy that holds only that unit's base, and judges it by the tests the unit was accepted with. One record says whether a stage of the named model made those tests pass; with no stage the call shows whether the case is valid. It is one pass, like a unit call: at most one stage, no fixer, no step repeated. It starts no `gh` and no `ont`, makes no network call and writes nothing outside `worktree` and the files of `out`; what the stage and the commands of the case do is theirs.

The case file (`evals/engineering/cases/<id>.json`, see `evals/README.md`), JSON with exactly these members: `id` (`^[a-z0-9][a-z0-9-]{0,63}$`; the file is `<id>.json`), `repository` (`owner/name`), `pull_request` (the merged pull request the case was taken from), `base` and `head` (40 hex digits: the first parent of the merge commit, and the accepted head), `tests` (a nonempty array of relative repository paths without `..`: every file that judges; the candidate gets them with their bytes at `head` and the evaluator restores them), `commands` (a nonempty array of argument arrays: what the evaluator runs in the copy, in order), `page_sha256` (64 hex digits: the page given to the candidate; its text is a host file and never enters this repository).

The request, exactly: `case` (the absolute path of the case file), `clone` (a local clone that holds `base` and `head`), `worktree` (the path of the case's copy; it must not exist), `page`, `out`, `acceptance` (the evaluator, `evals/engineering/evaluate`), optional `implementer` (the members of a stage of a unit call without `resume`, `runtime` included), optional `at` (`"base"`, the default, or `"head"`), optional `acceptance_seconds` (1 to 86400, default 2700). `at: "head"` together with `implementer` is refused (`invalid_input`, `at`): no stage ever works in a copy that holds the head. Every other member of a unit call (`repository`, `branch`, `task_key`, `verifier`, `verdict`, `gate`, `store`, `merge`, `pull_request`) is refused with `invalid_input` and its name.

Refusals (exit 2, before any effect, in the form of a unit call): those of a unit call that apply (`invalid_input`, `outside_work_root` for `page` and `out`, `inside_worktree` for `acceptance`, `page_unreadable`, `prompt_unreadable` (also a prompt that leaves no room for the block of facts), `acceptance_unreadable`, `out_exists`, `out_unwritable`, `worktree_exists`, and the stage's own, judged by `ap run`'s code with the prefix `implementer.`), and `case_unreadable` (`case` is not a regular file, not JSON, or a member is missing, unknown or malformed); `case_page_differs` (the SHA-256 of `page` is not `page_sha256`); `case_commit_missing` (`base` or `head` is not a commit of `clone`, or a path of `tests` is not a regular file at `head`: Git mode `100644` or `100755`, so a symbolic link, whose target would be the candidate's to change, is no judging file; `field` is `case.base`, `case.head` or `case.tests`). A case call's page needs no line `Write set:`.

The steps, each recorded before it begins and after it ends; no other step is in a case record:

| Step | What it does | How it ends |
| --- | --- | --- |
| `worktree` | creates `worktree` as a new Git repository with ONE commit and no remote: at `base` the tree of `base` with every path of `tests` holding its bytes (and mode) at `head`; at `head` the tree of `head`. Only the objects of that tree are copied out of `clone` (`pack-objects` into `unpack-objects`): the copy shares no object store with `clone` and names it nowhere, so no commit of `clone` can be reached from inside the copy. The commit is made with an identity given on the command line (`-c user.name=… -c user.email=…`), so it needs none from the host. Every `git` of this step runs with `GIT_NO_REPLACE_OBJECTS=1`: a `refs/replace/` entry of `clone` changes neither the tree nor a judging file of the copy | stops with `copy_failed` |
| `implementer` | only with `implementer`: ONE `ap run` stage, role `implementer`, cwd the copy; its prompt is `<out>.implementer.prompt.md`: the request's prompt file unchanged, followed by a block of facts (the page's path, the copy's path, the paths of `tests`, each array of `commands` as JSON on a line of its own, and that the copy has no remote); answer `<out>.implementer.md` | the stage's state `ok`: the step passed. `timeout`: the call ends `failed` (`detail` `{"stage": "timeout"}`), `acceptance` does not run, `cleanup` does. Any other state (`cut`, `no_result`, `failed`), `stage_refused`, or `stage_record_unwritten` (as in a unit call): the call stops with it as the cause |
| `acceptance` | first `worktree` must still be a directory and not a link (a process of the candidate may have put a link there, which would send the evaluator to another place); else the call stops with `copy_replaced`, starts no evaluator, removes nothing and leaves the path for a reader. Then the digest of `acceptance` is compared as in a unit call, and so is the digest of the case file with `case.sha256` (it names the judging files and the commands, so the stage cannot change it); then `acceptance <case> <clone>` runs in the copy, stdin `/dev/null`, under `timeout -k 10 <acceptance_seconds>`, with the environment of the `ap unit` call (so the caller's `CARGO_TARGET_DIR` and `HOST_CARGO_LOCK` reach it); output to `<out>.accept.log`. No condition on the copy's state: the candidate may have committed or not | exit 0: the call ends `passed`. Exit 1, or the bound reached (exit 124): the call ends `failed` (`detail` `{"exit": 1}` or `{"exit": 124}`). Any other exit: the call stops with `acceptance_failed` (the evaluator could not judge). The suite's evaluator ends on the first signal, so the bound reached is exit 124; an evaluator that had to be killed (exit 137: it ignored the signal, or the host killed it) is another exit and a no-result row, because a kill is no statement about the candidate. `digest_differs` (of `acceptance` or of the case file) stops the call before the run |
| `cleanup` | after the result is `passed` or `failed`: first the same check of `worktree` (a link ends the call `stopped` at this step with `copy_replaced`, with no diff written and nothing removed); then writes `<out>.candidate.diff`, the difference between the copy's one commit and its final files (new files included, ignored files not, binary as Git's binary patch), then removes the copy. After a stop the copy stays for the Lead to read | a failure is recorded in the step (`result: failed`, `detail` `{diff, copy: removed\|failed}`) and changes no result |

The ends: exit 0 with `state: passed`; exit 4 with `state: failed`; exit 3 with `state: stopped` (`stopped_at`, `cause`, `detail`); 2 a refusal and 5 a record that could not be written, as in a unit call. A unit call never exits 4.

The record `<out>.unit.json` is claimed and replaced as in a unit call, with the same members; those that have no meaning in a case call are null: `branch`, `task_key`, `write_set`, `verifier_prompt`, `verdict_file`, `merge`, `pull_request`, `head`, `review`, `merge_commit`, `stages.verifier`, `files.gate`. `repository` and `base` are the case's, `files.report` is the stage's answer (null without a stage), and `detail` is the failed step's detail at `failed` too. It adds `mode` (`"case"`), `case` (`{path, sha256, id}`), `at`, `prompt` (`{path, sha256}` of the request's prompt file, null without a stage: the digest of the stage's own prompt is of a file that holds the copy's path and differs in every call), `stage_seconds` (the stage's bound in effect, its `timeout_seconds` or `ap run`'s default; null without a stage: it defines what `failed` by timeout means) and `files.candidate_diff`. A killed case call leaves the record naming the step begun.

What a case record means, for the read-out (`evals/readout.py`) and any other reader. One record is one row of the suite: the case (`case.id`, its digest `case.sha256`), the target (the model and effort in the record of `stages.implementer`, whose usage is the row's cost), the prompt's digest (`prompt.sha256`), the result. The reader reads `mode` first and then `state` alone, never a step's result: `passed` is a pass, `failed` is a fail, `stopped` is no result. A no-result row is run again once; a second stop stays in the reading as no result; the usage of a no-result row counts in the reading's cost. A record without a stage is a validity row: a case is valid when its row at `base` ends `failed` and its row at `head` ends `passed`; a case with another pair counts in no reading. A suite value measures implementing to given tests, the easier half of the same work (the other half is writing the tests from the page): the read-out prints that beside it. A reading runs alone on the host: a build that waits on the build lock spends the stage's bound.

## The board

`ap backlog <task key> [--text] [--store <path>]` prints the board of a task of the store and writes nothing: no store write, no file. It reads the task's board, items, objectives and decisions (searches by `task`), and an element of the order that is no item of the task with `ont get`. `--store` is forwarded to every `ont` call. A malformed argument is refused with `{"error":{"code":"usage","field":"args","detail":null}}` on stderr and exit 2; a failed read with its code (`store_answer_unreadable`, `process_failed`) in the same form.

The answer is one JSON object on stdout:

- `board`: `set_at` and `reason` of the board, or null when the task has none.
- `objectives`: the task's objectives by `rank`, each `name`, `rank`, `status`, `statement` and `last_check` (`exit`, `line`, `at`, or null when none was recorded).
- `order`: the items of the task the order names, in its sequence, each `key`, `title`, `state`, `objective` (its name), `repository` and `branch` when `in_work`, and `refusal`: the code a unit call for the item would be refused with before any effect, computed by the function of `ap unit` ("The item" in "One unit") without the write of `start_item`, or null. A queued item of the order has null (its start is the store's to refuse); an item in work has `item_of_another_unit`, because no new unit may start it (its own unit goes on).
- `bad`: the elements of the order that are of another task, `done`, `dropped` or missing (`id`, `key` for an item of the task, `problem`: `another_task`, `done`, `dropped`, `missing`). A done or dropped item is also in `order`.
- `unplaced`: the queued items the order does not name (`key`, `title`, `added_at`), oldest first.
- `in_work_unlisted`: the items in work the order does not name (`key`, `title`, `repository`, `branch`).
- `untriaged`: `count` and `topics` (at most 10, oldest first) of the task's `current` rows decided by the user that have no `triage`.

A task without a board prints `board: null` with `objectives`, `unplaced` (every queued item) and `untriaged`. `--text` prints the same as plain lines for a reader: the board, one line per objective, one per item of the order (with its refusal), one per bad element, unplaced item and item in work that is not ordered, and one for the untriaged rows; at most 80 lines (the 80th says how many more the JSON form holds); a line break inside a value is printed as a space.

## One row

`ap row [--store <path>] < row.json` records one row of the user or of the Lead as a `decision` of a task and, for a row of the user, triages it, in one call. `--store` is forwarded to every `ont` call; any other argument is refused with `{"error":{"code":"usage","field":"args","detail":null,"after":null}}` on stderr and exit 2. It uses the store's actions `record_decision` and `triage_decision` with the client `lead`, and no other action; it writes no file.

The request is one JSON object (at most 1 MiB); a member that is not named here, a missing one and one of the wrong kind is refused with `invalid_input` and its field:

- `task`: the task key, made into the store's task as `ap backlog` makes it; `request_id`: a string (the two actions use `<request_id>-record` and `<request_id>-triage`, so at most 57 bytes of ASCII letters, digits, `.`, `_` and `-`); `agent` and `session`, passed to both actions; `topic`; `text`, the reading (at most 1000 bytes); `by`: `user` or `lead`. Each is a non-empty string. The store's own rules for `task`, `topic`, `request_id`, `agent`, `session` and `form` are not repeated: `ont action validate` of the record refuses a breach, with the store's code, before anything is applied.
- `by: "user"`: exactly one of `words` (the user's words), `words_file` (an absolute path of a regular UTF-8 file whose whole text is the words) and `words_from` (`record`: the absolute path of a Claude Code session record; `at`: a UTC time to the second, `YYYY-MM-DDTHH:MM:SS`); `form`, `decision` (the default) or `question`; `triage`: `word` (`item`, `intent`, `not_adopted` or `none`), `item` (an item key of the task: with the word `item` and with no other), `objective` (an objective name of the task: with `intent` and with no other), `reason` (at most 600 bytes; required for `not_adopted` and `none`). A `triage` member that breaks this is `invalid_input` with the field `triage` (`triage.word`, `triage.reason` or `triage.<member>` for a member of its own).
- `by: "lead"`: `reason` (at most 600 bytes) and `undo` (at most 300 bytes); no words and no triage.

The words from a session record are the string of exactly one line whose `timestamp` begins with `at` and that is a line of `type` `user` with a `message.content` that is a string, or of `type` `queue-operation` with `operation` `enqueue` and a string `content` (a message sent while a turn ran); no such line is `words_not_found`, more than one `words_ambiguous`, both with the count as `detail`. The words are that string byte for byte. They are never cut, trimmed or changed: words above 1000 bytes are refused `words_too_long` with `{"bytes","limit"}` as `detail`, and the Lead then gives `words` itself; `text`, `reason`, `undo` and `triage.reason` likewise against their limits (`text_too_long`, `reason_too_long`, `undo_too_long`; `detail` as above). An item key or objective name the task does not have is `item_unknown` or `objective_unknown`. Every one of these refusals is made before any call that changes the store.

The order: `ont action validate` of the record; its `apply`; then the current row of the task with that `topic` is read back (a search of the task's decisions) and its words (`user_words`; for a row of the Lead `text`) compared byte for byte with the request's (`readback_differs` when they differ); then, for a row of the user, the triage validated and applied on that row. `validate` does not see the store's record of applied requests, so a repeated call meets `decision_already_current` (record) or `already_triaged` (triage) there: these two alone do not stop the call, and `apply` answers a repeated `request_id` with `already_applied`. A call cut after the record and run again triages the row and records nothing twice; a call repeated whole answers `already_applied` twice and writes nothing.

The answer is one JSON line on stdout, exit 0: `topic`, `decision` (the row's id), `record` (`applied` or `already_applied`), `triage` (the word, or null for a row of the Lead) and `words_bytes` (the byte count of the compared words). A refusal is `{"error":{"code","field","detail","after"}}` on stderr with exit 2: `after` is null before any change, and `record` when the record was applied and the triage was not (also for a failed read-back); a refusal of the store keeps the store's first code (`user_question_is_not_a_decision`, `decision_already_current`, `not_a_user_row`, ...) in `code` and the action (`record` or `triage`) in `field`; a failed `ont` call is `process_failed` or `store_answer_unreadable`.

## The task's state

`ap state <task directory> [--text]` prints what the records of a task's directory and Git say of its unit calls and stages, so that a Lead types none of it into `STATE.md`. It reads the directory's `runs/` (the files directly in it: `*.unit.json`, `*.run.json`, `*.stream.jsonl`) with the file system, Git with `--no-optional-locks -c core.fsmonitor=false` (`rev-parse HEAD`, `status --porcelain`: no index lock, no refresh of the index, no hook named by the repository's configuration), `systemctl is-active` and `ps` through the host's `System`; it writes nothing (no file, no store call, no network, no `gh`). A malformed argument (no directory, another word or option, `--text` twice) or a directory without `runs/` is refused with `{"error":{"code":"usage","field":"args","detail":null}}` on stderr and exit 2. A record that does not parse as one JSON object is listed in `unreadable` and the rest is printed, exit 0. It reads no session record and no prompt or answer text, and changes no record's member.

The answer is one JSON object on stdout:

- `at`: the time of the read (UTC, RFC 3339).
- `task`: `dir` (the resolved directory), `head` (`git rev-parse HEAD` there, null when Git says nothing) and `uncommitted` (the number of lines `git status --porcelain` prints; null when that call fails, as without Git).
- `units`: the calls of `ap unit`, the records `runs/*.unit.json`, in chains: the records with the same `repository` and the same non-null `pull_request` are one chain, a call whose `pull_request` is null is a chain of its own. A chain has `item` (the `item.key` of its first call that has one, else null), `repository`, `pull_request` and `calls` in order of `start`, each `record` (the path relative to the directory), `state`, `stopped_at`, `cause`, `head`, `merge_commit`, `start`, `end` (null where the record lacks the member) and `stale`. Chains are newest first by their last call's `start`.
- `stages`: every record `runs/*.run.json` whose `end` is null, and the newest 20 by `start` of those that belong to no unit call, newest first. A stage record belongs to a call when its path begins with the call's record path less `.unit.json`, followed by `.` (`runs/U-1.unit.json` owns `runs/U-1.implementer.md.run.json`, not `runs/U-1-2.fixer.md.run.json`). Each has `record`, `role`, `runtime`, `model`, `account`, `state`, `start`, `end`, `stale` and, where the record has it, `served_by`.
- `stale`: for a stage record whose `end` is null, read from `systemctl is-active` of its systemd unit (the record's `unit`): the answer is the word on stdout and the exit is not read. `active`, `activating`, `deactivating`, `reloading` or `refreshing` gives false; any other word, including `inactive` of a unit that does not exist (exit 4), gives true; no word (the call failed, timed out or printed nothing) gives null. A record whose `start` is less than 10 seconds before `at` prints null where true would be printed, because `ap run` writes the record before it starts the unit. For a unit call whose `state` is `running`: false when one of its stage records (the ownership above) is live (its `stale` is false), else true when no process of `ap unit` lives on the host (`ps`: a process whose program is named `ap` and whose first argument is `unit`), else null (some `ap unit` lives and nothing ties it to this record); a failed `ps` call, a non-zero exit or empty output gives null for a call that no live stage decides. Null for every record that does not say it runs. `stale: true` speaks only for this host's service manager and process table: a stage or call that runs under another host's manager is stale here.
- `streams_without_record`: the files `runs/*.stream.jsonl` that have no `.run.json` of the same stem (stages started by hand), each `path` and `modified` (the modification time, UTC).
- `limits`: per account named by a stage record (every readable `*.run.json`), the newest record by `end`, else `start`, whose `limit` is present and not null: `account`, `record` and that `limit`; a missing `limit` counts as null; an account with none is not listed.
- `unreadable`: the paths of the `*.unit.json` and `*.run.json` files that do not parse as one JSON object.

`--text` prints the same as plain lines, at most 60: first every stage record that runs (`end` null) and every unit call that is `running`, each with the word `stale` when it is, then the newest ten chains (item, pull request, last state, the merge commit or the head in its first 12 characters, end), then one line per account with a limit; when lines were cut, the last line says how many more the JSON form holds. A line break inside a value is printed as a space.

What it does not print: the installed revisions (`deploy/README.md`, "Read the state"), the store's holds, items and rows ("The board"), the host's disk and CPU.

`ap route index [--directory <dir>] [--store <path>] [--prune] [--repository <owner/name>]... [--instructions <dir>]`, and `ap` with no argument and `ONT_FN_NAME=route`, the program of the store's function `route` (`ont fn route`): `specs/ap/route.md`. The objects `section` and `component` and the function are those of schema version 14 (`ontology/README.md`, "Version 14: routes"); the timer, its install and the undo are in `deploy/README.md`, "Routes"; the evaluation of the answers is `evals/route/run` (`evals/README.md`, "The route suite").

## The policy check

`ap policy check [<file>]`: `specs/ap/policy.md` R12 to R16. Its last reader, `writer`, reads the member `writer` of the page writer (`specs/ap/unit-write.md` R2).

## One check

`ap check <dir> [--timeout <seconds>] [-- <command> [<arg>...]]`: `specs/ap/check.md`. It runs `./check`, or the given command without a shell, for the worktree `<dir>`: on the local PC when the policy file names it in `hosts.pc` and the PC answers, is not busy and has at least `min_available_mb` (default 2,048) MB available, the smaller of its Linux's `MemAvailable` and Windows' free memory, else in `<dir>` here (a command other than `./check` under the host's build lock). The output streams back, the exit status is the command's (124 at the timeout), and one record line goes to `AP_CHECKS_LOG` (default `/var/lib/agent-platform/checks.jsonl`), with what the probe read of the PC and the lowest `MemAvailable` of its Linux while the command ran there. The command's environment, on either host, holds the cargo settings `./check` exports (`CARGO_INCREMENTAL=0`, `CARGO_PROFILE_DEV_DEBUG=0`, `CARGO_PROFILE_TEST_DEBUG=0`), so that every cargo command shares `./check`'s artifacts; on the PC it also holds the marker `AP_CHECK_HOST=pc`, which `ap check` removes from a command it runs here (`specs/ap/check.md` R17). Inside a stage with `limits` the PC is reached through the door (`specs/ap/check.md` R20).

## The door

`ap fn <name> < request.json` and the door of a stage with `limits`: `specs/ap/door.md` R1 to R8. The door's record is the file `AP_DOOR_LOG` names (default `/var/lib/agent-platform/door.jsonl`).
