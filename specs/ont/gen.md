# Generated types

Purpose: `ont-gen`, a library that turns the bytes of one schema file into the text of one Rust module, so that a consumer of the engine names its action types, object types, links, functions and parameters by Rust items the compiler checks instead of strings.

The module holds types and request builders only. It answers nothing by itself: every call goes through the consumer's implementation of `Engine`, and the engine stays the judge of everything it judges.

## Entry

- R1: The one public entry is `ont_gen::generate(schema: &[u8]) -> Result<String, Vec<ont_core::schema::Violation>>`. It checks the bytes with `ont_core::schema::Schema::check_bytes` and an empty set of other domains' types (what `ont schema check FILE` runs on a store that does not exist); a schema that check refuses gives its violations unchanged and no text. The generator refuses on its own with code `name_collision` when two names the module would define in one place get one Rust name by R4: two items of one submodule (two schema names of one kind, a link's reverse hop and another link, a generated struct of R7 and another item), two fields of one struct (the parameters `self` and `self_`), or two variants of one enum of `properties`. The pointer is the JSON pointer of the later of the two schema names, in the order the module defines its items: the kinds in the order `objects`, `properties`, `values`, `actions`, `functions`, `links`; within a kind the schema names in byte order; an action's or a function's own struct before the structs of its parameters, the parameters in byte order; a link's forward hop before its reverse hop. A value type's enum is not refused: R6 gives it the struct form. `generate` reads no file, no environment and no clock, and returns either the whole text or faults, never both.
- R2: The same bytes give the same text, byte for byte, on every host and in every environment: every list the text follows is in byte order of the schema names or in the order of the schema's own arrays.

## The text

- R3: The first line is a `//` comment that names `ont-gen`, the domain, the version and the sha256. Then comes one item: attribute lines, a line that is exactly `pub mod <module> {` with `<module>` the domain written by the field rule of R4, the items, and `}`. The module names an outside item only by an absolute path under `::std` or `::serde_json`; it uses no derive or macro of another crate, no `unsafe`, starts no process and opens no file. It is written for edition 2024, stands at item position wherever `include!` puts it, and compiles without a warning of rustc and Clippy in a crate that uses none of its items: its attributes allow `dead_code`, `non_snake_case`, `non_camel_case_types`, `clippy::upper_case_acronyms`, `clippy::enum_variant_names` and `clippy::module_inception`, and never `unsafe_code`, `clippy::unwrap_used` or `clippy::expect_used`. A description of the schema appears only in a `//` comment of one line, with every control character and every character of U+202A to U+202E and U+2066 to U+2069 replaced by a space. Every other text of the schema appears only as an identifier by R4 or in a string literal in which the quote, the backslash and every character outside U+0020 to U+007E are escapes (`\"`, `\\`, `\u{...}`).
- R4: Names. A type's name is the schema name split at `_`, the first letter of each part in upper case, the parts joined (`set_hold` gives `SetHold`, `a_1` gives `A1`); the same rule names an enum's variant; a type or variant whose name would be `Self` is written `Self_`. A field keeps the schema's name; a keyword of edition 2024, strict or reserved (`type`, `gen`, `try` among them), is written raw (`r#type`), and `self`, `super` and `crate` take one trailing underscore (`self_`). The module's own name follows the field rule (`pub mod example {`, `pub mod r#type {`, `pub mod self_ {`). The member of a JSON object and every `NAME` are always the schema's name. The kinds live in the submodules `objects`, `properties`, `values`, `actions`, `functions` and `links` of the module, so one name in two kinds does not collide.

## Object types, values, actions, functions, links

- R5: The trait `ObjectType` has `const NAME: &'static str`. For every object type, `objects::<Type>` is a unit struct that implements it with the schema name, and `properties::<Type>` an enum with one variant per property (in byte order) and `pub fn name(&self) -> &'static str`, the property's schema name. `Id<T: ObjectType>` is an object's id: `Id::new(native_key)` in the schema's namespace, `Id::in_namespace(instance, account, native_key)` (each argument `impl Into<String>`), `native_key(&self) -> &str`, `to_value(&self)` giving `{"object_type","namespace":{"instance","account"},"native_key"}`, and `Id::from_value(&Value) -> Option<Self>`, which is `None` for a value that is not an id of that form (exactly those members, each a string of 1 to 512 bytes) or whose object type is another. `Id<T>` is `Clone`, `Debug`, `PartialEq`, `Eq` and `Hash`.
- R6: For every value type, `values::<Name>`: when the base is `string` and it has an `enum` whose every value is a string that follows `valid_name` and gives a variant no other value gives, an enum with one variant per value in the order of the `enum`, `pub fn as_str(&self) -> &'static str` and `pub fn parse(&str) -> Option<Self>`; in every other case a tuple struct of one public field of the base's Rust type by R7, `pub struct <Name>(pub String);` for a string base. The engine stays the judge of `pattern`, `min` and `max`.
- R7: The types of fields: `string`, `decimal` and `date` are `String`; `integer` and `timestamp` are `i64`; `boolean` is `bool`; `{ref: T}` is `Id<objects::T>`; `{array: X}` is `Vec<X>`; `{value_type: V}` is `values::V`; `{struct}` is a generated struct with one public field per member (every member required), in the submodule of its action or function, named by the type rule from `<action>_<parameter>` or `<function>_<parameter>` (`add_unit` and `acceptance` give `actions::AddUnitAcceptance`). A parameter with `required: false` is `Option<...>`, and `None` leaves the member out of the JSON object (omission and null are one request: R64 and R67 of `specs/ont/action.md`). An action or a function is built as a struct literal with named fields and has no constructor with positional arguments: two parameters of one type cannot change places silently, and a parameter added to the schema, an optional one too, is a compile error at each caller that names the struct.
- R8: The trait `Action` has `const NAME: &'static str` and `fn parameters(&self) -> ::serde_json::Value`. For every action type, `actions::<Action>` is a struct with one public field per parameter that implements it: `NAME` is the action type's name and `parameters` the object of the given parameters under their schema names.
- R9: The trait `Function` has the same two members. For every function, `functions::<Function>` is a struct of the same form that implements it.
- R10: The trait `Hop` has `type From: ObjectType`, `type To: ObjectType` and `const NAME: &'static str`. For every link type, `links::<Link>` is a unit struct from `from` to `to` named `names.forward`, and `links::<Link>Reverse` a unit struct from `to` to `from` named `names.reverse`. The trait `Path` has `type From: ObjectType`, `type To: ObjectType` and `fn names(&self) -> Vec<&'static str>` (the hops' names in order). A path is a tuple of one, two or three hops, `(A,)`, `(A, B)` or `(A, B, C)`, and implements `Path` only where each hop's `From` is the `To` of the hop before: a fourth hop and a hop that starts at another type than the one reached are compile errors.

## The engine

- R11: `Command` is an enum `ActionApply`, `ActionValidate`, `Get`, `Search`, `Around`, `Fn(&'static str)`; `argv(&self) -> Vec<&'static str>` gives the words of the subcommand (`action apply`, `action validate`, `get`, `search`, `around`, `fn <name>`). `Engine` is a trait with `type Error` and `fn call(&mut self, command: Command, request: ::serde_json::Value) -> Result<::serde_json::Value, Self::Error>`; the consumer implements it once, and the module calls the engine nowhere else. `Call` holds what an action request has besides the schema's part, `Call::default()` empty: `request_id`, `agent`, `session` and `role` of type `Option<String>`, and `expected: Vec<(::serde_json::Value, String)>`, pairs of an id's value and a revision. Each call function returns the engine's answer unchanged and sends no member `op`:
  - `apply(engine: &mut E, action: &A, call: &Call)` sends `Command::ActionApply` and `validate(engine, &action, &call)` `Command::ActionValidate`, each with `{"action_type","parameters"}` and the members of `call` that are set, `expected` as `[{"id","revision"}]` and only when it is not empty (R2, R3 and R12 of `specs/ont/action.md`; a consumer on the library takes `role` out as R17 there says);
  - `get(engine, &id)` sends `Command::Get` with `{"id"}`;
  - `search::<T, E>(engine, filter: Option<Value>, limit: Option<u64>, continuation: Option<&str>)`, written `search::<objects::Item, _>(engine, filter, limit, continuation)`, sends `Command::Search` with `{"object_type"}` and the given ones of `where`, `limit` and `continuation`; the filter is a value the consumer writes, its property names taken from `name()` of `properties::<Type>`;
  - `around(engine, filter: Option<Value>, path: P, limit: Option<u64>)` with `P: Path` (`(links::ItemShelf,)`) sends `Command::Around` with `{"from":{"object_type","where"?},"path","limit"?}`, the object type of the path's `From` and the hops' names (R66 and R67 of `specs/ont/read.md`);
  - `call(engine, &function)` sends `Command::Fn(NAME)` with `{"parameters","domain"}`, the domain always given, so that a call is never `function_ambiguous` (R4 and R5 of `specs/ont/fn.md`).
- R12: `DOMAIN: &str`, `VERSION: u64` and `SHA256: &str` are the pin `CheckedSchema::pin()` gives for the bytes, which is what the envelope of an answer of a read or an action shows under `schema.<domain>` once the bytes are installed, so that a consumer can compare them.

## The command

- R13: `ont schema gen FILE` prints on standard output, with exit 0, exactly the text `ont_gen::generate` gives for the bytes of FILE (R1 to R3): nothing is added, no envelope and no newline, and standard error stays empty.
  - The form is `schema gen FILE`: exactly one FILE, no option of its own (an option outside the global `--store`, `--now`, `--version`, `--help` and `-h` is refused `invalid_argument` as for every command), no standard input (`stdin_json` false); `ont help` and `ont schema gen --help` list it, and `schema gen` without FILE or with two is refused `invalid_argument`.
  - A refusal is one JSON line on standard output with exit 2 and no module text, of the form of every refusal (`status` `refused`, `code`, `trust_limit`). A FILE the generator refuses is `schema_gen_refused` with the member `violations`, the array the generator returned, unchanged and in its order (`name_collision` and every schema check fault alike, invalid JSON included). A FILE that cannot be read is `schema_file_unreadable` with `path`, as `schema check` answers it.
  - The command makes no uid check, because it binds no principal (R24 of `specs/ont/schema-language.md`): it answers alike for any real and effective uid. The checks that `run` makes before the uid check hold for it as for every command other than help and version: `now_requires_store`, and `now_at_default_store` (R104 of `specs/ont/action.md`). It is not a writing command (R15 of `specs/ont/fn.md`), so `ONT_FN_READ_ONLY=1` does not refuse it. It opens, creates and reads no store file, whatever `--store` names, reads no standard input and writes nothing but its answer on standard output.

## Use

A consumer pins `ont-gen` at the one revision it pins the engine at (R23 of `specs/ont/schema-language.md` names `ont-core`, `ont-store` and `ont`). Its build script reads the schema file, calls `ont_gen::generate` and writes the text to a file under `OUT_DIR`; the crate then writes `include!(concat!(env!("OUT_DIR"), "/<domain>.rs"));` at item position and declares `serde_json` among its dependencies.

The second way has no Git dependency on `ont-gen`: the build script runs the pinned engine's `ont schema gen FILE` (R13) and writes its standard output to `$OUT_DIR/<domain>.rs`; the crate includes that file in the same way.

## Not included

- Typed answers: no struct is decoded from a head, a row of `search` or `around`, an applied action's edits or a refusal; a call function returns the engine's JSON.
- Typed filters, and call functions for `aggregate`, `describe`, `action list`, `log` and `render`: a consumer writes those requests itself with `NAME` and `name()`.
- A check on the client of what the engine checks (patterns, bounds, criteria, grants).
- An implementation of `Engine`, a proc macro, and reading a schema out of a store.
- One module over several schemas, and a reference to an object type of another domain.
