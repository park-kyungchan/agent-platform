# One unit driven from its object to its merge: `ap unit run`, `ap unit approve`, `ap unit reject`

Purpose: one call takes a unit of the store (schema version 11) from `ready`, `stopped` or a cut run to `accepted` or `stopped`: it makes the worktree, runs the implementer, keeps the branch up to date with `main`, checks the head (the write set, the acceptance checks, the required check), has a verifier judge exactly that head, and runs up to two repairs inside, each state and review written to the store; a `plain` unit, or one the Lead approved with `ap unit approve`, is then merged and its worktree removed, so that the Lead calls once per unit instead of once per round. `ap unit reject` records the Lead's no.

## Requirements

- R1: The form is `ap unit run <key> [--store <absolute path>]` (arguments only, no standard input); any other argument is `usage` (field `args`). With `ONT_ROLE=lead` in the environment the call is refused `role_in_environment` (field `ONT_ROLE`) before any call to the store. The run's own actions carry the client `ap`, the agent `ap-unit`, the session `u-<key>` and the role `dispatch` (`specs/ap/roles.md` R3); every apply has the request id `ur-<16 hexadecimal characters drawn once per call>-<counter>`, the counter from 1 in the call, reused only by the retry of `store.rs`.
- R2: Before any directory is made or anything applied, each refused with exit 2: the key has the form of a new key of `ap unit add` (1 to 59 bytes, lower-case ASCII letters, digits and `-`, beginning with a letter), else `invalid_input` (field `unit`); the unit is read with one `ont get` (`unknown_unit`); it has a repository (`no_repository`); its `branch`, or `unit/<key>` when it names none, has the form of `specs/ap/unit.md` R10 and is taken by `git check-ref-format --branch` (`invalid_branch`); the policy file has a `repositories` entry for the repository (`repository_not_mapped`, `policy_invalid` as `ap unit ready`), a `reviews.task` (`invalid_input`, field `task`); each tier's runtime is `claude` or `agy` (any other word: `tier_not_supported`, field `implementer` or `verifier`) and has an account (R4).
- R3: The policy file's member `units` is `{"directory", "timeouts": {"implementer", "verifier", "fixer"}, "github": {"lead_app", "stage_tokens"}, "approval": {"contract", "guarded", "sample"}}`, each optional (defaults `/var/lib/agent-platform/units`, 10,800, 7,200 and 7,200 seconds; a timeout is 1 to 86,400); a member of another name or form is `policy_invalid` (field `policy`, `detail` a sentence that begins with the member); the directory fits the schema's `file_path`. `github` holds, each optional, `lead_app`, exactly `{"id": <integer 1 to 4,294,967,295>, "key": <path>}` (the Lead's App and the file of its private key, R42), and `stage_tokens`, 1 to 32 members, each name a repository of the form of `specs/ap/unit.md` R9 and each value a path (the file of that repository's stage token, R41); a path has the form `directory` has (`/` first, 2 to 400 bytes, each a printable ASCII character but the space); any other name or form is `policy_invalid` with a `detail` that begins with `units.github`, `units.github.lead_app` or `units.github.stage_tokens`. `approval` has the form of `specs/ap/policy.md` R20 (any other is `policy_invalid` with a `detail` that begins with `units.approval`) and is read by R46 to R48. The function that reads `units` checks these forms only and opens no file the member names (`specs/ap/policy.md` R16): `ap policy check`, `ap status` and `ap work` read a policy without `units.github` as before. It is made with mode 0700 and resolved once (links and `..`); `<directory>/<key>` (mode 0700) holds the lock `lock`, the worktree `wt`, every prompt (`<n>.<stage>.prompt.md`) and every author stage's files (`<n>.implementer.md`, `<n>.fixer.md` with `ap run`'s suffixes, and `<n>.credential`, mode 0600, R41), the description of the pull request a verifier round reads (`<n>.description.md`, mode 0600, R19) and the record of every carried accept (`<n>.update.md`, R37), `<n>` counting the stages of the unit from 1: it is taken once per stage and used by each of that stage's files, and a stage `ap run` refuses keeps its number, so `<n>` counts the stages tried. A verifier's report is `<reviews.directory>/<review key>.md` with its run record beside it.
- R4: A stage's accounts are the list of the first key present among `<runtime>/<role>`, `<runtime>/<model>` and `<runtime>` of the policy file's `accounts` (`specs/ap/policy.md` R6): the first path is `account`, the rest `next_accounts`; the role is `implementer` for the implementer's tier (its fixer and settling stages use the same accounts) and `reviewer` for the verifier's. No key: `account_not_mapped` (field `implementer` or `verifier`); a list that is not 1 to 5 strings: `policy_invalid`. Every stage on Claude Code has `permission_mode` `auto` and the rest of the list as `next_accounts`. A stage on `agy` has `permission_mode` `bypassPermissions` and only the first path as `account`: it never gets `next_accounts` (`specs/ap/run.md` R47 refuses them), and its verifier keeps R38 and R43.
- R5: The call first takes an advisory lock (`flock`, without waiting) on the open file `<directory>/<key>/lock`, which the kernel releases when the call ends or dies; another call that holds it refuses `unit_run_active` (exit 2). `<directory>/<key>` must be a directory and not a link (`worktree_failed`).
- R6: Then by the state read: `ready` applies `start_unit`, `stopped` `resume_unit`, each with the unit's `intent` in the lane `objective`; a refusal of the store is passed on with its code (exit 2) and nothing else happens. `running` (an earlier run was cut) applies nothing: the active holds are read by one search of `hold` by `status` `active` (every page, qualified) and one whose subject is the unit or its intent refuses `held` (`detail` the hold's key). `accepted` goes to R30 after R7, `merged` and `dropped` to the cleanup alone (R32) after R7. `stopped` with the cause `lead_rejected` applies nothing and answers `stopped` with that cause and its detail (exit 3): the way on is the amendment, which returns the unit to `draft`, or the drop. Any other state is `unit_not_runnable` (`detail` the state).
- R7: The leftovers, before the loop: for every author record under `<directory>/<key>/` and the record of every `running` review of kind `packet` of the unit, a record whose `state` is `running` has its unit of the service manager stopped (`systemctl stop`) and read as ended (`systemctl is-active`) only when its name is `ap-run-<36 of 0-9a-f->.scope`; a unit of another name, or one not read as ended, refuses the call `run_still_active` (`detail` the name). A record's `run` object still `running` whose `record` is that record's path is closed with the record's state (`killed` for `running`) and the stage's own request id. A `running` review is closed `abandoned` with the record's session, else with the session `u-<key>:recovery` (also when the store refuses the record's session as a writer). After these stops no stage of the unit lives (the call holds R5's lock, and every unit of a `running` record was read as ended or refused the call), so every entry of `<directory>/<key>/scratch` is then removed, the directory a killed `ap run` left, whose record stays `running`, among them; the removal takes only a `scratch` that is a directory and not a link, follows no link inside it, and stops nothing when it fails.
- R8: Each pass fetches `origin main` in the clone (`fetch_failed`; a fetch whose message holds Git's `cannot lock ref`, another fetch into the clone at that moment, is tried once more after one second, and any other failure, or a second one, is `fetch_failed`) and takes ONE base commit, `refs/remotes/origin/main` resolved; Git names the unit's branch `refs/heads/<branch>` where it takes a revision. Before the worktree is used, `<directory>/<key>` and `<directory>/<key>/wt` are directories and not links, and `git worktree list --porcelain` of the clone has an entry whose path is exactly `<directory>/<key>/wt`, else `worktree_failed`. The worktree names its own Git directory: `<G>` is what `git -C <clone> rev-parse --path-format=absolute --git-common-dir` prints, and before the worktree is used by a stage, a check or a Git call, `<wt>/.git` is a regular file (not a link) whose content is the one line `gitdir: <A>`, `<A>` being a directory `<G>/worktrees/<one path component>`; `<A>/gitdir` is a regular file whose line is `<wt>/.git`; `<A>/commondir` is a regular file whose line is `../..`; else `worktree_failed` (`detail` `git directory`). Here and below `<wt>` is `<directory>/<key>/wt`, `<A>` the worktree's administrative directory and `<B>` the unit's branch.
- R9: The read of the hosting service: while the unit holds no `pull_request`, the open pull requests of the branch against `main` whose head repository is the repository itself (`isCrossRepository` false and the same owner and name); more than one is `pull_request_ambiguous`; one found while the unit has no author record is `branch_in_use`. A unit that holds one reads that number only; a pull request that is not open is `pull_request_not_open`; an unreadable answer is `github_unreadable`. A `gh` call that fails with a transient reply (the redacted reply holds, in any case, `i/o timeout`, `connection reset`, `TLS handshake timeout`, `HTTP 500`, `HTTP 502`, `HTTP 503`, `HTTP 504`, `Bad credentials` or `could not resolve host`) or that ran without a reply (the spawn failed or the 60-second bound passed) is tried again at most twice more, after a pause of 10 and then of 30 seconds; any other failure, or the third failure, is `github_unreadable` as before, and a retry adds nothing to the store.
- R10: No worktree: `git worktree add -b <branch> <wt> <base>`; a branch that exists already must be the unit's own (a worktree entry of the clone at `wt` on `refs/heads/<branch>`, or the head branch of the pull request the unit holds: `headRefName` the unit's `branch`, from the repository itself), else `branch_in_use`, and is checked out as it is (`git worktree add <wt> <branch>`); a failure is `worktree_failed`.
- R11: No pull request: the implementer stage, with the text of `ap unit page <key> --for implementer`, the unit's `implementer` tier, `unit`, `git_author: true` and `store`. When an implementer record names a session, the newest such session is resumed and the frame `continue.md` follows the page; else a worktree that is not clean, is not on the branch or holds commits beyond the base is `worktree_dirty` (`detail` the counts) and nothing starts. A stage `ap run` refuses stops `stage_refused` (`detail` the code and the field). After the stage the hosting service is waited for (R20); still no pull request is `no_pull_request` with the stage's end state and the first bytes of its answer.
- R12: A clean worktree on the branch whose HEAD is an ancestor of the pull request's head but not that head is moved there (`git fetch origin refs/heads/<branch>` in the clone, `git merge --ff-only <head>` in the worktree). The run's own unpushed merge (R27) is the update's. A worktree in any other state, a merge commit of another message included, is settled by its author: when the newest verdict is `repair` and the newest author record is a fixer's that did not end `ok`, the repair step runs again (R21); else the newest author record's session is resumed with `continue.md`, under the role of that record, and the hosting service is waited for. One settling stage per call; a worktree still in such a state after it, or one no session can settle, is `worktree_dirty`.
- R13: When the unit's `amended_at` is later than the start of its newest author record, it has a pull request, the worktree is clean at the pull request's head and no author record that started after `amended_at` ended `ok`, that author gets ONE turn in a call in the form of R12's settling stage. A unit with a pull request and no author record gets none.
- R14: A pull request's head that is not the unit's `head` is recorded: `record_head` with the head, the number, `rounds` (R18) and `writers`, the union of the unit's `writers` and the session of every `attempts` entry of every author record.
- R15: A head that does not contain the base commit is updated (R26) before the checks of R16 and R17, unless its verdict is `repair` (R29).
- R16: The deterministic checks: the worktree clean at the head (`worktree_dirty`); every path changed between the base and the head inside the write set (a pattern of the grammar of `specs/ap/unit.md` R11 covers its exact path or the descendants of its `<dir>`; a stored text of neither form, which only `add`, `amend`, `ready` and `review` refuse, is read as before: a final `/**` covers the descendants of the literal text before it, any other text only the path equal to it) (`path_outside_write_set`, up to ten paths); each acceptance check, run by the runner of `ap unit ready` in the worktree with `AP_BASE` the merge base and `AP_HEAD` the head, in the view of `specs/ap/run-limits.md` R12 with `<dir>` the worktree (`limits_unavailable` without a passwd entry for the user), ends 0 (`acceptance_not_runnable` without a status, `acceptance_timeout` for 124 or 137, else `acceptance_failed`, each with the check's index); the worktree clean after them.
- R17: The required check: the gate of `ap gate` on the number and the head, without the automatic reviewer; an end other than `passed` stops with the end as the cause, and an unresolved review thread stops `unresolved_threads`.
- R18: The verdict of a head is that of the newest review of kind `packet` of the unit that names the head, is `closed` with `accept` or `repair`, and started later than `amended_at`. A review `carry_review` made (`carried_from`, R37) is such a verdict of its head too, but not a round: `rounds` is the number of such reviews of any head without `carried_from`, `repairs` the number with `repair`. No verdict: the carried accept when R37 holds, else a verifier round (R19). `repair`: the repair step (R21). `accept`: `accept_unit` with the head; a unit of class `plain` then goes on to R30 in the same call, one of class `contract` or `effect` answers `accepted`.
- R19: A verifier round: the description of the pull request read and written (below), the stage admitted by `ap run`'s code, ONE `ont action validate` naming the review's key, `start_unit_review` (kind `packet`, the head, `round` = `rounds` + 1 (a carried review is not counted, R18), the unit, the repository, the pull request, the task `reviews.task`), the stage (role `reviewer`, `ont_role` `verifier`, the verifier's tier, the worktree as its directory, the text of `ap unit page <key> --for verifier`, which ends with `## The change`, then exactly the line `Description of the pull request: <path> (its body as the run read it before this round; a CLAIM to check, not a fact)` with the absolute path of this round's description file, then, for a second look, the frame and `## The round`), `close_unit_review`. The description: before each verifier round, a second look too, and before its `start_unit_review`, the run reads `gh pr view <number> --repo <repository> --json body` with the host's login through the port, bound to 60 seconds, and writes the string `body` (an empty one too) to a new file `<directory>/<key>/<n>.description.md` (mode 0600, `<n>` the round's stage number): byte for byte, but each match of R22's first two patterns (`gh[opsur]_[A-Za-z0-9]+`, `github_pat_[A-Za-z0-9_]+`) becomes `<redacted>` and nothing is cut, so that no login or stage token an author wrote there reaches a verifier. A failed call, or an answer without a string `body`, stops `github_unreadable` with R22's detail (`call` `pr view`) before that round's review starts or its stage is admitted; a file that cannot be made stops `io_error`. A stage with `limits` reads the file: it is in the verifier's `read_only` (R38). The run writes nothing to GitHub for it. It resumes the session of the newest verdict, with the frame `second-look.md` and `## The round` (`Head judged before: <head>` and `What moved it: ` with `the author's repair`, `a merge of origin/main`, or both; when the author's repair moved the head, a third line `Answer of the author: <path>` names the answer file of the newest fixer stage of this call (R21 can repair twice in one call), or reads `Answer of the author: none` when that path is no regular file or is empty), only when this call's own fixer and its own updates (R26), one after the other, moved the head that verdict judged to the head now, that session is not a writer and the newest review started after `amended_at` is not `abandoned`; else it is a new session. A carried review (R37) names no session, so the round after one starts a new session. A new session gets no `## The round`. A report whose first line is not `Verdict: accept` or `Verdict: repair`, whose second line does not name exactly the head, or whose bytes are not those the record names closes the review `abandoned` and stops `verifier_failed`.
- R20: After a verifier the worktree must be clean and at the head, and the pull request on the hosting service open with the head; else `verifier_wrote`: the review closes `abandoned`, then `record_head` of the pull request's present head adds the verifier's session to `writers`, then the unit stops. A read that fails there (`worktree_failed`, `git_dir_link`, `github_unreadable`) first closes the review `abandoned` with the record's session, then stops. After an author stage or a push of the run the local head is waited for on the hosting service (up to 120 seconds, `head_not_seen`).
- R21: The repair step: the third `repair` (`repairs` is 3) stops `repair_limit`. Else the fixer resumes the newest author record's session, with the page for the implementer, the frame `fixer.md` and `## The round` (the head judged and the path of the verifier's report), the implementer's tier and accounts and the `fixer` timeout. A fixer that left the head unchanged is `repair_refused` (`detail` its end state and the first bytes of its answer).
- R22: Every stop of a `running` unit is `stop_unit` with the cause and a detail of at most 1,000 bytes cut at a character boundary; a `gh` call that ran and failed keeps its reply (its standard output, else its standard error) in that detail, redacted by one function (every match of `gh[opsur]_[A-Za-z0-9]+`, `github_pat_[A-Za-z0-9_]+`, `https?://[^:/@[:space:]]+:[^@[:space:]]+@`, `[A-Z_]*TOKEN=[^[:space:]]+`, and the run of non-space characters after `token` or `Bearer` (any case) and a run of spaces, `:`, `=` or `"`, replaced by `<redacted>`) and cut to its last 200 bytes at a character boundary (`github_unreadable`: `{"call", "reply"}`); the call then answers `stopped` (exit 3). A step that fails while the unit is `accepted`, `merged` or `dropped` applies no `stop_unit` (the store refuses it there): the call answers with `refused` (R25). A refusal or a failure of the store after the first apply, other than those R30, R31, R35 and R37 answer, ends the call at once: `store_refused` (`detail` the store's refusal) or the failure's code, exit 3, no further step.
- R23: The run applies no `approve_unit` and merges a pull request only by R31; it pushes only the update (R26), never forced; beside that push and the gate's `gh pr ready` (R17) it writes to a pull request only the comment of R43, the status of R42 and the merge of R31; merges nothing in a worktree but the fast-forward of R12 and the update's own merge, rebases nothing, changes nothing of the clone's own checkout, and removes only the one worktree and deletes only the one branch of R32; it stops only a unit of the service manager of R7's form that a record of this unit names.
- R24: The frames `fixer.md`, `second-look.md` and `continue.md` are compiled in byte for byte from `crates/ap/src/unit/frames/`, and none changes for the description; the run appends the description's line of R19 (a verifier), a frame and `## The round` after the text `ap unit page` gives, which does not change.
- R25: The answer, one JSON object on standard output: `unit`, `state` (`accepted`, `stopped`, `merged` or `dropped`), `head`, `pull_request`, `rounds`, `repairs`, `reviews` (`[{key, round, head, verdict}]` of every review of kind `packet` of the unit, by `started_at`), `updates` (the updates of this call), `carried` (`{review, from, file}`: the key of the review `carry_review` made, the key of the review it carried and the path of the `.update.md` file) only when the call carried an accept (R37; the last one when it carried more than one), `merged_commit` (the unit's, or the merge the hosting service names in the call of R35), `cleanup` when the call did one (R32), `credentials` (`[{"stage": <n>, "role": <role>, "credential": "token"|"host"}]`, one per author stage this call admitted, in order, R41) only when there was one, `detail` beside `refused` when a failed `gh` call caused it (its reply redacted and cut as in R22: `github_unreadable`, `status_failed`, `merge_failed`), and `waits_for` (`approve` for the classes `contract` and `effect`, `merge` for `plain`) for an `accepted` unit, or `stop_cause` and `stop_detail` for a `stopped` one, or `refused` (the code of the store's or the hosting service's refusal or of the failed step) where the call ended with the unit as it was. Exit 0 for `merged`, for `accepted` with `waits_for` and for a cleanup; 3 for `stopped`, for `refused`; a refusal is one line `{"error":{"code","field","detail","unit"}}` on standard error, exit 2 before the run applied anything, else 3 (always 3 in a call on a `merged` or `dropped` unit).
- R26: The update: a head that does not contain the base commit gets that commit merged into the branch in the unit's worktree, at most five times in one call (`update_limit`). The worktree is clean at the pull request's head (R12), or holds the run's own unpushed merge of exactly that head (R27). The merge is `git merge --no-ff -m "Merge origin/main into <branch> (ap unit run)" <base>` with `GIT_AUTHOR_*` and `GIT_COMMITTER_*` set to `ap unit run <ap-unit@agents.invalid>` for that one command. A conflict is aborted (the worktree left clean) and stops `merge_conflict` (`detail` the base and up to ten conflicting paths): it repeats on every call until the Lead amends the page (the branch must take `main` in, and where the conflict is) and makes the unit ready again, which gives the author one turn (R13), or drops it. The push is `git push origin HEAD:refs/heads/<branch>`, never forced; a refusal is `push_failed`. Then the hosting service is waited for until it shows the pushed head (R20). The verdict on the new head is the loop's (R37, else R19).
- R27: A clean worktree on the branch whose HEAD is a merge commit with the pull request's head as its first parent, as its second the base commit or an ancestor of it, and the message of R26 is the run's own merge left by a call cut before its push: the update takes it and pushes it, and merges again only on a later pass when `main` moved since. Any other merge commit is R12's.
- R28: Before the update's push, `record_head` is applied with the unit's present head and its writers with the word `u-<key>:update` (not the session of the run's actions, so that the run can still close a review), so that a call cut between the push and the next `record_head` loses no writer.
- R29: When the verdict of the pull request's head is `repair`, the pass goes from the read of that verdict straight to the repair step (R21), before the update and with no R16 and R17 on that head; the fixer takes `main` in by its frame.
- R30: An accepted unit (after `accept_unit` for a unit of class `plain`, or the call on an `accepted` unit): `origin main` is fetched again and its commit is the base; then the pull request the unit holds is read; one whose base is not `main` answers `refused` `pull_request_not_open` and nothing is applied or merged. Merged into `main` with the unit's `head`: `merge_unit` with the merge commit the hosting service names, then R32, and nothing else; a refusal of the store (merged by hand without the approval) answers `refused` with the unit `accepted`. Merged with another head, or closed: nothing is applied, `refused` `pull_request_not_open`. Open with another head: `reopen_unit` with the cause `head_moved`, and the loop goes on (a new verifier session). Open with the unit's head that does not contain the base: `reopen_unit` with the cause `main_moved`, and the loop goes on with the update. Open, the unit's head, up to date: for class `plain`, or an `approved_head` equal to `head`, the merge (R31); else the answer `accepted` with `waits_for` `approve`, nothing applied. A refused `reopen_unit` (a hold) answers `refused` with the unit `accepted`.
- R31: The merge: `merge_unit` is validated first (`ont action validate` with the head, the unit's `intent` in the lane `objective` and 40 zeros as the merged commit, under the request id its apply will have); a refusal (`held`, `not_approved`, `head_not_reviewed`) answers `refused` with nothing posted or merged. Then the status `lead-review` `success` (`review <key> accept`) is posted on the head as R42 says (`status_failed`), the pull request is merged with `--merge --match-head-commit <head>`, and the result is read back (merged into `main` with the head). A failed merge call whose read shows the pull request not merged has the head's statuses read (`gh api repos/<repository>/commits/<head>/status`); when `lead-review` reads `success` there (GitHub may refuse a merge for a status it has not yet taken), `gh pr merge` is called once more after a pause of 5 seconds and the pull request read again, all before a `failure` is posted. A merge not confirmed (the last call succeeded) answers `refused` `merge_unconfirmed`; a merge that failed (the last call failed) has `lead-review` posted again as `failure` for that head (R42) and answers `refused` `merge_failed` with the call's reply as `detail` (R25); the unit stays `accepted` and the next call reads the pull request first (R30). Then `merge_unit` is applied with the merge commit, then R32. The read of the head's statuses, every other read, the merge and the comment of R43 are calls with the host's login. Nothing is merged without `merge_unit` validated before and applied after it, and never twice; no unit of class `contract` or `effect` without an `approved_head` equal to the merged head.
- R32: The cleanup, after `merge_unit` and as the whole of a call on a `merged` or `dropped` unit (after R7); a failed step is a reason in `cleanup`, and `stop_unit` is never applied. The worktree: `git worktree remove` of exactly `<directory>/<key>/wt` in the clone (`--force` for a `dropped` unit, never for a merged one), only when `<directory>/<key>` and that path are each a directory and not a link and `git worktree list --porcelain` holds an entry of exactly that path; else, or when Git refuses (the worktree is not clean), `worktree_kept` with the reason. The branch, only when the unit holds a `pull_request` or has an author record: deleted (`git branch -d`, then `-D` when Git refuses it as not fully merged) only when its tip is an ancestor of `refs/remotes/origin/main` after a fetch in this call; else it stays, with the reason. A dropped unit's open pull request is not closed: it is named `pull_request_open` only when a read in this call shows it open. The unit's directory with its stage files stays; its `scratch` and `remotes` are removed, each only when it is a directory and not a link, following no link inside it, and a failed removal stops nothing. `cleanup` is `{"worktree": "removed"|"nothing"|"worktree_kept", "branch": "removed"|"nothing"|"kept"}` with `worktree_reason` and `branch_reason` for a kept one and `pull_request_open`.
- R33: `ap unit approve [--store <path>] < request.json`: one JSON object with `request_id` (1 to 44 bytes of ASCII letters, digits, `.`, `_`, `-`), `agent` and `session` (1 to 64 bytes, also `:`), `unit` (the form of R2), `head` (40 lower-case hexadecimal characters) and `reason` (at most 600 bytes); another member or form is `invalid_input` with its field, and another argument `usage`, before any call to the store. ## Interface

`ap unit run <key> [--store <path>]`; `ap unit approve [--store <path>] < request.json` (`request_id`, `agent`, `session`, `unit`, `head`, `reason`); `ap unit reject [--store <path>] < request.json` (`request_id`, `agent`, `session`, `unit`, `reason`). The policy file's member `units`: `{"directory", "timeouts": {"implementer", "verifier", "fixer"}, "github": {"lead_app": {"id", "key"}, "stage_tokens": {"<owner>/<name>": "<path>"}}, "approval": {"contract", "guarded", "sample"}}`, each optional (R3, R46 to R48); `ap unit run` refuses a policy without `units.github.lead_app` (R41).

Codes of `ap` itself: `usage`, `invalid_input`, `role_in_environment`, `unknown_unit`, `no_repository`, `invalid_branch`, `repository_not_mapped`, `policy_invalid`, `tier_not_supported`, `account_not_mapped`, `unit_run_active`, `held`, `unit_not_runnable`, `run_still_active`, `store_refused`, `no_intent`, `unknown_intent`, `not_the_lead`, `approved`, `github_not_mapped`, `input_too_large`, `store_answer_unreadable`, `store_answer_unqualified`, `process_failed`. The store's refusals of `start_unit` and `resume_unit` pass on with their codes (`held`, `dependency_not_merged`, `intent_not_confirmed`, `unit_not_ready`, `unit_not_stopped` and the others).

Stop causes: `fetch_failed`, `worktree_failed`, `git_dir_link`, `github_unreadable`, `pull_request_ambiguous`, `branch_in_use`, `pull_request_not_open`, `worktree_dirty`, `stage_refused`, `no_pull_request`, `head_not_seen`, `merge_conflict`, `push_failed`, `update_limit`, `path_outside_write_set`, `protected_path_changed`, `secret_in_diff`, `diff_unread`, `acceptance_failed`, `acceptance_timeout`, `acceptance_not_runnable`, the ends of the gate (`check_failed`, `check_timeout`, `head_differs`, `head_moved`, `merged`, `closed`, `ready_failed`), `unresolved_threads`, `verifier_failed`, `verifier_wrote`, `repair_limit`, `repair_refused`, `git_failed`, `io_error`, `limits_unavailable`, `stage_token_unreadable`.

Refusals that leave an accepted unit as it is (`refused`, R30, R31): the store's codes (`held`, `not_approved`, `head_not_reviewed`, `unit_not_accepted`, ...), `pull_request_not_open`, `status_failed`, `merge_failed`, `merge_unconfirmed`, `fetch_failed`, `github_unreadable`.

## What the Lead does after a stop

A stop that a later call would only repeat (`acceptance_failed`, `path_outside_write_set`, `protected_path_changed`, `secret_in_diff`, `diff_unread`, a gate end that did not pass, `unresolved_threads`, `merge_conflict`, `repair_limit`, `repair_refused`, `no_pull_request`) has two ways out: amend the page (`ap unit amend`), have it reviewed where its class asks (`ap unit review`), make the unit ready (`ap unit ready`) and run it again, which gives the author ONE turn on the amended page (R13) and counts `rounds` and `repairs` anew from the amendment; or drop it (`ap unit drop`). For `protected_path_changed` the amendment either changes the class to `contract` (the page is then reviewed, and its write set names the paths) or says that the author takes the change out. For `secret_in_diff` the Lead reads the named lines in the unit's worktree without printing them, and the amendment then either admits an invented fixture line (R44's admission: the digest computed from the head's file without printing the line) or says that the author takes the line out; a fixture moved to another path is read at its new path (`--no-renames`) and needs an admission line for that path; a line of a real credential was on the branch of the hosting service before the scan read it and stays in that branch's history after the author takes it out, since the run rewrites no history (R23): the credential is revoked, which is the user's step. For `diff_unread` the amendment has the author bring the change of that path under the port's limit (for example over two units), or the Lead drops the unit. For `merge_conflict` the amendment says that the branch must take `main` in and where the conflict is. A stop on a cause outside the unit (`fetch_failed`, `github_unreadable`, `head_not_seen`, `push_failed`, `update_limit`, `stage_refused`, `worktree_failed`, `stage_token_unreadable`) is run again once its cause is gone: `resume_unit` takes the unit back on the same page. `git_dir_link`, and `worktree_failed` with `git directory unreadable`, repeat while the entry stays; the Lead reads where a link points, removes the entry and calls `ap unit run` again (a `stopped` unit is taken back by `resume_unit`, R6; a `merged` or `dropped` unit gets its cleanup), or drops the unit.

An accepted unit of class `contract` or `effect` waits for the Lead (but for a `contract` unit the policy approved, R47, whose sample finding the Lead reads, R48): `ap unit approve` with the head the Lead read, then `ap unit run` merges it; or `ap unit reject` with the reason, then the amendment (`ap unit amend`, review, `ap unit ready`) or the drop. A reject cut between its two applies leaves the unit `running`: the Lead repeats it with the same `request_id` before any run. An `accepted` unit answered `refused` is run again once the cause is gone, rejected (unless approved) or dropped; an approved unit can only be held or dropped.

## Trust

The stages' sessions are claims of `ap run`'s records; `writers` holds every session that an author record names, so the store refuses each of them as the closer of a review of the unit. A verifier that writes or pushes becomes a writer before the unit stops. The run trusts no path or name of a record or of the store before it was checked: a stage's unit by its form, a run object by its record path, a review's report by its key.

## Not included

- The closing of a dropped unit's pull request, and the cleanup of a branch that is not in `main`.
- A lock taken by `ap unit drop` (R35 states the limit).
- A unit without a repository, a tier of another runtime, a verifier beside the required check, the dispatch pass.
- Two leftovers the run cannot find: a check's own unit, which ends by its bound of 320 seconds, and a `run` object left `running` by a call that died between `start_run` and the record's first write.
