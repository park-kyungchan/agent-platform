# The dispatch pass: `ap work`

Purpose: one pass starts every unit of the store that may start now (a `ready` unit whose constraints hold, or an `accepted` unit that waits only for its merge run) as a run of `ap unit run <key>` in a transient unit of the service manager, and notes on every `ready` unit that does not start what it waits on; a timer of the service manager runs a pass every minute, so that the Lead no longer starts units by hand.

## Requirements

- R1: The form is `ap work [--store <absolute path>]`, one pass, by arguments only (no standard input); another argument, or `--store` twice or without an absolute path, is `usage` (field `args`). Before any effect, in this order: `ONT_ROLE` `lead` in the environment is `role_in_environment` (field `ONT_ROLE`), as `ap unit run` refuses it; `AP_POLICY_FILE` set and not empty without `--store` is `invalid_input` (field `store`: a trial's pass never reads the host's store); `--store` without `AP_POLICY_FILE` set and not empty is `invalid_input` (field `policy`: a scratch store's units never run under the host's policy, slice and units directory). Each is exit 2.
- R2: No policy file answers `{"skipped":"no policy file"}`; a policy file without the member `work` answers `{"skipped":"no work"}` (the Lead's switch: removing the member stops every start); when the host has no service manager (`System::units` is false) the answer is `{"skipped":"no service manager"}`. Each skip is exit 0 with no other call and no file or directory made. A policy file that cannot be read or is not one JSON object is `policy_invalid` (field `policy`, the detail beginning with `file`), exit 2.
- R3: The member `work` is an object of `slots` (an integer from 1 to 16, default 3: the units in flight), `slice` (1 to 32 characters of `a-z0-9` followed by `.slice`, no dash; default `agents.slice`) and `prefix` (1 to 16 characters of `a-z0-9-`, beginning with a letter and not ending with `-`; default `ap-unit`). Another member, a `work` that is not an object or a value out of its form is `policy_invalid` (field `policy`, the detail beginning with `work`), exit 2. With `--store`, a `work` without `slice` or `prefix`, or a policy without `units.directory`, is `invalid_input` (field `policy`), exit 2. The units directory is the member `units.directory` `ap unit run` reads (`specs/ap/unit-run.md` R3, `policy_invalid` as there); when the policy has `quota` (`specs/ap/quota.md` R2, refused as there), its `busy_limit` and `floor` bound the starts (R13). A run's unit of the service manager is `<prefix>-<key>.service`.
- R4: The pass makes the units directory when it is absent (mode 0700), opens `<units directory>/work.lock` (made with mode 0600 when absent, never through a link) and waits for an exclusive advisory lock (`flock`) on it for at most 120 seconds; one not taken then answers `{"skipped":"pass_running"}`, exit 0, with no call to the store. The pass reads the store only after it holds the lock, so that a pass that waited sees what the pass before it changed, and holds the lock to its end.
- R5: The reading, once per pass with the lock held: every unit in the states `ready`, `running` and `accepted` (one search by `state` through `store.rs`, paged, each page qualified), and the units of the service manager whose names begin with `<prefix>-` (`systemctl list-units --all --plain --no-legend <prefix>-*`). Only a name `<prefix>-<rest>.service` is a run unit, live when its third column is `active`, `activating`, `deactivating` or `reloading`. A `systemctl list-units` that fails, or a line whose first three columns cannot be read, ends the pass with `reading_failed` (field `list_units`), exit 3, before any start.
- R6: A unit whose key does not have the form `ap unit add` gives a new key (1 to 59 bytes of `a-z0-9-`, beginning with a letter) is in no set of the pass, and no path or name is built from its key. A unit's lock `<units directory>/<key>/lock` is tested only when the file exists: opened without create and without following a link, with a shared `flock` attempt that does not wait and is released at once. A shared attempt does not hold off another reader, but a run's own exclusive attempt (`ap unit run`), or one of `ap unit approve` or `ap unit reject`, at that same instant answers `unit_run_active`. A unit is in flight when its run unit is live or its lock is held, in any state (a run started by hand, a merge run the Lead started); a live run unit whose key is not among the units read (a unit dropped while its run works, or a name of another form) counts in `slots` too.
- R7: A `running` unit that is not in flight is cut: the pass never starts it (a run that ends with its unit as it was would be started again by every pass); it lists it under `cut`, and the Lead's direct `ap unit run <key>` takes it over.
- R8: The candidates are the units that are not in flight, in this order: the `accepted` units that wait only for their merge run (class `plain`, or `approved_head` equal to `head`), by key; then the `ready` units by `ready_at`, then key. A candidate's revision and fields are read with one `ont get`, and that read decides its state (a unit no longer `ready`, or no longer such an `accepted` unit, is skipped) and its stored `waits_on`. A `waits_on` text is cut to 300 bytes at a character boundary.
- R9: A unit is started at most once for one revision of it in the store: a candidate whose revision equals the text of the file `<units directory>/<key>/started` is not started and is listed under `not_restarted`.
- R10: Every other candidate is started when all of R10 to R13 hold; a `ready` one that is not started gets the first that fails as its `waits_on`, in this order: it has a repository (`no repository`); the checks `ap unit run` makes before any action (the key, the branch, the policy's entries, the tiers: `specs/ap/unit-run.md` R2), as the one function of the run's module that both call (`run refused: <code>`); the store would let it go on: for a `ready` unit one `ont action validate` of `start_unit` (with its `intent` in the lane `objective`), the failed codes joined by `, `, but `dependency dropped: <key>` when a unit of `depends_on` is `dropped` (a unit of `depends_on` is read with one `ont get` each only when the validate fails `dependency_not_merged`); for an `accepted` unit one validate of `merge_unit` with its head and a placeholder commit of 40 zeros, and one that fails it is listed under `waiting` with the codes and gets no note.
- R11: A `ready` unit does not start while another unit of the same repository that is in flight (the starts of this pass included: such a unit is still `ready` in the pass's one reading) or in the state `running` or `accepted` has a write set that overlaps its own: `write set overlaps <key>`. Two patterns overlap when the literal beginning of one, up to its first `*`, is a prefix of the other, compared as path components: a pattern without `*` is a prefix only of itself and of the paths below it, and the last component before a `*` is a prefix of a component (`crates/ap/src/**` and `crates/ap/src/run.rs` overlap, `crates/ap/**` and `crates/ont/**` do not, `check` and `check` do, `a/b*` and `a/bc/d` do). The rule is the write-set matcher's (`outside` in `crates/ap/src/review.rs`, which `ap unit run` calls) where that matcher knows exact paths and `<dir>/**`, and stricter where it does not: the matcher takes `a/b*` as a file of that literal name, the overlap rule as every path that begins `a/b`.
- R12: The units in flight, this pass's starts and the live run units of R6 included, must be fewer than `slots`: else `slots <n>/<slots>`.
- R13: When the policy has `quota`: one reading per pass by the reading function of `crates/ap/src/quota.rs` (`load`: the busy share of all CPUs and `outside` of `quota.slice`, over ten seconds), taken only when the pass has a candidate that passed R10 to R12. A start needs both: the busy share at or under `quota.busy_limit` (else `cpu over <busy_limit>%`), and what the limit leaves for the slice at least its floor, `busy_limit` × CPUs − `outside` ≥ `quota.floor` (else `cpu outside`). The second is the pass's own: when the load outside the slice leaves the slice less than its floor, `ap quota` holds the floor and cannot hold the limit (`specs/ap/quota.md`), so a start would take the host over. The texts hold no reading, so a unit that waits on them gets one note, not one per pass; the readings are the answer's `busy` and `outside`. A reading that fails ends the pass with `reading_failed`, exit 3, after the starts it made.
- R14: A start: a `ready` unit's stored `waits_on`, when not empty, is cleared (`note_unit_wait` with the empty string), and the revision the apply's answer names (`edits[].revision`) is the unit's; that revision is written to `<units directory>/<key>/started` (the directory `<key>` made with mode 0700 when absent); then `systemd-run --unit <prefix>-<key> --slice <slice> --collect --quiet --expand-environment=no --setenv <NAME>=<value>… -- <this ap> unit run <key> [--store <path>]`, with the names `ap run` keeps for a stage (`PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_ALL`, `TERM`, `TMPDIR`, `TZ`) as the pass has them, and `AP_POLICY_FILE` when it is set; `<this ap>` is `/proc/self/exe` read as a link with a trailing ` (deleted)` cut. The run unit has no bound (every stage, check and wait inside has its own; a bound here would kill only the driver and leave its stage running) and is a transient unit of its own, not a child of the pass's service, so the end of the pass's service does not end it. The pass does not wait for the unit.
- R15: A `systemd-run` that fails (a name still loaded, a unit that is ending) is no start: the file `started` the pass just wrote is removed, the unit is not in flight, a `ready` one gets `waits_on` `start failed`, and the pass goes on (the next pass tries it again).
- R16: `note_unit_wait` is applied for a waiting `ready` unit only when its `waits_on` differs from the stored one; a refusal `unit_not_ready` (the unit moved meanwhile) is no failure of the pass, and a unit whose clear is refused so is not started. A store call that fails ends the pass with that error, exit 3, after the starts it already made: they are the error's `started`.
- R17: The pass's applies and validates carry the client `ap`, the agent `ap-work`, the session `w-<16 hexadecimal characters drawn once per pass>`, no role, and the request id `wk-<those characters>-<counter>`, the counter from 1 in the pass; no id is built from a unit or a text.
- R18: The answer, one JSON object on standard output, exit 0: `started` (keys), `cut`, `not_restarted`, `waiting` (`[{unit, waits_on}]`), `in_flight` (the keys of the units read that were in flight, then the names of the live run units whose keys were not read), `busy` and `outside` (each null when not read). A refusal or failure is `{"error":{"code","field","detail"}}` on standard error, with `started` after the lock was taken.
- R19: The pass's only effect on the service manager is the `systemd-run` of R14, of a unit named `<prefix>-<key>` from a key whose form it checked, in the policy's slice: it sets no property, stops and removes no unit and runs no reload. It removes no file but a file `started` it wrote in the same pass, and writes no file but `work.lock` and the files `started`.
- R20: `observe` of `crates/ap/src/work.rs` is the reading `ap status --wait` needs: for given units (key and revision), which are in flight and which have a file `started` equal to their revision, by the rules of R5, R6 and R9. It writes nothing and takes no `work.lock`; its test of a unit's lock is the shared attempt of R6.
- R21: `deploy/ap-work.service` is `Type=oneshot`, `ExecStart=/usr/local/bin/ap work`, `Environment=HOME=/root`, `Environment=PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin`, `TimeoutStartSec=300` and has no `Slice=` (the pass runs outside the slice it fills). `deploy/ap-work.timer` has `OnBootSec=2min`, `OnUnitInactiveSec=60s`, `AccuracySec=1s` and `WantedBy=timers.target`.

## Interface

`ap work [--store <path>]`. The policy file's member `work`: `{"slots", "slice", "prefix"}`, each optional without `--store`. The answers: `{"started", "cut", "not_restarted", "waiting", "in_flight", "busy", "outside"}`, or `{"skipped": "no policy file" | "no work" | "no service manager" | "pass_running"}`.

Codes of `ap` itself: `usage`, `role_in_environment`, `invalid_input`, `policy_invalid` (exit 2); `reading_failed`, `io_error`, `store_answer_unreadable`, `store_answer_unqualified`, `store_refused`, `process_failed` (exit 3).

The texts of `waits_on`: `no repository`, `run refused: <code>`, the store's codes joined by `, `, `dependency dropped: <key>`, `write set overlaps <key>`, `slots <n>/<slots>`, `cpu over <busy_limit>%`, `cpu outside`, `start failed`.

The timer, its install, the switch and the undo: `deploy/README.md`, "The dispatch pass".

## What the pass does not hold

- A unit that may start waits up to one period of the timer.
- With the timer stopped, or the member `work` absent, nothing starts; the runs in flight go on.
- A cut run, a run that ended with its unit as it was (a merge the hosting service refused, a start the store refused), and a unit whose pass was killed between the write of `started` and `systemd-run` are started by no pass (they are listed under `cut` or `not_restarted`): the Lead reads why and calls `ap unit run <key>`.
- A `stopped` unit is never a candidate (the Lead amends it and makes it ready), and it holds no write set: a `ready` unit that overlaps it may start while its pull request is open.
- The overlap rule is stricter than the write-set matcher for a `*` that is not `<dir>/**` (R11): two such units of one repository may wait on each other where their paths would not meet.
- The shared attempt on a unit's lock (R6) can meet a run's own exclusive attempt at the same instant; that run answers `unit_run_active` and the next pass sees it not in flight.

## Not included

- A pass run by any other verb, a flag `--now` (a direct `ap unit run` is that override, and its `start_unit` is the log), the CPU quota itself (`specs/ap/quota.md`), `ap status --wait`, limits on memory or on the accounts, an automatic hold after repeated stops, the start of a unit without a repository, a priority beyond the order of `ready_at`, and the install (a Lead installs the timer).
