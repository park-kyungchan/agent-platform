# The API credit: `ap api batch` and the function `api_spend`

Purpose: the one door of the Claude API credit. `ap api batch <job> --requests <file> --out <dir>` reads a request file a builder wrote, admits it against the job's cap, the day's cap and the month's stop of the policy's member `api` by its worst case before any call is made, reserves that worst case as a `run` of role `batch` in the store, submits one Message Batch through `curl` with the key in a header file, polls it, writes its results and settles the run with the results' `usage`. `ont fn api_spend` answers what a month spent by job, by the same rule the admission counts with. The objects and the function are those of schema version 18 (`ontology/README.md`, "Version 18: the credit's ledger"); the prices are the rows of `evals/prices.tsv`, read when `ap` is built.

## Requirements

- R1: `ap api batch <job> --requests <file> --out <dir> [--queue standard|soak] [--store <path>]` takes its options in any order, each once; `<job>` is 1 to 40 of `[a-z0-9_-]`; the three paths are absolute; `--queue` is `standard` when absent. `ap api --help` and `ap api batch --help` print the usage, exit 0. Any other argument list (a first argument other than `batch`, no job or two, an unknown option, an option twice or without its value, an argument that is not UTF-8, a missing `--requests` or `--out`) is `usage` (field `args`); a value of another form is `invalid_input` with the option's name without dashes as the field (`job`, `requests`, `out`, `queue`, `store`).
- R2: A path given (`--requests`, `--out`, `--store`) with a component that begins with `education-` or `edu-`, or with a component `evals` directly followed by a component `lesson`, is refused `academy_path` (field the option) before any file system call on it.
- R3: The policy's member `api`, read from the file of `specs/ap/policy.md` R1, is an object with exactly `key_file` (an absolute path directly under `/etc/agent-platform/credentials/`), `stops_usd` (exactly `standard` and `soak`, integers 1 to 1000, `standard` at most `soak`), `day_cap_usd` (an integer 1 to 1000) and `jobs` (1 to 32 entries, each key of R1's job form, each with exactly `cap_usd` (an integer 1 to 1000, the job's cap of a month), `models` (1 to 8 distinct Claude API model identifiers, `claude-` then 1 to 57 of `[a-z0-9.-]`, each with an `input` and an `output` row of the price file), `max_tokens` (1 to 128000) and `max_requests` (1 to 100000)); amounts are whole USD. The credit's account is the last path component of `key_file`. No policy file or no member `api`: `api_not_configured` (field `policy`); a file that cannot be read as one JSON object, or a member of another form: `policy_invalid` (field `policy`, `detail` a sentence beginning with the member, such as `api.jobs.drift.models`); a job the member does not name: `unknown_job` (field `job`).
- R4: The key file is examined and read only through the port: the trait `Api` of `crates/ap/src/api.rs` extends `System` with `examine`, which reads a path's kind without following a link, its owner's uid, its mode and the effective uid of this process from `/proc/self/status`. The file must be a regular file (a link is not), owned by uid 0 or by the effective uid, with no permission bit for group or others; then it is read through the port's `read`, its one final line feed dropped, and must be 1 to 256 bytes of printable ASCII without a space. Else `key_unusable` (field `key_file`, `detail` `not_found`, `not_regular_file`, `owner_not_trusted`, `group_or_other_access` or `not_one_line`); no refusal names a byte of the file.
- R5: The request file is read once, at most 200,000,000 bytes (`requests_too_large`, field `requests`). Each line is one JSON object with exactly `custom_id` (`^[A-Za-z0-9_-]{1,64}$`, each once) and `params` (an object with `model` (a string), `max_tokens` (an integer from 1) and `messages` (an array), and no member outside `model`, `max_tokens`, `system`, `messages`, `output_config`, `tools`, `tool_choice`, `thinking`); else `request_invalid` (field `requests`, `detail` `{"line","reason"}`, the line counted from 1). A file without a line is `no_requests` (field `requests`); more lines than the job's `max_requests` `over_max_requests` (field `requests`); lines that name more than one `params.model` `models_mixed` (field `model`); a `params.model` outside the job's `models` `model_not_allowed` (field `model`); a `max_tokens` above the job's `over_max_tokens` (field `max_tokens`).
- R6: An `--out` path that exists (a link included) is `out_exists`; one whose parent is no directory is `invalid_input` (both field `out`). The directory is made, mode 0700, only at R10.
- R7: The refusals of R1 to R6 exit 2 with `{"error":{"code","field","detail"}}` on standard error before any effect: no lock, no store call, no `curl`.
- R8: The run directory is the one `AP_API_RUN` names in the port's environment when it is set and not empty, else `/run/agent-platform`; it is made mode 0700 when absent, and one that is no directory or is a link is `invalid_input` (field `run`, exit 3). An exclusive `flock` on its file `api.lock` (made mode 0600) is held from the first read of R9 to the end of R10, waited for at most 300 seconds by the port's clock, then `lock_busy` (field `run`, exit 3, nothing reserved). Under the lock, a key directory of R11's form whose `<pid>` names no live process (no `/proc/<pid>`) is removed; the directory of a live process is never removed.
- R9: The spend of a period is the runs whose `role` is `batch` and whose `started_at` falls in the period; a run counts its `settled_usd_micros` when it is `closed` and has one, else its `reserved_usd_micros` (a running run, and a closed one without a settlement; none counts 0). The periods of a call are the UTC calendar month and the UTC day of its start. The read is one search of `run` whose filter names only `role` and `started_at`, every page read through `crates/ap/src/store.rs`; a read that fails is `store_failed` (field `store`, exit 3), and nothing is called.
- R10: The worst case of a request at the batch price, half the rate of `evals/prices.tsv`, in whole micro-USD rounded up once per request: its output part is ceil(max_tokens x output / 2); its whole is ceil((n x r_in + max_tokens x output) / 2), n the `input_tokens` the counting endpoint answers for its `params` without `max_tokens`, r_in the rate `input`, or `cache_write_1h` when `params` holds a member `cache_control` at any depth, and the rows of `<model>+long` when the model has a `long_over_tokens` row that n passes. The caps, in this order: `job` (the job's spend of the month plus the amount over `cap_usd`), `day` (the day's spend plus the amount over `day_cap_usd`), `month` (the month's spend plus the amount over the `stops_usd` of `--queue`). The sum of the output parts is admitted before any `curl`; then one count call is made per request, in order; then the sum of the wholes is admitted. A refusal is `budget_exceeded` (field the cap's name, `detail` `{"cap_usd_micros","counted_usd_micros","worst_usd_micros"}`), exit 2, with no run and no batch call. A count call without a 200 answer holding an integer `input_tokens` (a 429 included, without a retry) is `count_failed` (field `requests`, `detail` `{"line"}`), exit 3. Then `--out` is made and `start_run` is applied through `store::start_run_api` (one attempt of 15 seconds, claimed as `api`, `specs/ap/roles.md` R3) with the parameter `role` `batch`, `runtime` `api`, `model` (the file's one model), `account` and `uses` (R3's account), `host` (the reference of the host `local`), `job`, `reserved_usd_micros` (the sum of the wholes) and `record` `<out>/batch.json` (when it is a `file_path` of the schema), under the request id `api-<first 32 hex digits of the SHA-256 of the path of --out, the call's start time in nanoseconds since 1970 and its pid, joined by a line feed>-start`, made once per call. A start without an answer is sent once more with that id and the same parameters, and only that retry may accept `already_applied`; a refusal, a first `already_applied`, an answer without a run, or a second failure is `store_failed` (exit 3) with no batch call, and `--out` keeps `batch.json` at `store_failed`. `<out>/batch.json` (mode 0600, rewritten at each later step) holds `job`, `run`, `model`, `requests`, `reserved_usd_micros`, `batch` and `state` (`store_failed`, `reserved`, `submitted`, `submit_refused`, `submit_uncertain`, `poll_timeout`, `results_unreadable`, `settled`, `close_failed`). Then the lock is released.
- R11: Every call of the API is one `curl` through the port, whose first argument is `-q`, with the headers `anthropic-version: 2026-10-21` and `content-type: application/json`, `--proto =https`, a `--max-time` and `--write-out` of the HTTP status as the last line of standard output; a body goes on standard input. The key reaches `curl` only through a header file: for each call `ap` makes a directory of a fresh name `key.<pid>.<n>` (mode 0700) in the run directory, writes into it the file `header` (mode 0600, created new, one line `x-api-key: <key>`), passes `-H @<that file>`, and removes the file and the directory when the call has ended, whatever its end. The key is in no argument, environment variable, standard input, record, answer, store parameter or other file. The URL is one of `https://api.anthropic.com/v1/messages/count_tokens`, `https://api.anthropic.com/v1/messages/batches`, `https://api.anthropic.com/v1/messages/batches/<id>` and `https://api.anthropic.com/v1/messages/batches/<id>/results`, never one taken from an answer.
- R12: The submit is one POST of `{"requests": [the lines as read, in order]}`. A 200 answer whose `id` matches `^[A-Za-z0-9_]{1,128}$` makes `state` `submitted`, and that id is the only text of an answer that enters a URL. A 4xx answer: `close_run` (R14's request id and attempts) with `state` `submit_refused`, `settled_usd_micros` 0, no `session` and no token count, `batch.json` at `submit_refused` (`close_failed` when the close failed), and `submit_refused` (field `requests`, `detail` `{"status"}`), exit 3. No answer, a timeout, a 5xx, an unreadable answer, or a 200 answer without such an id: `submit_uncertain` (field `requests`), the run left `running` at its reservation, exit 3; no submit is sent twice.
- R13: The poll is one GET of the batch every 60 seconds of the port's clock until its `processing_status` is `ended`; a failed poll is asked again at the next turn; 25 hours after the submit without `ended`: `poll_timeout` (field `batch`), the run left running, exit 3. Then one GET of the results into `<out>/results.jsonl` (made mode 0600 before the call), the lines as the API gives them: each must be one JSON object, the result of a `custom_id` of the file with a `result.type` of `succeeded`, `errored`, `canceled` or `expired`, and every `custom_id` of the file must have exactly one; else, or when the GET has no 200 answer, `results_unreadable` (field `results`, the run left running, exit 3).
- R14: The settlement of a `succeeded` line is ceil((input_tokens x input + cache_read_input_tokens x cache_read + c5 x cache_write_5m + c1 x cache_write_1h + output_tokens x output) / 2) of its `usage`, c1 `cache_creation.ephemeral_1h_input_tokens` when present (else 0) and c5 `cache_creation_input_tokens` less c1, with the `+long` rows when the three input counts together pass `long_over_tokens`; an `errored`, `canceled` or `expired` line is 0. Then `close_run` (claimed as `api` through `store::close_run_api`, request id the start's with `-close` in place of `-start`, sent once more when it has no answer) with `state` `ended`, `session` the batch id, `input_tokens`, `cache_read_tokens`, `cache_write_tokens` and `output_tokens` summed over the `succeeded` lines and `settled_usd_micros` the sum of the settlements. A close that fails twice is `close_failed` (field `store`), exit 3, and the run counts at its reservation.
- R15: The answer is one JSON line on standard output, `{"job","run","batch","requests","results":{"succeeded","errored","canceled","expired"},"stop_reasons":{<stop_reason>: <count>},"reserved_usd_micros","settled_usd_micros","out"}`, exit 0. A failure after R7 is `{"error":{"code","field","detail"}}` on standard error, exit 3, but `budget_exceeded`, exit 2.
- R16: The effects are the run directory with its lock file and its key directories (each removed after its call), `--out` with `batch.json` and `results.jsonl`, `start_run`, `close_run` and the `curl` calls; nothing else is written or applied.
- R17: `ap` started with no argument and `ONT_FN_NAME=api_spend` is the function `api_spend`: it reads `{"month": "YYYY-MM"}` (a month 01 to 12) from standard input and the store at `ONT_FN_STORE` through `crates/ap/src/store.rs`, and prints `{"month","jobs":[{"job","runs","running","settled_usd_micros","reserved_usd_micros","counted_usd_micros"}],"settled_usd_micros","reserved_usd_micros","counted_usd_micros"}`, the jobs by key (a run without `job` under the job `""`), by R9 (`settled` sums the runs counted at their settlement, `reserved` those counted at their reservation, `counted` both), exit 0. Another member, a missing `month` or a month of another form is `invalid_input` (field the member), exit 2; a store that cannot be read exits 3, in the form of `specs/ap/route.md` R15.
- R18: The parameters of R10's `start_run` and R14's `close_run` are those of schema version 18: `start_run` takes `job` and `reserved_usd_micros`, `close_run` takes `settled_usd_micros`, and their rules set the run's properties of those names.

## Interface

`ap api batch <job> --requests <file> --out <dir> [--queue standard|soak] [--store <path>]`; `ont fn api_spend` with `{"parameters": {"month": "YYYY-MM"}}`. The policy's member `api` (R3):

```json
{"key_file": "/etc/agent-platform/credentials/anthropic-api-key",
 "stops_usd": {"standard": 160, "soak": 185}, "day_cap_usd": 40,
 "jobs": {"drift": {"cap_usd": 60, "models": ["claude-sonnet-5-5"], "max_tokens": 8000, "max_requests": 100}}}
```

The key file holds the bare key on one line, owned by root with mode 0600. The run directory is `/run/agent-platform`, or `AP_API_RUN`. The prices are the rows of `evals/prices.tsv` of the commit `ap` was built from: `crates/ap/src/api.rs` includes the file at build time, and no price is written in Rust or in the policy.

Codes of `ap api batch`, exit 2: `usage`, `invalid_input` (but field `run`), `academy_path`, `api_not_configured`, `policy_invalid`, `unknown_job`, `key_unusable`, `requests_too_large`, `request_invalid`, `no_requests`, `over_max_requests`, `models_mixed`, `model_not_allowed`, `over_max_tokens`, `out_exists`, `budget_exceeded`. Exit 3: `invalid_input` (field `run`), `lock_busy`, `store_failed`, `count_failed`, `submit_refused`, `submit_uncertain`, `poll_timeout`, `results_unreadable`, `close_failed`, `io_error`. Codes of `api_spend`: `invalid_input` (exit 2), and the store's codes (exit 3).

## Not included

- The timers, the choice of `--queue`, the soak rule and the watch's detector `credit` (a later unit); the policy's `api` on the host, the key file and the Console's steps (the user's).
- A resume of a batch after `ap` died, a cancel, and the close of a run left `running` (an uncertain submit, a poll timeout, a failed close): it counts at its reservation until it is closed by hand.
- A new try of an `errored` request; `fallbacks`; server tools (the counting endpoint refuses them: `count_failed`).
- A margin over the counting endpoint's count: the settlement takes the results' `usage`.
- A credit month other than the UTC calendar month; a comparison with the Console's figure.
- The credit's `account` object and its allowance: `uses` may dangle.
- A grant of the role `batch` (the run's `role` parameter is `batch`; the claim of its applies is `api`, `specs/ap/roles.md` R2); `api_spend` through a stage's door.
- A retry of a count call answered 429, and a split of a request file over days.
