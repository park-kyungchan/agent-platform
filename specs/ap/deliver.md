# Delivery: `ap deliver` installs the accepted tip of `main` and brings the host's main checkouts to it

Purpose: the pair `ap` and content of this repository on the host is the fetched tip of `origin/main` when every merge on the way is accepted, the engine and the work schema follow what that tip names when the request asks for it, and a file under a platform repository's main checkout on the host equals `origin/main` after delivery has run, so that an agent that reads it reads the current code; every attempt is an `install` object of the store, the pair is rolled back by the command itself when the installers leave it at no single commit, and a Lead's rollback request undoes the newest install by the same command; the unit files of `deploy/` on the host follow the commit an install brings the pair to, and a clone's scripts run only from a commit the command judged. This file is the whole of `ap deliver`: R1 to R7 the checkouts, R8 to R10 the form `ap deliver check`, R11 to R36 the install of the pair (R20 to R31 are the steps 1 to 12 of a call), R37 to R46 the engine and the schema, R47 the clone's tree, R48 to R51 the unit files, R52 the confinement of the services.

## Requirements

- R1: The request may carry `checkouts`: an array of 1 to 20 strings, each an absolute path of at most 4,096 bytes with no `.` or `..` component, no control character and no trailing `/`, and no two equal. Anything else refuses `invalid_input` with field `checkouts` (exit 2, nothing written, as for every other member). `checkouts` is one of the members a request may hold, in the timer's form and in a Lead's form, and a rollback request may carry it.
- R2: The step runs only in a call whose `end` is `current` or `installed` and whose request has no `rollback`, after every step that ends the call today and before `last.json` is written, while the call holds the deliver lock. It never runs in a call that ended `refused`, `failed`, `failed_restored`, `not_started` or `unrecorded`, and never in a rollback call. It changes neither `end`, `code` nor the exit.
- R3: For each checkout, in the request's order, the step runs the commands below one by one through the call's `System`, each as `git --no-optional-locks -C <path> -c core.hooksPath=/dev/null -c gc.auto=0 -c maintenance.auto=false <words>`. A command passes only when it exits 0 within its bound and prints what its line asks.
  1. `rev-parse --show-toplevel` (30 seconds) prints exactly `<path>`.
  2. `symbolic-ref --short -q HEAD` (30 seconds) prints `main`.
  3. `status --porcelain --untracked-files=no` (30 seconds) prints nothing. Untracked files do not count.
  4. `fetch --quiet --no-tags origin +refs/heads/main:refs/remotes/origin/main` (60 seconds).
  5. `rev-parse --verify HEAD^{commit}` (the `from`) and `rev-parse --verify refs/remotes/origin/main^{commit}` (the tip), each 30 seconds and 40 hex digits, read once. When they are equal the checkout is `current` and the steps end. Otherwise `merge-base --is-ancestor <from> <tip>` (30 seconds) with the two ids.
  6. `merge --ff-only --quiet <tip>` (600 seconds), with the tip's 40 hex digits and never the ref name, then `rev-parse --verify HEAD^{commit}` (30 seconds) read again.
- R4: The result of a checkout is one of: `not_a_checkout` (step 1 did not pass), `not_on_main` (step 2), `dirty` (step 3 printed something), `fetch_failed` (step 4 failed or timed out), `current` (step 5, equal), `diverged` (the `merge-base` of step 5 did not succeed: `<from>` is not an ancestor of the tip), `forwarded` (step 6, the read after the merge equals the tip) and `git_failed`: step 3 failed, a read of step 5 failed or printed something else than 40 hex digits, or step 6 ended with a `HEAD` that is not the tip. The read after the merge decides, whatever the merge's exit. A result other than `forwarded` and `current` stops the steps of that checkout; the next checkout is still taken.
- R5: No other Git command and no other write touches a checkout: no reset, stash, clean, checkout, commit, push or branch change, and no command after a step that did not pass. A checkout whose result is not `forwarded` is unchanged: its working tree's files, its index's entries, `HEAD` and `refs/heads/*`; step 4 adds objects and moves `refs/remotes/origin/main` and `FETCH_HEAD`.
- R6: The record has the member `checkouts` only when the request holds it: `null` when the step did not run (R2), otherwise an array in the request's order of `{"path", "from", "to", "result"}`. `from` is the `HEAD` read in step 5, `null` when step 5 did not read it. `to` is equal to `from` for `current`; the `HEAD` read after step 6 for `forwarded` and for a `git_failed` of step 6, `null` when that read failed; `null` for every other result. The `invalid_input` record never has the member. The answer on stdout is the same record.
- R7: A request without `checkouts` gives exactly the record and the calls it gave before this specification: no `git -C <checkout>` command and no member `checkouts`.
- R8: `ap deliver check < request.json` runs exactly the request check of `ap deliver` and nothing after it: no state directory, no lock, no fetch, no store action, no `last.json`, no program call. A request that passes exits 0 and prints `{"status":"ok"}`.
- R9: A request the check refuses exits 2 and prints the record `ap deliver` prints for that request (`end` `refused`, `code` `invalid_input`, `detail` `{"field"}`), with the same `at` form and no other difference.
- R10: `ap deliver` without an argument is unchanged, and any other argument, `check <x>` included, is refused `invalid_input` with field `args`.
- R11: `ap deliver < request.json`, called by a Lead or by the timer `ap-deliver.timer`, brings the pair to the fetched tip T of `origin/main` when every merge on the way is accepted, records the attempt as an `install` object of the store, and prints one JSON record on standard output (R35). Its only network calls are the fetches of R22 and R43 (and of the checkouts, R3); it calls no API of the hosting provider and needs no token.
- R12: The request is one JSON object on standard input with these members: `repository` (`owner/name`, the name the reviews carry), `url` (where `git` fetches it from), `state` (an absolute directory, made when absent: the command's clone `<state>/<name>`, its build directory `<state>/target`, its last record `<state>/last.json`), `build_lock` (the absolute path of the host's build lock, the file `scripts/install-ap.sh` locks around its build), optional `build_wait_seconds` (an integer from 0 to 900, absent means 0), optional `engine` (R14) and `checkouts` (R1), and one of three forms, told apart by the other members: a Lead's install, `by` (who calls: a session id, 1 to 200 bytes), `reason` (1 to 400 bytes) and optional `past` (an array of at most 50 commits of 40 hex); a Lead's rollback, `by`, `reason` and `rollback: true`, no `past`; the timer's, none of `by`, `reason`, `past`, `rollback`. The timer's `by` in the record and in the attempt is `timer:` followed by the value of the environment variable `INVOCATION_ID`, or `timer` when that is unset or empty (systemd sets it for each run of a unit).
- R13: An unknown, missing or malformed member, or any other combination of the four, refuses `invalid_input` before anything is made (`detail.field`: a malformed or false `rollback` names `rollback`; else the first missing member of `by`, `reason`; `past` beside `rollback` names `past`). The name of the clone may not be `.`, `..`, `target` or `last.json` (`invalid_input`, field `repository`).
- R14: `engine`, optional in each form, is an object with exactly `repository` (`owner/name` of the engine's repository, the name its reviews carry) and `url` (where `git` fetches it from), each checked as the request's own; the engine's name follows the rules of the clone's name and may be neither the repository's name nor `migrate.pending`, and with `engine` the repository's name may not be `migrate.pending` either (`invalid_input`, field `engine`, or `repository`). Without `engine` a call is as R11 to R36 say; R37 to R46 apply only with it.
- R15: The target is the `installed_artifact` whose key is `/usr/local/bin/ap`, always. The pair is the file `ap` in the directory `AP_INSTALL_DIR` names and the content tree `AP_CONTENT_DST` names; the command reads these two, `AP_BACKUP_DIR` and `AP_CONTENT_BACKUP_DIR` from its environment with the installers' own defaults and passes its environment on to the installers. The pair is at commit C when `ap --version` of that file names C and every line of `content/SHA256SUMS` of C (read from the clone) matches the file of the tree (what `sha256sum -c` checks). Every read asks whether the pair is at one named commit, first T, then I, and never gives the tree a commit of its own; "the tree is not at I" means that it does not pass I's manifest. The command reads `content/SHA256SUMS` of a commit from the clone once per call.
- R16: The lock is the file `AP_DELIVER_LOCK` names (default `/run/lock/ap-deliver.lock`), one per host whatever `state` a request names; its descriptor is inherited by every installer, so the lock stays held while an installer lives after the command alone was killed, and a free lock means that nothing of a call runs. The installers take no deliver lock.
- R17: The file handle of an attempt, the copy a rollback of it restores, is the kept copy `<AP_BACKUP_DIR>/ap.before-<first 7 hex of the attempt's from_sha256>`; it counts only when the file's whole digest equals `from_sha256`.
- R18: The content handle is a tarball `agents-before-<UTC stamp>-<pid>.tar` of the directory `AP_CONTENT_BACKUP_DIR` names that HOLDS THE TREE OF `from` and that the content installer takes back. Holding the tree: every line of `content/SHA256SUMS` at `from` names a regular file of the archive with that digest; the archive is read in memory and never extracted, and one that cannot be read to its end does not pass. Taking back: `scripts/install-content.sh rollback-check <tarball>`, of the clone's script that a rollback would call, exits 0 (a script that does not know the verb answers exit 2: the tarball is no handle); only a tarball whose members pass is asked. Where the content installer printed a tarball in this call (on stdout after `backup=` at success, on stderr after `kept copy` at its exit 1), that one is the handle when it passes. Where none was printed (a dead call, a repair, a close after an `unrecorded` end, a second install of one attempt), it is the OLDEST tarball stamped not older than the attempt's `started_at` (to the second) that passes. Which call made a tarball, and in which second, decides nothing. A tarball that does not pass either check is never recorded as a handle and never given to `install-content.sh rollback`: one function answers the content handle of an attempt, and every close, the repair and the rollback request that reads a recorded handle use it. Every close of an attempt whose installers ran records both handles (`rollback_binary`, `rollback_content`), each when there is one.
- R19: Both install actions are applied with the client `ap-deliver` and the agent `ap-deliver`, whoever calls. The request id of an attempt is `ap.<commit>.<attempt>`, of a rollback attempt `ap.<commit>.rb<attempt>`; its close is that id followed by `.close`. Every search names only properties every object of its type has: a review by `kind`, `head`, `status`, an attempt by `target`, `status`, `commit`, `kind`; `verdict`, `repository`, an attempt's `outcome` and a report's digest are compared on the objects of the answer, which must be qualified.
- R20: Step 1. The lock (R16), taken without waiting and held to the end, including while this call waits for the build lock in step 7. Held by another (or not openable): `busy`; another call waiting for the build lock is busy too.
- R21: Step 2. The running attempt of the target (`target` and `status: running`) belongs to a dead call, because the lock is free. The pair is read against it, from the clone as it stands: at its `from` it is closed `not_started` with the code `dead_call`; at its `commit` it is closed `installed` with its handles. A running attempt of kind `forward` at neither is repaired: when the clone's `origin/main` as it stands is the attempt's commit, the installers are called again, each only for the part that is not at the commit (the file by `install-ap.sh install <commit>`, then, when that was not needed or exited 0, the tree by `install-content.sh install <commit>`); the pair is read; at the commit the attempt is closed `installed`. When the pair is still not at the commit, or `origin/main` is not the attempt's commit (no installer is called then), the command's rollback of step 10 runs with the attempt's handles; the pair is read; at `from` the attempt is closed `failed_restored`, else `failed`. After a close with `failed` the call ends there: `end: failed`, exit 4, the record names the attempt (`install`, `attempt`, `from`, `outcome`, `to`, `code`, the handles) and `closed`. After any other close the call goes on, and the record's `closed` names the attempt and its outcome; a repair's programs are rows of `installers`, and the index run of step 12 follows its close. `attempt_running` with the attempt's id remains for: a clone that cannot answer (another `state`, a lost clone: no `content/SHA256SUMS` of the attempt's commit or `from` to read and no scripts to call); a running attempt of kind `rollback` at neither of its commits (a dead rollback is not repaired); a close by a read that the store did not apply. A repair whose close the store did not apply ends `unrecorded` (exit 5, or 4 when its outcome is `failed`); the next call reads the attempt again.
- R22: Step 3. A rollback request goes to R33. The clone `<state>/<name>` is made (`git init`) or reused, `main` of `url` is fetched into `refs/remotes/origin/main` (nothing else), and that tip T is read from the clone's objects; the clone is not checked out here (R47). A failure: `fetch_failed`.
- R23: Step 4. The pair is read. At T: the end `current`. At a commit I that is not T, file and tree both: I is the `from` of the attempt. Anything else (file and tree at different commits, a tree at none): `pair_differs`.
- R24: Step 5. `engine_differs`: `ontology/ENGINE-PIN` at T is not the commit `ont --version` names. `schema_differs`: the `version` of `ontology/work.schema.json` at T is not the version of the installed work schema (the store's answers name it). With `engine` this step is R40's.
- R25: Step 6, accepted. I must be on the first-parent chain of T. Every commit after I up to T, oldest first, unless `past` names it: it has two parents (`not_a_merge`); its tree is its second parent's tree (`tree_differs`); the store holds a review of kind `packet`, `status: closed`, `verdict: accept`, this `repository` and the second parent as `head` (`no_accepting_review`; a revoked review is not closed). For T alone, also: the report file of that review exists (`report_missing`) and has the digest the object names (`report_differs`). When a head has more than one accepting review the one closed last is used. The first that fails ends the call `not_accepted` (`detail`: `commit`, `why`: `not_on_chain`, `not_a_merge`, `tree_differs`, `no_accepting_review`, `report_missing`, `report_differs`). T is never exempt, also when `past` names it. A commit of `past` that is not one of the commits after I up to T: `past_not_on_chain`. Then, for the timer's request only, the limits of R32.
- R26: Step 7. `disk_low`: under 10,240 MiB free where `<state>` lies (`df`). The build lock is probed with `flock -n`. When held, `build_wait_seconds: 0` refuses `build_busy` at once; a positive bound N waits up to N seconds with `flock -w`, then proceeds when the lock is free, or refuses `build_busy` if it remains held. The command releases the build lock at the end of this step, before the installers take it themselves. Only when starting to wait, it writes one JSON line on standard error: `{"at":"<UTC RFC 3339, to the second>","waiting":"build_lock","seconds":N}`; standard output remains the call's one answer line. No new attempt exists yet, and the wait changes neither the pair nor the store; a call killed while waiting needs no repair by the next call.
- R27: Step 8. `ont index --source installed_binaries`. The attempt is one more than the attempts of this target and T the store holds. `start_install` is applied with `kind: forward`, the target, `repository`, `commit` T, `attempt`, `from` I, `from_sha256` (the digest of the installed `ap` file, read now), `by`, `reason` (absent for the timer), `head` (the second parent of T), `review` (its accepting review), `reviews` (the accepting reviews of step 6, oldest first) and `past` (the request's commits joined by one space, absent when empty). Only the answer `applied` that names the created attempt goes on; `already_applied` or a refusal ends `store_refused`, a failure `store_unreadable`, and no installer is called. An answer `applied` that names no created object also ends `store_unreadable`: the store may hold a running attempt then, which the next call closes by the read of step 2 (at `from`: `not_started`).
- R28: Step 9. The installers, from the clone, whose tree is at T: the checkout of T follows step 7 and precedes the marker's migration (R45), the schema step (R44) and step 8 (R47). With the command's environment and its lock: `scripts/install-ap.sh install <T>` with `CARGO_TARGET_DIR=<state>/target`; when it exits 0, `scripts/install-content.sh install <T>`.
- R29: Step 10. The pair is read again and decides the outcome, not an exit code. At T: `installed`. At I: `not_started` when the first installer ended with its code `install_busy`, else `failed_restored`. Anything else: the command rolls back with the installers' own verbs, `install-ap.sh rollback <the file handle>` when the file is not at I and the handle counts, and `install-content.sh rollback <the content handle>` when the tree is not at I and that installer printed a tarball that holds the tree of I (no printed path, no content rollback in this step), reads again, and the outcome is `failed_restored` at I, else `failed`.
- R30: Step 11. `close_install` with the outcome, `to` (the commit the pair is at, or `neither`), `rollback_binary` and `rollback_content` (the file handle when it counts, the content handle when there is one) and `code` (the first code of the installers and, when that is null, the code of the unit step, R51). The read decides: an attempt closed `installed` can carry the code of an installer that failed (an installer that exited non-zero after the pair was at T). When the store cannot be written here the end is `unrecorded`: the attempt stays `running` and the record still says the outcome the read decided.
- R31: Step 12. After every close of an attempt whose installers ran, also one the store did not apply (`unrecorded`): the index run of step 8 again; its failure is in the record's `index` and changes no outcome.
- R32: The timer's limits, for the timer's request only, read from every attempt of the target (one search by `target`), newest first by `started_at` as the view `installs` orders them; each refuses with `detail` `{"install"}`, the attempt it names, and a Lead's request has none of them. `suppressed` (exit 3): the newest attempt whose outcome is not `not_started` (a running one has none) ended `failed_restored` or `failed`; it stays until a Lead's install call ended `installed`, and a later `not_started` attempt of anyone does not lift it. `held_by_rollback` (exit 2): that attempt is of kind `rollback`; the timer installs nothing until a Lead's install call ended `installed`. `attempt_exists` (exit 2): an attempt of kind `forward` on T ended `installed`, `failed_restored` or `failed`; the timer installs a commit at most once. `attempts_exhausted` (exit 3): three attempts of kind `forward` on T ended `not_started`. After `failed` the pair is at no one commit, so the timer's next call ends at step 4 with `pair_differs` and never reaches these limits: for the timer's request only, `pair_differs` therefore exits 3, and its `detail` is `{"install"}` with the newest attempt of the target whose outcome is not `not_started`, or null when there is none; a Lead's request keeps exit 2 and `detail` null.
- R33: A Lead's rollback, after steps 1 and 2. The pair is read from the clone as it stands, with no fetch; it must be at one commit C (`pair_differs`). Once the pair is read at C, the clone is checked out at C (R47; a checkout that fails refuses `fetch_failed`), before `rollback-check` and before either rollback. A is the newest attempt of the target of kind `forward` with outcome `installed` and `commit` C. `nothing_to_roll_back` (exit 2, `detail` null) when: there is no A; A's file handle does not count; A has no content handle (its recorded `rollback_content` is gone, or does not hold the tree of A's `from`: it is checked by R18 before it is used, and then counts as absent) while `content/SHA256SUMS` differs between A's `from` and C. Then the index run, and `start_install` with `kind: rollback`, `commit` A's `from`, `from` C, `from_sha256`, `rolls_back` A, `by`, `reason`, the attempt number counted over the rollback attempts of this target and commit, under the request id `ap.<commit>.rb<attempt>`; only `applied` goes on, as in step 8. Then, in this order: `install-content.sh rollback <A's content handle>` when A has one; only when that exited 0 or was not needed, `install-ap.sh rollback <A's file handle>`. A content rollback that does not exit 0 ends the attempt by the read: at C `not_started` (its refusal, exit 2) or `failed_restored` (any other exit), else `failed`; the file is not touched. After both: at A's `from`, `installed`, and the unit step runs from C to A's `from` (R48); at C, `failed_restored`; else `failed`. Then `close_install` (with `to` and `code` as in step 11), the index run, the record (`tip` null, `from` C, `to` A's `from` when `installed`). A rollback that ends `installed` holds the timer (`held_by_rollback`) until a Lead's install call ended `installed`.
- R34: An installer's code: for `install-ap.sh` the word before `@` of its line `code@install-ap.sh:LINE` on standard error; for `install-content.sh`, which prints no code, `content_refused` at exit 2, `content_failed_restored` at exit 1, `content_exit_<n>` otherwise. Null at exit 0. A program ended by a signal has the exit 128 plus the signal. The `code` of a closed attempt is the first code of its installers (for a repair and a rollback, of its rollbacks as well) and, when that is null, the code of the unit step (R51).
- R35: The record, on standard output and, for every end but `invalid_input`, replaced through a temporary name in `<state>/last.json` (the record is still printed when that write fails). Exactly these members, null where one does not apply: `at` (UTC), `by` (the request's, or the timer's), `repository`, `target` (`/usr/local/bin/ap`), `tip`, `from`, `end`, `outcome`, `code`, `detail`, `install` (the attempt's id), `attempt`, `installers` (one row per program of steps 2, 9 and 10 and of a rollback, in order: `name` one of `ap`, `content`, `ap-rollback`, `content-rollback`; `exit`; `code`; an empty array when none ran), `to`, `rollback_binary`, `rollback_content`, `index` (`{"before", "after"}`, each `ok`, `failed` or null; null when no index ran), `closed` (`{"install", "outcome"}` of the dead call's attempt that step 2 closed), with `engine` also `schema` (R46), `checkouts` as R6 says, and `units` (R51). `end` is one of `current`, `refused`, `installed`, `not_started`, `failed_restored`, `failed`, `unrecorded`; `outcome` is null or one of `installed`, `not_started`, `failed_restored`, `failed`, and under `unrecorded` it is what the read decided. `code` is the refusal's code, or the `code` of the close (R30). `detail`: `{"field"}` for `invalid_input`; `{"install"}` for `attempt_running`, `suppressed`, `held_by_rollback`, `attempt_exists` and `attempts_exhausted`, and for the timer's `pair_differs` (or null); `{"commit", "why"}` for `not_accepted`; `{"commit"}` for `past_not_on_chain`; `{"tip", "installed"}` for `engine_differs` and `schema_differs`; `{"store"}` for `store_refused` and `store_unreadable` (the store's code: its failed criteria joined by a space, its `code`, `already_applied`, or null when its answer could not be read); else null. No credential, no text of a report and nothing of an installer's output but its code and the printed tarball path; of the two backup directories only names are read.
- R36: The exit: 0 `installed` and `current`; 2 `refused` (no installer ran in this call), except 3 for `suppressed`, `attempts_exhausted` and, for the timer's request only, `pair_differs` and `attempt_running` (a Lead's request keeps exit 2 for both); 3 `not_started` and `failed_restored` (an attempt is recorded, the pair is where it was); 4 whenever `outcome` is `failed` (the pair is at no single commit: a person acts), recorded or not, and for the ends `schema_install_failed` and `migrate_failed` (R46); 5 `unrecorded` with any other outcome. The service `deploy/ap-deliver.service` states that exit 2 is no failure of the unit (`SuccessExitStatus=2`); 3, 4 and 5 fail it.
- R37: With `engine` a call also brings the engine and the work schema to what T names, so that a merged move of `ontology/ENGINE-PIN` or a merged higher version of `ontology/work.schema.json` no longer stops delivery until a Lead installs them by hand. The engine is the file `ont` in the directory `ONT_INSTALL_BIN_DIR` names (default `/usr/local/bin`); its target is the `installed_artifact` whose key is `/usr/local/bin/ont`; its revision is the commit `<that file> --version` names (`ont <version> <commit>`). The store's path, the first argument of `ontology/migrate`, is `<ONT_INSTALL_STATE_DIR>/ont/ontology.sqlite` (default directory `/var/lib/ontology-platform`). Both variables are the engine installer's, read with its own defaults; the command passes its environment on to that installer unchanged and adds nothing to it. The engine's clone is `<state>/<engine name>`.
- R38: Step 2 with `engine` also reads the running attempt of the engine target, which belongs to a dead call. The engine is read against it: at its `commit` it is closed `installed`, at its `from` `not_started` with the code `dead_call`, and the call goes on. At neither, the engine clone's `scripts/install-ont.sh rollback` runs once (row `ont-rollback`), the engine is read again and the attempt is closed `failed_restored` at `from`, else `failed` (`to` the pin when it is at the pin, else `neither`); after `failed` the call ends there (exit 4, the record names the attempt with `target` `/usr/local/bin/ont`). `attempt_running` remains for an engine clone without its installer and for a close the store did not apply.
- R39: Step 4 with `engine`. A pair at T ends the call `current`, as without `engine`, also when the engine or the schema differ from T's: a later T installs them. Only when the marker (R45) exists, before that end: T's chain is empty and counts as accepted; for the timer the limits `suppressed` and `held_by_rollback` of the target `ap` apply (the two that are not about T, which is installed); then step 7; then the call acts on the marker, and ends `current`.
- R40: Step 5 with `engine`. The engine differs when the pin is not the revision the engine names: that is no refusal. `engine_differs` remains for a pin that is not 40 hex and for an engine whose revision cannot be read. `schema_differs` remains for a version at T that cannot be read or that is LOWER than the store's; a higher one is installed (R44); an equal one goes on.
- R41: Step 6 with `engine`, the timer's limits: when the engine differs, after those of the target `ap`, the limits of the engine target by the rules of R32, over its own attempts, with the pin in the place of T (the record's `target` is then `/usr/local/bin/ont`). So the timer installs a pin at most once (`attempt_exists`), three `not_started` attempts of one pin stop it (`attempts_exhausted`), one that ended `failed_restored` or `failed` suppresses it until a Lead's call installed the engine (`suppressed`), and a rollback attempt of the engine holds it (`held_by_rollback`).
- R42: After step 7 with `engine`: the marker (R45), then the engine (R43) when it differs, else the schema (R44), then steps 8 to 12.
- R43: The engine, when it differs. The engine clone is made (`git init`) or reused; unlike the clone of the repository it has the remote `origin` with the URL `engine.url` (`git config remote.origin.url`, and `remote.origin.fetch` `+refs/heads/main:refs/remotes/origin/main`), because the engine's installer runs `git fetch origin` itself and refuses without it. `git fetch origin` brings `main` into `refs/remotes/origin/main` (`fetch_failed`, `detail` `{"repository"}` the engine's). The pin must be an ancestor of that `origin/main`, and every first-parent commit after the installed revision up to the pin must pass the rule of step 6 (R25), with the engine's repository as `repository` and no `past` (the request's `past` is of T's chain only): else `engine_not_accepted` with `{"commit", "why"}` (the reasons of `not_accepted`; a pin not under `origin/main`, or an installed revision not on the pin's first-parent chain, is `not_on_chain`), nothing is installed and the engine clone's `HEAD` stays where it was. Then the pin is checked out, detached (R47; a checkout that fails is `fetch_failed` with the engine's repository), before `scripts/install-ont.sh install`. Then the index run; `start_install` with the target `/usr/local/bin/ont`, `kind: forward`, the engine's repository, `commit` the pin, `attempt` (counted over the attempts of this target and pin), `from` the installed revision, `from_sha256` the digest of the engine file, `by`, `reason`, and `head`, `review` and `reviews` of that walk, under the request id `ont.<pin>.<attempt>`; only `applied` goes on, as in step 8. The installer is the clone's `scripts/install-ont.sh install <pin>` with the command's environment and its lock and nothing passed beyond those two words (row `ont`); the command waits for it with no bound of its own. Then the engine is read: at the pin, `installed`; at `from`, `failed_restored`; at neither, the script's `rollback` once (row `ont-rollback`) and a read again: `failed_restored` at `from`, else `failed`. `close_install` with the outcome, `to` (the pin, `from` or `neither`), `code` (the installer's: `engine_refused` at exit 2, else `engine_exit_<n>`) and `rollback_binary`, the copy the installer kept (`<ONT_INSTALL_STATE_DIR>/install/ont.before-<first 12 hex of from_sha256>`) when its digest is `from_sha256`; then the index run. The call ends there: the record's `target` is `/usr/local/bin/ont`, its `from` and `to` are the engine's, its `tip` is T. The next call finds the engine at the pin and goes on to the schema and the pair.
- R44: The schema, when T's version is higher than the store's; the engine is at the pin by then. When T holds an executable `ontology/migrate` (mode `100755` in `git ls-tree`), the marker is written first; an entry that `git ls-tree` cannot read is no answer "absent": the call ends `schema_install_failed` before the backup. Then `ont backup` (the `path` it answers), `ont schema install --from <the clone> --commit <T> --path ontology/work.schema.json`, and the store's version read back. A marker that cannot be written, a backup or an install that does not answer `ok`, or a version read back that is not T's ends the call `schema_install_failed`, and nothing else is installed. When `ontology/migrate` is there it runs from the clone with the command's environment and its lock (row `migrate`, code `migrate_exit_<n>`), with three arguments: the store's path, the version before and the version after. Exit 0 removes the marker; any other exit ends the call `migrate_failed`, and the schema stays installed (it is fixed forward). Then steps 8 to 12 install the pair in the same call. A schema install makes no `install` object (no `installed_artifact` stands for a schema).
- R45: The marker `<state>/migrate.pending`, `{"from", "to"}` (the two versions), keeps an owed migration from being passed over. It is written, through a temporary name, before `ont schema install`, whenever T holds an executable `ontology/migrate`; it is removed only after the migration exited 0. A call with `engine` that finds it acts on it after every refusal that precedes an effect (T's chain accepted, the timer's limits, `disk_low`, `build_busy`) and before the engine, the schema and the installers; no such call ends `current` before it acted on it (R39). Acting on it: the store's version is read. At the marker's `from`, the install did not happen: the marker is removed and the call goes on (the schema step writes it again). At its `to`: T's `ontology/migrate` runs with the marker's two versions; exit 0 removes the marker and the call goes on, any other exit ends it `migrate_failed` and nothing is installed. At any other version, for a marker that cannot be read, or when T holds no executable `ontology/migrate`: `migrate_failed`, with the three versions in the detail. A Lead's rollback request is not subject to it; a call without `engine` does not read it.
- R46: The record of a call with `engine` has one more member, `schema`: null, or `{"from", "to", "backup", "migrate"}` of the schema step or of the marker the call acted on (`backup` the path `ont backup` answered, null when none ran; `migrate` `none`, `ok` or `failed`). `schema_install_failed` and `migrate_failed` end the call with `end: failed`, `outcome` null, `detail` `{"from", "to", "store"}` (the versions before and after, and the version the store answered, null when it did not), exit 4. `engine_not_accepted` has `detail` `{"commit", "why"}`. The rows of `installers` also name `ont`, `ont-rollback` and `migrate`.
- R47: The clone's tree. `ap deliver` checks a clone out (`git checkout --quiet --force --detach <K>`) only at a commit K of one of three kinds: T, after step 6 accepted its chain; the commit a read of this call found the pair at (a Lead's rollback: C; a dead call's attempt found at its `commit`; the end `current`, before it acts on the marker); the `commit` of the running forward attempt that step 2 repairs. That checkout precedes the first program the call runs from the clone's tree (`scripts/install-ap.sh` and `scripts/install-content.sh` with any verb, `rollback-check` included, and `ontology/migrate`), and no such program runs from a tree at another commit. Steps 3 to 7 read commits from the clone's objects only (`git show`, `rev-parse`, `rev-list`, `ls-tree`) and make no checkout: a refusal in them (`not_accepted`, `engine_differs`, `schema_differs`, the timer's limits, `disk_low`, `build_busy`) leaves `HEAD` and the tree of the clone as step 2 left them, which is as the call found them unless step 2 checked out for a dead call's attempt; the fetch moves only `refs/remotes/origin/main`. The checkout of T follows step 7 and precedes the marker (R45), the engine (R43), the schema step (R44) and step 8. The engine's clone is checked out at the pin only after the pin's chain is accepted (R43). A checkout that fails refuses `fetch_failed` before any attempt is started; in step 2 it is `attempt_running` with the attempt.
- R48: The unit files of a commit K are the entries of `git ls-tree K deploy/` of the clone that are blobs of mode 100644 directly in `deploy/` whose name is made of ASCII letters, digits, `@`, `_`, `.` and `-` and ends in `.service` or `.timer`. No list is read, no file of the tree on disk, and no other entry (a link, a directory, `README.md`, `deliver.json`); a commit's files are read from the clone's objects (`git ls-tree`, `git show`, `git rev-list`). The host's directory is the value of `AP_UNIT_DIR` (default `/etc/systemd/system`), read as R15 reads the installers' variables. The unit step runs at most once in a call, between the read of step 10 and the close of step 11: in a forward attempt only when that read found the pair at T (it goes from I, the `base`, to T, the `to`); in a Lead's rollback only when the read after both rollbacks found the pair at A's `from` (from C to that commit). No other end runs it: `current`, a refusal, `not_started`, `failed_restored`, `failed`, an engine attempt, a schema step, an attempt of a dead call that step 2 closes or repairs.
- R49: One file. A name of the unit files of `to`: when the host has no entry of that name it is written; when the host's copy has the bytes of `to` it is `same`; when the host's copy is a regular file with the bytes `deploy/<name>` has at `base` or had at any commit of the first-parent chain of `base` (read from the clone's objects) it is written; any other host entry (other bytes, a link, a directory, a file that cannot be read) is `host_differs` and is not touched. Writing: the bytes of `to` under a temporary name in `AP_UNIT_DIR`, mode 0644, renamed over `<name>`; a write that fails is `failed` and leaves the previous file. In a rollback also each name of the unit files of `base` that `to` does not have: a host copy that passes the same test is removed (`removed`), any other is `host_differs`, and a name the host has no entry of is `same`. A timer is removed only after `systemctl disable --now <name>` exited 0 within its bound; otherwise its file stays and its row is `failed`. A file whose history the clone cannot answer is `failed` and is not touched. Nothing else under `AP_UNIT_DIR` is created, changed or removed: no drop-in directory `<name>.d`, no unit that `deploy/` does not name. So a step a killed call missed is made up by the next install, and a file a Lead removed is written again.
- R50: The service manager: `systemctl` through the call's `System`, each call bound to 120 seconds, in this order: R49's `disable --now` of each timer to remove, before any file is written or removed; after the files, `daemon-reload`, only when a file was written or removed; for each written `.timer` the host had no entry of, `enable --now <name>` and then `is-enabled <name>`, which must print `enabled`; for each other written `.timer`, `try-restart <name>`. No other call: no `start`, `stop`, `restart` or `mask`, no `disable` but R49's, nothing for a `.service`, nothing for a file that is `same` or `host_differs`; so a timer a Lead stopped or disabled stays so until a merge changes its file, and stays stopped then too. A `daemon-reload` that fails ends the step: no `enable` and no `try-restart` follow it. Then each file is read back: a written one's digest must be that of `to`.
- R51: The record and the attempt. The record's member `units` is null when the step did not run, else an array (empty, with the code `units_failed`, when the clone cannot answer the unit files of `to`, or in a rollback of `base`: nothing is written then) ordered by `name` of exactly `{"name","before","after","result","enabled"}`: `before` and `after` are the SHA-256 of the host's copy before the step and read back after it (null for no regular file), `result` is one of `same`, `written`, `removed`, `host_differs`, `failed`, and `enabled` is true or false for a timer the step enabled (whether `is-enabled` printed `enabled`), else null. The step's code is `units_failed` (a row `failed`, a `systemctl` call that failed or ran out of its bound, a read-back that differs, an `enabled` false, or unit files the clone could not answer), else `units_host_differs` (a row `host_differs`), else null. `close_install` carries as `code` the first code of the installers and, when that is null, the step's code; the record's `code` is the same value. The step changes neither `outcome`, `to`, `end`, the handles nor the exit (R36): the reads of the pair decide them. The attempt is the pair's `install` object of R27 or R33: no action, object type or property is added for the unit files.
- R52: Each `deploy/*.service` carries in `[Service]`, once each, the lines `NoNewPrivileges=yes`, `ProtectKernelModules=yes`, `ProtectKernelLogs=yes`, `ProtectKernelTunables=yes`, `ProtectControlGroups=yes`, `ProtectHostname=yes`, `LockPersonality=yes`, `RestrictRealtime=yes`, `RestrictSUIDSGID=yes` and `SystemCallArchitectures=native`; each but `ap-deliver.service` also `ProtectSystem=full` (delivery writes `/usr/local/bin` and `AP_UNIT_DIR`: a comment of its file says so). A service a later unit adds carries them too.

## Interface

`ap deliver < request.json` and `ap deliver check < request.json` (R8 to R10); `ap deliver --help` prints its usage (`specs/ap/verbs.md` R2). The request of R12 to R14 and R1, the record of R35, R46 and R6 (on standard output and in `<state>/last.json`), the exits of R36. The results of a checkout: `forwarded`, `current`, `not_a_checkout`, `not_on_main`, `dirty`, `fetch_failed`, `diverged` and `git_failed`. The unit files of `deploy/` under `AP_UNIT_DIR` (R48 to R50), the record's `units` with the results `same`, `written`, `removed`, `host_differs` and `failed`, and the calls of `systemctl` `disable --now`, `daemon-reload`, `enable --now`, `is-enabled` and `try-restart` (R50). It replaces the install by hand of `BUILD-AND-DELIVERY.md` section 5. The host's request is `/etc/agent-platform/deliver.json` (`deploy/deliver.json`, `state` `/var/lib/agent-platform/deliver`); the first enable of the timer and the commands of a repair by hand are in `deploy/README.md`, which also says what the unit step does on the host.

Refusal codes, the complete list, each with the requirement that holds it (exit 2 unless R36 says 3):

| Code | Requirement |
| --- | --- |
| `invalid_input` | R13, R14, R1, R10 |
| `busy` | R20 |
| `attempt_running` | R21, R38 |
| `fetch_failed` | R22, R43 |
| `pair_differs` | R23, R32, R33 |
| `engine_differs`, `schema_differs` | R24, R40 |
| `not_accepted`, `past_not_on_chain` | R25 |
| `suppressed`, `held_by_rollback`, `attempt_exists`, `attempts_exhausted` | R32, R41 |
| `disk_low`, `build_busy` | R26 |
| `store_refused`, `store_unreadable` | R27, R33, R43 |
| `nothing_to_roll_back` | R33 |
| `engine_not_accepted` (only with `engine`) | R43 |

Not refusals: `schema_install_failed` and `migrate_failed` end a call with `end: failed` after an effect of the schema step (R44 to R46). `units_failed` and `units_host_differs` are the code of an attempt and a call whose `end` the reads decided, mostly `installed`, when its installers left no code (R51).

Why the rules read as they do. A tree can pass the manifests of several commits at once (most merges change no file of `content/`), so a read names the commit it asks about (R15). `install-content.sh rollback-check` runs every check of `rollback` that does not read the target (the files `<tarball>.sha256` and `<tarball>.paths`, the checksum, the member names, the entries of `.paths`), writes nothing, and exits 2 with the refusal line `rollback` prints; `rollback` runs the same lines, so the rule of R18 has one home, the script. A tarball that holds the tree of `from` restores the tree of `from` whoever made it, and a tarball of another tree, or of a half-swapped tree that a repair or a killed install kept, does not pass. On the engine of `ontology/ENGINE-PIN` a filter on an optional property answers `qualified: false` as soon as one scanned object lacks it, while `unresolved_excluded` stays 0 (`ontology/README.md`, "Version 8"), which is why R19 searches by properties every object has (`ap unit` adds its task to a review). The store's path of R37 is the store the engine's installer names, which the command's own `ont` calls reach on the host. The engine's installer fixes its own build lock and directories and builds cold under its own temporary directory; the unit's `TimeoutStartSec` of 3,600 seconds bounds it (R43). A schema install's record is the engine's own (the backup, the provenance `ont schema install --from` records) and `last.json` (R44).

The contract of `ontology/migrate`, binding every unit that ships or changes it: it stays in the tree from its first version on; it handles every pair of versions it was ever shipped for, with a step for each version in the half-open range above `from` up to `to` (a version without work being an empty step); it exits non-zero, changing nothing, on a pair it does not know (a `to` above the highest version it names, or a `from` not below `to`); and it is repeatable: a second run with the same arguments changes nothing.

## What a Lead does after each end

Where a Lead sees it, with the request of the host in `/etc/agent-platform/deliver.json`:
- whether the timer runs: `systemctl is-enabled ap-deliver.timer` answers `enabled`; `systemctl is-failed ap-deliver.service` answers `failed` after a run that exited 3, 4 or 5, until the next run;
- the last call, its end, code and time: `python3 -m json.tool /var/lib/agent-platform/deliver/last.json` (`end`, `code`, `detail`, `at`, `by`);
- the newest attempt: the first row of the view `installs`, `printf '{"view":"installs","args":{}}' | ont render`;
- the unit step of a call: its record, one line of `journalctl -u ap-deliver.service -o cat` (member `units`; `last.json` holds it only until the next call), and the property `code` of the attempt, read with `ont get` (the view `installs` has no column for it). No exit, detector or status line shows `units_failed` or `units_host_differs`.

After each end:
- `installed`, `current`: nothing; the view `installs` shows the attempt. With the code `units_host_differs`: a host copy of a unit file is no version the repository had; compare it with `git -C <clone> show <installed commit>:deploy/<name>`, then keep the hand edit as a drop-in or copy the installed commit's file over it by hand, after which the next install manages the file. With `units_failed`: read the row and `systemctl status <name>`; the next install writes again what is not at its tip's bytes.
- `not_started`: another install held the installers' lock; call again later (the timer tries a commit three times). `failed_restored`: the pair is back at `from`; read `code` and `installers`, repair, call again (the next attempt has the next number); the timer stays `suppressed` until then.
- `failed`: the pair is at no single commit, and every later request refuses `pair_differs`; the timer's runs then exit 3, name the failed attempt, and keep `ap-deliver.service` failed until the pair is repaired. Stop the timer, read the pair (`ap --version`, `sha256sum -c content/SHA256SUMS` in the content tree at the commit it should be at), put it back by hand with the installers' `rollback` verbs and the handles of the record (`deploy/README.md` names the commands), then, if the attempt is still running, close it by hand as below, and call `ap deliver` with `by` and `reason`. The installers take no deliver lock: a Lead stops the timer before calling one by hand.
- `refused`: `code` and `detail` say why; nothing was installed in this call. `not_accepted`: review the commit named, or name it in `past` with a reason when it is a commit a Lead steps over. `busy`, `build_busy`, `disk_low`: call again later. `engine_differs`, `schema_differs`: install the engine or the schema first. `pair_differs`: read and repair the pair by hand. `suppressed`, `held_by_rollback`: the timer waits for a Lead's install call that ends `installed`. `attempt_exists`, `attempts_exhausted`: the timer is done with T; a Lead's call installs it. `nothing_to_roll_back`: no verified handle; restore by hand or install forward.
- `attempt_running` and `unrecorded`: an attempt is `running` that no call will close (the timer's `attempt_running` exits 3 and keeps `ap-deliver.service` failed until a call settled the attempt; a Lead's exits 2). For a dead rollback (kind `rollback`) at neither commit, stop the timer and run again the two commands of the rollback, from the clone checked out at the attempt's `from`, the commit the pair was installed at (`git -C <state>/<name> checkout --quiet --force --detach <its from>`), with the handles of the attempt it rolls back (`rolls_back`): `bash <state>/<name>/scripts/install-content.sh rollback <its rollback_content>`, and when that exited 0, `bash <state>/<name>/scripts/install-ap.sh rollback <its rollback_binary>`. Read the pair as above, then close the attempt by hand with the outcome the read shows (`installed` at its `commit`, `not_started` or `failed_restored` at its `from`, `failed` otherwise) through `ont action apply --client ap-deliver` with the agent `ap-deliver`, for example `{"action_type":"close_install","request_id":"ap.<commit>.<attempt>.close","agent":"ap-deliver","parameters":{"install":<id>,"outcome":"installed","to":"<commit>"}}` (`ap.<commit>.rb<attempt>.close` for a rollback); an `unrecorded` record holds the id, the outcome, `to` and the handles to give.

With `engine`:
- `engine_not_accepted`: review the engine's commit named (the rule is that of T's chain).
- An engine attempt that ended `failed_restored` or `failed`: read `code` and `installers`, repair, then a Lead's call (with `by` and `reason`) installs the engine; for `failed`, `scripts/install-ont.sh rollback` of the engine clone puts the previous engine back first. An engine that a Lead rolled back by hand stays rolled back: the attempt on the pin exists.
- `schema_install_failed`: read the store's version (`ont describe`) and the engine's answer; the next call tries again.
- `migrate_failed`, or a marker that cannot clear (a migration that fails on every call): stop the timer, run the corrected script by hand with the marker's versions (`<the corrected ontology/migrate> <the store's path> <from> <to>`), read the result (the store's version, the migration's own effects), then remove `<state>/migrate.pending`; the next call goes on.
- Undo: remove the member `engine` from the request: delivery stops on a difference as before (`engine_differs`, `schema_differs`) and no longer reads the marker. An installed engine goes back with the engine's own `scripts/install-ont.sh rollback`, with the timer stopped. A schema is repaired by a higher version that delivery installs forward, never by delivery restoring a backup.

## Limits

- The fetch of step 4 uses the remote `origin` the checkout names: the checkout of a private repository fetches with the credential helper of the service's user (`HOME=/root`), unlike the fetch of the pair, which reads a public URL.
- A `git_failed` after a merge cut by its bound can leave the checkout part-written (changed tracked files, a lock file). The next run then reads it `dirty` or `git_failed` until a person repairs it. Delivery repairs nothing.
- A checkout read `dirty` is left as it is; saving its edits is a person's step, never delivery's.

## Not included

- A repository-local `core.fsmonitor` can still start a program during the checkouts' `git status` (step 3 of R3): the service inherits root's global Git configuration, and the checkouts' commands set no `core.fsmonitor`.
- A cut fetch's `git-remote-*` helper can outlive the killed `git`.
- Delivery never restores the store from a backup and never runs `ont compact`; it repairs no checkout and no pair by hand.
