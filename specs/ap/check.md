# One check: a repository's check for a worktree, on the local PC or here

Purpose: the cargo builds and tests of an implementer, a fixer and a verifier leave this host's two CPUs and its one build lock for the local PC when the PC is there and free, and run here as before when it is not. The PC sees exactly the worktree's state, the caller sees the command's output and exit status as if it had run here, and every call leaves one record line saying where it ran and how long it took. The agent sessions stay on this host.

## Requirements

- R1: `ap check <dir> [--timeout <seconds>] [-- <command> [<arg>...]]` takes `<dir>` as the first argument, then at most one `--timeout` with its value, then at most one `--` followed by at least one word. Any other form is refused `usage` (field `args`); a `<dir>` that is not an absolute path is `invalid_input` (field `dir`); a timeout that is not a whole number from 1 to 14,400 is `invalid_input` (field `timeout`); a command word that is not UTF-8, or an empty first word, is `invalid_input` (field `command`). The command defaults to `./check` and the timeout to 2,700 seconds; a given command runs as its arguments, without a shell.
- R2: `<dir>` must be a directory whose resolved path equals `git rev-parse --show-toplevel` run in it and whose `HEAD` names a commit, else `not_a_worktree` (field `dir`); its remote `origin` (`git remote get-url origin`) must be a GitHub repository (`https://github.com/<owner>/<name>`, `ssh://git@github.com/<owner>/<name>` or `git@github.com:<owner>/<name>`, with or without `.git`; user information before the host is allowed and never recorded), else `origin_not_github` (field `origin`).
- R3: The policy file is the one of `specs/ap/policy.md` R1. A file that is unreadable, not JSON or not one JSON object, or whose member `hosts` is malformed (R16), is refused `policy_invalid` (field `policy`, the detail a sentence that begins with the member: `file`, `hosts`, `hosts.pc`, `hosts.pc.ssh`, `hosts.pc.work`, `hosts.pc.busy_load`, `hosts.pc.min_available_mb`, `hosts.pc.stages`, `hosts.pc.stages.ssh` or `hosts.pc.stages.work`). An absent file is no refusal: the call runs here with reason `no_pc_in_policy`, as it does with a file without `hosts`. Every refusal of R1 to R3 exits 2 before any effect, with one line `{"error":{"code","field","detail"}}` on standard error and nothing on standard output: no record, no call of the PC.
- R4: The call runs on the PC when the policy has `hosts.pc`, `tailscale ping` reaches the PC's host within 10 seconds, the PC answers a probe through `tailscale ssh` with its CPU count, its one-minute load average and its available memory, the worktree has no pinned engine or the PC's engine is that one (R19), that load is below `busy_load` times the CPU count, and that memory is at least `min_available_mb`; else here. The available memory, in MB rounded down, is the smaller of two readings: (a) `MemAvailable` of `/proc/meminfo` in the PC's Linux (WSL), the memory a command there can still take; a probe that cannot read or parse it has not answered, as one without a CPU count; (b) Windows' free physical memory, `FreePhysicalMemory` of `Win32_OperatingSystem` in kB, the memory left to the PC user's own work under Windows, which the user watches: one call of `/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe -NoProfile -NonInteractive -Command`, bounded by `timeout 10`, its standard input empty and its standard error discarded, which only reads; its answer is trimmed of whitespace, and a missing program, a failure or an answer that is not then a whole number leaves (b) out, so that (a) alone counts. Before any output of the command, one line on standard error: `check: on pc (<cpus> CPUs, load <load>, <mb> MB available)`, or `check: on this host (<reason>)` with the reason `no_pc_in_policy` (no `hosts`), `pc_unreachable` (no answer to the ping or the probe), `pc_engine_differs` (the PC's engine is not the worktree's pinned one, R19), `pc_busy` (the load is not below the bound), `pc_memory_low` (the load is below its bound and the available memory is below `min_available_mb`) or `pc_lost` (R11).
- R5: Here the command runs in `<dir>` with this process's environment and standard input empty. A command whose program is not `./check` runs under `flock <lock>` of the host's build lock, `HOST_CARGO_LOCK` when it is set and not empty, else `/var/lib/agent-platform/build.lock`, when that file exists; `./check`, with any of its arguments, is not wrapped, because it takes the lock itself where it needs it. A command that `ap check` wraps gets `CHECK_LOCKED=1` in its environment, so that a `./check`, or a copy of its lock block, inside that command does not take the lock again (it would wait on the lock its own wrapper holds); for a command it does not wrap, `ap check` removes `CHECK_LOCKED` from the environment, as it removes `AP_CHECK_HOST` and `AP_DOOR`. The command's environment also holds the cargo settings of R17, and never an inherited `AP_CHECK_HOST` (R17).
- R6: On the PC the command runs in a tree, kept per `<dir>` under the policy's `work`, whose `git rev-parse HEAD` equals `<dir>`'s; whose files and symbolic links equal, byte for byte and with their modes, the paths that `git ls-files --cached --others --exclude-standard` lists in `<dir>` and that exist there (a deleted tracked file is absent), and nothing else beside `.git`; whose `.git` is the Git repository kept for the key outside the tree, holding `<dir>`'s index entries (`git ls-files -s`), so that `git ls-files --cached` and `git ls-files --others --exclude-standard` equal `<dir>`'s; and whose exclude rules are `<dir>`'s: its `info/exclude` and the excludes file its Git configuration names (`core.excludesFile`, else `$XDG_CONFIG_HOME/git/ignore` or `~/.config/git/ignore` of this host's user), never the PC user's. Before each use the script resets that repository (no hooks, no alternates, no attributes or other file under `info`, no link to another repository, a configuration of the script's own) and runs its own git on it with hooks off, so nothing a command could have left there runs outside the sandbox, nor in the step of R18.
- R7: What reaches the PC from this host is the fixed script of `ap check`'s PC side, its arguments (the policy's `work`, the key of `<dir>`, a fresh nonce, the seconds left and the command's words) and one payload on standard input: the commit as a Git bundle of what the PC's tree lacks, the index entries, the two exclude files and a tar of the listed files. No credential, key, token, account file, environment variable or other file of this host is sent: every `tailscale` child of `ap check` gets only `PATH`, `HOME`, `USER` and `LOGNAME` of this process, so the ssh client's default `SendEnv` (`LANG`, `LC_*`) and an agent socket have nothing to send. The command's environment on the PC is the PC user's own login environment. Beside that login environment the command gets only what `ap check` itself sets (R8, R17); no variable of this host.
- R8: On the PC the command runs under `bwrap` as uid 0 and gid 0 of a new user namespace (as `unshare -r`), in its own PID namespace that ends with it, in a network namespace of its own that has no interface but the loopback (no address outside the sandbox answers and no abstract socket of the PC is reached), under `nice -n 10`, and sees the following of the PC and nothing else: read-only at their own paths, `/usr`, `/etc` and each of `/bin`, `/sbin`, `/lib`, `/lib32`, `/lib64` and `/libx32` that the PC has, as it is there (a link stays a link); a `/proc` and a `/dev` of its own; writable, the tree (its `.git`, the key's repository, mounted read-only), a cargo target directory kept per `<dir>` (`CARGO_TARGET_DIR`) and a temporary directory of the call mounted at `/tmp` (`TMPDIR`) and removed at the call's end; read-only, one cargo home shared by every call (`CARGO_HOME`), which only the step of R18 writes; and the toolchain, read-only at its own paths, each part only where it exists: rustup's home (`RUSTUP_HOME` of the PC user's login environment when it is set and not empty, else `$HOME/.rustup`), the directory `bin` of the account's own Cargo home (`CARGO_HOME` of that environment when it is set and not empty, else `$HOME/.cargo`), and the file of the program `ont` as that environment's `PATH` finds it, where neither the system's directories nor those two show it. The tree, the target directory and the cargo home lie under the policy's `work`; of the account's home the command sees only the toolchain and these three by their own paths: no other key's tree, repository or target directory, and not `<work>/tmp`, `<work>/locks` or `<work>/used`. Of `/mnt`, `/run`, `/var`, `/root` and `/home` it has only the parents of a shown path: none of them exists unless a shown path lies below it, and then it holds only the names that lead to that path. Nothing else can be written: not the view's root, and not a directory the view has only as the parent of a shown path. The toolchain is the PC's own: a program or a component the command needs and the view lacks fails the command like any failure, and the call does not run again here. The command's environment is the PC user's login environment, its `PATH` and `HOME` kept, with `AP_CHECK_HOST=pc`, the cargo settings of R17 and `CARGO_NET_OFFLINE=true`, set by the script with `bwrap --setenv` as it sets `CARGO_TARGET_DIR`, `CARGO_HOME` and `TMPDIR`.
- R9: The target directory of a `<dir>` persists between calls, so a later build of that worktree is incremental. Calls for different `<dir>` run at once on the PC, each with its own tree and target directory; calls for one `<dir>` wait for each other on a lock of its key, and the wait counts against the timeout.
- R10: At the timeout the call ends with exit status 124 and no process of the call is left: here the command's process group is killed; on the PC the script's own bound (the seconds left when the call was sent, its lock wait included) ends the command's PID namespace, and this host waits at most 30 seconds past the deadline for the PC's end before it cuts the connection. The memory sampler of R11 ends with the script: its process group and its PID are killed (the group exists only once the sampler's own `setsid` ran) before the status line is written and when the script exits, and it ends by itself at the call's deadline (the start plus the seconds left, as the command's bound) or within 2 seconds of a script whose PID is gone, so that a script killed outright leaves no sampler either.
- R11: A call on the PC whose command's exit status never came back (the connection failed, or the PC's side failed before the command ran, the step of R18 included) is `pc_lost`: after the line `check: on this host (pc_lost)`, the command runs here once (R5), bounded by the time left of the timeout, or ends with 124 when none is left. The status travels as a last line of the PC's standard error, NUL `ap-check <nonce> <status> <lowest MB>`, that carries the call's nonce and that the caller takes out of the stream, so a command's own exit 255 is passed on as 255; a line without both fields carries no status. `<lowest MB>` is the lowest `MemAvailable` of the PC's Linux while the command ran, in MB rounded down, read outside the command's namespaces: once by the script itself, synchronously, before the command starts, so that every command that started has a value however soon it ends; then every 2 seconds by a sampler whose standard output and error are not the session's and which keeps its lowest reading in a file of the call under the payload's directory, which the command cannot write (never the call's temporary directory, the command's `/tmp`). The script reads that file after the sampler's end; an empty or unparsable file leaves the first reading. `-` where no command ran (the lock wait or the step of R18 ran out of time, or no time was left) or where that first reading failed; the call is not lost for it. No Windows process runs while the command runs.
- R12: A tree, repository or target directory under the policy's `work` whose key no call has used for seven days (its use stamp, else the directories themselves, older than seven days) is removed by a later call, which holds that key's lock while it removes and skips a key whose lock another call holds; a temporary directory left by a call that ended without its cleanup is removed a day later. Nothing outside `work`, and no name under it that is not a key, is removed.
- R13: The command's standard output and standard error stream back as they are produced, each to its own stream of `ap check`.
- R14: The exit status of `ap check` is the command's; a command ended by a signal is 128 plus the signal; a command that cannot be started here is 127.
- R15: Every call that passed R1 to R3 and has no `AP_DOOR` appends one line, a JSON object, to the file `AP_CHECKS_LOG` names when it is set and not empty, else `/var/lib/agent-platform/checks.jsonl`: `start` and `end` (UTC, RFC 3339 to the second), `seconds` (the call's whole duration, to the millisecond), `host` (`pc` or `local`), `reason` (null on the PC, else the reason of R4), `dir` (the resolved path), `repository` (`<owner>/<name>`), `head`, `command` (the words), `exit`, and what the probe of R4 read: `pc_cpus`, `pc_load`, `pc_wsl_available_mb` (a), `pc_windows_available_mb` (b) and `pc_available_mb` (the smaller), each null only where the call did not probe or the probe did not answer (so they are kept for `pc_busy`, `pc_memory_low` and `pc_lost`; `pc_windows_available_mb` is null as well where (b) was left out), and `pc_min_wsl_available_mb`, the lowest value of R11, null where the command did not run on the PC or the status line carried `-`. A check's memory use on the PC is `pc_wsl_available_mb` minus `pc_min_wsl_available_mb`, from which the policy's `min_available_mb` is set. Where the file does not exist it is created with mode 0600 (the open asks for 0600; the umask can only take bits away); a file that exists is appended to, and its mode and owner are not changed, so that `AP_CHECKS_LOG` may name a device such as `/dev/null`. A line that cannot be written is said on standard error and changes no exit status. For a call under the door (R20) the door appends this line when the PC ran the command (`specs/ap/door.md` R4), and no line is appended otherwise.
- R16: The policy's optional member `hosts` is an object whose one key is `pc`, an object with exactly `ssh` (`<user>@<host>` for `tailscale ssh`: a user of lowercase letters, digits and `_.-` beginning with a letter or `_`, at most 32 characters; a host of letters, digits, `.` and `-` beginning with a letter or digit), `work` (an absolute path of letters, digits and `._-/`, at most 1,024 characters, without an empty, `.` or `..` component) and `busy_load` (a number from 0.1 to 1.0), and at most two more members: `min_available_mb` (a whole number from 0 to 1,048,576, the PC's available memory of R4 in MB that a call needs; absent means 2,048) and `stages`, an object of exactly `ssh` (the form of `hosts.pc.ssh`: the login of the stage account, for `tailscale ssh`) and `work` (the form of `hosts.pc.work`: the stage account's work directory), where a look of `ap run` may run (`specs/ap/run.md` R57 to R63); a missing or other member of `stages`, or a value of another form, is `policy_invalid` with that member (`hosts.pc.stages`, `hosts.pc.stages.ssh` or `hosts.pc.stages.work`). `ap check` and its door read `stages` and ignore it. No member bounds what a command uses on the PC. `ap policy check` runs this reader as `check` (`specs/ap/policy.md` R12).
- R17: `AP_CHECK_HOST` and three cargo settings are `ap check`'s own markers and settings, not variables of this host, and they hold for every repository `ap check` serves. The command's environment, here and on the PC alike, holds `CARGO_INCREMENTAL=0`, `CARGO_PROFILE_DEV_DEBUG=0` and `CARGO_PROFILE_TEST_DEBUG=0` (the settings `./check` exports under the build lock; here they are set whether or not the lock file exists), so that `./check` and any cargo command sent through `ap check` build in one profile and share one target directory. On the PC the command's environment also holds `AP_CHECK_HOST=pc`, set by `crates/ap/src/check/pc.sh`; here `AP_CHECK_HOST` is not set: `ap check` removes an inherited one before it runs a command here (R5). A script that cannot run on the PC may skip itself under `AP_CHECK_HOST=pc`.
- R18: When the tree's root holds the regular files `Cargo.toml` and `Cargo.lock`, the script fetches the dependencies in one step after the tree is in place and before the first memory reading of R11: `cargo fetch --locked --manifest-path <tree>/Cargo.toml`, with the `cargo` the PC user's login environment's `PATH` finds, started in a directory outside the tree, so that no `.cargo/config.toml` and no `rust-toolchain.toml` of the tree chooses a program, a toolchain or a source (the toolchain is the account's default one); the step reads the tree as data and runs none of its code. It runs in a sandbox of its own with the view of R8 and four differences: the network is the PC's; the cargo home is writable; the tree is read-only and there is no target directory; and where `/etc/resolv.conf` resolves through its links to a file outside `/etc`, that one file is shown read-only at its own path, so that the step can resolve a name (the command's view does not have it). Its environment is the login environment with `CARGO_HOME` and `TMPDIR` set as the command's are, and without `CARGO_NET_OFFLINE` and `CARGO_TARGET_DIR`. Its standard input is empty; both its outputs go to the call's standard error and nothing of it to standard output. It runs under the script's bound with the seconds left: a step the bound ends is the call's end with status 124 and `-`, as the lock wait of R9. A step that fails otherwise is the PC's side failing before the command (R11): the script says `check: pc: fetch` and ends without a status line, so the call is `pc_lost` and the command runs here once. A tree without both files has no step. The step is the only writer of the cargo home; `<lowest MB>` of R11 still covers the command alone.
- R19: A worktree has a pinned engine when `<dir>/ontology/ENGINE-PIN` is a regular file of its working tree; the pin is the file's text without whitespace, read by `ap check` on this host, which runs nothing of the worktree for it. The probe of R4, in the same `tailscale ssh` call and with no further call to the PC, also reads the account's engine: in the PC user's login environment, the program `ont` as `PATH` finds it, run once as `ont --version`, outside any sandbox, under `timeout 10`, its standard input empty and its standard error discarded. The revision it names is the third word of the first line when that line is exactly three words, the first `ont` and the third 40 hexadecimal digits (the reading of `ap deliver`); no `ont`, a failure, the bound or any other answer names none, and a probe without an engine has still answered. When the worktree has a pinned engine and the PC's `ont` names no revision equal to it (a pin that is not 40 hexadecimal digits equals none), the call runs here with the reason `pc_engine_differs`: the line `check: on this host (pc_engine_differs)` before any output of the command, `reason` `pc_engine_differs` in the record, and the probe's readings kept in the record as for `pc_busy`; the PC's script is not started. The reason is decided once the probe answered (no answer stays `pc_unreachable`) and before the load and the memory, so a busy PC with another engine says `pc_engine_differs`. A worktree without the file is placed as R4 says, whatever the PC's engine. No step of `ap check` builds, installs or fetches an engine.
- R20: With `AP_DOOR` set and not empty in its environment, `ap check` does R1 to R3 as without it and starts no `tailscale`. A policy without `hosts.pc` is `no_pc_in_policy`, as in R4, and the door is not asked. Else it sends one `check` request (`specs/ap/door.md` R2) with `<dir>` as resolved, the seconds of its timeout and the command's words to the socket `AP_DOOR` names. The door ran the command on the PC: the door's two streams are `ap check`'s own as they come (R13) and its exit status the one the door closed with (R14). The door closed with `here`: the line `check: on this host (<reason>)`, then the command here as R5, within what is left of the timeout. The door refused: the same with the reason `door_refused`. The door cannot be reached, or its answer ends `ended` or without a closing message: the same with the reason `no_door`. Under `AP_DOOR` `ap check` appends no row of R15 itself. A command that `ap check` runs here, with or without `AP_DOOR`, never gets `AP_DOOR`: it is removed from the command's environment as an inherited `AP_CHECK_HOST` is (R5, R17), so no program of a worktree reaches a door. Without `AP_DOOR`, R1 to R19 hold as before.
- R21: Every record line of R15 becomes a `check` object of the store within one pass of `ap resource` (`specs/ap/resource.md` R7), the timer's pass every five minutes: its key the first 32 hexadecimal digits of the SHA-256 of the line, its members those of the line with `command` joined and `seconds` as `milliseconds`. The log itself is not changed by the pass.
- R22: A check that `./check` cannot run where it runs is a declared skip, not a pass. Before its first step, in every mode (`./check content` too), `./check` makes a directory with `mktemp -d` under `TMPDIR` (else `/tmp`) and in it a file with `mktemp`, and exports the file's path as `CHECK_SKIPS`; the directory is its own, so that a step under `sudo` appends to the file too (the kernel's `fs.protected_regular` refuses root's append to another user's file in `/tmp`), and every `sudo env` line of `./check` passes `CHECK_SKIPS`. Its re-exec under the build lock keeps that file: before the `exec` it sets `CHECK_SKIPS_KEEP` to the file's path, and a `./check` that finds `CHECK_SKIPS_KEEP` equal to `CHECK_SKIPS`, naming a file `ids.*` in a directory `check-skips.*`, keeps that file; it removes `CHECK_SKIPS_KEEP` from its environment before its first step. Any other `./check` makes its own file, whatever it inherits (`CHECK_LOCKED`, which others set, is not the marker). Each skip site, a place where `./check` or a script, Python file or Rust test it starts does not run a check it cannot run there, prints what it printed before and appends its row's id of `ci/skips.json` (R23) as one line to the file `CHECK_SKIPS` names, when that variable is set and not empty; a test that drives a skip site on purpose removes `CHECK_SKIPS` from the environment it gives it. On each of its four successful ends, `./check` prints `check: skipped <id> <id> ...` just before its last line, the ids in the order of their first line and each once, when the file holds a line; the code before the last line prints it, never an `EXIT` trap. Its one `EXIT` trap removes the directory, joined with the removal of its test root. A skip still exits 0: the last line and the exit status of `./check` are those it had before, for every outcome.
- R23: `ci/skips.json` is `{"rows": [...]}`, each row exactly `{id, file, covers, runs_on, how}`: `id` lower-case letters, digits and hyphens, unique; `file` the script, Python file or Rust test that skips, an exact path of the write-set grammar (`specs/ap/unit.md` R11); `covers` 1 to 20 patterns of that grammar, the paths whose change the skipped check is the evidence for; `runs_on` `vps-root`, `vps` or `ci`, where the check runs (`ci`: the CI job runs it, so no head owes it); `how` one command line, run at the repository's root, that runs the skipped check where it can run. A skip site is one line that holds the name `CHECK_SKIPS` and the id as a literal, in one of three forms: a shell line `echo <id> >> "$CHECK_SKIPS"`, a Python line that holds `CHECK_SKIPS` and `.write("<id>\n"`, a Rust test line `skipped(CHECK_SKIPS, "<id>")`. `python3 -I -B ci/skips.py declared` exits 0 only when the table has this form, every row's file exists, and over `check`, `ci/*.sh`, `scripts/*.sh` and every row's file, every line that appends to `CHECK_SKIPS` is a site of these forms whose id is a declared row of that same file, and every declared id has a site in its file; else it prints one line `<code>@<path>[:<line>]: <detail>` on standard error and exits 1. `./check` runs it among its steps that need no Rust build.
- R24: `python3 -I -B ci/skips.py owed <base> <head>` prints, for the paths `git diff --name-only --no-renames <base> <head>` gives, one line `<id>\t<runs_on>\t<how>` per row whose covers meet a path and whose `runs_on` is not `ci`, and exits 0. It reads the rows of `ci/skips.json` at both commits (`git cat-file`): a row of either counts; for an id both have, a path meets the row when it meets its covers at either commit, and the row is not `ci` when its `runs_on` is not `ci` at either, its line then that of the head's row when that one is not `ci`, else the base's. A file absent at a commit gives no row of that commit; one that is not of the form of R23, or a name that is not a commit, makes it print one error line on standard error and exit 1. It reads Git and files only and starts no check. The Lead runs each line's `how` on its host before approving a guarded head (`specs/ap/unit-run.md` R49).

## Interface

The PC's side is the script `crates/ap/src/check/pc.sh`, run as `bash -c` by the PC user's shell through `tailscale ssh <ssh>`. Under `work` it keeps `trees/<key>` (the worktree's files), `repos/<key>` (the Git repository of that tree, mounted read-only at `trees/<key>/.git` for the command), `targets/<key>`, `cargo-home`, `locks/<key>`, `used/<key>` (the use stamp) and `tmp/<nonce>`; the key is the first 16 hexadecimal digits of the SHA-256 of `<dir>`'s resolved path. The commit reaches the tree as a bundle of `HEAD` less the tree's own `HEAD` when this host knows that commit, all of `HEAD`'s history otherwise, and nothing when the repository already holds it. The probe reads the repository's `HEAD` file as text and runs no git there. Besides its readings and that `HEAD`, the probe reads the revision the account's `ont --version` names (R19). The step of R18 alone writes `cargo-home`; every command reads it.

## Not included

- A verifier's look may run on the PC by `specs/ap/run.md` R57 to R63, while every build of `ap check` and every other stage stays as this file says: the sessions of implementer, fixer and writer stay on this host, and a build on the PC leaves no artifact here.
- No change of CI, of the acceptance checks `ap unit run` runs, or of delivery's build; `./check` changes only by the declared skips of R22 and R23 and the marker of R5, and no check it ran is removed. No skipped check is run by the dispatch pass or by delivery, and the store keeps no record of where one last ran.
- A stage with `limits` reaches the PC through the door alone (R20), and a call the door places here leaves its line in the door's record, not a row here.
- Submodules and nested repositories are sent as the directory entries Git lists, without their content.
