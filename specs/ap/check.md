# One check: a repository's check for a worktree, on the local PC or here

Purpose: the cargo builds and tests of an implementer, a fixer and a verifier leave this host's two CPUs and its one build lock for the local PC when the PC is there and free, and run here as before when it is not. The PC sees exactly the worktree's state, the caller sees the command's output and exit status as if it had run here, and every call leaves one record line saying where it ran and how long it took. The agent sessions stay on this host.

## Requirements

- R1: `ap check <dir> [--timeout <seconds>] [-- <command> [<arg>...]]` takes `<dir>` as the first argument, then at most one `--timeout` with its value, then at most one `--` followed by at least one word. Any other form is refused `usage` (field `args`); a `<dir>` that is not an absolute path is `invalid_input` (field `dir`); a timeout that is not a whole number from 1 to 14,400 is `invalid_input` (field `timeout`); a command word that is not UTF-8, or an empty first word, is `invalid_input` (field `command`). The command defaults to `./check` and the timeout to 2,700 seconds; a given command runs as its arguments, without a shell.
- R2: `<dir>` must be a directory whose resolved path equals `git rev-parse --show-toplevel` run in it and whose `HEAD` names a commit, else `not_a_worktree` (field `dir`); its remote `origin` (`git remote get-url origin`) must be a GitHub repository (`https://github.com/<owner>/<name>`, `ssh://git@github.com/<owner>/<name>` or `git@github.com:<owner>/<name>`, with or without `.git`; user information before the host is allowed and never recorded), else `origin_not_github` (field `origin`).
- R3: The policy file is the one of `specs/ap/policy.md` R1. A file that is unreadable, not JSON or not one JSON object, or whose member `hosts` is malformed (R16), is refused `policy_invalid` (field `policy`, the detail a sentence that begins with the member: `file`, `hosts`, `hosts.pc`, `hosts.pc.ssh`, `hosts.pc.work`, `hosts.pc.busy_load` or `hosts.pc.min_available_mb`). An absent file is no refusal: the call runs here with reason `no_pc_in_policy`, as it does with a file without `hosts`. Every refusal of R1 to R3 exits 2 before any effect, with one line `{"error":{"code","field","detail"}}` on standard error and nothing on standard output: no record, no call of the PC.
- R4: The call runs on the PC when the policy has `hosts.pc`, `tailscale ping` reaches the PC's host within 10 seconds, the PC answers a probe through `tailscale ssh` with its CPU count, its one-minute load average and its available memory, that load is below `busy_load` times the CPU count, and that memory is at least `min_available_mb`; else here. The available memory, in MB rounded down, is the smaller of two readings: (a) `MemAvailable` of `/proc/meminfo` in the PC's Linux (WSL), the memory a command there can still take; a probe that cannot read or parse it has not answered, as one without a CPU count; (b) Windows' free physical memory, `FreePhysicalMemory` of `Win32_OperatingSystem` in kB, the memory left to the PC user's own work under Windows, which the user watches: one call of `/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe -NoProfile -NonInteractive -Command`, bounded by `timeout 10`, its standard input empty and its standard error discarded, which only reads; its answer is trimmed of whitespace, and a missing program, a failure or an answer that is not then a whole number leaves (b) out, so that (a) alone counts. Before any output of the command, one line on standard error: `check: on pc (<cpus> CPUs, load <load>, <mb> MB available)`, or `check: on this host (<reason>)` with the reason `no_pc_in_policy` (no `hosts`), `pc_unreachable` (no answer to the ping or the probe), `pc_busy` (the load is not below the bound), `pc_memory_low` (the load is below its bound and the available memory is below `min_available_mb`) or `pc_lost` (R11).
- R5: Here the command runs in `<dir>` with this process's environment and standard input empty. A command whose program is not `./check` runs under `flock <lock>` of the host's build lock, `HOST_CARGO_LOCK` when it is set and not empty, else `/var/lib/agent-platform/build.lock`, when that file exists; `./check`, with any of its arguments, is not wrapped, because it takes the lock itself where it needs it.
- R6: On the PC the command runs in a tree, kept per `<dir>` under the policy's `work`, whose `git rev-parse HEAD` equals `<dir>`'s; whose files and symbolic links equal, byte for byte and with their modes, the paths that `git ls-files --cached --others --exclude-standard` lists in `<dir>` and that exist there (a deleted tracked file is absent), and nothing else beside `.git`; whose `.git` is the Git repository kept for the key outside the tree, holding `<dir>`'s index entries (`git ls-files -s`), so that `git ls-files --cached` and `git ls-files --others --exclude-standard` equal `<dir>`'s; and whose exclude rules are `<dir>`'s: its `info/exclude` and the excludes file its Git configuration names (`core.excludesFile`, else `$XDG_CONFIG_HOME/git/ignore` or `~/.config/git/ignore` of this host's user), never the PC user's. Before each use the script resets that repository (no hooks, no alternates, no attributes or other file under `info`, no link to another repository, a configuration of the script's own) and runs its own git on it with hooks off, so nothing a command could have left there runs outside the sandbox.
- R7: What reaches the PC from this host is the fixed script of `ap check`'s PC side, its arguments (the policy's `work`, the key of `<dir>`, a fresh nonce, the seconds left and the command's words) and one payload on standard input: the commit as a Git bundle of what the PC's tree lacks, the index entries, the two exclude files and a tar of the listed files. No credential, key, token, account file, environment variable or other file of this host is sent: every `tailscale` child of `ap check` gets only `PATH`, `HOME`, `USER` and `LOGNAME` of this process, so the ssh client's default `SendEnv` (`LANG`, `LC_*`) and an agent socket have nothing to send. The command's environment on the PC is the PC user's own login environment.
- R8: On the PC the command runs under `bwrap` as uid 0 and gid 0 of a new user namespace (as `unshare -r`), in its own PID namespace that ends with it, under `nice -n 10`, with the root file system read-only except the tree (its `.git`, the key's repository, is mounted read-only), a cargo target directory kept per `<dir>` (`CARGO_TARGET_DIR`), one cargo home shared by every call (`CARGO_HOME`), all three under the policy's `work`, and a temporary directory of the call mounted at `/tmp` (`TMPDIR`) and removed at the call's end; the network is kept. The toolchain is the PC's own: a component the command needs and the PC lacks fails the command like any failure, and the call does not run again here.
- R9: The target directory of a `<dir>` persists between calls, so a later build of that worktree is incremental. Calls for different `<dir>` run at once on the PC, each with its own tree and target directory; calls for one `<dir>` wait for each other on a lock of its key, and the wait counts against the timeout.
- R10: At the timeout the call ends with exit status 124 and no process of the call is left: here the command's process group is killed; on the PC the script's own bound (the seconds left when the call was sent, its lock wait included) ends the command's PID namespace, and this host waits at most 30 seconds past the deadline for the PC's end before it cuts the connection. The memory sampler of R11 ends with the script: its process group and its PID are killed (the group exists only once the sampler's own `setsid` ran) before the status line is written and when the script exits, and it ends by itself at the call's deadline (the start plus the seconds left, as the command's bound) or within 2 seconds of a script whose PID is gone, so that a script killed outright leaves no sampler either.
- R11: A call on the PC whose command's exit status never came back (the connection failed, or the PC's side failed before the command ran) is `pc_lost`: after the line `check: on this host (pc_lost)`, the command runs here once (R5), bounded by the time left of the timeout, or ends with 124 when none is left. The status travels as a last line of the PC's standard error, NUL `ap-check <nonce> <status> <lowest MB>`, that carries the call's nonce and that the caller takes out of the stream, so a command's own exit 255 is passed on as 255; a line without both fields carries no status. `<lowest MB>` is the lowest `MemAvailable` of the PC's Linux while the command ran, in MB rounded down, read outside the command's namespaces: once by the script itself, synchronously, before the command starts, so that every command that started has a value however soon it ends; then every 2 seconds by a sampler whose standard output and error are not the session's and which keeps its lowest reading in a file of the call under the payload's directory, which the command cannot write (never the call's temporary directory, the command's `/tmp`). The script reads that file after the sampler's end; an empty or unparsable file leaves the first reading. `-` where no command ran (the lock wait ran out, or no time was left) or where that first reading failed; the call is not lost for it. No Windows process runs while the command runs.
- R12: A tree, repository or target directory under the policy's `work` whose key no call has used for seven days (its use stamp, else the directories themselves, older than seven days) is removed by a later call, which holds that key's lock while it removes and skips a key whose lock another call holds; a temporary directory left by a call that ended without its cleanup is removed a day later. Nothing outside `work`, and no name under it that is not a key, is removed.
- R13: The command's standard output and standard error stream back as they are produced, each to its own stream of `ap check`.
- R14: The exit status of `ap check` is the command's; a command ended by a signal is 128 plus the signal; a command that cannot be started here is 127.
- R15: Every call that passed R1 to R3 appends one line, a JSON object, to the file `AP_CHECKS_LOG` names when it is set and not empty, else `/var/lib/agent-platform/checks.jsonl`: `start` and `end` (UTC, RFC 3339 to the second), `seconds` (the call's whole duration, to the millisecond), `host` (`pc` or `local`), `reason` (null on the PC, else the reason of R4), `dir` (the resolved path), `repository` (`<owner>/<name>`), `head`, `command` (the words), `exit`, and what the probe of R4 read: `pc_cpus`, `pc_load`, `pc_wsl_available_mb` (a), `pc_windows_available_mb` (b) and `pc_available_mb` (the smaller), each null only where the call did not probe or the probe did not answer (so they are kept for `pc_busy`, `pc_memory_low` and `pc_lost`; `pc_windows_available_mb` is null as well where (b) was left out), and `pc_min_wsl_available_mb`, the lowest value of R11, null where the command did not run on the PC or the status line carried `-`. A check's memory use on the PC is `pc_wsl_available_mb` minus `pc_min_wsl_available_mb`, from which the policy's `min_available_mb` is set. A line that cannot be written is said on standard error and changes no exit status.
- R16: The policy's optional member `hosts` is an object whose one key is `pc`, an object with exactly `ssh` (`<user>@<host>` for `tailscale ssh`: a user of lowercase letters, digits and `_.-` beginning with a letter or `_`, at most 32 characters; a host of letters, digits, `.` and `-` beginning with a letter or digit), `work` (an absolute path of letters, digits and `._-/`, at most 1,024 characters, without an empty, `.` or `..` component) and `busy_load` (a number from 0.1 to 1.0), and at most one more member, `min_available_mb` (a whole number from 0 to 1,048,576, the PC's available memory of R4 in MB that a call needs; absent means 2,048). No member bounds what a command uses on the PC. `ap policy check` runs this reader as `check` (`specs/ap/policy.md` R12).

## Interface

The PC's side is the script `crates/ap/src/check/pc.sh`, run as `bash -c` by the PC user's shell through `tailscale ssh <ssh>`. Under `work` it keeps `trees/<key>` (the worktree's files), `repos/<key>` (the Git repository of that tree, mounted read-only at `trees/<key>/.git` for the command), `targets/<key>`, `cargo-home`, `locks/<key>`, `used/<key>` (the use stamp) and `tmp/<nonce>`; the key is the first 16 hexadecimal digits of the SHA-256 of `<dir>`'s resolved path. The commit reaches the tree as a bundle of `HEAD` less the tree's own `HEAD` when this host knows that commit, all of `HEAD`'s history otherwise, and nothing when the repository already holds it. The probe reads the repository's `HEAD` file as text and runs no git there.

## Not included

- No agent stage on the PC: the sessions of implementer, fixer and verifier stay on this host, and a build on the PC leaves no artifact here.
- No store object for a check: the record line only.
- No change of `./check`, of CI, of the acceptance checks `ap unit run` runs, of delivery's build or of `ap run`.
- A stage launched with `limits` hides `/run/tailscale` and has a read-only `/var/lib/agent-platform` (`specs/ap/run-limits.md`): there the ping fails, the call runs here with `pc_unreachable`, and its record line cannot be written.
- Submodules and nested repositories are sent as the directory entries Git lists, without their content.
