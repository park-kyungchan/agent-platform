# One stage: `ap run`

Purpose: one stage of work (an implementer, a reviewer, a fixer, or the writer of a unit's page) runs as ONE headless session of a coding CLI (Claude Code, or the Antigravity CLI with `runtime: "agy"`) in a transient systemd scope `ap-run-<uuid>.scope` under `agents.slice`, and `ap run` returns when nothing of it is alive, with one record `<out>.run.json` that says how it ended, so that a caller judges a stage by its record and never by a session it watched. This file holds the request, the refusals, the run, the states, the record, the typed answer and the two runtimes. Three specifications hold the rest and are not repeated here: `specs/ap/run-limits.md` (a stage with `limits`), `specs/ap/run-object.md` (a stage of a unit or an intent, the role and the author, and the close of an orphan `run` object) and `specs/ap/policy.md` (the host's policy file, the last check of admission).

## Requirements

### The request

- R1: The form is `ap run < request.json`: no argument (an argument refuses `usage`, field `args`), and standard input one JSON object of at most 1 MiB (more refuses `input_too_large`, field `stdin`; input that is not JSON or not an object refuses `invalid_input`, field `stdin`; input that cannot be read refuses `io_error`, field `stdin`). It reads no role table and calls no Herdr or GitHub; it calls the store only as `specs/ap/run-object.md` says (a request with `unit`, `intent` or `close`).
- R2: The members: `role` (`implementer`, `reviewer`, `fixer`, `writer`), `account` (the Claude configuration directory, required), optional `next_accounts`, `model`, `effort`, `permission_mode` (one of Claude Code's: `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan`), `cwd`, `prompt` (a regular file, at most 1 MiB, given to the CLI on stdin), `out` (the answer's path), and optional `timeout_seconds` (an integer from 1 to 86400; default implementer 5400, fixer 3600, reviewer 3300, writer 5400), `expect` (an object of `file`, a path that this run must write nonempty, `first_line`, a pattern of at most 200 bytes and no newline that the answer's first line must match, where `*` matches any run of characters, and `second_line`, a pattern of the same form that the answer's second line must match, an empty line when the answer has one line; `second_line` is admitted only together with `first_line`, and alone, or of another form, refuses `invalid_input` with the field `expect.second_line`), `resume` (`{"record": "<absolute path of the earlier run's record>"}`), `continue_dirty`, `integration` (a reviewer's only: another role refuses `invalid_input`; it does not choose the account), `mcp_config` (files; the only MCP servers loaded), `env` (extra variables), `runtime` (`claude`, the default, or `agy`), `bind`, `skills` and `memory` (booleans: the account's skills and slash commands, and its auto-memory, load only when true), `answer_schema` (R30), `compact_window` (R5), the members of `specs/ap/run-object.md` R1 (`unit`, `intent`, `store`, `git_author`, `ont_role`) and `limits` (`specs/ap/run-limits.md` R1). Every path is absolute. Another member refuses `invalid_input` with its name, and so does a member of the wrong type or out of its range, with the member's name as the field.
- R3: `env` may not name a variable beginning `HERDR_`, `CLAUDE_` or `ANTHROPIC_`, nor `HOME`, nor the names of `specs/ap/run-object.md` R2 (`ONT_ROLE`, `ONT_AGENT`, `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `BASH_ENV`, `ENV`), nor a name a runtime reserves (R47): each refuses `env_forbidden`, field `env`, so the account named in the record is the account that answers.
- R4: An `out` whose file name ends with a suffix `ap run` derives (`.run.json`, `.stream.jsonl`, `.err`, `.ap-tmp`) refuses `invalid_input`, field `out`: no run's answer path is another run's file.
- R5: `compact_window` is a Claude stage's only: an integer from 100000 to 1000000, read as `timeout_seconds` is read, so a fraction, an exponent, a string or null refuses `invalid_input` with that field; the CLI starts with `CLAUDE_CODE_AUTO_COMPACT_WINDOW` set to it in the `env` of its `--settings` value (R12), so the stage's compaction window is this one; without it the account's settings decide; a stage with `limits` has no settings of the account (`specs/ap/run-limits.md` R14), so for it the CLI's default decides. A stage on another runtime refuses the member with `invalid_input`, field `compact_window`.
- R6: `bind` is the name of a systemd unit that is active now: when it ends for any reason, stopped, killed or failed, the stage's unit stops (`-p BindsTo=<bind> -p After=<bind>`, R11). A name that is not a unit name refuses `invalid_input`, field `bind`; a unit that is not `active` refuses `bind_inactive` (R9). A unit that ended between the request and the launch makes the launch fail (the record says `failed`); a unit that systemd can start again by name is started again by the launch, because `BindsTo` requires it.

### The refusals before any effect

- R7: Every refusal exits 2 with `{"error":{"code","field","detail"}}` on standard error, before any effect: no file is written, a refusal has no record, and an earlier run's files stay as they were. The request's own members: `invalid_input` (R1 to R6), `env_forbidden` (R3), and `account_missing` (`account` or an entry of `next_accounts` is not an existing directory; `/root/.claude` is an account like any other, for every role, as `account` and in `next_accounts`).
- R8: The files: `cwd_missing` (`cwd` is no directory); `prompt_unreadable` (the prompt cannot be read, is empty or is over 1 MiB); `out_unwritable` (the directory of `out` does not exist, `out` is a directory, or `out` is the prompt); `out_named_in_prompt` (the prompt contains the out file's name); `out_exists` (`out`, `<out>.run.json`, `<out>.stream.jsonl` or `<out>.err` exists: nothing of an earlier run is replaced, removed or truncated by a later one).
- R9: The host: `worktree_dirty` (a fresh implementer run in a Git worktree with changes, unless `continue_dirty`); `worktree_unreadable` (Git cannot read `cwd` for a reason other than "not a git repository"; `git` runs with the fixed short list of variables only, not the request's `env`); `systemd_absent` (the host has no service manager); `bind_inactive` (`systemctl is-active` for `bind` did not answer `active`).
- R10: A resume: `resume_record_missing` (the earlier record cannot be read as JSON, lacks its session or account, or its session begins with `-`); `resume_runtime_differs` (field `runtime`: the earlier record's `runtime` is not the request's; a record without the member is a Claude stage's); `resume_account_differs` (the record's account is not one of the request's accounts); `resume_cwd_differs`, `resume_role_differs` (a resume keeps the earlier record's runtime, `cwd` and role, or is a `fixer` over an implementer's or a fixer's record); `run_still_active` (whatever the earlier record's state, `systemctl is-active` for its unit did not answer a state in which nothing of its unit lives: `active`, `activating`, `deactivating`, `reloading`, `refreshing`, a failed call and no answer all refuse). `ap run` guards a run's files against another run; it does not guard a session against its caller: two resumes of one record at the same time are not refused.

### The run and its record

- R11: Every run, fresh or resumed, creates its own record. `<out>.run.json` is created exclusively, and that creation is the claim: of two requests on one `out` started at the same instant, one passes and the other is refused `out_exists`. Then `<out>.stream.jsonl` and `<out>.err` are created exclusively; every write of the answer or the record goes through a temporary name unique to that write and created exclusively, so it is never another run's file. `<out>.run.json`, `<out>.stream.jsonl` and `<out>.err` are each created with mode 0600, asked for at the exclusive creation and not set afterwards; every temporary name a write of the record goes through is created with mode 0600, and so is a record written in place after a failed rename; so the record has mode 0600 from the claim to the end of the call, on a resumed run, on a launch of a next account, and as the fallback record of a call whose files cannot be opened. The answer file `<out>` is not covered: it keeps the mode it gets. A session id is chosen (or taken from the earlier record on a resume), and the record is written with state `running` BEFORE the launch; a resume's record names the earlier record in `resumes`. The launch is `systemd-run --scope --quiet --collect --unit=… --slice=agents.slice -p RuntimeMaxSec=<timeout + 10>s -p TimeoutStopSec=10s [-p BindsTo=<bind> -p After=<bind>] -- claude --print --output-format stream-json --verbose --model … --effort … --permission-mode … --permission-prompts none --setting-sources user --settings <settings> --disallowedTools Monitor --strict-mcp-config [--mcp-config …] [--disable-slash-commands] (--session-id | --resume) <session>`; `--disable-slash-commands` is left out only with `skills`. `RuntimeMaxSec` is the unit's own bound: it ends the stage when `ap run` is gone. This holds except for a launch on the PC (`specs/ap/run.md` R59), whose words after `systemd-run … --` are `tailscale ssh …`.
- R12: The settings, for every role and with nothing in the request: `disableAllHooks: true`; `env` with `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS` at 2700000 (a 40-minute check runs in the foreground of one Bash call) and `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` (a command that reaches its limit stops instead of moving to the background); `autoMemoryEnabled: false` unless `memory`; with `compact_window`, `env` holds one more name, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, whose value is the window as a decimal string (the other names are as they are). So the stage has no `Monitor` and no background shell.
- R13: The stage's environment is only `PATH HOME USER LOGNAME SHELL LANG LC_ALL TERM TMPDIR TZ` of the caller (when set), the request's `env`, the role and the author of `specs/ap/run-object.md` R3 to R5, and `CLAUDE_CONFIG_DIR=<account>`, or for a stage with limits its home of the launch (specs/ap/run-limits.md R14): no hook (of the account, the host, a project or a plugin), no MCP server the request does not name, and only the account's settings, a stage with limits the settings of R12 alone (a worktree's `.claude/settings.json` and `settings.local.json` do not load). A key launch (R54) has the same environment and one name more, `ANTHROPIC_API_KEY` (R55). This holds except for a launch on the PC (`specs/ap/run.md` R59), whose environment is the four variables of `PATH`, `HOME`, `USER` and `LOGNAME`.
- R14: stdout goes to `<out>.stream.jsonl`, which `ap run` reads only through the handle it opened before the launch; stderr to `<out>.err`, removed at the end when empty.
- R15: The end, by role. A `result` ends the stage only for a `reviewer` and a `writer`: at its first `result`. An `implementer` or a `fixer` runs to the CLI's exit (a print session that left a background shell emits a `result`, waits for the shell, then may run a second turn and emit another `result`; each `result` carries the `usage` and `num_turns` of its own part, and the sum is the session's); for every role `timeout_seconds` ends the stage. Then `systemctl stop` ends every process in the unit, the stream is read to its end (a last line without a newline included), and `systemctl is-active` must answer a state that is not `active`, `activating`, `deactivating`, `reloading` or `refreshing`; anything else, a failed call included, makes the state `failed` with `unmet: stop`.
- R16: The result a stage is judged by is the LAST `result` whose answer is nonempty, not an error or a cut, and meets `expect.first_line` and `expect.second_line` (each when given) when one met them (a later result does not unmake it), else the last `result` seen (a reviewer and a writer have only their first). An answer meets `expect` only when both lines match.
- R17: The states: `ok` (a non-error result whose text is nonempty and meets `expect`); `no_result` (a non-error result that is empty or does not meet `expect`; `unmet` names which: `answer`, `file`, `first_line`, `second_line` (the first line matches, the second does not), `schema`; a nonempty answer is still saved); `cut` (an error result with a rejected rate-limit event, API status 429 or the usage-limit text, or a non-error result with the usage-limit text and a rejected rate-limit event; no answer is written); `timeout` (the bound ended the stage, for every role, even when a result is read during the shutdown; the last answer, if any, is saved and `expect_met` says whether it met `expect`); `failed` (the CLI ended without a result event, an error result that is not a cut, the launch failed, the stop was not confirmed, or a write failed: `unmet` `result_event`, `launch`, `stop` or `write`). The answer is the result text, byte for byte, in `out`.
- R18: The exit: 0 `ok`, 75 `cut`, 3 any other end, 5 a file of the run could not be written after the record was claimed, which includes the case in which nothing ran (standard output holds the final record; the file holds it when a write in place succeeded). The record is printed on standard output.
- R19: `expect.file` is met only by a nonempty file whose digest or modification time differs from `expect_file_before`: the file as it was before THIS run's launch. Only a resume that continues the same unfinished stage (the earlier record has the same role and a state other than `ok`) takes the earlier record's `expect_file_before` instead; a fixer over an implementer always takes its own.
- R20: A fresh run cut before it did any work (the stream holds no `tool_use` block, so no tool ran), and a fresh run of a `reviewer` or a `writer` cut at any point (it changes no file of its `cwd`: what it did is lost, not wrong), is run again, within the same run and its record, on the next of `next_accounts` with a new session. So is an `implementer` or a `fixer` cut after a tool ran, when a next account is left, with the continuation (R21); with none left it stays cut. A move to a next account is read from `attempts` of the record (R28). Every other state ends the call, but one: a launch of a Claude stage, fresh or resumed, that ends `no_result` with `unmet` `first_line` (never one that missed `expect.file`, timed out, was cut or failed) is asked again, once per call: one more launch resumes that launch's session on its account (`--resume` with that session, the arguments of R11 otherwise unchanged) and reads on standard input only this sentence and a newline: "Your last answer did not begin with the line your task asks it to begin with: give the whole answer again with that line as its first line and nothing before it, and post, push, send or change nothing a second time." So is one that ends `no_result` with `unmet` `second_line`, by the same rule (once per call, the same session and account, the shared bound, the same record, the entry `asked` true), reading on standard input only this sentence and a newline: "Your last answer did not have as its second line the line your task asks for: give the whole answer again with the same first line, that line as its second line and nothing before them, and post, push, send or change nothing a second time." An answer that misses the first line keeps the first sentence. The launch that is asked again and its ask share one `timeout_seconds`: `ap run` ends the ask when what remained of the bound at its start has passed, and makes no ask when nothing remains (its scope keeps `RuntimeMaxSec` of R11 as the backstop); a move to another account keeps its own bound as before. The ask is judged on its first line, and its second line when `expect.second_line` is given, as every answer is (R16, R17): only when a line misses too is the state `no_result`. Whatever the ask ends in ends the call: one that ends `cut`, `timeout` or `failed` ends it with that state and moves to no account of `next_accounts`. A stage of another runtime is never asked again. A launch on the PC (R59) and its ask are no move to an account of `next_accounts` and are not counted among the moves read from `attempts`; whatever that launch ends in other than `ok` (after its ask on the PC where R62 gives one), and whatever that ask ends in other than `ok`, is followed by R62's one launch here alone, and no move or end this requirement names applies to them; from that launch on, this requirement applies as to any fresh run of a `reviewer`, but an ask spent on the PC is not given again.
- R21: The continuation. For the roles `implementer` and `fixer`, once a launch of a fresh call has worked (a tool ran) and was cut, every later launch of the call reads on stdin the continuation text, then the bytes of the prompt file; no file is written for it (the input is a pipe), so the names a call writes are the same. The text is these four sentences in one line, followed by one empty line: "A session of this stage on another account was cut by a usage limit after it had begun to work. This directory may hold its work, committed or not. First read the state it left: in a Git worktree `git status`, `git log --oneline origin/main..HEAD` and `git diff HEAD`. Keep what serves the task, do not start over, and go on until the task below is done." A reviewer's or a writer's next launch starts over without it, a launch that is not preceded by a launch that worked gets none, and a resumed call gets the text of a move instead (R23).
- R22: A resume is a run of its own with its own `out`; it continues the session of the earlier run on that run's account, for a stage with limits in that session's home (specs/ap/run-limits.md R14). The launches of a call with `resume` take the accounts in this order: the account of the record it names; then the request's `account` and the entries of `next_accounts` in their order, without any that equals the record's account and without a repetition (the record's account must be one of the request's accounts, else `resume_account_differs`). The first launch resumes the record's session, with the prompt file as its input.
- R23: The move of a resumed call. When a launch of a resumed call ends `cut`, before or after a tool ran, for every role, an account is left, and the resumed record holds `prompt.path` and `answer.path` as strings that hold no control character and do not contain the file name of the call's `out`, the call goes on within the same run and record: the next launch is a NEW session on the next account (a new session id, no resume argument) whose input is one line, an empty line, and the bytes of the prompt file; no file is written for it. A later launch that ends `cut` moves on in the same way while an account is left. With no account left, or with a record that lacks the two paths in that form, the call stays cut; a launch that ends in any other state ends the call, but for the ask of R20. The line, with `<P>` the resumed record's `prompt.path` and `<A>` its `answer.path` byte for byte, is for every role: "This stage was to resume an earlier session, and a usage limit cut that session on its account. You are a new session and hold nothing of what it read or wrote: before anything else read completely the prompt it was given, the file <P>, and the answer it gave, the file <A>. The task below was written for that session: where it speaks of what you did, wrote or were told, it means that session, its answer and its prompt." and, for the roles `implementer` and `fixer` (not for a `reviewer` or a `writer`, which get the first part alone), on the same line after one space: "This directory holds its work, committed or not. Read the state it left: in a Git worktree `git status`, `git log --oneline origin/main..HEAD` and `git diff HEAD`. Keep what serves the task, do not start over, and go on until the task below is done." The text goes only to a launch that follows a cut launch of the same call; the resumed launch reads the prompt file alone, and no launch of a resumed call gets the continuation text.
- R24: After a move the record's `session` and `account` are the new session's, so a later `resume` of that record resumes the new session on its account. A move of a resumed call is read from its record: `resumes` is not null and `attempts` holds more than one entry whose `asked` is false (the first is the resumed launch, with the resumed record's session; every later one is a new session). The member `asked` of an entry tells an ask from a move: it is true only in the entry of the launch that asked again (R20), which resumed the session of the entry before it on that entry's account, so its `session` and `account` are that entry's; it is false in every other entry. An entry that asked again is no move, in a fresh call as in a resumed one. The record's `prompt` stays the path and the digest of the prompt file.
- R25: The record `<out>.run.json`: `role`, `runtime` (`claude` or `agy`), `model`, `effort`, `account`, `session`, `cwd`, `unit`, `prompt{path,sha256}`, `answer{path,sha256}|null`, `start`, `end|null` (UTC, RFC 3339), `state`, `turns`, `tokens{input,output,cache_read,cache_creation}` (sums over the `result` events; null where the CLI did not report), `permission_denials` (`tool_name` and `tool_use_id` as reported, over all results), `results` (the number of `result` events read), `expect_met` (null without a result), `expect_file_before` (`{path, sha256, modified}` or null), `unmet`, `resumes` (the earlier record's path, or null), `run_object` (`specs/ap/run-object.md` R8), `policy` (`specs/ap/policy.md` R11), `compact_window` (the request's window, or null without the member; for every runtime, from the first write of the record, a launch that could not be started included), and with `answer_schema` the member `answer_schema{path,sha256}`. A stage on the Claude runtime also holds `auth` and `auth_fault` (R56). A stage on the Claude runtime also holds `limit` and `attempts`; a stage on `agy` (R50) and a Claude stage with `limits` (`specs/ap/run-limits.md` R14) also hold `home`. No prompt or answer text.
- R26: `limit` is what the last launch's stream held of rate limits: null when it held no line of type `rate_limit_event` (and while a launch runs); else an object made from ONE such line, the last whose `rate_limit_info.status` is `rejected` when the launch saw one, else the last line. Its members: `status` (`rate_limit_info.status` when it is a string, else null), `kind` (`rateLimitType` when it is a string, else null), `resets_at` (`resetsAt` when it is a non-negative integer, copied as that number, else null: a number in float form, `1794772800.0` included, is null) and `windows` (an object: for at most eight members of `unifiedWindows` whose value is an object, taken in the order of their names, the same name with `status`, `utilization` (a number, else null) and `resets_at`, by the same rules; `{}` when there is none).
- R27: No other member of a `rate_limit_event` is read: `overageStatus` is never a status, and no line of the stream alone makes a stage `cut` (R17 says what does).
- R28: `attempts` is an array with one entry per launch the call began, in order, a launch that could not be started included: `account`, `session`, `start`, `end`, `state` (as the record holds them for that launch), `worked` (a tool ran in it), `continued` (it got the continuation text; false for a launch that could not be started, in every entry of a resumed call and in the entry of an ask), `asked` (it asked again, R24), `limit` (R26, of that launch) and, for a Claude stage, `auth` and `auth_fault` (R56, of that launch). While a launch runs its entry is the last one, with `state` `running`, `end` null and `limit` null. Every other member of the record is the last launch's, and the last entry agrees with them, with two exceptions after an ask (R20): the record's `turns` and each member of `tokens` are the sums of the asked launch and its ask (null when both are null, a null counting 0 otherwise), and when the ask wrote no answer (it ended without a result, cut, or with an empty answer) the record keeps the asked launch's `answer` (`path`, `sha256`), which is what `out` still holds.
- R29: A call whose files could not be opened after the claim (the stream or the error file cannot be created) launches nothing, ends `failed` with `unmet: launch` (exit 5) and writes the record of three members, `state`, `unmet` and `account`: without `limit`, `attempts`, `compact_window`, `policy` and `run_object`.

### The typed answer

- R30: `answer_schema` makes the answer of a stage on the Claude runtime one JSON object that the CLI validated against a schema of the request, in place of free text. Its value is the absolute path of a regular file of at most 65,536 bytes whose text parses as one JSON object. A value that is no such path or file, the member together with `expect.first_line` (there is no first line to match), and the member on any other runtime refuse `invalid_input` with the field `answer_schema`, before any effect.
- R31: With the member the CLI's arguments gain `--json-schema` followed by the file's text exactly as read, for a first run and for a `resume` alike; nothing else of them changes. The record holds `answer_schema{path,sha256}` (the file as it was read) from the launch on.
- R32: A `result` event counts as an answer only when its member `structured_output` is a JSON object; the choice among several `result` events is the one of R16 with that condition in place of the first-line pattern. The answer file `out` then holds that object as JSON text, pretty-printed with one trailing newline, written through a temporary name, and the record's `answer` names its path and digest; the text of the `result` member is not the answer. A chosen `result` whose `structured_output` is absent, null or not an object ends the stage `no_result` with `unmet: schema` (exit 3); its result text, when it is not empty, is saved to `out` as a miss of `expect.first_line` saves it. An error, a cut and a time bound end as without the member.
- R33: Without the member every argument list, record, file, output and exit code is what it is without R30 to R32.

### A stage on the Antigravity CLI

- R47: `runtime: "agy"` starts a reviewer, an implementer or a fixer stage on the Antigravity CLI (`agy`) through the same request, scope, record files and order of judgment, and the request differs: `role` is `reviewer`, `implementer` or `fixer` (a `writer`, which stays Claude-only by R53, and any other role refuse `invalid_input` with `role`); `account` is the template of the stage's homes, an existing directory (else `account_missing`) that holds `.gemini/antigravity-cli/antigravity-oauth-token` (a symbolic link to the real token counts; a missing file or a link to nothing refuses `invalid_input`, field `account`) and holds no `.gemini/config` (the same refusal); `model` is the CLI's slug, passed as one argument of its own, so a value that begins with `-` refuses `invalid_input` with `model`; `effort` is required and must be the level the slug ends with (`low`, `medium`, `high` or `xhigh`), else `invalid_input` with `effort`, and is not passed to the CLI; `permission_mode` must be stated and be `bypassPermissions`; `next_accounts` and `mcp_config` must be absent or empty; `skills`, `memory`, `integration`, `answer_schema` and `compact_window` must be absent (each refuses `invalid_input` with its name); `env` refuses `env_forbidden` also for a name beginning `AGY_` or `GEMINI_`. A resume refuses `resume_runtime_differs` across runtimes in both directions. The admission `ap unit`'s case verb makes before a stage exists (`specs/ap/unit.md`) is unchanged: there an `agy` stage is a reviewer alone.
- R48: The prompt reaches the CLI as one argument: a prompt above 131071 bytes (one argument's limit on Linux is 131072 bytes with its terminating NUL byte), one that holds a NUL byte and one that is not UTF-8 text refuse `invalid_input` with `prompt`, before any effect.

## Interface

`ap run < request.json`; the request of R2 and of the three specifications named in the Purpose; the record `<out>.run.json` of R25 and the files `<out>`, `<out>.stream.jsonl` and `<out>.err`; the exits of R18. `ap run --help` prints its usage (`specs/ap/verbs.md` R2). A request with the member `close` is the close of an orphan `run` object, `specs/ap/run-object.md` R14.

Every refusal code `ap run` emits, exit 2 before any effect, with the requirement that holds it:

| --- | --- |

| `invalid_input` | R1, R2, R4, R5, R6, R30, R47, R48, R50, R53, R57; `specs/ap/run-object.md` R1, R14; `specs/ap/run-limits.md` R1, R11, R14 |

The usage-limit text is the rule `ap run` reads in an error result's message for every runtime.

A caller's use: `bind` is for a transient unit (the caller's own, as a chain's). On a resume the prompt file is the next message to the session: give a continuation or the findings, not the first prompt again. The caller is the one owner of a session and runs its stages in sequence. The stream holds the session's transcript (answers and tool output): the record, the stream and the error file are readable by their owner alone (R11), while the answer file and the directory of `out` are the caller's, so keep `out` where it is private. A reader of a typed answer types the members it reads: it checks each member's type when it reads it, and does not take a type from `ap run`, which does not validate the object against the schema (the CLI did, and a stage that ends `ok` holds the object the CLI accepted). An `agy` stage runs with no approval and no sandbox of the CLI's own, so without `limits` it is held to its worktree or its copy by its prompt alone (a Claude stage in `ap unit` runs in the mode `auto` by default). In `ap unit` a verifier block may name `runtime: "agy"`; an `implementer` block (and so its fixer) that names it is refused before any effect with the error `ap run` gives, under the block's field (`implementer.role`); the second look of an agy verifier resumes its record as for the other runtimes. `git`, `gh`, `cargo` and `rustup` of an agy stage read the directory given as `HOME`, which is the stage's home and not the caller's home: a request whose stage needs them names their directories in `env` (`GH_CONFIG_DIR`, `CARGO_HOME`, `RUSTUP_HOME`); `ap` does not yet give a writing agy stage those files, which is why an agy stage is a reviewer. The homes of a unit that is closed stay under `<account>/homes` until the operator removes them. `ci/host-run-scope.sh` exercises the real scope on a host with systemd.

## Not included

What the CLIs do of their own, which `ap run` does not hold and no test of this repository can show:

- Claude Code: with the settings of R12 and `--setting-sources user`, the stage's first event lists no skill and no memory directory, while the account's `CLAUDE.md` still loads, for a stage with `limits` through the read-only bind in its home (`specs/ap/run-limits.md` R15, shown on Claude Code 2.1.330); a worktree's project `CLAUDE.md` and `.claude/agents` do not load (shown on Claude Code 2.1.325). The documented rate-limit statuses are `allowed`, `allowed_warning` and `rejected` (the SDK's); `rateLimitType` and `unifiedWindows` are shown by the CLI and not documented, and the members of a `rejected` event have not been seen: a member of another shape is null (R26).
- The Antigravity CLI: the home is a directory given as `HOME`, so a writing stage's `git`, `gh` and `cargo` would lose their own files. A `.gemini/config` is where the CLI reads the MCP servers, hooks, skills and plugins registered for it, and a home made from a template that holds one would link into it (why R47 refuses it). For Hydrogen the slugs are `gemini-4-hydrogen-low`, `-medium`, `-high`, `-xhigh` (`agy models`); `--effort` was never run. What each flag of R49 carries: the prompt text, run once without a terminal (`--print`: the next argument is its value, also when it begins with dashes, observed); one JSON object per line (`--output-format stream-json`); the stage's model, whose slug carries the level (`--model`); no approval prompt (`--dangerously-skip-permissions`; the line `init` then shows `permission_mode` `always-proceed`); and the stage's own bound as the CLI's time limit (`--print-timeout`; `ap run` ends the stage at the same bound and judges by what it read). The CLI has no working-directory flag: it works in the process's `cwd`, which also keys its conversations; the session cannot be chosen. The CLI creates `.gemini/config` (an empty `mcp_config.json`, a `config.json` that enables the plugin `swarm`, `.migrated` and `projects/`) and its own state under `.gemini/antigravity-cli` (the conversation as `conversations/<id>.db` and `brain/<id>/`, among it) at its first run in a home, so one shared home could not pass the account rule twice, and a shared home would let a fresh stage read the conversations of the stages before it (why R50 makes a home for each fresh stage and the template stays as it was).
