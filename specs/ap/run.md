# One stage: `ap run`

Purpose: one stage of work (an implementer, a reviewer or a fixer) runs as ONE headless session of a coding CLI (Claude Code; the Codex CLI with `runtime: "codex"`; the Muse Code CLI with `runtime: "muse"`; for a reviewer, the Antigravity CLI with `runtime: "agy"`) in a transient systemd scope `ap-run-<uuid>.scope` under `agents.slice`, and `ap run` returns when nothing of it is alive, with one record `<out>.run.json` that says how it ended, so that a caller judges a stage by its record and never by a session it watched. This file holds the request, the refusals, the run, the states, the record, the typed answer and the four runtimes. Three specifications hold the rest and are not repeated here: `specs/ap/run-limits.md` (a stage with `limits`), `specs/ap/run-object.md` (a stage of a unit or an intent, the role and the author, and the close of an orphan `run` object) and `specs/ap/policy.md` (the host's policy file, the last check of admission).

## Requirements

### The request

- R1: The form is `ap run < request.json`: no argument (an argument refuses `usage`, field `args`), and standard input one JSON object of at most 1 MiB (more refuses `input_too_large`, field `stdin`; input that is not JSON or not an object refuses `invalid_input`, field `stdin`; input that cannot be read refuses `io_error`, field `stdin`). It reads no role table and calls no Herdr or GitHub; it calls the store only as `specs/ap/run-object.md` says (a request with `unit`, `intent` or `close`).
- R2: The members: `role` (`implementer`, `reviewer`, `fixer`), `account` (the Claude configuration directory, required), optional `next_accounts`, `model`, `effort`, `permission_mode` (one of Claude Code's: `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan`), `cwd`, `prompt` (a regular file, at most 1 MiB, given to the CLI on stdin), `out` (the answer's path), and optional `timeout_seconds` (an integer from 1 to 86400; default implementer 5400, fixer 3600, reviewer 3300), `expect` (an object of `file`, a path that this run must write nonempty, `first_line`, a pattern of at most 200 bytes and no newline that the answer's first line must match, where `*` matches any run of characters, and `second_line`, a pattern of the same form that the answer's second line must match, an empty line when the answer has one line; `second_line` is admitted only together with `first_line`, and alone, or of another form, refuses `invalid_input` with the field `expect.second_line`), `resume` (`{"record": "<absolute path of the earlier run's record>"}`), `continue_dirty`, `integration` (a reviewer's only: another role refuses `invalid_input`; it does not choose the account), `mcp_config` (files; the only MCP servers loaded), `env` (extra variables), `runtime` (`claude`, the default, `codex`, `muse` or `agy`), `bind`, `skills` and `memory` (booleans: the account's skills and slash commands, and its auto-memory, load only when true), `answer_schema` (R30), `compact_window` (R5), the members of `specs/ap/run-object.md` R1 (`unit`, `intent`, `store`, `git_author`, `ont_role`) and `limits` (`specs/ap/run-limits.md` R1). Every path is absolute. Another member refuses `invalid_input` with its name, and so does a member of the wrong type or out of its range, with the member's name as the field.
- R3: `env` may not name a variable beginning `HERDR_`, `CLAUDE_` or `ANTHROPIC_`, nor `HOME`, nor the names of `specs/ap/run-object.md` R2 (`ONT_ROLE`, `ONT_AGENT`, `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `BASH_ENV`, `ENV`), nor a name a runtime reserves (R34, R39, R45): each refuses `env_forbidden`, field `env`, so the account named in the record is the account that answers.
- R4: An `out` whose file name ends with a suffix `ap run` derives (`.run.json`, `.stream.jsonl`, `.err`, `.ap-tmp`) refuses `invalid_input`, field `out`: no run's answer path is another run's file.
- R5: `compact_window` is a Claude stage's only: an integer from 100000 to 1000000, read as `timeout_seconds` is read, so a fraction, an exponent, a string or null refuses `invalid_input` with that field; the CLI starts with `CLAUDE_CODE_AUTO_COMPACT_WINDOW` set to it in the `env` of its `--settings` value (R12), so the stage's compaction window is this one; without it the account's settings decide. A stage on another runtime refuses the member with `invalid_input`, field `compact_window`.
- R6: `bind` is the name of a systemd unit that is active now: when it ends for any reason, stopped, killed or failed, the stage's unit stops (`-p BindsTo=<bind> -p After=<bind>`, R11). A name that is not a unit name refuses `invalid_input`, field `bind`; a unit that is not `active` refuses `bind_inactive` (R9). A unit that ended between the request and the launch makes the launch fail (the record says `failed`); a unit that systemd can start again by name is started again by the launch, because `BindsTo` requires it.

### The refusals before any effect

- R7: Every refusal exits 2 with `{"error":{"code","field","detail"}}` on standard error, before any effect: no file is written, a refusal has no record, and an earlier run's files stay as they were. The request's own members: `invalid_input` (R1 to R6), `env_forbidden` (R3), and `account_missing` (`account` or an entry of `next_accounts` is not an existing directory; `/root/.claude` is an account like any other, for every role, as `account` and in `next_accounts`).
- R8: The files: `cwd_missing` (`cwd` is no directory); `prompt_unreadable` (the prompt cannot be read, is empty or is over 1 MiB); `out_unwritable` (the directory of `out` does not exist, `out` is a directory, or `out` is the prompt); `out_named_in_prompt` (the prompt contains the out file's name); `out_exists` (`out`, `<out>.run.json`, `<out>.stream.jsonl` or `<out>.err` exists: nothing of an earlier run is replaced, removed or truncated by a later one).
- R9: The host: `worktree_dirty` (a fresh implementer run in a Git worktree with changes, unless `continue_dirty`); `worktree_unreadable` (Git cannot read `cwd` for a reason other than "not a git repository"; `git` runs with the fixed short list of variables only, not the request's `env`); `systemd_absent` (the host has no service manager); `bind_inactive` (`systemctl is-active` for `bind` did not answer `active`).
- R10: A resume: `resume_record_missing` (the earlier record cannot be read as JSON, lacks its session or account, or its session begins with `-`); `resume_runtime_differs` (field `runtime`: the earlier record's `runtime` is not the request's; a record without the member is a Claude stage's); `resume_account_differs` (the record's account is not one of the request's accounts); `resume_cwd_differs`, `resume_role_differs` (a resume keeps the earlier record's runtime, `cwd` and role, or is a `fixer` over an implementer's or a fixer's record); `run_still_active` (whatever the earlier record's state, `systemctl is-active` for its unit did not answer a state in which nothing of its unit lives: `active`, `activating`, `deactivating`, `reloading`, `refreshing`, a failed call and no answer all refuse). `ap run` guards a run's files against another run; it does not guard a session against its caller: two resumes of one record at the same time are not refused.

### The run and its record

- R11: Every run, fresh or resumed, creates its own record. `<out>.run.json` is created exclusively, and that creation is the claim: of two requests on one `out` started at the same instant, one passes and the other is refused `out_exists`. Then `<out>.stream.jsonl` and `<out>.err` are created exclusively; every write of the answer or the record goes through a temporary name unique to that write and created exclusively, so it is never another run's file. `<out>.run.json`, `<out>.stream.jsonl` and `<out>.err` are each created with mode 0600, asked for at the exclusive creation and not set afterwards; every temporary name a write of the record goes through is created with mode 0600, and so is a record written in place after a failed rename; so the record has mode 0600 from the claim to the end of the call, on a resumed run, on a launch of a next account, and as the fallback record of a call whose files cannot be opened. The answer file `<out>` is not covered: it keeps the mode it gets. A session id is chosen (or taken from the earlier record on a resume), and the record is written with state `running` BEFORE the launch; a resume's record names the earlier record in `resumes`. The launch is `systemd-run --scope --quiet --collect --unit=… --slice=agents.slice -p RuntimeMaxSec=<timeout + 10>s -p TimeoutStopSec=10s [-p BindsTo=<bind> -p After=<bind>] -- claude --print --output-format stream-json --verbose --model … --effort … --permission-mode … --permission-prompts none --setting-sources user --settings <settings> --disallowedTools Monitor --strict-mcp-config [--mcp-config …] [--disable-slash-commands] (--session-id | --resume) <session>`; `--disable-slash-commands` is left out only with `skills`. `RuntimeMaxSec` is the unit's own bound: it ends the stage when `ap run` is gone.
- R12: The settings, for every role and with nothing in the request: `disableAllHooks: true`; `env` with `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS` at 2700000 (a 40-minute check runs in the foreground of one Bash call) and `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` (a command that reaches its limit stops instead of moving to the background); `autoMemoryEnabled: false` unless `memory`; with `compact_window`, `env` holds one more name, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, whose value is the window as a decimal string (the other names are as they are). So the stage has no `Monitor` and no background shell.
- R13: The stage's environment is only `PATH HOME USER LOGNAME SHELL LANG LC_ALL TERM TMPDIR TZ` of the caller (when set), the request's `env`, the role and the author of `specs/ap/run-object.md` R3 to R5, and `CLAUDE_CONFIG_DIR=<account>`: no hook (of the account, the host, a project or a plugin), no MCP server the request does not name, and only the account's settings (a worktree's `.claude/settings.json` and `settings.local.json` do not load).
- R14: stdout goes to `<out>.stream.jsonl`, which `ap run` reads only through the handle it opened before the launch; stderr to `<out>.err`, removed at the end when empty.
- R15: The end, by role. A `result` ends the stage only for a `reviewer`: at its first `result`. An `implementer` or a `fixer` runs to the CLI's exit (a print session that left a background shell emits a `result`, waits for the shell, then may run a second turn and emit another `result`; each `result` carries the `usage` and `num_turns` of its own part, and the sum is the session's); for every role `timeout_seconds` ends the stage. Then `systemctl stop` ends every process in the unit, the stream is read to its end (a last line without a newline included), and `systemctl is-active` must answer a state that is not `active`, `activating`, `deactivating`, `reloading` or `refreshing`; anything else, a failed call included, makes the state `failed` with `unmet: stop`.
- R16: The result a stage is judged by is the LAST `result` whose answer is nonempty, not an error or a cut, and meets `expect.first_line` and `expect.second_line` (each when given) when one met them (a later result does not unmake it), else the last `result` seen (a reviewer has only its first). An answer meets `expect` only when both lines match.
- R17: The states: `ok` (a non-error result whose text is nonempty and meets `expect`); `no_result` (a non-error result that is empty or does not meet `expect`; `unmet` names which: `answer`, `file`, `first_line`, `second_line` (the first line matches, the second does not), `schema`; a nonempty answer is still saved); `cut` (an error result with a rejected rate-limit event, API status 429 or the usage-limit text, or a non-error result with the usage-limit text and a rejected rate-limit event; no answer is written); `timeout` (the bound ended the stage, for every role, even when a result is read during the shutdown; the last answer, if any, is saved and `expect_met` says whether it met `expect`); `failed` (the CLI ended without a result event, an error result that is not a cut, the launch failed, the stop was not confirmed, or a write failed: `unmet` `result_event`, `launch`, `stop` or `write`). The answer is the result text, byte for byte, in `out`.
- R18: The exit: 0 `ok`, 75 `cut`, 3 any other end, 5 a file of the run could not be written after the record was claimed, which includes the case in which nothing ran (standard output holds the final record; the file holds it when a write in place succeeded). The record is printed on standard output.
- R19: `expect.file` is met only by a nonempty file whose digest or modification time differs from `expect_file_before`: the file as it was before THIS run's launch. Only a resume that continues the same unfinished stage (the earlier record has the same role and a state other than `ok`) takes the earlier record's `expect_file_before` instead; a fixer over an implementer always takes its own.
- R20: A fresh run cut before it did any work (the stream holds no `tool_use` block, so no tool ran), and a fresh run of a `reviewer` cut at any point (it changes no file: what it did is lost, not wrong), is run again, within the same run and its record, on the next of `next_accounts` with a new session. So is an `implementer` or a `fixer` cut after a tool ran, when a next account is left, with the continuation (R21); with none left it stays cut. A move to a next account is read from `attempts` of the record (R28). Every other state ends the call, but one: a launch of a Claude stage, fresh or resumed, that ends `no_result` with `unmet` `first_line` (never one that missed `expect.file`, timed out, was cut or failed) is asked again, once per call: one more launch resumes that launch's session on its account (`--resume` with that session, the arguments of R11 otherwise unchanged) and reads on standard input only this sentence and a newline: "Your last answer did not begin with the line your task asks it to begin with: give the whole answer again with that line as its first line and nothing before it, and post, push, send or change nothing a second time." So is one that ends `no_result` with `unmet` `second_line`, by the same rule (once per call, the same session and account, the shared bound, the same record, the entry `asked` true), reading on standard input only this sentence and a newline: "Your last answer did not have as its second line the line your task asks for: give the whole answer again with the same first line, that line as its second line and nothing before them, and post, push, send or change nothing a second time." An answer that misses the first line keeps the first sentence. The launch that is asked again and its ask share one `timeout_seconds`: `ap run` ends the ask when what remained of the bound at its start has passed, and makes no ask when nothing remains (its scope keeps `RuntimeMaxSec` of R11 as the backstop); a move to another account keeps its own bound as before. The ask is judged on its first line, and its second line when `expect.second_line` is given, as every answer is (R16, R17): only when a line misses too is the state `no_result`. Whatever the ask ends in ends the call: one that ends `cut`, `timeout` or `failed` ends it with that state and moves to no account of `next_accounts`. A stage of another runtime is never asked again.
- R21: The continuation. For the roles `implementer` and `fixer`, once a launch of a fresh call has worked (a tool ran) and was cut, every later launch of the call reads on stdin the continuation text, then the bytes of the prompt file; no file is written for it (the input is a pipe), so the names a call writes are the same. The text is these four sentences in one line, followed by one empty line: "A session of this stage on another account was cut by a usage limit after it had begun to work. This directory may hold its work, committed or not. First read the state it left: in a Git worktree `git status`, `git log --oneline origin/main..HEAD` and `git diff HEAD`. Keep what serves the task, do not start over, and go on until the task below is done." A reviewer's next launch starts over without it, a launch that is not preceded by a launch that worked gets none, and a resumed call gets the text of a move instead (R23).
- R22: A resume is a run of its own with its own `out`; it continues the session of the earlier run on that run's account. The launches of a call with `resume` take the accounts in this order: the account of the record it names; then the request's `account` and the entries of `next_accounts` in their order, without any that equals the record's account and without a repetition (the record's account must be one of the request's accounts, else `resume_account_differs`). The first launch resumes the record's session, with the prompt file as its input.
- R23: The move of a resumed call. When a launch of a resumed call ends `cut`, before or after a tool ran, for every role, an account is left, and the resumed record holds `prompt.path` and `answer.path` as strings that hold no control character and do not contain the file name of the call's `out`, the call goes on within the same run and record: the next launch is a NEW session on the next account (a new session id, no resume argument) whose input is one line, an empty line, and the bytes of the prompt file; no file is written for it. A later launch that ends `cut` moves on in the same way while an account is left. With no account left, or with a record that lacks the two paths in that form, the call stays cut; a launch that ends in any other state ends the call, but for the ask of R20. The line, with `<P>` the resumed record's `prompt.path` and `<A>` its `answer.path` byte for byte, is for every role: "This stage was to resume an earlier session, and a usage limit cut that session on its account. You are a new session and hold nothing of what it read or wrote: before anything else read completely the prompt it was given, the file <P>, and the answer it gave, the file <A>. The task below was written for that session: where it speaks of what you did, wrote or were told, it means that session, its answer and its prompt." and, for the roles `implementer` and `fixer`, on the same line after one space: "This directory holds its work, committed or not. Read the state it left: in a Git worktree `git status`, `git log --oneline origin/main..HEAD` and `git diff HEAD`. Keep what serves the task, do not start over, and go on until the task below is done." The text goes only to a launch that follows a cut launch of the same call; the resumed launch reads the prompt file alone, and no launch of a resumed call gets the continuation text.
- R24: After a move the record's `session` and `account` are the new session's, so a later `resume` of that record resumes the new session on its account. A move of a resumed call is read from its record: `resumes` is not null and `attempts` holds more than one entry whose `asked` is false (the first is the resumed launch, with the resumed record's session; every later one is a new session). The member `asked` of an entry tells an ask from a move: it is true only in the entry of the launch that asked again (R20), which resumed the session of the entry before it on that entry's account, so its `session` and `account` are that entry's; it is false in every other entry. An entry that asked again is no move, in a fresh call as in a resumed one. The record's `prompt` stays the path and the digest of the prompt file.
- R25: The record `<out>.run.json`: `role`, `runtime` (`claude`, `codex`, `muse` or `agy`), `model`, `effort`, `account`, `session`, `cwd`, `unit`, `prompt{path,sha256}`, `answer{path,sha256}|null`, `start`, `end|null` (UTC, RFC 3339), `state`, `turns`, `tokens{input,output,cache_read,cache_creation}` (sums over the `result` events; null where the CLI did not report), `permission_denials` (`tool_name` and `tool_use_id` as reported, over all results), `results` (the number of `result` events read), `expect_met` (null without a result), `expect_file_before` (`{path, sha256, modified}` or null), `unmet`, `resumes` (the earlier record's path, or null), `run_object` (`specs/ap/run-object.md` R8), `policy` (`specs/ap/policy.md` R11), `compact_window` (the request's window, or null without the member; for every runtime, from the first write of the record, a launch that could not be started included), and with `answer_schema` the member `answer_schema{path,sha256}`. A stage on the Claude runtime and a stage on Muse Code also hold `limit` and `attempts`; a stage on `agy` also holds `home` (R50); a Muse stage stopped for its model holds `served_by` (R46). No prompt or answer text.
- R26: `limit` is what the last launch's stream held of rate limits: null when it held no line of type `rate_limit_event` (and always for a Codex stage, and while a launch runs); else an object made from ONE such line, the last whose `rate_limit_info.status` is `rejected` when the launch saw one, else the last line. Its members: `status` (`rate_limit_info.status` when it is a string, else null), `kind` (`rateLimitType` when it is a string, else null), `resets_at` (`resetsAt` when it is a non-negative integer, copied as that number, else null: a number in float form, `1794772800.0` included, is null) and `windows` (an object: for at most eight members of `unifiedWindows` whose value is an object, taken in the order of their names, the same name with `status`, `utilization` (a number, else null) and `resets_at`, by the same rules; `{}` when there is none).
- R27: No other member of a `rate_limit_event` is read: `overageStatus` is never a status, and no line of the stream alone makes a stage `cut` (R17 says what does).
- R28: `attempts` is an array with one entry per launch the call began, in order, a launch that could not be started included: `account`, `session`, `start`, `end`, `state` (as the record holds them for that launch), `worked` (a tool ran in it), `continued` (it got the continuation text; false for a launch that could not be started, in every entry of a resumed call and in the entry of an ask), `asked` (it asked again, R24) and `limit` (R26, of that launch). While a launch runs its entry is the last one, with `state` `running`, `end` null and `limit` null. Every other member of the record is the last launch's, and the last entry agrees with them, with two exceptions after an ask (R20): the record's `turns` and each member of `tokens` are the sums of the asked launch and its ask (null when both are null, a null counting 0 otherwise), and when the ask wrote no answer (it ended without a result, cut, or with an empty answer) the record keeps the asked launch's `answer` (`path`, `sha256`), which is what `out` still holds; a Codex stage has one entry (`continued` false, `limit` null).
- R29: A call whose files could not be opened after the claim (the stream or the error file cannot be created) launches nothing, ends `failed` with `unmet: launch` (exit 5) and writes the record of three members, `state`, `unmet` and `account`: without `limit`, `attempts`, `compact_window`, `policy` and `run_object`.

### The typed answer

- R30: `answer_schema` makes the answer of a stage on the Claude runtime one JSON object that the CLI validated against a schema of the request, in place of free text. Its value is the absolute path of a regular file of at most 65,536 bytes whose text parses as one JSON object. A value that is no such path or file, the member together with `expect.first_line` (there is no first line to match), and the member on any other runtime refuse `invalid_input` with the field `answer_schema`, before any effect.
- R31: With the member the CLI's arguments gain `--json-schema` followed by the file's text exactly as read, for a first run and for a `resume` alike; nothing else of them changes. The record holds `answer_schema{path,sha256}` (the file as it was read) from the launch on.
- R32: A `result` event counts as an answer only when its member `structured_output` is a JSON object; the choice among several `result` events is the one of R16 with that condition in place of the first-line pattern. The answer file `out` then holds that object as JSON text, pretty-printed with one trailing newline, written through a temporary name, and the record's `answer` names its path and digest; the text of the `result` member is not the answer. A chosen `result` whose `structured_output` is absent, null or not an object ends the stage `no_result` with `unmet: schema` (exit 3); its result text, when it is not empty, is saved to `out` as a miss of `expect.first_line` saves it. An error, a cut and a time bound end as without the member.
- R33: Without the member every argument list, record, file, output and exit code is what it is without R30 to R32.

### A stage on the Codex CLI

- R34: `runtime: "codex"` starts the stage on the Codex CLI through the same request, scope, record files and order of judgment, and the request differs: `role` is `implementer` or `fixer` (a `reviewer` refuses `invalid_input` with `role`); `account` is a Codex home (an existing directory, given to the CLI as `CODEX_HOME`); `next_accounts` must be absent or empty, and `mcp_config` absent or empty; `skills`, `memory`, `integration` and `compact_window` must be absent (each refuses `invalid_input` with its name); `model` is the CLI's model name and `effort` its reasoning effort; `permission_mode` must be stated and be `bypassPermissions`; `env` refuses `env_forbidden` also for a name beginning `CODEX_` or `OPENAI_`. Every other member means what it means above. A Codex stage has one account and never moves.
- R35: The launch, after the same `systemd-run … --`: `codex --no-daemon exec --json --ignore-user-config --ignore-rules --disable hooks --disable apps --disable plugins --disable plugin_discovery_prefetch --disable skill_mcp_dependency_install --disable memories --disable multi_agent -c features.multi_agent_v2.max_concurrent_threads_per_session=1 --skip-git-repo-check --dangerously-bypass-approvals-and-sandbox -m <model> -c model_reasoning_effort="<effort>" -C <cwd> -`, the prompt on stdin (`-`), the environment of a Claude stage with `CODEX_HOME=<account>` in place of `CLAUDE_CONFIG_DIR`. A resume is `codex --no-daemon exec resume <the same flags> -m <model> -c model_reasoning_effort="<effort>" <session> -` in the record's `cwd`. No `--ephemeral` and no `--dangerously-bypass-hook-trust`; `ap` writes no file of the home.
- R36: The CLI's `--json` events are read into the shape the judgment reads, so one order of judgment serves every runtime. `thread.started` names the session: its `thread_id` is written into the record at once (state `running`), and stays there in every state (null only when the CLI named no thread); a failed write of the record at that point is a failed write of the record after the launch (exit 5). A turn end is a result: `turn.completed` gives the answer, the text of the LAST `agent_message` item completed in that turn (empty when there is none: `no_result` with `unmet: answer`), and the usage; `turn.failed` is an error result whose message is the error's, never written to `out` or to the record (the stream holds it). A message of a turn that did not complete is never an answer. An `error` event alone decides nothing. A failed turn is `failed`, or `cut` (exit 75) when its message is the usage-limit text; no turn end is `timeout` when the bound stopped the stage and `failed` (`unmet: result_event`) when the CLI ended by itself.
- R37: The Codex record: `tokens` maps the turn's usage as `evals/readout.py` maps a Codex session: `input` is `input_tokens` without `cached_input_tokens` and `cache_write_input_tokens`, `cache_read` is `cached_input_tokens`, `cache_creation` is `cache_write_input_tokens` (0 when the CLI gives none), `output` is `output_tokens`. A resume's record holds its own part: the reported usage less the `tokens` of the earlier record and of every record that one resumes (a record without tokens counts 0); when that chain cannot be followed to its end (more than 256 records, a record that cannot be read, or a record met twice), the record's `tokens` are null. `turns` is the number of completed items (messages, reasoning, commands, file changes, …), not comparable with a Claude stage's turns; `results` the number of turn ends read; `permission_denials` is empty. A tool ran when an item that is neither an agent message, nor reasoning, nor an error started or completed.

### A stage on Muse Code

- R38: `runtime: "muse"` starts the stage on the Muse Code CLI through the same request, scope, record files and order of judgment, and the request differs: `role` is any of the three roles; `account` is the Muse Code configuration directory (an existing directory, else `account_missing`) whose last path component is `muse` (else `invalid_input`, field `account`), and the CLI is given its parent as `XDG_CONFIG_HOME`; `next_accounts` must be absent or empty, and `mcp_config` absent or empty; `skills`, `memory`, `integration`, `answer_schema` and `compact_window` must be absent (each refuses `invalid_input` with its name); `model` and `effort` are passed as they are, each as an argument of its own, so a value that begins with `-` refuses `invalid_input` with its field; `permission_mode` must be stated and be `bypassPermissions`.
- R39: `env` refuses `env_forbidden` also for a name beginning `MUSE_` and for `XDG_CONFIG_HOME`. A resume refuses `resume_runtime_differs` across runtimes in both directions.
- R40: The launch, after the same `systemd-run … --`: `muse exec --json --model <model> --reasoning-effort <effort> --contributor-mode off --disable-reminders --session-id <session> --workspace <cwd> --prompt-file <prompt> --yolo`, these arguments in this order and no other, for a fresh and a resumed stage alike (a resume is the same launch with the session of the record, in its `cwd`). The environment is that of a Claude stage with `XDG_CONFIG_HOME=<the parent directory of account>` in place of `CLAUDE_CONFIG_DIR`, and `MUSE_NO_AUTO_UPDATE=1`; the standard input is the null device: the prompt reaches the CLI as the path. The session id is chosen by `ap run` and stands in the record before the launch.
- R41: A Muse stage has one account: a launch that ends `cut` ends the call, with no continuation and no move. `ap run` reads and writes no file under the account directory.
- R42: The lines of standard output (each one JSON object whose member `payload.kind` names it) are read into the shape the judgment reads. A line of kind `task_lifecycle` whose `payload.event.task_kind` begins with `tool.` shows that the session did work. A line that is no JSON object, or of another kind, decides nothing.
- R43: Each line of kind `run_terminal` is a result: `terminal` `completed` gives the answer, `text` (empty: `no_result`, `unmet: answer`); any other `terminal` is an error result whose message is `reason`, never written to `out`: `failed`, or `cut` (exit 75) when `reason` meets the usage-limit rule. A `text` or a `reason` that is no string counts as empty. A reviewer's stage ends at the first `run_terminal`; for the other roles it ends when the CLI ends or at the bound, and a CLI that outlives its `run_terminal` to the bound is `timeout` with that answer kept. No `run_terminal` ends `timeout` when the bound stopped the stage and `failed` with `unmet: result_event` when the CLI ended by itself.
- R44: The Muse record: `tokens` and `turns` come from the last line `run_usage`: `cache_read` is `cached_tokens`, `input` is, per entry of `models`, `input_tokens` less `cached_tokens` (never below 0), summed, `output` is `output_tokens`, `cache_creation` is 0, `turns` is `calls`; a member that is no number counts 0 (`turns` null for a `calls` that is none), and without the line all five are null. A resume's record holds its own run's numbers and nothing is subtracted. `permission_denials` is empty; `results` is the number of `run_terminal` lines read.
- R45: The Muse `limit` is null without a `run_usage` line or when its `allowance` is no object; else an object of the Claude shape with `status`, `resets_at` and `kind` null and `windows` holding an entry for each of `weekly` and `window` that is an object: `status` null, `resets_at` the integer `resets_at_ms` divided by 1000 without its remainder (null when it is no integer of 0 or more), `utilization` the hundredth of `used_percent` (null when that is no number).
- R46: The serving model is checked: a `task_lifecycle` line with an entry of `payload.event.details.facets` whose `detail.model` is a string other than the request's `model` stops the stage at once, as the bound stops one, and the launch is `failed` with `unmet: model`, whatever else was read before or after it; no answer is written to `out`, and the record's member `served_by` names that model (the only record member a stage of another runtime does not hold).

### A stage on the Antigravity CLI

- R47: `runtime: "agy"` starts a reviewer stage on the Antigravity CLI (`agy`) through the same request, scope, record files and order of judgment, and the request differs: `role` is `reviewer` alone (an `implementer` or a `fixer` refuses `invalid_input` with `role`); `account` is the template of the stage's homes, an existing directory (else `account_missing`) that holds `.gemini/antigravity-cli/antigravity-oauth-token` (a symbolic link to the real token counts; a missing file or a link to nothing refuses `invalid_input`, field `account`) and holds no `.gemini/config` (the same refusal); `model` is the CLI's slug, passed as one argument of its own, so a value that begins with `-` refuses `invalid_input` with `model`; `effort` is required and must be the level the slug ends with (`low`, `medium`, `high` or `xhigh`), else `invalid_input` with `effort`, and is not passed to the CLI; `permission_mode` must be stated and be `bypassPermissions`; `next_accounts` and `mcp_config` must be absent or empty; `skills`, `memory`, `integration`, `answer_schema` and `compact_window` must be absent (each refuses `invalid_input` with its name); `env` refuses `env_forbidden` also for a name beginning `AGY_` or `GEMINI_`. A resume refuses `resume_runtime_differs` across runtimes in both directions.
- R48: The prompt reaches the CLI as one argument: a prompt above 131071 bytes (one argument's limit on Linux is 131072 bytes with its terminating NUL byte), one that holds a NUL byte and one that is not UTF-8 text refuse `invalid_input` with `prompt`, before any effect.
- R49: The launch, after the same `systemd-run … --`: `agy --print <prompt> --output-format stream-json --model <model> --dangerously-skip-permissions --print-timeout <seconds>s`, these arguments in this order and no other for a fresh stage, in the request's `cwd`, with `timeout_seconds` as `<seconds>`; a resume adds `--conversation <session>` at the end and runs in the record's `cwd`. The environment is that of a Claude stage with `HOME=<the stage's home>` in place of `CLAUDE_CONFIG_DIR` (the child's environment holds one `HOME`), and `AGY_CLI_DISABLE_AUTO_UPDATE=1`; the standard input is the null device. The session is the CLI's: the line `{"event":"init"}` names it as `conversation_id`, and `ap run` writes that id into the record at once (state `running`); before the line the record's `session` is null, and after it the id stays in the record in every state.
- R50: The stage's home. For a fresh stage `ap run` makes `<account>/homes/<new uuid>` (mode 0700; `homes` is made, mode 0700, when it is absent). The new home holds three symbolic links, with the directories that hold them, and nothing else: `.gemini/antigravity-cli/antigravity-oauth-token` to the account's token, and `.gemini/AGENTS.md` and `.gemini/GEMINI.md` to the account's files of those names (a link is made also when its target is absent). That path is given as `HOME`, and `ap run` writes it into the record as `home` before the launch. A resume gives the record's `home` as `HOME`: a `home` that is absent, is no directory, or is not under `<account>/homes` of the record's account (compared after links and `..` are resolved) refuses `invalid_input` with `resume`, before any effect; its `.gemini/config` is not checked, since only that conversation ran there. The account is read, never written, by a stage. `ap run` never makes a home under the record's directory or under the `cwd`, and never removes a home.
- R51: The lines of standard output (each one JSON object whose member `event` names it; `init` carries `conversation_id` and the member `init`, and `step_update` and `result` carry their payload in the member of the same name) are read into the shape the judgment reads. A line `step_update` whose `step_update.step_type` is `tool` shows that the session did work. The line `result` is the result: `result.status` `SUCCESS` gives the answer, `result.response` (empty or no string: `no_result`, `unmet: answer`); any other `status` is an error result whose message is `result.error`, never written to `out`: `failed`, or `cut` (exit 75) when the message meets the usage-limit rule. A reviewer's stage ends at the first `result`. No `result` ends `timeout` when the bound stopped the stage and `failed` with `unmet: result_event` when the CLI ended by itself. A line that is no JSON object, or of another event, decides nothing.
- R52: The agy record: `tokens` come from `result.usage`: `input` is `input_tokens`, `output` is `output_tokens` alone, `cache_read` is `cache_read_tokens`, `cache_creation` is 0, and `turns` is `num_turns` (null when that is no number); any other member that is no number counts 0, and without a `result` all are null. A resumed stage's `tokens` are the result's sums less the `tokens` of every earlier record of the same conversation in the chain of `resume` (a record without tokens counts 0; null when that chain cannot be followed to its end: a record that cannot be read, more than 256 records or a record met twice); its `turns` is the conversation's `num_turns` as the CLI reports it, not reduced. `limit` is null, `permission_denials` is empty, `results` is the number of `result` lines read, and `served_by` is not a member of this runtime's record.

## Interface

`ap run < request.json`; the request of R2 and of the three specifications named in the Purpose; the record `<out>.run.json` of R25 and the files `<out>`, `<out>.stream.jsonl` and `<out>.err`; the exits of R18. `ap run --help` prints its usage (`specs/ap/verbs.md` R2). A request with the member `close` is the close of an orphan `run` object, `specs/ap/run-object.md` R14.

Every refusal code `ap run` emits, exit 2 before any effect, with the requirement that holds it:

| Code | Requirement |
| --- | --- |
| `usage`, `input_too_large`, `io_error` | R1 |
| `invalid_input` | R1, R2, R4, R5, R6, R30, R34, R38, R47, R48, R50; `specs/ap/run-object.md` R1, R14; `specs/ap/run-limits.md` R1, R11 |
| `env_forbidden` | R3, R34, R39, R47; `specs/ap/run-object.md` R2 |
| `account_missing` | R7, R38, R47 |
| `cwd_missing`, `prompt_unreadable`, `out_unwritable`, `out_named_in_prompt`, `out_exists` | R8 (`out_exists` also R11) |
| `worktree_dirty`, `worktree_unreadable`, `systemd_absent`, `bind_inactive` | R9 (`bind_inactive` also R6) |
| `resume_record_missing`, `resume_runtime_differs`, `resume_account_differs`, `resume_cwd_differs`, `resume_role_differs`, `run_still_active` | R10 (`resume_runtime_differs` also R39, R47; `resume_account_differs` also R22) |
| `scratch_exists`, `scratch_parent_missing`, `limits_unavailable` | `specs/ap/run-limits.md` R2, R3 |
| `policy_invalid`, `model_not_allowed`, `account_not_allowed` | `specs/ap/policy.md` R3 to R10 (the last check of admission) |
| `unknown_unit`, `unknown_intent` | `specs/ap/run-object.md` R6 (read after the policy step, before the claim of `out`) |
| `unknown_run`, `record_mismatch`, `run_still_active` of a close | `specs/ap/run-object.md` R14 (a failed store call of a close exits 3) |

The usage-limit text is the rule `ap run` reads in an error result's message for every runtime; every sentence Codex CLI 0.167.2 holds for a usage limit meets it.

A caller's use: `bind` is for a transient unit (the caller's own, as a chain's). On a resume the prompt file is the next message to the session: give a continuation or the findings, not the first prompt again. The caller is the one owner of a session and runs its stages in sequence. The stream holds the session's transcript (answers and tool output): the record, the stream and the error file are readable by their owner alone (R11), while the answer file and the directory of `out` are the caller's, so keep `out` where it is private. A reader of a typed answer types the members it reads: it checks each member's type when it reads it, and does not take a type from `ap run`, which does not validate the object against the schema (the CLI did, and a stage that ends `ok` holds the object the CLI accepted). A Codex or Muse stage runs with no approval and no sandbox of the CLI's own, so it is held to its worktree or its copy by its prompt alone (a Claude stage in `ap unit` runs in the mode `auto` by default; `ap unit` gives no default mode to a Muse block). In `ap unit` a verifier block may name `runtime: "agy"`; an `implementer` block (and so its fixer) that names it is refused before any effect with the error `ap run` gives, under the block's field (`implementer.role`); the second look of an agy verifier resumes its record as for the other runtimes. `git`, `gh`, `cargo` and `rustup` of an agy stage read the directory given as `HOME`, which is the stage's home and not the caller's home: a request whose stage needs them names their directories in `env` (`GH_CONFIG_DIR`, `CARGO_HOME`, `RUSTUP_HOME`); `ap` does not yet give a writing agy stage those files, which is why an agy stage is a reviewer. The homes of a unit that is closed stay under `<account>/homes` until the operator removes them. `ci/host-run-scope.sh` exercises the real scope on a host with systemd.
