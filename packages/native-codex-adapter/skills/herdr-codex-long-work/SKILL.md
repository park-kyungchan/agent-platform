# Herdr Codex long work

Carry the complete entrusted outcome through implementation, actual use, verification, and delivery. Maintain a Whole-Lens of the user's purpose, owners, dependencies across repositories/runtimes/domains, and unfinished acceptance criteria while delegating Tasks. Native Codex retains its loop, tools, delegation, sessions, retries, Goal lifecycle and compaction; do not build another runtime or session store.

## Recover the current contract

- Start with the selected owner's bounded current entrypoint, latest checkpoint and relevant original feedback/interview decisions. Distinguish actual user answers, attributed relays, proposals, derived Memory and observed execution. Follow later corrections; do not label a projection as its original or infer a cause from a user's hypothesis. Read originals needed for the next consequential decision, not every transcript.
- Recover the full outcome, topology and owner boundaries before prioritizing a convenient local repair. An initial repository inventory or first usable milestone is not the whole completion scope. Keep completed outcomes complete and unresolved dependencies visible. Ask only about consequential uncertainty available sources cannot resolve; do not make the user reconstruct preserved facts.
- Apply the [standing user decision](references/standing-user-decision.json) only to this user's entrusted sustained, complex unattended work. Honor the latest explicit interview/approval sequence, pause and effect instructions; the standing decision does not override them or authorize a held action. After scope is settled, execute granted authority without repeating general approval questions. Session-specific flags, budgets, declined tests and runtime paths remain in the Work contract, not universal defaults.

## Bind the native Goal and plan

- Call `get_goal` before considering `create_goal`. Reuse the active Goal for its scope; preserve an unfinished different Goal and resolve its scope conflict before dependent work. Never complete or replace a Goal to free the slot. A resolved blocker or narrower follow-up does not resume paused work: perform only that separately authorized follow-up until the user/native lifecycle resumes the main Goal.
- If no unfinished Goal exists and qualifying authority applies, create one without redundant confirmation. Keep the objective within 4,000 characters: complete outcome, meaningful verification, cross-owner dependencies, constraints, allowed scope and stopping conditions. Put changing pins and detailed Tasks in existing Work records. Set `token_budget` only for an explicitly provided Goal budget; evaluation caps are separate.
- Use `update_plan` for outcome-oriented phases and the next useful action, aligned with the Work/checkpoint. Preserve completed milestones and remaining scope. If tools are unavailable, record the limitation and use owner continuity; do not emulate the native runtime with a scheduler or model loop.
- Follow the callable Goal tool's exact status rules. Complete only when the whole objective and required delivery are achieved, not because a milestone/evaluation/budget ended. Pause only on an actual user pause instruction; use `blocked` only after its required consecutive-turn threshold. Report final native usage when completing a budgeted Goal.

## Choose useful progress

Prioritize the promised end-to-end operation at its actual caller. Repair an observed blocker with a specific check and exit condition, then return to useful use. Installation, documentation selection, registration and source tests do not establish native use/adoption; inspect the first failing boundary before prescribing more Memory, indexes or optimization.

Scale decomposition, records and checks to the effect and required claim. Reuse canonical commands/contracts and valid exact-source review under repository rules; group small dependent changes. Keep mandatory checks/review order without inventing recursive reviews or proof machinery for routine edits. Trace consumers of changed routes/IDs and check the affected positive path. Once evidence settles the next action, take it.

## Delegate and control runtimes

- Keep purpose, integration, cross-owner ordering, shared-source CAS and acceptance with the Lead. Use native internal subagents for bounded implementation, investigation or independent review. Use Herdr panes for actual CLI/TUI operation, runtime-specific capability/recovery evidence or persistent terminal work. Internal source review is not proof of a native TUI action; a pane is a location, not a logical Task or native execution identity.
- Bind substantial delegations to the selected Domain/Project/Work/Task, exact source base, ownership, effects and expected result. Workers may decompose inside that contract; native runtimes generate their own occurrence identities. Keep logical IDs, native session/thread/Task/Run and Herdr server/tab/pane/process observations separate. Unexposed fields stay null/unknown, never filled with logical IDs. Preserve the selected model, effort and permissions using supported native mechanisms.
- Agree on a bounded result address under the existing Task/Work/evidence owner: source commit/tree, relevant checks, findings and effects. Retain exact bytes/hash before releasing a worker or relying on a result after interruption. Recover that address before asking for repeat work. Temporary scrollback or a missing pane does not prove durable delivery or result loss.
- Before Herdr controls, verify `HERDR_ENV=1` and apply `herdr`. If the guard fails, do not inspect/control Herdr; retain other authorized work. Use installed help, live server-qualified IDs, caller context and `--no-focus`. Apply `herdr-hermes` when available for requested Hermes operation. Close owned idle panes no longer useful, retaining those needed for context continuity; leave unrelated resources alone.
- Prefer native completion notifications/state waits to repeated status prompts. Do independent authorized work while waiting and keep the user informed. Accepted input, timeout, settled UI or `unknown` does not prove failure/success. Inspect the same dispatch's correlated native input/session/result and live foreground before another submission. Do not spawn an agent merely to check status.

## Preserve authority, budgets and effects

Separate user authorization, installed capability and the configured connection's permission for the intended operation. Suitable existing maintained connectors may be used within authority; their use is not itself a credential bridge, and one connection's success does not prove another's permission. Preserve native authentication/tool ownership and explicit permission-related pauses. Source-provider proof grants no native permission.

Before dependent evaluation dispatch, distinguish Goal budget, evaluation occurrences, reservation, native-reported usage, elapsed deadline and additional money. Preserve unknown usage/history and deduplicate totals using native semantics. Use an explicit source-owned successor under delegated expansion authority without silently resetting a suite or reasking the same approval. A successor preserves the same suite/history; deadline changes need applicable authority and do not waive payment or unknown-usage limits. The standing decision alone authorizes no new evaluation suite. An expired evaluation window stops dependent evaluations, not unrelated authorized engineering; a whole-work pause still governs.

Never replay completed/consumed or uncertain dispatches. Lost output/disconnection does not prove an effect never happened. Inspect original correlated receipts and current state first. A justified later attempt has its own bounded identity/authority after reconciliation; retain earlier outcomes and uncertainty.

## Keep continuity small and current

Use the owner's existing typed checkpoint contract and CLI. Do not bypass a held source provider. If unavailable, record why and use a separate scoped English JSON/TypeScript Work checkpoint following the [fallback contract](references/checkpoint-contract.json); it is not a native session replica.

Keep a clear current entrypoint: full outcome, actual authority, phase, relevant source/native identities, in-flight and non-replayable effects, holds and next safe action. Reference large originals/evidence and archived detail rather than duplicating live summaries. The 16,000-character ceiling is not a target; keep readable prose and a compact current delta. Distinguish historical identities from freshly observed liveness.

Checkpoint material decisions, dispatch/results, interruption and handoff; update before compaction when practical. Prepare and size-check candidates before replacing records. Read back version/hash and update active locators together so later verification/authority does not hide behind stale pointers. Reuse the existing writer instead of rebuilding checkpoint machinery each turn. There is no guaranteed pre-compaction hook; recover from the latest durable material-boundary record.

## Recover, adopt and finish

After compaction/reconnection/handoff, follow the current entrypoint and explicit latest successor locator. Read current authority/holds and relevant originals; re-observe Goal, source revisions and native/container/pane identities before effects. Reconcile the plan without restarting from a remembered summary or replaying completed work.

Verify retained results against producer/source and the receiver's selected Work/Task; use existing receipt contracts for actual receiver readback where applicable. Keep source verification, installed bytes, native caller behavior, local durability, shared delivery, formal completion and Acceptance distinct. Consuming transported output does not prove invoking its producing native API. Honor required exact-source review, authenticated publication, explicit merge and separate owner activation. Verify source/global skill equality after adoption rather than assuming installation followed a source merge.

Continue within native lifecycle/authority until verified whole-work completion or a real stopping condition. A skill edit or credential setup does not resume a paused Goal. Preserve stopped-worker state/pending effects and report the concrete unblock action. Herdr/server/host liveness and native budgets still matter; this skill cannot prevent compaction or guarantee multi-day process survival.
