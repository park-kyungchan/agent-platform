# Batch jobs

A batch job asks a model, through the Message Batches API, a question whose input is wholly in Git, and reads the answers into findings of the store. The programs here only build the requests and read the results: they call no model, open no socket and hold no key. Sending `requests.jsonl` and writing the result lines is the work of another program (unit api-batch), which reads the request lines and writes the result lines named below. `lib.py` holds what the jobs share; each job's programs load it by its path.

## Shared rules

- The Academy rule: a path is the Academy's when one of its components begins with `education-` or `edu-`, or when a component `evals` is directly followed by a component `lesson`. `is_academy` of `lib.py` decides it for every path a program takes or meets. A path given as an argument is asked as given first; then it is resolved one component at a time, the rule asked of the path so far before each `lstat` or `readlink` of it, and of a link's target before it is followed. Such a path is refused `academy_path` before any file system call on it; a tracked path of the Academy in a clone is not opened.
- The output of a program is one JSON line on standard output; standard error stays empty. A refusal is `{"status":"<code>"}` with exit 2 and nothing written or applied: `usage`, `academy_path` and the codes of each program; an exception of the program is `internal_error`, exit 2.
- The request line: `{"custom_id":<key>,"params":<params>}`, one entry of `requests` of the Message Batches API. The result line: `{"custom_id","result":{"type":"succeeded","message":{...}}}`, or `result.type` `errored`, `canceled` or `expired`, as that API's results give them. A line of a result file that is not of this form (or not UTF-8, or whose `succeeded` result has no `message` object) is no result line; an empty line is not counted.
- The key: the 64 lower-case hex digits of the SHA-256 of `params` written as JSON with sorted keys, no white space between tokens and non-ASCII characters unescaped, in UTF-8. Nothing of a run (a time, a host path, a commit) is in `params`, so the same input keeps its key, and a changed prompt, model or `max_tokens` changes every key.

## The drift job

The question: does a test that cites a numbered requirement of a specification test its sentence? `ci/check-spec-trace.py` shows that a requirement is cited; this job asks whether the citing tests would fail if the sentence stopped holding. Its first user is the Lead at a session's start, who reads its findings (detector `batch:drift`, severity `info`) in `findings` of `ap status`; they stay out of `needs` of `ap status --brief`.

### The builder

`python3 -I -B evals/batch/drift/build --repo <owner>/<name>=<clone> [--repo ...] --model <id> --out <dir> [--rev <rev>] [--results <file>]... [--max-tokens <n>]`

- Before any read: `academy_path` when a repository's name is the Academy's, or when the path of a clone, of `--out` or of a `--results` file is. `--rev` (default `origin/main`) is resolved once per clone to a commit; `repo_unreadable` (with the member `repository`) when the clone or the revision cannot be read. Every file is read from Git's objects at that commit (`git ls-tree`, `git cat-file --batch`): no file of a checkout is read, nothing is fetched (`protocol.allow=never`), nothing in a clone changes. Git is the only program started.
- A requirement: in each regular file whose path begins with `specs/` and ends with `.md`, each line that `REQ_RE` of `ci/check-spec-trace.py` matches; its rule is `R<digits>`; a later line of the same rule in one file is no requirement. A citation: each match of `CITE_RE` of that file in a regular file of the same commit whose path does not end with `.md`; it belongs to the requirement of the same repository that its path and rule name. The builder holds the two patterns, and a test fails when they are not those of `ci/check-spec-trace.py`. A tracked path that is the Academy's is not opened and is counted (`academy_skipped`).
- A group: the requirements of one spec file in the file's order, twelve to a group, the last one shorter. A file without a requirement has no group.
- The excerpt of a citation. In a file ending with `.rs`: the `fn` item whose lines hold the citation (the innermost one), else the first `fn` item that begins after it; an item runs from the first of the comment (`//`) and attribute (`#[`) lines directly above its `fn` line to the first later line that is `}` at the indentation of the `fn` line, so a citation above the item and one inside its body both find it; without such an item the excerpt is the citation's line. In any other file: from the first line of the unbroken run of citation lines the citation is in, to the line before the next citation line after that run, or to the file's end. An excerpt over 400 lines is cut there, and a last line `[excerpt cut at 400 of <n> lines]` says so; its location then names the 400 lines it holds.
- `params` of a group has exactly `model` (as given), `max_tokens` (`--max-tokens`, an integer from 1024 to 32000, default 8000), `system` (the text of `drift/prompt.md`), `messages` (one `user` message whose content is one string) and `output_config`, `{"format":{"type":"json_schema","schema":<drift/verdict.schema.json>}}`. The user text holds, in this order: the repository and the spec's path; the spec file whole, between `<spec path="...">` and `</spec>`; the rules of the group; per rule its citing tests as `<path>:<line>` (the citation's line; by path, then line), or `none`; each distinct excerpt once, by path and first line, between `<excerpt location="<path>:<first>-<last>">` and `</excerpt>`.
- A group whose user text is over 300,000 bytes gets no request and the state `too_large`.
- `--results` (repeatable) names files of result lines: a key is settled when one of them holds a line of that key with `result.type` `succeeded`, so a refusal is settled and an error is asked again at the next build. A file that cannot be read is `results_unreadable`; a line that is no result line is skipped and counted (`result_lines_skipped`).
- Written into `--out` (made with mode 0700 when absent; `out_unwritable`), each file under a temporary name and renamed, mode 0600, after every read succeeded. `requests.jsonl`: one request line per group that is neither settled nor too large, ordered by repository, path and the number of the group's first rule; an empty file when there is none. `groups.json`: `{"job":"drift","model","groups":[{"key","repository","commit","path","rules":[{"rule","line","tests":["<path>:<line>"]}],"state"}]}`, every group of the build in that order, `state` one of `requested`, `settled`, `too_large`. The same commits, options and result files give byte-equal files.
- Standard output: `{"status":"ok","out","groups","requested","settled","too_large","requirements","citations","academy_skipped","result_lines_skipped"}`, exit 0.

### The verdict

`drift/verdict.schema.json`: an object with exactly `rules`, an array of objects with exactly `rule` (string), `verdict` (`tested`, `untested` or `miscited`), `tests` (array of strings) and `why` (string); every member required, no other property. `drift/prompt.md` defines them: `tested`, at least one citing test would fail if the sentence stopped holding, and no citing test fails to test it; `untested`, no citing test would fail; `miscited`, at least one would and at least one, named in `tests` as `<path>:<line>`, would not; `why` is one sentence; one entry per rule of the group and none for another rule.

### The reader

`python3 -I -B evals/batch/drift/read --groups <groups.json> --results <file> [--store <path>]`; the engine is `ONT_BIN`, default `ont`, as in `evals/route/run`, called with `--store` when given and every apply with `--client batch-drift`; `ONT_AGENT` and `ONT_ROLE` are not passed to it, so that a request id names the same action whoever runs the reader.

- `academy_path` as for the builder for both paths and the store's, and for a repository, spec path or test that `groups.json` names; `groups_unreadable` when the file is not of the builder's form; `results_unreadable`.
- Of the lines of one key, the first whose `result.type` is `succeeded` is the one counted, else the first; every other line of that key is `duplicate` (so the reader reads what the builder settles). Each result line is counted in exactly one of: `skipped` (no result line), `stale` (its key is of no group of `groups.json`), `duplicate`, `errored` (type `errored`, `canceled` or `expired`), `refused` (`succeeded` with `stop_reason` `refusal`), `unreadable` (`succeeded` with a `stop_reason` other than `end_turn`, or the `text` blocks of `message.content` joined are not JSON of the verdict schema), `read`. `lines` counts the lines that are not empty. A line that is not counted `read` causes no action.
- The signals of a `read` group, per rule: `untested` when `groups.json` gives the rule no test, whatever the verdict says; else the rule's verdict, `untested` and `miscited` being signals and `tested` none; a rule with no entry or with two is `unjudged` (no signal, nothing closed). An entry for a rule outside the group is ignored, and so is a test a verdict names that `groups.json` does not give that rule; a `miscited` verdict that then names no test of the rule is `unjudged`.
- One finding per requirement. Signature: `<owner>/<name>:<path>#R<n>` (the clause key of `ap clause`). Native key: `batch-drift-` and the first 16 hex digits of the SHA-256 of the signature. Kind `drift`, detector `batch:drift`, severity `info`. Summary: `<signature> untested: no citing test tests this requirement`, or `<signature> miscited: <k> of <m> citing tests do not test this requirement`, `<m>` the rule's tests in `groups.json` and `<k>` those of them the verdict names. Evidence: `key <key> commit <commit>; tests <the tests named, or none>; why <why>`, each control character of `why` a space; the whole cut at 2,000 bytes on a character boundary. The id is `{"object_type":"finding","namespace":<the one of id() in crates/ap/src/host.rs>,"native_key"}`; a test reads that file and fails when the reader's namespace differs.
- The pass, as `ap watch` keeps a finding (`specs/ap/watch.md` R5, R6). One `ont search` of `finding` with `eq` on `detector`, every page; an answer that is not `ok` and qualified is `{"status":"store_failed"}`, exit 3, before any action. A field of `head.fields` is `{"kind":"value","value":...}`; one of another kind reads as absent. Per rule of a `read` group, in the order of `groups.json` and of its rules: a signal with no finding, `open_finding`; `open` or `planned`, `see_finding_again` with the evidence, only when the stored evidence differs; `closed`, `reopen_finding`; `dismissed`, nothing (counted `dismissed`). A judged rule that is no signal and has a finding `open` or `planned`: `close_finding`, reason `not shown by batch drift, key <key>, commit <commit>`. Then, by signature, every finding `open` or `planned` of the detector whose summary's first word is a signature of a repository of `groups.json` and of no rule in it: `close_finding`, reason `the requirement is not in the specs at <commit>`; this close follows from `groups.json` alone and runs at every call, also one with no `read` line. No finding of another detector is read for closing or changed.
- The cap: `open_finding` and `reopen_finding` together are answered `applied` at most ten times a call; after the tenth none is sent and each further one is counted `over_cap`, so a later call over the same result file applies the next ten. Sees and closes are not capped.
- Each apply is `ont action apply` of `action_type`, `parameters`, `agent` `batch-drift` and a `request_id` that is `bd-` and the first 40 hex digits of the SHA-256 of the JSON, in the key's form, of the array of the action, the finding's key, the group's key (for the close of a requirement that left the specs, the repository's commit) and the parameters. So the same call again answers `already_applied`, and changed evidence is a new request. An answer `already_applied` wrote nothing: it is counted `already_applied`, is in none of the four lists and takes no place under the cap. A refusal's code in `failed` is `failed[0]` of the answer when the code is `submission_criteria`, else the code; an answer that is no answer is `store_answer_unreadable`; an answer `store_busy` is asked again up to five times. An apply that is refused or fails is listed in `failed`, and the pass goes on.
- Standard output: `{"status":"ok","lines","read","refused","errored","unreadable","stale","duplicate","skipped","unjudged","opened":[],"seen":[],"reopened":[],"closed":[],"dismissed","over_cap","already_applied","failed":[{"key","code"}]}`, the four lists holding finding keys; exit 0, or 1 when `failed` is not empty.

### A pass

```
build --repo <owner>/agent-platform=<clone> --repo <owner>/ontology-platform=<clone> --model <id> --out <dir> [--results <earlier result files>...]
# unit api-batch sends <dir>/requests.jsonl and writes a result file
read --groups <dir>/groups.json --results <result file>
```

Read the same result file again until `over_cap` is 0. A later build given every earlier result file asks only what changed and what ended with an error.

### The undo

The builder writes only into `--out`: remove that directory. The reader writes only through the four finding actions of detector `batch:drift`: the Lead dismisses a finding that is wrong (it is never changed again by the job) or closes it; reverting the pull request that added these files removes the job, and its findings stay in the store as records until the Lead closes them.

### What the job does not show

- A verdict is a model's reading, not a run of the test: `tested` does not show that the test passes, nor that it would fail; `untested` and `miscited` are leads for the Lead to read, which is why the severity is `info`.
- Only what a citation names is read: a test that tests a requirement without citing it is not seen, and a requirement no test cites is `untested` whatever the code holds (also one listed in `scripts/spec-trace-untested.txt` of ontology-platform, which the Lead dismisses once).
- The excerpt is what the rules above cut: a helper the test calls, a fixture or a file the test reads is not in it, and an excerpt over 400 lines is cut, so a verdict on it may miss what follows.
- A key whose answer was cut (a `stop_reason` other than `end_turn`) or does not parse is settled too: it is not asked again until its input, the prompt, the model or `max_tokens` changes, and the reader counts it `unreadable` at every call. A refused key is settled the same way and counted `refused`. An error is asked again at the next build; there is no other retry.
- The same group asked of two models gives two keys; the job does not reconcile their verdicts, and the reader acts on the result file it is given.
- A finding's evidence names the commit of the last call that saw it; a close sent again at the same commit after the Lead reopened a finding answers `already_applied` and changes nothing until the next commit.
