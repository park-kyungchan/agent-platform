# evals

`readout.py` reads the cost of the same work (K1) and the field reading of the implementer tier (K2) from records that already exist; its prices are `prices.tsv`.

- Stage records are read from the work root and from every `--stage-dir <directory>` (repeatable; the default is the store's unit and review directories, `/var/lib/agent-platform/units` and `/var/lib/agent-platform/reviews`, and a given `--stage-dir` replaces both). A stage directory is read at a fixed depth, `<dir>/*.run.json` and `<dir>/*/*.run.json`, so no copy inside a unit's worktree or a review's clone is read; a file reached twice is read once. A session takes the role of its stage record wherever the record lies, and a record read from a stage directory puts the session in the route `engineering` (the lesson directory still comes first). The read-out calls no store.
- The routes, by the first rule that holds: `lesson` (the lesson directory); `engineering` (a stage record read from a stage directory, or the work root, or the platforms root); `temporary` (a session with no stage record that ran under `/tmp` or `/var/tmp`; no path is printed); else `other`.
- Role of a session with no stage record: `lead` for a directory given by `--lead-cwd` and, when no `--lead-cwd` is given, for a task directory under the work root (not a `wt/` worktree, not the lesson directory); `worker, no record` for a worktree or a platform checkout; else `interactive`.
- The spend of the role `reviewer` is also printed by review kind, `week <w> reviewer kind page|plan|packet|other`, outside the route blocks, so no route total changes. The kind is read from the stage record's `prompt.path`: a file name that begins `page-` or `plan-`; a path `units/<unit>/<n>.verifier.prompt.md` is `packet`; anything else is `other`.
- For the page and plan reviews whose `start[:10]` is within `--since` to `--until`, it reads the lines beginning `blocking` of the answer files (after any run of spaces, `-`, `*` and `<digits>.`; case-sensitive), counted and never printed: one line per review kind with a review in the window, `BLOCKING <page|plan> reviews=<n> <name>=<count> ... unnamed=<count>`, the names being the closed list of the kind's frame (`reviewer.md`: `unbuildable`, `contradiction`, `check`, `write_set`, `unguarded_effect`; `plan-reviewer.md`: `unreached_criterion`, `dependency`, `conflict`, `unguarded_effect`), in the frame's order. A line `blocking <name>:` is counted under the name; any other line that begins `blocking` under `unnamed`. An answer file that cannot be read counts in `reviews` and adds nothing else. No finding's text is printed.

## The lesson replay

`lesson/replay` counts how many recorded daily-record reads of real lesson days the read store answers equal (K3's first value): `python3 -I -B evals/lesson/replay --store PATH --day YYYY-MM-DD [--day ...] [--sessions GLOB] [--lesson-cwd DIR] [--ont BIN] [--cut-marker TEXT]`. It reads Claude session records (default: every `~/.claude*/projects`; only lines whose `cwd` is at or under the lesson directory and whose time is on an asked day in Asia/Seoul) and the store's `lesson_record` objects through `ont` (`describe`, `search`), and writes nothing.

- A recorded `academy_dailyrecord_get` call, once per call id, gets the first outcome that applies: `unavailable` (status is not `observed`, or no answer was recorded), `malformed` (fewer than six counted fields, a field named twice, a `lessonDate` or a `target.studentId` that is not a string, or a result whose text is not a string; only the members the script uses are typed: a `recordId` that is not a string is `key_missing`, a `membershipId` that is not a string chooses no object among several, a handle that is not a string leaves the call without one), `saved_later` (a `dailyrecord_save` that answered `saved` came later on the same Seoul day, with the observation handle of a get answer of the same student and date: the store holds the value after that save), `no_object` (no `lesson_record` of that date and `student_name`), `ambiguous` (several, and the membership does not leave one), `identity_differs` (`student_id` is not the answer's), else `compared`.
- A compared call gets one word per field, comparing the recorded `before.value` with the object's member exactly: `equal`, `equal_after_whitespace`, `store_cut` (`cut_fields` above 0 and the store's text, without a trailing `--cut-marker`, is a proper prefix of the recorded one), `store_missing` (the member is not in the value state), `differs`; and one word per key, `record_key` (against the five same-date fields' `recordId`) and `previous_record_key` (against the previous-homework field's): `key_equal`, `key_missing`, `key_differs`. `answered_equal` is a call whose six fields are `equal` or `equal_after_whitespace` and neither key `differs`; `k3_equal` over `k3_of` (all `dailyrecord_get` calls) is the value.
- A check inside the store alone (`store`): where an object's `previous_record_key` is the `record_key` of another object of the same `student_id` and `membership_key`, its `previous_progress`, `previous_homework` and `previous_lesson_memo` are compared with that object's `progress`, `homework` and `lesson_memo` by the same words (the cut test uses the asked-day object's `cut_fields`); `pairs` and the count per member per word.
- The schema is read first: when `lesson_record` or a member it reads is not declared the run ends `schema_missing_members` before any search.
- The output is ONE JSON object of integers and fixed words, or one `{"status":"<code>"}` line with exit 2 (`bad_arguments`, `day_invalid`, `ont_not_found`, `ont_failed`, `store_unreadable`, `schema_missing_members`, `internal_error` with the exception's class name in `exception` for an exception of the script); standard error stays empty, also for a closed standard output (exit 2, nothing written). An interrupt is not handled: SIGINT keeps its default action from the script's first statements, so the process ends by the signal and prints nothing further. A record line that is not a JSON object is skipped, and an answer with a member of another type than the interface names is `malformed`. No name, id, date, text, hash or length of one is printed, on any path. The records hold students' names and texts: run it on real days only where the task permits, and test it on invented fixtures only (`ci/test_lesson_replay.py`, run by `./check` with the engine `check` found or built).

## The engineering suite

`engineering/` holds the first cut of the suite: past units of the platform repositories that a stage of a chosen model runs again, judged by the tests the unit was accepted with.

- A case is one file `engineering/cases/<id>.json`: the merged pull request it was taken from, its `base` (the first parent of the merge commit) and accepted `head`, the `tests` (every file that judges), the `commands` the evaluator runs, and the SHA-256 of the page given to the candidate. Its exact form and the call that runs it: `crates/ap/README.md`, section "One case".
- The rule of `tests`, for every case: every path the pull request changed under a `tests` directory, and, where `./check` is a command, `check` and each script it sources. Every path of `tests` is a regular file at `head`: a symbolic link is no judging file, and a case that names one is refused (and the evaluator exits 2 for it, writing nothing). A case whose base `check` runs installs or touches the host (as `ap-158`) is judged by the cargo commands of its check instead.
- The pages are host files written by the Lead, `evals/engineering/pages/<id>.md` in the Lead's task directory below the work root; their text never enters this repository, only its digest (`page_sha256`), and a case file holds no host path.
- `engineering/evaluate <case> <clone>` is the evaluator: it restores the files of `tests` from `head`, runs `commands` in the copy and exits 0 (passed), 1 (failed) or 2 (it could not judge). The restore is total: whatever the candidate left at a judging path or at one of its parents (a file, a link, a directory) is replaced, and nothing is written through a link. Exit 1 is a statement about the candidate and nothing else: an error of the evaluator itself is exit 2, and so is a command whose first word holds no `/` (a program of the search path) and cannot be started, the host's cause; a first word with a `/` that cannot be started is a failed command, the candidate's tree. Every `git` the evaluator starts, and every `git` of the case call's copy step, ignores `refs/replace/` entries of the clone. No model judges.
- `engineering/prompt.md` is the suite's prompt to the candidate; the call appends the block of facts.
- The validity pair: a case is valid when its call without a stage ends `failed` at `base` and `passed` at `head`. A case with another pair counts in no reading.
- What a case record means as a row of a reading (the target, the cost, pass, fail, no result, the rerun of a no-result row): `crates/ap/README.md`, section "One case", the last paragraph.

## The Lead suite

`lead/` measures what a change of the instructions that shape a Lead (`content/AGENTS.md`, `content/skills/lead/`) does to a Lead's decisions. `lead/run answers` writes one answer per frozen case under an instruction text; `lead/run score` scores one set of answers, or two sets blind, into a sheet that says per case `caught`, `partly` or `missed`, and for two sets which cases were lost and gained. Both verbs start every stage through `ap run` (`--ap`) and call no model by themselves.

- A case is a directory `<id>/` with `PROMPT.txt` (the question, with the token `@TASK@`), `EXPECTED.md` (the rubric) and `TASK/` (the files the answering session may read). The cases are host files, cut from task directories of the host: their bytes never enter this repository, only one digest per case, in `lead/cases.sha256`. The digest is the SHA-256 of the text of one line `<sha256 of the file>  <path relative to the case directory>` per regular file below the case, sorted by path as bytes, each line ended by a newline. Both verbs refuse `case_digest_differs` (naming the id) when a case is absent or differs, and `case_unknown` for a directory the file does not name, before any effect.
- `answers` gives each case a fresh scratch root that holds only `task/` (a copy of `TASK/`) and `instructions/` (a copy of `--instructions`, laid out like `content/`); the prompt is `lead/prompt.md` with the case's question put in. An answer is valid when the stage ended `ok`, the answer is not empty, and no tool call in the stage's stream names an absolute path outside the scratch root other than one under `/root/.agents/` or `/dev/` (reads under `/root/.agents/` are counted as `installed_reads` and shown). An own saved result is a path `<account>/projects/<one directory>/<session>/tool-results/<anything below>` where `<account>` and `<session>` are the ones named in that try's own record (`<case>.<try>.md.run.json`): Claude Code saves a long tool result there and the session reads it back, so such a path is counted per try as `own_results` and does not make the answer invalid; every other path under an account directory (another session, the `projects` directory itself, any other subdirectory) is still outside. The judgment is recomputed from the files at every call of `answers`. A case is tried at most twice; a second call tries only the cases that have no valid answer and replaces nothing. `META.json` in the output fixes the digest of the instructions, of the cases file and of the prompt, the model and the effort; a call with other values is refused `meta_differs`.
- A model scores because the result is a decision in prose and a case has no executable oracle. What keeps the score honest: a case or an instruction directory that holds a link or any file that is not regular is refused `not_regular` before any effect, so a stage is given exactly what the digests cover; the rubric is never below the working directory of the answering stage (the scorer's scratch root holds the rubric and the answers, the answering stage's holds neither); which set is `p` and which is `q` is drawn per case and written to `mapping.json`, never below the scorer's root; and the scorer's lines are read strictly, exactly one line per answer file with one of the three results, so a missing, doubled or unknown line, another result word, or a stage that did not end `ok` makes the sheet incomplete (`sheet.json` says `complete: false`, no `sheet.md`, exit 1). Two sets are scored together only when their cases file, prompt, model and effort are the same (`sets_not_comparable`), and `score` refuses `set_stale`, naming `a` or `b`, a set whose `META.json` is absent or unreadable or whose digest of the cases file or of the prompt is not the current one.
- `sheet.json` is private (it holds the scorer's quote and clause per answer). `sheet.md` is the public sheet: case ids, the result per set, the counts, `lost` and `gained`, the digests, models and efforts, and no quote, clause or path; it may be carried by a pull request.
- What the suite does not show. The boundary of an answering stage is its prompt, not the file system: a stage that ignores the prompt can read what its account can read, and the program only finds, afterwards, an absolute path in the stream that is outside the scratch root. One answer per case is one sample: a difference of one case between two sets is read, not trusted. The scorer is a model and its quote is the evidence to read.
- When a result is acted on. A case in `lost` is read by the Lead (the two answers and the rubric) before the change merges. An incomplete sheet is no result.
- How a case is added: the directory on the host and its digest line in `lead/cases.sha256`, in one pull request.

## The instructions suite

`instructions/` measures whether a reader that starts at `AGENTS.md` section 3 of the shared instructions finds how Claude Code, Muse Code and the Antigravity CLI are run and configured without a terminal UI, and gives a complete right answer.

- A case is one entry of `instructions/cases.json` (16 cases): `id`, `situation` (the text given to the reader), `files` (the reference files in which the answer stands, at least one), `tokens` (literal strings a right answer contains) and `evidence` (for each token, the help line, documentation line or run that shows it).
- The call: `python3 -I -B evals/instructions/run --root <dir> --reader claude-haiku|muse-ember|agy-hydrogen --out <dir> [--case <id> ...] [--jobs <n>]`. `--root` is laid out as `/root/.agents` (`AGENTS.md` and `runtime-references/`); for a change, a copy of `content/` of a revision. For each case it starts ONE headless session of the reader in a new empty directory, with the fixed prompt of the script and nothing else, bounded at 600 seconds (a session past it is ended by its process group and counts as not run). Under `--out` it saves `<id>.md` (the answer), `<id>.jsonl` (the events), `<id>.err` and `<id>.json` (state, exit code, session id). `--score <dir>` starts no session and scores the answers saved there. The command line of each reader is a row of the table `READERS` in the script.
- The two rules, and no other: `routed` (the last line of the answer that begins `File:` names one of `files`, matched as an exact basename after markdown marks and a section suffix are stripped) and `answered` (every token is in the answer, compared literally). No model judges. The script prints ONE JSON object: per case `state`, `routed`, `answered` and the missing tokens; the counts `routed`, `answered`, `both` and `not_run`; the failing ids; `start_failed` and `mcp_rule_broken`. Exit 0 when every session ran, or when the reader is one the rule below forbids to run (its cases are `not_run`); 2 when a start failed, a session ran past its bound, a session ran but exited non-zero or gave no answer, or the rule below did not hold (the object names the cases).
- The rule for every run: no session starts an MCP server registered in a CLI's home. Claude Code runs with `--strict-mcp-config`; Muse Code only in a new workspace it does not trust (no `--yolo`, no `--trust-workspace`), and after each run the session record must say `MCP startup withheld` only where a server is registered (with none registered that text never appears, and the rule is that no MCP server process ran); the Antigravity CLI with `HOME` set to a new directory that holds a link to the login token and no MCP configuration. The script also watches the reader's process tree for the command line of a registered server. When a run breaks the rule the script starts no further session. A reader that cannot be run under the rule gets `runnable: False` in its row.
- Every reader also loads the installed instructions through its own pointer file, which the prompt overrides for the test. The run without that mixture is the Lead's: after the delivery the Lead runs the suite again with `--root /root/.agents` on the installed files.
- What the suite does not show: one answer per case is one sample, so a difference of one case between two runs is read, not trusted; a token found in the answer does not show the rest of the answer is right. Every reader can read any path the host user can, the login token linked into the `agy` reader's temporary HOME included: an allow rule of `--settings` does not confine `read_file`, and that boundary belongs to the item `stage-limits`. A session's answer and events are kept in `--out` (`<id>.md`, `<id>.jsonl`), so that directory is to be treated as able to hold anything a reader read.

## The routing suite

`routing/` measures whether a reader that is given an assignment, and starts at `AGENTS.md` of the shared instructions, finds the context the assignment needs: with several samples per case, scored by facts in the answer, and no model as judge. A later change of the shared instructions, of a repository's `AGENTS.md` or map, or of the route table of the design sources is gated by it: a change that drops a reader under its recorded baseline, beyond the noise, does not merge.

- A case is an object with `id`, `situation` (the assignment given to the reader), `must` and `wrong`; other members are not read. Each of `must` and `wrong` is a list of facts, a fact is `{"fact": [<strings>]}`, and it holds when every one of its strings is in the answer, both compared after backticks are removed and each run of whitespace is made one space. A sample of a case passes when every `must` fact holds and no `wrong` fact holds (a `wrong` fact that holds shows that stale or wrong context was loaded).
- Case files. `routing/cases.json` holds the 16 cases of `instructions/cases.json` in this form (one `must` fact per token, no `wrong`). Host cases are files on the host, given with `--cases <absolute path>`, and never committed: the repository holds only their SHA-256, one line `<sha256>  <short name>` per accepted file in `routing/host-cases.sha256`; a host file whose digest is not listed is refused `cases_digest_unknown`. Case ids are unique over all files of a call (`case_id_twice`). A record names a host file by its short name, never by its path.
- `python3 -I -B evals/routing/run answers --root <dir> --reader claude-sonnet|claude-haiku|muse-ember|agy-hydrogen --out <dir> [--cases <file> ...] [--samples N] [--jobs N] [--case <id> ...] [--deny <glob> ...]` runs N samples (default 3, 1 to 9) of each case, `--jobs` at a time (default 2, 1 to 4). `--root` holds `AGENTS.md` (`root_invalid`): `/root/.agents`, or a copy of `content/` of a candidate revision. The prompt (the assignment, the root to start from, the limits on the Academy's paths, "do not do the assignment", the form of the answer) is in the script. The reader has every tool and command, as a worker has them; MCP stays off by the rule of the instructions suite (Claude Code `--strict-mcp-config`; Muse Code in a new workspace it does not trust; the Antigravity CLI with a new `HOME` without MCP configuration), and the processes of the unit are watched for a registered server's command line: when one runs, no further session starts. The account of a Claude reader is the caller's `CLAUDE_CONFIG_DIR`: the caller sets it. Under `<out>/<reader>/` it writes `run.json` at the first call (`samples`, `cases`, `case_files` as short name to SHA-256, `suite` the SHA-256 of `run`; a later call may raise `samples`, any other difference is refused `run_differs`) and per case and sample `<case>__s<n>.md` (the answer, written under another name and renamed), `.json` (input tokens, cached included; output tokens; seconds; the session id; `answered`), `.jsonl` (the event stream) and `.err`. A sample is done when its `.json` says `answered: true` and its answer is not empty; a next call runs every other sample again. A call is refused `run_still_active` when the unit of a sample it would start is active. It prints ONE JSON object (`reader`, the state per sample, `mcp_rule_broken`); exit 0, or 2 when the MCP rule broke.
- `run score --out <dir> [--cases <file> ...]` scores every reader directory under `--out` from its `run.json` (refused: `run_record_missing`, `no_reader`, `case_sets_differ` when the case files given do not hold those ids with those digests, `run_differs` when the readers' `run.json` disagree in `suite` or `case_files`). A pair (case, sample) without an answered sample fails and is counted in `unanswered`. Per reader: `n`, `passes` (case to passed samples), `samples` (per sample its passed cases), `mean`, `majority` (the cases passed in more than half of the samples), `unanswered`, `tokens_median`; and `parity`: for each reader other than `claude-sonnet`, the share of Sonnet's `majority` that is in the reader's `majority` (null without Sonnet or with an empty majority). It prints the object, writes it to `<out>/score.json`, and writes `<out>/sheet.md`, the public sheet: case ids, counts, parity, token medians and the digests of the case files and of the suite; no situation, fact, answer or path.
- `run gate --baseline <score.json> --candidate <score.json>` judges each reader of the baseline: with nb, nc its samples and b_i, c_i its passes of case i, `drop` = Σb_i/nb − Σc_i/nc, p_i = (b_i + c_i)/(nb + nc), `noise` = sqrt(Σ p_i(1 − p_i) × (1/nb + 1/nc)); the reader is ok when `drop` ≤ 2 × `noise`. `lost` (in the baseline's `majority`, not in the candidate's) is for the Lead to read and decides nothing. A reader of the baseline absent from the candidate fails; a reader only in the candidate is not judged. Exit 0 `pass`, 1 `fail`; refused with exit 2 before any judgment: `samples_too_few` (a reader with `n` under 3), `run_incomplete` (a reader with more `unanswered` than a twentieth of cases × n), `case_sets_differ`.
- Every refusal is one line `{"status":"<code>"}` with exit 2.
- The sandbox of a reader. Every reader is started through the `systemd-run` on `PATH`, as a transient service in `agents.slice` named `routing-<16 hex digits of the SHA-256 of the sample's path>`, with a description that holds the reader, case and sample and no prompt, without expansion of `$` in its arguments, with `ProtectSystem=strict`, `ProtectHome=read-only` and `RuntimeMaxSec` the 600-second bound. Writable are only `/tmp` and the state of the reader's own CLI (Claude Code: the directory `CLAUDE_CONFIG_DIR` names, or `~/.claude` and `~/.claude.json`; Muse Code: `~/.config/muse`, `~/.local/share/muse`, `~/.local/state/muse`, `~/.cache`; the Antigravity CLI: `~/.gemini/antigravity-cli`). Inaccessible is every path that exists when the session starts and matches the deny list: `/home/palantirkc/work/edu-*`; `context`, `apps`, `modules` and `migration` of `/home/palantirkc/platforms/education-platform` and of `/home/palantirkc/work/*/wt/education-platform*`; the session records `~/.claude*/projects/*edu-*` and `~/.claude*/projects/*education-platform*`; and each `--deny <glob>`, which adds and never removes. Each path is its own `InaccessiblePaths=` assignment. There is no way to start a reader without `systemd-run`: when it is absent, or the unit ends before the CLI started (a probe unit of the same properties runs first, and each session leaves a mark when its CLI starts), the call is refused `sandbox_unavailable`. The unit's processes, read from its control group, are what the MCP watch reads.
- The files of a call. A sample's answer (`<case>__s<n>.md`), event stream (`.jsonl`), error output (`.err`) and usage record (`.json`) hold the reader's whole output: what it read, printed and ran, whatever the files it could read held. They are created with mode 0600, and `--out` belongs under a directory of mode 0700 (the suite does not make it so): the mode of a file is no protection where the directory is open. Each call makes its work directories in the temporary directory as `routing-<pid>-<process start time>-<random>`, and removes them when a sample ends. A call that is killed leaves its directory (for `agy-hydrogen` it holds the link to the sign-in token); the next `answers` removes every `routing-*` directory of that form whose owner (that pid with that start time) is no longer alive, after its own refusals, and no other directory of the temporary directory: not one of a live call, not one that is not of that form. The intake suite starts its sessions through the same function and has the same names and modes.
- What the suite does not show. A candidate root is indicative, because every reader also loads the installed `AGENTS.md` through its CLI's pointer file: the decisive run is the one on the installed instructions after delivery. A string found in an answer does not show the rest is right. At three samples the loss of a single case is not reliably caught: a `fail` is followed by raising `--samples` on both sides. What the unit does not confine: every file not denied stays readable (credentials included), and signals, the service manager, Docker, the network and the GitHub token are open to a reader with every command; Git objects of a repository whose directories are denied stay readable; a reader running as root can undo the mounts. The unit guards against a reader that opens or changes something by mistake, not against one that works around it. `--out` is to be treated as able to hold anything a reader read: the answers and event streams are private, only `sheet.md` is public.
- How it differs from an "assignment alone, scored by files read": its prompt has five parts (the assignment, the root to start from, the limits on the Academy's paths, "do not do the assignment", the form of the answer), its score is facts in the answer, and the reads are kept in the event stream, not scored.

## The intake suite

`intake/` measures whether an agent the user speaks to records the request, chooses the lane and asks only what is missing: with several samples per case, five facts read from a scratch store and from the answer, and no model as judge. It is the routing suite's twin for the first turn of work (`crates/ap/README.md`, `ap request`, `ap intent`, `ap unit add`), and gates a later change of the shared instructions with the routing suite.

- A case is `{id, words, seed, expect}`. `words` is the message as the user would type it and the session's only message. `seed` is the store before the session: `none`, `drafted` (an intent `nightly-backup` in draft, with one criterion) or `confirmed`. `expect` is `lane` (`objective`, `small` or `none`), `out_of_order` (`intent` or `confirmation`, the stage the order skips, or null) and `missing` (facts of the routing suite's form, `{"fact": [<strings>]}`, the facts an answer to an out-of-order order names; empty exactly when `out_of_order` is null). `intake/cases.json` holds the synthetic cases of the repository. The user's own requests never enter the repository: host cases are files on the host given with `--cases <absolute path>`, admitted by their SHA-256 listed in `intake/host-cases.sha256` (one line `<sha256>  <short name>`, as in the routing suite; refusals `cases_unreadable`, `cases_digest_unknown`, `cases_invalid`, `case_id_twice`).
- `python3 -I -B evals/intake/run answers --reader claude-sonnet|claude-haiku|muse-ember|agy-hydrogen --out <dir> [--root <dir>] [--cases <file> ...] [--samples N] [--case <id> ...]`, `run score --out <dir> [--cases <file> ...]`, `run gate --baseline <score.json> --candidate <score.json>`. The readers, their command lines, the samples' files and `run.json`, the unit of a session, `gate` and every refusal are those of the routing suite: `intake/run` loads `routing/run` as a module and does not copy it. The differences: the Claude readers run without `--disable-slash-commands`, so the skills load as installed; the first and only message is `words`; `--root` (default `/root/.agents`) is given to the argv as there; and each sample has its own scratch store.
- The session. The store of a sample is built before it in `<out>/<reader>/<case>__s<n>.store/` as `ontology.sqlite`, from `ontology/work.schema.json` of the tree `run` lies in and the seed (applied at fixed past times, so every later action is the session's), and is bound at the host store's path `/var/lib/ontology-platform/ont` (`BindPaths=`): `ap` and `ont` without `--store` use it. The unit is the routing suite's (`ProtectSystem=strict`, `ProtectHome=read-only`, the 600-second bound, the deny list) and adds: `InaccessiblePaths=` for `~/.config/gh`, `~/.git-credentials`, `~/.netrc`, `~/.ssh`, `/etc/agent-platform/credentials`, `/etc/agent-platform/ci`, `/run/user`, `/run/docker.sock`, `/run/containerd/containerd.sock`, `/run/tailscale`, `/run/systemd/private`, `/run/dbus/system_bus_socket` and `/home/palantirkc/work/edu-*` (each existing path its own assignment); `CapabilityBoundingSet=CAP_CHOWN CAP_DAC_OVERRIDE CAP_FOWNER CAP_FSETID CAP_SETGID CAP_SETUID`, `NoNewPrivileges=yes`, `PrivateDevices=yes`; `ReadOnlyPaths=/sys`, `/proc/sys`, `/proc/sysrq-trigger` (not `ProtectKernelTunables=yes`: with systemd 255 it leaves `/sys` writable and undoes `ReadOnlyPaths=/sys`). A variable whose name holds `TOKEN`, `SECRET`, `PASSWORD`, `CREDENTIAL`, `AUTH` or `KEY` is never given to a session. The unit's name begins `intake-`. A refusal `sandbox_unavailable` (the probe unit of the same properties does not start), `store_build_failed` or `ont_not_found` comes before a reader starts.
- The five facts, per sample, read from the scratch store after the session and from the answer. (a) For `objective` and `small`, a `request` whose words equal `words` exists, whatever its `words_verified` (only Claude Code leaves a session record `ap request` reads: `score` prints `requests_recorded` and `requests_verified` per reader); for `none`, no `record_request` or `supersede_request` was applied after the seed. (b) `objective`: that request is routed to an intent (a draft in the same turn counts); `small`: a unit of lane `small` has it as `origin`; `none`: no action was applied after the seed. (c) no unit of lane `objective` has an intent that is not `confirmed` (or `met`); the log holds no refused `add_unit` of lane `objective` with `intent_required` or `intent_not_open_for_units`; and on a case whose `out_of_order` is `confirmation`, no `confirm_intent` was applied after the seed. (d) no `assume_intent` was applied after the seed. (e) the answer holds at most five questions and, on an out-of-order case, every fact of `missing` (compared as in the routing suite). A question is one `?` or `？` in the answer once fenced code blocks and inline code are removed; a question without the mark is not counted. A sample passes when all five hold; one without an answer fails and is counted in `unanswered`.
- `score.json` has the routing suite's members (`n`, `passes`, `samples`, `mean`, `majority`, `unanswered`, `tokens_median`, `parity` against `claude-sonnet`) and per reader `facts` (per case, the samples that hold each of `a` to `e`), `requests_recorded` and `requests_verified`; `sheet.md` is the public sheet. `gate` is the routing suite's.
- What the suite does not show. (a) and (b) of an `objective` or `small` case depend on one request, so one failed fact can fail the other. A delegated confirmation (`confirm_intent_delegated`) is not read by (c). The seeds are one intent; a case says nothing about a store with many. Still open, as in the routing suite: signals to root's processes; the network; the shared `/tmp`; the reader's own CLI state, which is writable; every file not masked stays readable. The unit hides the paths above, not the host: a reader that works around its limits is not stopped. `--out` holds the scratch stores, the answers and the event streams: private, only `sheet.md` is public. The baseline is run on the installed instructions after delivery; at three samples the loss of one case is not reliably caught.
